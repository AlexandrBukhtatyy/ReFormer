# forms-benchmark

Бенчмарк ReFormer против Formik, React Hook Form и RJSF на реальных числах из браузера.
Две части:

- **`projects/forms-benchmark`** (здесь) — страницы: одна форма на одну библиотеку, каждая
  собирается отдельной prod-сборкой;
- **`projects/forms-benchmark-e2e`** — Playwright: conformance (одинаковое поведение), калибровка
  счётчика рендеров, профилирование и отчёт.

Правила честности и методика — [BENCH-CONTRACT.md](BENCH-CONTRACT.md). План —
[docs/plans/reformer-crispy-gem.md](../../docs/plans/reformer-crispy-gem.md).

## Участники и формы

| id                 | Стек                                           |
| ------------------ | ---------------------------------------------- |
| `reformer-core`    | `@reformer/core` + headless `@reformer/cdk`    |
| `reformer-json`    | `@reformer/renderer-json`                      |
| `formik`           | Formik + Yup                                   |
| `rhf`              | React Hook Form + zod                          |
| `rjsf`             | RJSF + ajv8                                    |
| `baseline`         | та же разметка без библиотеки — нижняя граница |
| `reformer-core-aa` | копия `reformer-core` — контроль шума (A/A)    |

Формы: регистрация с капчей ([спека](../../docs/specs/registration-form.md)) и кредитная заявка
([спека](../../docs/specs/credit-application-form.md), охват — контракт §8).

## Запуск

Пакеты `@reformer/*` потребляются из `dist/` — сначала соберите их (core → cdk → renderer-react →
renderer-json): `npm run build:stackblitz -w @reformer/core` и т.д. Сборка страниц отказывается
работать со старым `dist`.

```bash
npm run bench:build         # сборка всех страниц + отчёты бандла и объёма кода (dist/*.json)
npm run bench:conformance   # паритет поведения всех реализаций
npm run bench:quick         # быстрый прогон: 3 итерации, без прогрева
npm run bench               # полный прогон: 10 итераций + прогрев, рендеры, трассы, отчёт
npm run bench:report        # отчёт по последним прогонам; -- --publish → docs/benchmarks/forms/
npm run bench:compare -- <было> <стало>   # сравнение двух отчётов или наборов прогонов
npm run bench:idle-check    # свободна ли машина для замеров (фоновая нагрузка)
```

Параметры прогона — переменные окружения (`projects/forms-benchmark-e2e/lib/config.ts`):
`BENCH_ITERATIONS`, `BENCH_WARMUP`, `BENCH_CPU` (например `1,4`), `BENCH_CADENCE`, `BENCH_REMOUNTS`,
`BENCH_RENDERS`, `BENCH_TRACE`, `BENCH_SEED`, `BENCH_LIBS`, `BENCH_REQUIRE_IDLE`.

Разработка страницы: `npm run dev -w forms-benchmark` → `http://localhost:5173/<id>/<form>/`
(dev-режим только для разработки; замеры — по prod-сборкам).

## Перед долгим прогоном: проверка машины

Числа бенча портит не только частота CPU, но и соседи: инференс LLM (Ollama), чужие браузеры
автоматизации (другой Playwright e2e), сборки и тесты, Docker. Они нагружают GPU, память и
композитор — DOM, layout и отрисовка замедляются, а калибровочная JS-нагрузка этого почти не
замечает. Поэтому перед полным прогоном:

```bash
npm run -s bench:idle-check                    # 3 с выборки: «свободна» или «ЗАНЯТА» и чем
npm run -s bench:idle-check -- --seconds 10    # дольше — точнее для прерывистых соседей
npm run -s bench:idle-check && npm run bench   # код выхода 1 на занятой машине
BENCH_REQUIRE_IDLE=1 npm run bench             # тест бенча откажется начинать на занятой машине
```

Вывод — чужая нагрузка в ядрах, загрузка GPU (macOS), тяжёлые соседи с долей CPU и пять самых
нагруженных чужих процессов. Пороги (контракт §7): Ollama и чужие браузеры автоматизации — от 5 %
ядра, инструменты на Node, десктопные браузеры и Docker/VM — от 10 %, любой другой процесс — от
20 %, GPU — от 30 %, все чужие процессы вместе — от 1 ядра.

Та же выборка идёт в каждом прогоне (в начале и в конце, вне окон замера) и в пред-проверке каждого
теста бенча. Предупреждение `⚠️ Фоновая нагрузка перед прогоном` в консоли значит, что машина занята
и числа будут шумными; в отчёте занятая сессия получает строку `⚠️ Фоновая нагрузка` в начале формы
и раздел «Фоновая нагрузка» с соседями. Такие числа несравнимы с прогоном на тихой машине, и
нормировка `bench:compare` их не выправляет — остановите соседей (например, выгрузите модель
Ollama: `ollama stop <модель>`) и перезапустите.

## Сравнение прогонов разных сессий

Абсолютные числа двух отчётов напрямую несравнимы даже на одной машине: частота и тепловой режим
CPU между сессиями меняются (baseline, тот же код, расходился до 1.6×). Поэтому в начале и в конце
каждого прогона идёт калибровочная JS-нагрузка (контракт §6): её время пишется в `runs.ndjson`,
сводка — в `env.json`, а отчёт показывает раздел «Калибровка скорости машины» с дрейфом внутри
прогона и за сессию (сноска при дрейфе больше 10 %).

Сравнить «до» и «после» изменения ядра:

```bash
npm run -s bench:compare -- docs/benchmarks/forms/summary.json projects/forms-benchmark-e2e/results/_reports/<stamp>
npm run -s bench:compare -- <run-было> <run-стало>              # прогоны из results/, без отчёта
npm run -s bench:compare -- <было> <стало> --form credit --out .tmp/compare.md
```

Вывод — markdown в stdout (`-s` убирает служебные строки npm), `--out` дополнительно пишет его в
файл.

Аргументы — `summary.json`, каталог отчёта или прогоны `results/<run>` через запятую (относительные
пути — от каталога, где запущен npm, затем от `results/`). Для каждой формы, профиля CPU, фазы,
метрики времени и участника печатается `было → стало ×стало/было · норм. ×…` и сводка по участникам
(геометрическое среднее по метрикам чистого CPU-времени). «Норм.» — после поправки на скорость
машины: «стало» делится на отношение медиан калибровки стало/было. Если калибровки нет хотя бы в
одном отчёте (снятые до неё) или нагрузки калибровки разные, делитель — геометрическое среднее
отношений baseline по CPU-метрикам, и вывод это называет; `--norm calibration|baseline|none`
выбирает способ явно. Метрики с таймерами, сетью, кадрами и TBT помечены `≈`: их нормировка
приблизительна. Для каждой стороны печатается фоновая нагрузка; если хоть одна снята на занятой
машине — предупреждение: разница может быть соседями, а не кодом.

## Быстрый замер «до/после» для правок ядра

Полный прогон идёт больше часа и требует тихой машины. Чтобы за минуты понять, что дала правка в
`@reformer/core` или `@reformer/cdk`, есть A/B-стенд:

```bash
npm run bench:ab                              # HEAD против рабочего дерева: кредит, монтирование
npm run bench:ab -- --base HEAD~3             # другая точка отсчёта
npm run bench:ab -- --scenario type --live    # JS на клавишу в живой фазе проверки
npm run bench:ab -- --with rhf,formik         # ориентиры — другие участники в тех же условиях
npm run bench:ab:profile -- --subtree '^createForm '   # куда уходит время: пакеты и функции
```

Стенд собирает страницу участника для каждого варианта, беря ядро и cdk из исходников — рабочего
дерева либо git-ревизии, — поэтому `dist` пакетов пересобирать не нужно. Раунды вариантов
чередуются, и разность считается по раундам: дрейф машины и соседи ложатся на варианты поровну.
Вывод — среднее и разность с разбросом (± две стандартные ошибки): разность меньше разброса
различием не считается, а малая выборка обманывает — увеличьте `--rounds` и `--n`.

Числа стенда — не числа отчёта: сборка несжатая, сценарий один. Итог правки подтверждает полный
прогон. Опции и сценарии — в шапках `projects/forms-benchmark-e2e/scripts/ab/{ab,profile}.mjs`;
сборки и профили лежат в `projects/forms-benchmark-e2e/results/_ab/`.

## Утечка памяти или прогрев

Рост `JSHeapUsedSize` между перемонтированиями ещё не утечка. В первые десятки циклов кучу растит
код движка — байт-код, векторы обратной связи, оптимизированный код — у всех участников, даже у
пустой страницы baseline. Утечка — это удержанные объекты. Отличить одно от другого за минуту:

```bash
npm run bench:leak                                        # reformer-core, кредит, сборка dist/
npm run bench:leak -- --lib reformer-json --form registration
npm run bench:leak -- --jit-off                           # без JIT: остаток роста — объекты
npm run bench:leak -- --retainers --dist results/_ab/dist-work   # кто держит новые объекты
npm run bench:leak -- --events                            # DOM-события на цикл перемонтирования
```

Скрипт открывает страницу участника из каталога сборки (`--dist`; по умолчанию `dist/` этого
проекта), делает `--warm` перемонтирований прогрева, снимает кучу и ещё `--cycles` перемонтирований
со сборкой мусора каждые `--step`, затем снимает кучу ещё раз. Что смотреть:

- **«объекты без JIT»** — прирост живых объектов страницы между снимками, без типов `code`,
  `hidden`, `object shape`. Утечка — когда он растёт с числом циклов; около нуля — утечки нет, даже
  если `JSHeapUsedSize` ещё растёт;
- **«по типам»** — где рост: `code` и `hidden` — JIT, `object`, `closure`, `array`, `native` —
  удержание;
- **`--jit-off`** запускает Chrome без оптимизирующих компиляторов и с ранними векторами обратной
  связи (`--no-opt`, `--no-maglev`, `--no-sparkplug`, `--no-lazy-feedback-allocation`): рост кода
  пропадает, и наклон кучи показывает одно удержание;
- **«живых по классам»** — число `FormControlNode`, `ModelLeafNode`, `OwnedSignal` и других классов
  из `--watch` в обоих снимках. Утечку выдаёт их рост. Список «новых и живых» (`--retainers`)
  включает и подмену: если после размонтирования жива одна последняя форма, её объекты — новые,
  хотя живых не прибавилось. Имена классов видны только в несжатых сборках — их собирает
  `bench:ab` в `projects/forms-benchmark-e2e/results/_ab/dist-*`.

Пути удержания пропускают слабые ссылки и рёбра таблиц `WeakMap` («part of key»): значение
`WeakMap` живо, только пока жив ключ, и путь через таблицу указал бы не на виновника. Строка
отчёта «Удержание объектов после размонтирования» считается так же, по снимкам до и после серии
фазы перемонтирования.

## Где что

```
src/shared/      общий слой: UI-примитивы, FieldFrame, fake API, домен, тексты, харнесс
src/libs/<id>/   реализации; README каждой — паттерны со ссылками на документацию и отклонения
scripts/         build-entries (сборка по входам), serve, bundle-size, code-size
```

Результаты прогонов — `projects/forms-benchmark-e2e/results/<run>/` (в .gitignore): `env.json`
(со сводками калибровки и фоновой нагрузки), `phases.ndjson`, `runs.ndjson` (калибровка начала и
конца прогона и `background` — что ещё работало на машине), `traces/*.json` (открываются в DevTools
→ Performance), отчёты в `results/_reports/<stamp>/`.
