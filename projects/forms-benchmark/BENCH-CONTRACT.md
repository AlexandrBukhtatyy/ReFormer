# Контракт бенчмарка форм

Пре-регистрация методики: что считается «одинаковой работой», что и как меряется, как читаются
числа. Меняется только до первого полного прогона; после — каждое изменение отдельной записью в
разделе «История» с причиной, а прежние результаты помечаются несравнимыми.

Спеки — вход и не меняются: `docs/specs/registration-form.md`, `docs/specs/credit-application-form.md`.
Всё, что спека оставляет открытым, решается здесь.

## 2. Правила реализации

1. **Идиоматично по официальной документации** библиотеки. В README каждой реализации — ссылка на
   страницу документации для каждого использованного паттерна.
2. **Одинаковый бюджет оптимизаций:** только то, что рекомендует официальная документация для форм
   такого размера, только публичный API. Для всех запрещены React Compiler, ручные `memo`/`useMemo`
   сверх рекомендованного документацией, внутренние API.
3. **Общий код** (`src/shared/**`) одинаков для всех и не считается в LOC реализации: UI-примитивы,
   `FieldFrame`, API-клиент, бизнес-функции из спеки, тексты сообщений, нормализатор payload, харнесс.
   Реализация сама решает, как привязать примитивы к своей библиотеке (адаптеры — часть реализации).
4. Реализации конкурентов пишутся без опоры на код ReFormer: вход — спека, этот контракт,
   `src/shared/**` и документация библиотеки.

## 3. Видимое поведение (одинаково у всех)

### Валидация

- **`afterFirstSubmit`:** до первой попытки отправки (в визарде — до первого «Далее» на данном шаге)
  ошибки не видны. После неё каждое изменение поля перепроверяет его правила, без debounce у
  синхронных правил.
  Нативно: ReFormer — `strategy: 'afterFirstSubmit'`; RHF — `mode: 'onSubmit'`,
  `reValidateMode: 'onChange'`; Formik — показ ошибок по `submitCount > 0`; RJSF — `liveValidate`
  включается после первой отправки.
- **Одно сообщение на поле** — первое нарушенное правило в порядке спеки. Тексты —
  `src/shared/messages`.
- Фокус на первую ошибку **выключен**, сводка ошибок **не показывается**.
- Зависимые правила: изменение `password` перепроверяет `confirmPassword` (после первой попытки).

### Асинхронные проверки

- Вызываются только через общий клиент `src/shared/api`. Проверки занятости (`checkUsername`,
  `checkEmail`) в клиенте уже **debounce 300 мс + кэш по значению**: запрос уходит, когда
  пользователь 300 мс ничего не вводит (отсчёт от последнего события `input` в документе, а не от
  вызова — проверка, вызванная после паузы, например при отправке, выполняется сразу); повторный вызов
  с тем же значением присоединяется к ожидающему, новое значение вытесняет ожидающее — оно
  возвращает «не проверено» (ошибки нет). Реализация вызывает клиент в штатном месте своей библиотеки
  для async-валидации и **не добавляет** своих debounce и кэша.
- Асинхронная проверка значения выполняется, только если оно прошло синхронные правила этого поля.
  Известное ограничение: значение, не прошедшее синхронные правила, в клиент не передаётся и поэтому
  не вытесняет уже ожидающую проверку предыдущего значения (`joh` → `jo`: проверка `joh` уйдёт через
  300 мс). Одинаково у всех реализаций; сценарии бенча вводят только «вперёд» и этого не задевают.
- Пока идёт серверная проверка поля, показанные ошибки **других** полей остаются на экране
  (conformance: «пока идёт серверная проверка поля…»). Ошибку самого проверяемого поля
  библиотека может снять сразу или по ответу — это её поведение, оно не выравнивается.
- Отправка дожидается незавершённых асинхронных проверок.
- Кнопка отправки не блокируется во время проверки.

### Отправка и сброс

- Payload формирует общий нормализатор (`toRegistrationPayload` и т.п.) из значений формы.
- Успех — элемент `submit-result` с текстом подтверждения; значения формы остаются на экране.
- «Очистить» — исходные значения (пустые или из приглашения), ошибки скрыты, состояние «до первой
  попытки».

### Визард (кредит)

- Неактивные шаги размонтированы. Значения всех шагов сохраняются при переходах.
- «Далее» проверяет только поля текущего шага; при ошибках шаг не меняется.
- Скрытые условием поля сбрасываются к начальному значению; выключение флага массива очищает массив.

## 4. DOM-контракт

Пути полей — через дефис: `personalData-lastName`; строка массива — `properties-9-value`.

| testid                                                       | Элемент                                           |
| ------------------------------------------------------------ | ------------------------------------------------- |
| `field-{path}`                                               | обёртка поля (`FieldFrame`)                       |
| `input-{path}`                                               | интерактивный элемент поля (у капчи — поле ввода) |
| `error-{path}`                                               | текст ошибки; отсутствует в DOM, если ошибки нет  |
| `computed-{path}`                                            | вычисляемое значение (только чтение)              |
| `captcha-image`, `captcha-refresh`                           | картинка и кнопка обновления капчи                |
| `btn-submit`, `btn-reset`                                    | отправка, очистка                                 |
| `btn-next`, `btn-prev`, `step-current` (атрибут `data-step`) | визард                                            |
| `btn-add-{array}`, `btn-remove-{array}-{i}`                  | массивы                                           |
| `submit-result`                                              | подтверждение отправки                            |

Разметка поля задаётся `FieldFrame`: `<div data-testid=field-…><label/>{контрол}<p role=alert
data-testid=error-…/></div>`. Реализация не добавляет вокруг полей своих обёрток, кроме требуемых
библиотекой (их число попадает в отчёт как DOM-узлы на шаг).

## 5. Fake API и время

- In-memory, без сети и service worker; один модуль на всех.
- Латентность — параметр URL `latency`: число миллисекунд (по умолчанию `20`) или `manual`
  (ответ только по `__bench.api.flush()`).
- Счётчики вызовов по эндпоинтам — `__bench.api.calls`; проверяются в conformance.
- Фиксированные «сегодня» (`2026-06-15`) и сид капчи — параметр `seed`.

## 6. Что меряется

Фазы сценариев и метрики — в `docs/plans/reformer-crispy-gem.md`, раздел 2–3. Окно замера фазы
содержит только сырой ввод (`page.keyboard`, `page.mouse` по заранее вычисленным координатам) и
ожидание in-page промиса простоя. Проверки (`expect`, счётчики, payload) — вне окна.

Готовность страницы определяет харнесс по DOM-контракту: присутствуют `input-*` всех полей первого
экрана, значения совпадают с ожидаемыми (пусто или префилл), прошёл кадр.

**Калибровка скорости машины.** В начале и в конце каждого прогона — до первой фазы и после
последней, вне окон замера и трассы — одна и та же детерминированная JS-нагрузка `form-work-v1`
(`projects/forms-benchmark-e2e/lib/calibration.ts`), около 50 мс при CPU 4x. Нагрузка похожа на
работу формы, а не на числовой цикл, который свернёт JIT: объекты полей со строками, нормализация и
правила (trim, регистр, regex, маска), иммутабельные обновления состояния через spread, мелкие
сортировки и группировка, JSON туда и обратно. Она идёт на пустой странице (`about:blank`) той же
вкладки под тем же CDP-троттлингом; в конце — в последнем browser context прогона (у участников с
загрузкой данных — во втором). Два прогревочных повтора и пять замеряемых, каждый — отдельная
задача, время — `performance.now()` в странице, в запись — медиана повторов. Контрольная сумма
сверяется с ожидаемой: нагрузку нельзя выкинуть или незаметно поменять — изменённая нагрузка
получает новый id, калибровки разных id несравнимы. До нагрузки и после — GC, после — пауза 250 мс.
Начало и конец пишутся в `runs.ndjson` (`calibration`), сводка — в `env.json`. Счётчики CDP фазы
загрузки — дельта от момента перед переходом (до калибровки вкладка перед переходом была пустой, и
абсолютные значения совпадали с дельтой).

**Перемонтирование и память.** Фаза перемонтирования начинается с прогрева без записи
(`BENCH_REMOUNT_WARMUP`, 30 циклов): в первые десятки циклов кучу растит код движка — байт-код,
векторы обратной связи, оптимизированный код — у всех участников, даже у пустой страницы. Затем
снимок кучи, замеряемые циклы (GC с простоем каждые 5) и второй снимок. «Удержание объектов» —
прирост объектов страницы между снимками без типов JIT (`code`, `hidden`, `object shape`;
`projects/forms-benchmark-e2e/lib/heap.ts`) на цикл: утечка — когда он больше нуля. «Рост heap» —
наклон `JSHeapUsedSize` по точкам после прогрева, вместе с кодом JIT. Обе строки — без отношений
«×»: это доли и единицы КБ на цикл, и разы между ними — шум. Проверка «утечка или прогрев» вне
полного прогона — `npm run bench:leak` (README).

**Фоновая нагрузка.** В тех же точках (начало и конец прогона, вне окон замера) Node снимает список
процессов `ps` (`projects/forms-benchmark-e2e/lib/background.ts`): доля CPU процесса за прогон —
приращение накопленного CPU-времени, делённое на длительность прогона (точное среднее за окно, в
отличие от `%cpu`). Дерево самого бенча — раннер Playwright, воркеры, запущенные ими браузеры,
webServer — исключается. На macOS добавляется загрузка GPU (IOAccelerator, `ioreg`, без root) —
моментальная, в точках замера, когда страница бенча пуста. Классификатор отмечает тяжёлых соседей:
Ollama (runner — и когда простаивает), чужие браузеры автоматизации (Playwright, Puppeteer),
инструменты на Node (vitest, tsc, vite/esbuild, eslint, jest, playwright), десктопные браузеры,
Docker/VM, любой другой процесс от 20 % ядра, GPU от 30 %. В `runs.ndjson` (`background`) — чужая
нагрузка в ядрах, своя, GPU, пять самых нагруженных чужих процессов, соседи и признак «грязного»
прогона; сводка и пороги — в `env.json`. Перед каждым тестом бенча — пред-проверка (2 с): на занятой
машине предупреждение в консоли, с `BENCH_REQUIRE_IDLE=1` — отказ до замеров. Без `ps` (Windows)
записывается null.

**Трассируемый прогон.** После замеряемых — по одному прогону на участника под трассой DevTools
(`BENCH_TRACE`, CPU первого профиля), в статистику он не идёт. Только в нём сессия ставит в страницу
метки фаз `performance.mark('bench:phase:<id>:start|end')`: начало — перед действием фазы (у загрузки
— перед переходом), конец — после ожидания простоя. У перемонтирования прогрев с принудительным GC
после него — свой кусок `remount-warmup`, а окно `remount` охватывает только замеряемые циклы.
Графики прогрев вырезают (`TRACE_CUT` в `scripts/metrics.mjs`), подпись под ними об этом говорит:
циклы прогрева идут подряд без GC, снятые формы копятся в счётчиках, пока движок их не соберёт, и
подъём линии читался как утечка. Замеряемые прогоны меток не получают.
По меткам отчёт выравнивает участников по началам фаз и рисует счётчики трассы (`UpdateCounters`: JS
heap, DOM-узлы, обработчики событий) во времени (`projects/forms-benchmark-e2e/scripts/traces.mjs`).
Счётчики там без принудительного GC: снятая форма остаётся в них до сборки мусора — значения после GC
остаются в таблицах фаз.

## 7. Как читаются числа

- Прогон сворачивается до медианы и p95 по клавишам внутри прогона; сравниваются прогоны.
- Отношение медиан с bootstrap-CI 95 %; Mann–Whitney U с поправкой Holm по всем сравнениям. До 60
  наблюдений в паре p считается по точному перестановочному распределению суммы рангов (связи —
  средними рангами), дальше — нормальным приближением.
- Различие меньше порога шума A/A-пары считается отсутствующим.
- p95 не публикуется при n < 20 прогонов.
- Публикуется всё, включая метрики, где ReFormer проигрывает; в таблицах — абсолютные значения и
  отношение к лучшему в строке.
- Таблицы отчёта — сырые миллисекунды сессии, калибровкой (§6) они не нормируются. Калибровка
  прогона — среднее начала и конца; дрейф прогона — конец к началу − 1; дрейф сессии — разброс
  (p10–p90) / медиана по прогонам без прогрева и изменение медианы от первой итерации к последней.
  Сноска в отчёте — если дрейф сессии больше 10 % или дрейф прогона больше 10 % больше чем в 10 %
  прогонов (одиночный скачок медиану по итерациям не сдвигает). 10 % — вдвое больше типичного
  разброса временных метрик между прогонами (медиана CV ≈ 5 %) при собственном шуме калибровки на
  тихой машине 1–3 %.
- Отчёты разных сессий сравниваются `npm run bench:compare`: «было → стало» по каждой фазе, метрике
  времени и участнику, сырые и нормированные — «стало» делится на отношение медиан калибровки
  стало/было. В отчётах без калибровки (или с разной её нагрузкой) делитель — геометрическое
  среднее отношений медиан baseline по метрикам чистого CPU-времени. Байты, счётчики и heap не
  нормируются; у метрик с таймерами, сетью, кадрами и у TBT нормировка приблизительна.
- Прогон «грязный», если занят тяжёлый сосед (Ollama и чужие браузеры автоматизации — от 5 % ядра за
  прогон: их нагрузка в основном на GPU, и CPU-доля её занижает; инструменты на Node, десктопные
  браузеры и Docker/VM — от 10 %: в покое они держатся в пределах нескольких процентов; прочий
  процесс — от 20 %; GPU — от 30 %: композитинг рабочего стола в покое — единицы процентов) или
  чужая нагрузка в сумме от 1 ядра: бенч сам занимает 1–2 ядра, у Apple M1 четыре производительных
  ядра, и ещё целое ядро соседей уводит потоки бенча на энергоэффективные. Сессия помечается в
  отчёте, если грязных прогонов больше 10 % (то же правило, что у дрейфа внутри прогона). Такая
  сессия несравнима с тихой и нормировкой не выправляется; `bench:compare` печатает фоновую
  нагрузку обеих сторон и предупреждает, если хоть одна грязная.

| Поле, появившееся после неудачного «Далее» (условие стало истинным)                                                  | Ошибку не показывает, пока его не изменили или не нажали «Далее» снова (conformance проверяет)                                                                                                                                                                                                           |
| Пустые значения                                                                                                      | Текстовые поля — `''` (нативный input не отличает `null`), числовые — `number \| null`                                                                                                                                                                                                                   |
| «Очистить»                                                                                                           | В кредитной заявке нет (в спеке не задана)                                                                                                                                                                                                                                                               |
| `carYear.max` = текущий год + 1 (🆕)                                                                                 | «Текущий» — фиксированные часы бенча (2026)                                                                                                                                                                                                                                                              |
| Маски (🆕): телефоны, ИНН, СНИЛС, паспорт, код подразделения, индекс, СМС                                            | Общий `MaskedInput`                                                                                                                                                                                                                                                                                      |
| Инициализация: пустая форма и «загрузка с данными» (`applicationId`)                                                 | Параметр URL `application=1` → `GET` заявки, данные — исходное состояние; справочники грузятся при старте                                                                                                                                                                                                |
| Подтверждение кодом из СМС                                                                                           | Асинхронная проверка на «сервере» (общий клиент, debounce + кэш), верный код — `123456`                                                                                                                                                                                                                  |
| Отправка                                                                                                             | «Отправить» проверяет **все шаги** (спека: «Все 6 шагов валидны»; межшаговые правила, например доля платежа шага 4 от ставки, зависящей от имущества шага 5, могли устареть). Ошибка на раннем шаге — переход на первый шаг с ошибкой, ошибки видны. Все валидны → `POST`, подтверждение `submit-result` |

### Вне охвата

| Строка спеки                                                                | Почему                                                                                              |
| --------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| Динамические лимиты `loanAmount.max` по доходу и `loanTerm.max` по возрасту | Спека задаёт их словами «например», без правила                                                     |

## История

- 2026-11-12 — первая редакция.
- 2026-11-12 (до первого полного прогона) — debounce общего клиента: повторный вызов с тем же
  значением присоединяется к ожидающей проверке (раньше вытеснял её — RHF с whole-schema
  резолвером терял результат); отсчёт задержки от паузы ввода, а не от вызова (пилот показал
  искусственные 300 мс на отправке у библиотек без проверок до отправки). Пилотные числа несравнимы.
- 2026-11-13 (после первого полного прогона, данные не менялись) — p Mann–Whitney по точному
  распределению вместо нормального приближения: при n = 10 на группу приближение не опускается ниже
  p ≈ 1.8e-4, и после Holm по ~550 сравнениям значимость была недостижима (в отчёте был один значок).
  Под таблицей фазы — сноска, если запросы к API у участников различаются, и пояснение к «UI затих»
  в асинхронных фазах.
- 2026-11-13 — правило «ошибки других полей не пропадают, пока идёт серверная проверка» и тест
  на него: первый полный прогон нашёл, что ReFormer (без исправления ReFormer-w83s) скрывал
  ошибки полей с async-правилами на время любой серверной проверки. Ветка бенча переведена на
  develop с исправлениями ядра; первый полный прогон с ними несравним.
- 2026-11-13 — калибровка скорости машины (ReFormer-q6ny): baseline (тот же код) между полными
  прогонами разных сессий одного дня расходился до 1.6× при одинаковой фоновой нагрузке (частота и
  тепловой режим CPU), и абсолютные числа разных отчётов были несравнимы. В начале и в конце каждого
  прогона — калибровочная нагрузка (§6), отчёт показывает её дрейф, `bench:compare` нормирует
  отчёты разных сессий (§7). Окна замера и метрики фаз не менялись; калибровка идёт на той же
  вкладке до первой фазы, поэтому счётчики CDP загрузки стали дельтой от момента перед переходом.
  Пилотная A/B-проверка (10 пар, ReFormer core, регистрация) не показала влияния калибровки на
  готовность и ScriptDuration загрузки сверх шума. Прежние отчёты сравнимы с новыми только через
  `bench:compare` с нормировкой по baseline.
- 2026-11-13 — детектор фоновой нагрузки (продолжение ReFormer-q6ny). Приёмочная серия из четырёх
  полных прогонов одного baseline с интервалом 15 минут (17:19, 17:36, 17:54, 18:12) нормировку не
  прошла: калибровка между сериями сдвинулась лишь на ×1.01–1.14, а CPU-метрики baseline — на
  ×0.78–1.61. Причина — параллельная работа на машине, а не частота CPU: в 17:30:22, между первой и
  второй серией, запустился runner Ollama (первая серия — самая быстрая); с 17:23 до 18:04 другие
  сессии Claude собирали и коммитили; шёл чужой кросс-браузерный Playwright e2e (chromium headless
  shell, firefox, webkit). Инференс LLM и чужие браузеры конкурируют за GPU, пропускную способность
  памяти и композитор; калибровка (JS в кэше процессора) этого почти не видит, а DOM, layout и
  отрисовка — видят. Поэтому каждый прогон теперь записывает, что ещё работало на машине (§6), отчёт
  помечает грязные сессии (§7), а перед долгим прогоном машину проверяет `npm run bench:idle-check`.
  Окна замера и метрики не менялись; выборка `ps` идёт в Node вне окон.
- 2026-11-18 — память на перемонтировании (ReFormer-2o1j.24). Строка «Прирост heap на
  перемонтирование (утечка)» была наклоном кучи по циклам 5–20 без прогрева и мерила в основном
  рост кода JIT: пустая страница baseline «текла» на 7.4 КБ за цикл. Отчёт на `cfb99b87` показал
  удвоение у ReFormer на кредите (8 → 16 КБ), но зонд в Chrome утечки не нашёл: с выключенным JIT
  200 перемонтирований после прогрева дают +0.0 КБ, число живых нод формы постоянно. Теперь фаза
  начинается с прогрева, а память — двумя строками: «Удержание объектов» по снимкам кучи и «Рост
  heap» после прогрева (§6). Прежние числа памяти перемонтирования с новыми несравнимы; остальные
  метрики фазы не менялись, кроме того, что точки GC ждут простоя страницы.
