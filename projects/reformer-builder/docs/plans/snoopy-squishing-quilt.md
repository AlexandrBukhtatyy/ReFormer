# План: брейншторм-сессия по `reformer-builder`

> Прошлый план (скелет проекта) выполнен и закоммичен (`65426692`), его текст сохранён в git.
> Этот файл переиспользован под новую задачу — организацию брейншторма.

## Context

Скелет `projects/reformer-builder` готов (пустой каркас на Vite+React+@reformer/*). Теперь нужен
**брейншторм: что этот визуальный конструктор форм собой представляет** — видение, UX,
архитектура, роль AI. Результат сессии пишем в отдельный живой md-документ; сам процесс
(раунды идей и решений) тоже фиксируем — пользователь просил «запись всего процесса».

**Ключевая рамка от пользователя** (организующая идея всего брейншторма):
- Билдер **не зависит от технологии и ui-kit** — ядро не хардкодит React или конкретные компоненты.
- **Вход** = ui-kit (набор компонентов) **+ схема компонентов и их свойств**. В экосистеме ReFormer
  это уже есть: `@reformer/ui-kit/meta` → `defaultPropSchemas` (машиночитаемые props-схемы ~20
  типов полей, с виджетами редактора через `x-doc.kind: boolean/text/number/enum`). Обобщаем до
  понятия «каталог компонентов» — его может поставить любая дизайн-система.
- **Выход/рендер** = JSON-рендерер ReFormer. Сейчас только React (`@reformer/renderer-json`), но
  формат `JsonFormSchema` renderer-agnostic → в будущем другие фреймворки рендерят тот же JSON.

**Два режима работы билдера** (второй добавлен пользователем и меняет продукт):
- **Режим A — Standalone-дизайнер**: форма создаётся с нуля, выход — `JsonFormSchema` «в вакууме»,
  preview через renderer-json.
- **Режим B — Проектно-связанный редактор** (локальный dev-инструмент): разработчик запускает наш
  билдер-dev-сервер → выбирает каталог своего проекта → билдер показывает файловую структуру и
  находит все JSON-схемы UI → каждую можно править и **сохранять обратно в исходный файл** →
  dev-сервер *самого проекта* (Vite, импортящий JSON) делает hot-reload → разработчик видит
  обновлённую форму в своём приложении. Стретч: preview показывает **живую форму с dev-сервера**
  (iframe), а не изолированную — с настоящими model/валидацией/behaviors.

Формат сессии: **смешанный** — я сначала сею стартовый набор идей/вариантов, дальше углубляемся
через мои вопросы и ответы пользователя. Фокус: все оси (видение, UX, архитектура/данные,
AI-генерация MCP) + проектная интеграция режима B.

## Опора: факты об экосистеме (из разведки)

- **Выходной артефакт** — `JsonFormSchema` (`{version, root}`, узлы `field/array/container`,
  операторы `$model/$component/$dataSource/$html/$fn/$locale`). Путь «JSON → живая форма» готов:
  `convertJsonToM1Tree` (`packages/reformer-renderer-json`).
- **Property-инспектор из коробки**: `@reformer/ui-kit/meta` `defaultPropSchemas` +
  `packages/reformer-ui-kit/src/fields/props-schema.ts` (JSON-Schema draft-07 + `x-doc`/`x-runtimeProps`).
- **Валидация выхода**: `form-schema.schema.json` (draft-07, ужимается под реестр приложения) +
  MCP-tool `validate_json_schema` / `validateFormSchema`. Матч этого `$schema` — способ обнаружить
  «схема-файлы» в чужом проекте (режим B).
- **Ключевое ограничение → превращается в дизайн-решение**: в JSON сериализуется **только layout**;
  model, валидаторы и behaviors — отдельный TS-код (`defineValidationSchema`, 10 behavior-операторов).
  В режиме B связанный preview снимает это: недостающие слои даёт живое приложение разработчика.
- **Обратный путь (форма → JSON) и codegen в `.tsx` в библиотеке отсутствуют** — для режима B
  round-trip (JSON → билдер → JSON в тот же файл) придётся спроектировать. AI-генерация форм есть
  через `@reformer/mcp` (`create-form` из текста).
- Эталон JSON-формы: `projects/react-playground/src/pages/examples/complex-multy-step-form-renderer-json/`
  (`json-schema.json` + `form-schema.schema.json` + `registry.ts` + `render-behavior.ts`).

## Что создаём — `docs/brainstorms/reformer-builder.md`

Живой документ брейншторма. Структура (она же — повестка сессии):

1. **Контекст и цель** — зачем билдер, что уже есть (скелет), опора на M1 / renderer-json, два режима.
2. **Видение и охват** — что за продукт, для кого (разработчик / аналитик-no-code / внутренний тул),
   какую боль решает; тезис technology-agnostic + ui-kit-agnostic; режимы A и B; MVP → roadmap.
3. **Модель «вход → редактор → выход»** (ядро):
   - Вход: *каталог компонентов* = {компоненты} + {props-схемы} (`defaultPropSchemas`);
     для режима B ещё — файловая структура реального проекта и его JSON-схемы.
   - Выход: `JsonFormSchema` (renderer-agnostic); в режиме B — запись обратно в исходные файлы (round-trip).
   - Preview: изолированный (renderer-json) **или** связанный (iframe живого dev-сервера — «не в вакууме»).
   - Явно: чего билдер **не знает** (React, конкретные компоненты, ui-kit).
4. **Проектная интеграция (режим B)** — отдельный крупный раздел:
   - *Доставка/архитектура доступа к ФС*: наш dev-сервер с Node-fs-бэкендом · Vite-плагин-панель
     внутри проекта разработчика · browser File System Access API (`showDirectoryPicker`). Плюсы/минусы.
   - *Обнаружение схем*: скан каталога, матч по `$schema`→`form-schema.schema.json` / форме `{version, root}`,
     дерево файлов проекта.
   - *Round-trip / сериализация*: JSON → состояние билдера → правка → сериализация обратно (сохранение
     порядка ключей и строк-операторов, стабильный diff-friendly вывод).
   - *HMR*: билдер только пишет файл; hot-reload делает Vite самого проекта (JSON-import). Что если у
     проекта другой сборщик.
   - *Связанный preview*: iframe запущенного приложения + мост (postMessage) для подсветки/выбора узла;
     реальные model/validation/behavior приходят от приложения.
   - *Безопасность*: fs-доступ только локально, подтверждение записи, бэкап/undo на уровне файла.
5. **UX и взаимодействие** — canvas (дерево/превью), палитра полей из каталога, инспектор свойств из
   props-схем (виджеты по `x-doc.kind`), drag-drop, wizard/steps, array/container, переключатель
   preview (изолированный ↔ связанный), файловый навигатор проекта (режим B).
6. **Белые пятна и вызовы** — round-trip fidelity; сериализация валидаторов/behaviors (частично
   снимается связанным preview, но не в режиме A); codegen/экспорт; персистентность, undo/redo,
   версионирование схемы; поведение с не-Vite проектами.
7. **AI-генерация (MCP)** — `create-form` из текста → скелет; `validate_json_schema` как гейт;
   ассист-редактирование существующей схемы.
8. **Открытые вопросы / решения** — что добиваем в Q&A (обновляется по ходу).
9. **Журнал сессии** — «запись всего процесса»: по раундам (дата, обсуждаемый вопрос, варианты,
   принятое решение / что отложили). Каждый ход брейншторма дописывает сюда строку.

## Как проводим (после утверждения плана)

1. Создать `docs/brainstorms/reformer-builder.md` со структурой выше и **первым посевом**: по каждому
   разделу — стартовые идеи/варианты + 2-4 открытых вопроса (это «я генерирую» часть смешанного формата).
2. Задать пользователю первый раунд углубляющих вопросов (через AskUserQuestion или списком в чате).
3. По каждому ответу — обновлять соответствующий раздел и дописывать строку в «Журнал сессии».
4. Повторять раунды, пока картина не сложится; в конце — раздел «Итоги и следующий шаг» (напр. это
   станет спекой в `docs/specs/` или планом реализации MVP).

Специи/код в этой сессии **не трогаем** — только документ брейншторма. Коммит — по явной просьбе.
