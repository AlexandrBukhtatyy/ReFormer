# Билдер внутри приложения

> Билдер открывается в рамке поверх страницы разрабатываемого приложения и даёт то же, что
> в своей вкладке. Отдаёт его dev-сервер приложения, а форму в его превью рисует само приложение.
>
> Решения, принятые при реализации, — в [decisions-log.md](decisions-log.md), записи «Билдер
> внутри приложения» и «Билдер в рамке». Раскладка каталогов —
> в [project-structure.md](project-structure.md).

## Зачем

Билдер в своей вкладке рисует форму сам: своим реестром компонентов и данными-заглушками.
О приложении, для которого форма делается, он не знает ничего — ни его API, ни его провайдеров,
ни того, как выглядит страница вокруг формы.

Встроенный билдер этот разрыв закрывает без единой точки интеграции: превью — это запущенное
приложение в рамке. Словарь в поле формы пришёл из настоящего API, потому что форму нарисовало
приложение; уведомление при отправке показало оно же; правка сервиса во встроенном редакторе
кода легла на диск, и dev-сервер приложения показал её в превью.

Это тот же билдер, что открывается своей вкладкой: один вход, одна сборка, один набор плагинов.
Различается только место, где он запущен.

## Как это выглядит

1. Приложение подключает плагин к своему dev-серверу и оборачивает себя компонентом
   `<ReformerBuilder>`.
2. Запускается dev-режим, открывается любая страница.
3. Кнопка «Билдер» в углу страницы открывает билдер поверх неё — тот же интерфейс.
4. Один раз выбирается папка проекта (File System Access); дальше она поднимается сама.
5. Форма или любой файл проекта правится и сохраняется — файл пишется прямо на диск.
6. Результат рисует приложение, и смотрят на него в двух местах:
   - **вид «Форма» открытой вкладки** — кнопка со значком в её полосе, рядом с деревом
     и исходником: только компонент формы, без остальной страницы. То же место и та же кнопка,
     что у билдера в своей вкладке, — только рисует приложение;
   - **панель «Превью»** в правом доке — приложение целиком, с адресной строкой;
     **↗** в ней — то же приложение в отдельной вкладке, уже без билдера.

Рабочий образец — [`projects/reformer-builder-host-example`](../../reformer-builder-host-example/README.md).

## Подключение

Пакет — в `devDependencies` приложения: `npm i -D @reformer/builder` (`@reformer/builder@beta`
для prerelease-линии). Peer-зависимости — `react` 18 или 19 и `vite` 6 или 7, они у приложения
уже есть. В прод-сборку приложения клиент не попадает (см. ниже), поэтому зависимость dev.

Две строки: плагин в конфиге сборки и компонент вокруг приложения.

```ts
// vite.config.ts приложения
import { reformerBuilder } from '@reformer/builder/vite';

export default defineConfig({
  plugins: [react(), reformerBuilder()],
});
```

```tsx
// main.tsx приложения
import { ReformerBuilder } from '@reformer/builder';

createRoot(document.getElementById('root')!).render(
  <AppProviders>
    <ReformerBuilder>
      <App />
    </ReformerBuilder>
  </AppProviders>
);
```

Компонент стоит ВНУТРИ провайдеров приложения: форму, показанную в превью отдельно от страницы,
рисует это же приложение, и провайдеры ей нужны те же.

Больше приложению ничего не нужно. Билдер оно не компилирует: ни псевдонимов его исходников,
ни Tailwind, ни путей в `tsconfig`, ни React определённой версии. Каталог плагинов оно
не собирает и не раздаёт. Клиент в пакете едет собранным (`client/`) вместе с объявлениями
типов — компилировать TypeScript из `node_modules` приложению тоже не приходится.

`reformerBuilder()` отдаёт два плагина, и Vite разворачивает массив сам. Первый работает на
dev-сервере: раздаёт билдер и кладёт на страницу мост. Второй — только в `vite build`: подменяет
`@reformer/builder` заглушкой `@reformer/builder/noop` с тем же API, которая рисует детей.
В прод-сборке приложения клиента билдера нет — ни кнопки, ни рамки, ни чтения хранилища сессии.

### Параметры плагина

| Параметр  | Что задаёт                                                                                                                                                   |
| --------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `config`  | конфиг уровня запуска — путь от корня приложения; по умолчанию `.ui_builder/config.json`                                                                     |
| `plugins` | каталог плагинов приложения вместо набора, который едет с билдером; отдаётся целиком                                                                         |
| `ui`      | откуда интерфейс: `auto` (по умолчанию) — из исходников, когда они лежат рядом с плагином, иначе из готовой сборки; `source` и `dist` называют источник явно |

Переменную окружения плагин для конфига не читает — путь называет `vite.config.ts` приложения.
Так выбирают конфиг запуска на старте, например пресет кита:

```ts
// По умолчанию — пресет ui-kit; `REFORMER_BUILDER_CONFIG=.ui_builder/presets/hexa-ui.json` — HexaUI.
const config = process.env.REFORMER_BUILDER_CONFIG || '.ui_builder/presets/ui-kit.json';
export default defineConfig({ plugins: [react(), reformerBuilder({ config })] });
```

Образец — пресеты и скрипты `preset:*`
[приложения-образца](../../reformer-builder-host-example/README.md#второй-кит-hexaui). Конфиг
проекта (`.ui_builder/config.json`) билдер читает ещё раз, открыв каталог, — умолчаниям
(`defaults`) там не место, если конфиг запуска другой файл: записанные иначе, они дают
предупреждение при каждом открытии.

### Пропы компонента

| Проп          | Что задаёт                                                                                                     |
| ------------- | -------------------------------------------------------------------------------------------------------------- |
| `projectBase` | префикс адреса, под которым dev-сервер отдаёт открытую в билдере папку; по умолчанию открыт корень dev-сервера |
| `loadForm`    | своя загрузка модуля формы по пути от корня проекта — для сборщиков, которые не отдают исходники по адресу     |
| `enabled`     | включён ли билдер; по умолчанию — когда к dev-серверу подключён плагин                                         |
| `labels`      | подписи кнопки и сообщений                                                                                     |

## Каталог `.ui_builder/` приложения

Тот же каталог и по тем же правилам, что у билдера в своей вкладке
([composition.md](composition.md)). Разница одна — кто читает конфиг запуска: у `npx
reformer-builder` это лаунчер, здесь — dev-сервер приложения.

| Что                      | Кто читает                       | Когда                                |
| ------------------------ | -------------------------------- | ------------------------------------ |
| `config.json`            | плагин Vite, от корня приложения | на каждый запрос: правка видна по F5 |
| `settings.json`          | билдер, из открытого проекта     | при открытии проекта                 |
| `plugins/`               | билдер, из открытого проекта     | при открытии проекта                 |
| `templates/`, `codegen/` | плагины шаблонов и кодогена      | по своей надобности                  |

Поля уровня запуска — `preset`, `presetChoices`, `profiles`, `plugins.enable/disable`,
`defaults` — действуют, потому что конфиг приходит уровнем запуска. Обычный случай «приложение
и есть проект» даёт один файл на оба уровня, и предупреждений о нём нет.

## Плагины

Слоёв столько же, сколько в своей вкладке, и читает их тот же код.

- **Плагины приложения** — набор, который едет с билдером: дерево файлов, редакторы, кодоген,
  шаблоны, «Превью приложением». Их отдаёт dev-сервер под адресом билдера. Состав —
  [`application-plugins.embedded.json`](../application-plugins.embedded.json): плагинов,
  которыми форму рисует сам билдер, в нём нет. Превью-хост (`forms/preview`) в наборе есть:
  он не рисует, а выбирает, ЧЕМ показать документ, — и здесь выбирает приложение.
- **Плагины проекта** — `.ui_builder/plugins/` приложения. Включаются в настройках билдера,
  права подтверждаются диалогом, как в своей вкладке.

### Разработка плагина

Свой плагин лежит в `.ui_builder/plugins/<имя>/` приложения. Плагин из одного файла без
зависимостей билдер читает как есть (`main.ts`); плагину с зависимостями нужна сборка на месте —
`reformer-plugin dev src --out .` следит за исходниками и пересобирает.

Чтобы видеть правки без перезагрузки, плагин помечают «в разработке» (палитра команд →
«Плагины: наблюдать…»). Билдер перечитывает его, когда файл сохранён во встроенном редакторе
или когда человек вернулся в окно браузера из другой программы.

В монорепозитории плагины приложения берутся живьём из каталога проекта-образца, из сборок
на месте (`npm run plugins:build -w reformer-builder-playground`). Каталог живой: индекс,
который отдаёт dev-сервер, называет ревизию каждого плагина — отпечаток содержимого его
файлов. Вернувшись в окно браузера, билдер перечитывает индекс и перезагружает плагины, чья
ревизия изменилась; остальные и сам документ не трогает. Помечать такие плагины «в разработке»
не нужно — живой каталог наблюдается целиком. Так же ведёт себя каталог, названный параметром
`plugins`. У готовой сборки билдера плагины лежат в ней самой и не меняются.

## Что рисует компонент

Один и тот же компонент стоит и на странице, где человек работает, и в документах, которые
открывает превью, — поэтому смотрит, ГДЕ он открыт.

| Где открыт документ        | Что на экране                                                     |
| -------------------------- | ----------------------------------------------------------------- |
| обычная страница           | приложение и кнопка «Билдер»                                      |
| режим включён              | поверх страницы — рамка с билдером; приложение остаётся под ней   |
| рамка превью               | только приложение — кнопки билдера внутри собственного превью нет |
| рамка превью, адрес стенда | одна форма вместо приложения                                      |
| прод-сборка с плагином     | только приложение: вместо клиента — заглушка с тем же API         |
| без плагина, сервер        | только приложение                                                 |

Несколько свойств, на которые можно опираться:

- **Клиент лёгкий.** Компонент импортирует только React: кнопка, рамка и стенд формы; в пакете
  он едет собранным (`client/`) с объявлениями типов. Билдера в сборке приложения нет вовсе,
  а в прод-сборке нет и клиента: плагин подменяет его заглушкой.
- **Билдер — отдельный документ.** Стили, тема и заголовок у него свои и документа приложения
  не касаются; стили приложения до него не доходят. React у каждого собственный.
- **Рамка создаётся один раз и не снимается.** Закрытие её прячет. Открытый проект, вкладки
  и несохранённые правки живут в документе билдера, поэтому переживают и закрытие, и «горячую»
  замену модулей приложения.
- **Приложение под рамкой остаётся на месте.** Оно не размонтируется: закрыв билдер, человек
  возвращается на ту же страницу в том же состоянии.
- **Режим переживает перезагрузку страницы.** Он хранится в хранилище сессии вкладки, а проект
  и открытые вкладки билдер восстанавливает так же, как в своей вкладке. Новая вкладка,
  открытая из превью, режим не наследует. «Очистить кэш» билдера стирает и режим: после
  следующей перезагрузки страницы билдер выключен, пока его не включат снова.
- **Без плагина билдера нет.** Компонент узнаёт о плагине по мосту, который тот кладёт
  на страницу; нет моста — рисуется одно приложение. В прод-сборке до этой проверки не доходит:
  там вместо клиента заглушка.

## Как это устроено

```text
страница приложения (верхний документ, адрес dev-сервера приложения)
 ├─ приложение
 ├─ <ReformerBuilder>            клиент: кнопка «Билдер»; в рамке превью — стенд формы
 └─ рамка «reformer-builder-shell»  →  /__reformer-builder/
        тот же вход, что у `npx reformer-builder` (src/main.tsx)
        ├─ вид «Форма» вкладки: рамка «reformer-builder-preview» → стенд формы
        └─ панель «Превью»:     рамка «reformer-builder-preview» → страница приложения

dev-сервер приложения + плагин reformerBuilder()
  /__reformer-builder/runtime.json   конфиг запуска из каталога приложения + признак embedded
  /__reformer-builder/plugins/*      плагины приложения: индекс на лету и файлы с диска
  /__reformer-builder/*              интерфейс билдера — вложенный dev-сервер над исходниками
```

| Часть               | Где                                                         | Что делает                                                                      |
| ------------------- | ----------------------------------------------------------- | ------------------------------------------------------------------------------- |
| Плагин Vite         | `vite/plugin.mjs`                                           | отдаёт билдер под префиксом; кладёт на страницу мост; в `vite build` — заглушка |
| Обработчик адресов  | `vite/endpoints.mjs`                                        | решает, кто отвечает на запрос под префиксом                                    |
| Общий серверный код | `bin/static.mjs`, `runtime-bundle.mjs`, `plugins-serve.mjs` | тот же, что у лаунчера                                                          |
| Клиент              | `src/client/` → сборка `client/`                            | кнопка, рамка, стенд формы; только React; `noop` — заглушка для прод-сборки     |
| Окружение           | `src/shell/embedded/`                                       | чем билдер рядом с приложением отличается от вкладки                            |

**Вложенный dev-сервер.** В монорепозитории интерфейс отдаётся из исходников: плагин
поднимает второй экземпляр Vite с конфигом самого билдера и пересылает ему запросы под
префиксом. Свои псевдонимы, свой Tailwind и своя «горячая» замена модулей — у билдера, а не
у приложения. Поднимается он по первому запросу; сокет «горячей» замены делит http-сервер
с приложением, различаются они путём.

**Готовая сборка.** Когда исходников рядом нет, плагин отдаёт `dist` билдера — тот же, что
под лаунчером. Сборка сделана с относительным базовым адресом, поэтому ей всё равно, откуда её
отдают: с корня сервера лаунчера или из-под адреса билдера. Плагины приложения лежат в ней
одним каталогом на оба набора; лаунчер отдаёт записанный при сборке индекс своего набора,
а плагин dev-сервера строит индекс набора для встроенного билдера сам.

В монорепозитории исходники всегда рядом, и готовую сборку называют явно: параметром
`ui: 'dist'` либо, не трогая конфиг приложения, переменной окружения
`REFORMER_BUILDER_UI=dist` (параметр важнее переменной).

**Мост.** Клиент о сборщике не знает ничего, а одна вещь нужна именно от dev-сервера — событие
«собираюсь перезагрузить страницу». Плагин кладёт на страницу приложения маленький модуль,
который заводит мост на глобальном объекте и пересылает в него это событие. По мосту же клиент
узнаёт, что билдер на этом сервере есть.

**Фокус.** Кнопка билдера стоит в документе приложения, и фокус после щелчка остался бы там:
Ctrl+S достался бы браузеру, а возврат из другой программы билдер не услышал бы. Поэтому
открытая рамка получает фокус сразу и каждый раз, когда его получает окно приложения.

## Окружение: свой документ, общий источник

Общая сборка (`shell/boot/boot.ts`) о месте запуска не знает: всё, что от него зависит,
она получает портом окружения.

```ts
// shell/boot/environment.ts
export interface ShellEnvironment {
  /** Заголовок документа. */
  applyTitle?(title: string | undefined): void;
  /** Куда ставится признак тёмной темы. */
  readonly themeRoot: ThemeRoot | null;
  /** Перезапуск приложения. Без него смена профиля недоступна. */
  readonly reload?: () => void;
  /**
   * Очистка хранилища: весь источник во вкладке, только своё пространство имён рядом
   * с приложением. Без неё команды «Очистить кэш» нет — и пункта меню тоже.
   */
  purgeStorage?(known: KnownStorage): Promise<PurgeReport>;
  /** Возможности, которые оболочка добавляет до активации плагинов. */
  registerCapabilities?(services: ServiceRegistry): void;
}
```

| Что                         | Своя вкладка        | Рядом с приложением                                       |
| --------------------------- | ------------------- | --------------------------------------------------------- |
| Документ                    | свой                | свой: рамка либо вкладка с адреса билдера                 |
| Заголовок, тема, перезапуск | есть                | есть — документ свой                                      |
| Выбор профиля состава       | есть                | есть                                                      |
| Очистка хранилища           | есть: весь источник | есть: только пространство имён билдера `reformer-builder` |
| Превью приложением          | нет                 | есть                                                      |
| Кто рисует форму            | билдер              | приложение                                                |
| Конфиг запуска              | отдаёт лаунчер      | отдаёт dev-сервер приложения                              |
| Плагины приложения          | рядом со сборкой    | под адресом билдера на dev-сервере приложения             |

Пространство имён — соглашение, по которому встроенный билдер отличает своё от чужого
на общем источнике: один каталог `reformer-builder/` в OPFS (внутри — рабочие копии, кэш
сборки, установленные плагины), префикс `reformer-builder.` у баз IndexedDB и ключей хранилищ.
Данные приложения, включая хранилища его форм (`reformer-forms*`), очистка не трогает.
Старая раскладка — `ws/`, `build/`, `plugins/` в корне источника — переезжает внутрь один раз
при старте; чужие каталоги с такими же именами остаются на месте.

Какое окружение взять, решает вход (`src/main.tsx`) по ответу сервера запуска: dev-сервер
приложения дописывает к конфигу признак `embedded`. Признак ставит сервер, а не страница:
«я в рамке» не годится — тот же адрес открывается и вкладкой, и окружение вкладки там означало
бы право стереть хранилище приложения.

Адрес билдера можно открыть и вкладкой. Окружение то же; приложением для превью тогда
считается корень источника.

## Превью приложением

Плагин [`base/app-preview`](../../reformer-builder-playground/.ui_builder/plugins/base/app-preview)
вносит два вида, и у каждого своё место: форму — видом открытой вкладки, приложение целиком —
панелью «Превью» в правом доке. Об устройстве приложения он не знает: адреса ему даёт
возможность, которую регистрирует окружение.

```ts
// @reformer/builder-plugin-api
export interface AppPreviewService {
  /** Адрес страницы приложения, поверх которой открыт билдер. */
  pageUrl(): string;
  /** Адрес, по которому приложение рисует одну форму. */
  formUrl(modulePath: string): string;
  /** Файлы проекта записаны на диск — пора показать приложение заново. */
  onDidWriteSource(cb: () => void): Disposable;
}
```

Возможности нет — нет ни вида, ни панели: в своей вкладке плагин ничего не вносит.

**Форма — вид вкладки, а не панель.** В билдере без приложения форму показывает вид «Форма»
открытой вкладки: редактор спрашивает у превью-хоста поверхность и отдаёт ей тело вкладки.
Встроенный билдер выглядит так же — отличается не место, а тот, кто рисует. Плагин вносит
ПОВЕРХНОСТЬ превью (`preview.surface`): рамку со стендом формы приложения. Кнопку вида, её
значок и тело вкладки по-прежнему даёт редактор — ReFormer или RJSF, — а правило выбора
поверхности — превью-хост. Поверхность честно говорит о себе: форму можно трогать, но выбрать
узел щелчком нельзя — документ приложения билдеру не виден, и редактор об этом предупреждает
полосой над формой.

**Стенд формы.** Адрес стенда — адрес страницы приложения с параметром, в котором лежит путь
модуля формы от корня проекта. Приложение в рамке, увидев параметр, вместо себя рисует
компонент, экспортированный модулем по умолчанию, — внутри тех же провайдеров. Модуль формы —
`index.tsx` её каталога: так его печатает кодоген билдера. Под dev-сервером Vite модуль
грузится по адресу; остальным сборщикам — проп `loadForm`.

**Какая форма показана.** Форма документа вкладки: его каталог и `index.tsx` в нём. Модуля
нет — вместо рамки сказано, какого файла не хватает; появится после записи (его печатает
кодоген) — форма покажется сама. У файла, который формой не является (сервис, из которого
форма берёт словарь), вида «Форма» нет: форму при правке такого файла держат на экране
панелью «Превью», открыв в ней страницу приложения с этой формой.

**Рамка в рамке.** Обе рамки приложения стоят внутри документа билдера, который сам открыт
в рамке. Имя окна у них одно: по нему приложение узнаёт, что открыто в превью, и кнопку
билдера внутри себя не показывает. Стенд от страницы отличает адрес.

**Несохранённое.** Приложение читает файлы с диска, а не рабочую копию билдера:
несохранённую правку оно не видит. В билдере без приложения вид «Форма» рисует модель редактора,
и правка видна сразу; здесь та же кнопка показывает сохранённое — направление группы поменяли,
а поля стоят как стояли. Чтобы это не выглядело поломкой, над формой стоит полоса: пока
в рабочей копии есть несохранённые правки, она говорит, что приложение рисует записанное
на диск, и предлагает сохранить тут же. О правках плагин спрашивает службу сохранения — ту же,
по которой их считает строка состояния, — поэтому объявляет право `workspace.save`.

**Обновление.** Собранную форму приложение хранит в состоянии компонента, и «горячее» обновление
модулей его сохраняет — правка схемы приехала бы, а форма осталась прежней. Поэтому после
записи файлов и вид, и панель перезагружают свою рамку сами, с небольшой задержкой: dev-сервер
замечает запись не мгновенно. Панель при этом возвращается на тот адрес, куда человек в ней
дошёл.

## Сохранение и dev-сервер

Запись на диск — по Ctrl+S, как в своей вкладке. У сохранения есть побочное действие:
dev-сервер приложения видит правку.

- Обычно он обновляет модули «на лету» — и на странице приложения, и в рамке превью. Билдера
  это не касается: он в своём документе.
- Когда обновить не получается (у изменённого модуля нет принимающей границы, либо правилась
  сама страница), сервер просит перезагрузиться все открытые документы приложения. Рамке
  превью это и нужно. Страница, в рамке которой открыт билдер, не перезагружается: вместе
  с ней ушла бы и рамка. Пока билдер открыт, такая перезагрузка откладывается и выполняется
  при выключении режима.
- Перезагрузка без названной причины-файла (сервер пересобрал зависимости) проходит как есть:
  прежние модули сервер уже не отдаёт. Режим, проект и вкладки билдер после неё поднимает сам,
  а несохранённое лежит в рабочей копии.

## Панель во всю высоту дока

Рамке с чужим документом понадобился признак, которого у панелей не было: тело обычной панели
лежит в прокручиваемой области оболочки, где высоту задаёт содержимое, — и «растянуться» там
не на что. Вклад панели с `fill: true` получает область дока целиком и прокручивает себя сам.
Признак — часть контракта плагинов.

Шапки дока у панели превью тоже нет (`headless: true`): её называет адресная строка,
а «Превью» уже написано на кнопке рейла. Какая панель открыта, видно по самой кнопке — у открытой
она залита и значок в полном цвете.

## Чего нет

- **Несохранённых правок в форме.** Вид «Форма» показывает записанное на диск; правка видна
  после сохранения. Показать рабочую копию могло бы только само приложение — получив её
  от dev-сервера вместо файла, — и такой подмены модулей у плагина нет.
- **Знания о приложении.** Его реестр компонентов в палитре, источники данных в инспекторе,
  уведомления приложения на события билдера, выбор узла щелчком по форме в превью — будущий
  плагин сотрудничества с конкретным приложением.
- **Сборщиков, кроме Vite.** Билдер отдаёт плагин dev-сервера Vite.
- **Браузеров, кроме Chromium.** File System Access есть только в нём.

- **Заглушка** — `src/client/noop.test.ts`: рисует детей, API совпадает с клиентом, импорт
  без побочных действий.
- **Пакет у потребителя** — `scripts/check-packaging.mjs` (`npm run check:packaging`, идёт
  в CI): тарбол ставится в чистый проект вне репозитория — раскладка `files` (клиент собранным,
  без `src/`), оба входа и плагин импортируются, прод-сборка приложения с плагином без клиента
  (а без плагина — с клиентом: контроль, что исключает именно псевдоним), типы обоих входов

- **Живой каталог плагинов** — `src/shell/platform/plugin/application/live.test.ts`

  параметр стенда, адрес билдера.
- **Клиент** — тесты в `src/client/`: в браузере — рамка, фокус, стенд формы, состояния
  компонента.
- **Плагин превью** — тесты его пакета: поверхность формы (какая рамка открыта, когда она
  перезагружается, сколько места занимает в теле вкладки) и панель приложения (адресная
  строка, обновление).

  [`projects/reformer-builder-playground-e2e`](../../reformer-builder-playground-e2e/README.md):
  dev-сервер приложения-образца над его копией, билдер в рамке пишет файл, приложение в виде
  «Форма» и в панели показывает новое; конфиг запуска и плагин из `.ui_builder/` приложения; пересобранный
  плагин приложения перечитан без перезагрузки страницы. Тот же набор идёт и над готовой
  сборкой билдера (`test:e2e:embedded:dist`) — кроме сценария пересборки: каталог плагинов
  там не живой. Последний сценарий набора — сторож: интерфейс отдаётся именно тем, что назвали
  прогону.

проверяется руками — по шагам в README приложения-образца.
