## 1. Контекст и цель

`reformer-builder` — новый проект в монорепо (скелет уже создан: Vite + React 19 + Tailwind v4 +
`@reformer/*`). Задача брейншторма — договориться, **что это за инструмент**: видение, UX,
архитектура, роль AI.

**Опора — экосистема ReFormer (архитектура M1):** форма = 4 разделённых слоя над одной реактивной
моделью:

| Слой             | Что несёт                                                                | Сериализуемо в JSON?      |
| ---------------- | ------------------------------------------------------------------------ | ------------------------- |
| **model**        | значения (сигналы), `createModel<T>`                                     | нет (TS)                  |
| **layout-схема** | дерево «поле → сигнал + компонент + пропсы»                              | **да** (`JsonFormSchema`) |
| **validation**   | правила, `defineValidationSchema` + фабрики валидаторов                  | нет (TS)                  |
| **behavior**     | реактивная динамика, 10 операторов (`compute`/`copyFrom`/`enableWhen`/…) | нет (TS)                  |

🔗 `packages/reformer/docs/llms/09-formschema.md`, `projects/reformer-doc/docs/intro.md`.

**Главный вывод для билдера**: единственный сериализуемый артефакт — **layout-схема** в формате
`JsonFormSchema` (`@reformer/renderer-json`). Билдер по сути — визуальный редактор этого JSON.
Всё остальное (model/validation/behavior) — TS-код, который живёт в проекте разработчика.

**Два режима работы** (см. [2](#2-видение-и-охват)):

- **A — Standalone-дизайнер**: форма с нуля → JSON → изолированный preview.
- **B — Проектно-связанный редактор**: открыть реальный проект → править его схемы → live-результат
  в приложении разработчика через HMR.

## 2. Видение и охват

### 2.1. Тезис: билдер **technology-agnostic** и **ui-kit-agnostic**

💡 Ядро билдера ничего не знает про React и конкретный ui-kit. Оно параметризуется:

- **каталогом компонентов** (что можно поставить на форму) и
- **props-схемами** (что и как настраивается у каждого компонента).

🔗 В ReFormer это уже есть машиночитаемо: `@reformer/ui-kit/meta` → `defaultPropSchemas`
(`Record<registryName, PropsSchema>`), где каждая схема — JSON-Schema draft-07 + расширения
`x-doc: { group, kind }` (kind = виджет редактора: `boolean|text|number|enum|readonly`) и
`x-runtimeProps` (пропсы, которыми управляет рантайм, — их в редакторе не показываем).
🔗 `packages/reformer-ui-kit/src/meta.ts`, `packages/reformer-ui-kit/src/fields/props-schema.ts`.

⚖️ Значит, «каталог» — это контракт. ui-kit ReFormer — первый поставщик каталога, но любая
дизайн-система, отдавшая такой же контракт, подключается без изменений ядра.

### 2.2. Выход — renderer-agnostic JSON

💡 Билдер выдаёт `JsonFormSchema` — чистый JSON без React-импортов. Сегодня его рендерит
`@reformer/renderer-json` (React), завтра — рендереры для других фреймворков. Билдер не привязан к
тому, чем JSON в итоге отрисуют.

### 2.3. Для кого (позиционирование) — ❓ развилка

| Аудитория                     | Что важно                                          | Какой режим первичен |
| ----------------------------- | -------------------------------------------------- | -------------------- |
| 💡 **Разработчик** (dev-tool) | правит схемы в своём проекте, видит live-результат | **B**                |
| 💡 **Аналитик / no-code**     | собирает форму без кода, экспорт JSON              | **A**                |
| 💡 **Смешанно** (dev-first)   | сначала dev-инструмент, no-code — позже            | B, затем A           |

✅ **Решение (раунд 1, Q1): обе аудитории сразу.** Реконсиляция с Q3 (режим B первым): редактор-ядро
общее для обоих, разное — только I/O. Т.к. выбран FS Access API (Q2 — браузерное приложение без
бэкенда), режим A (новая схема в браузере → экспорт JSON) достаётся почти бесплатно тем же
приложением. Вывод-принцип: UX-редактор должен быть дружелюбен и к no-code, хотя I/O режима B —
про разработчика. См. 2.4, 4.1.

### 2.4. MVP → roadmap (обновлено раундом 1)

- **MVP** (режим B первым, Q3): FS Access API → выбрать каталог → дерево + найденные JSON-схемы →
  визуально править схему (палитра + инспектор) → сохранить в файл → Vite проекта делает HMR.
  Preview — **оба режима с переключателем** (Q4): схематичный (agnostic) ↔ живой (iframe dev-сервера).
  Режим A (новая схема → экспорт JSON) — включаем минимально тем же браузерным приложением
  (✅ Q15; почти бесплатно на FS Access API).
- **v2**: drag-drop реордер, wizard/array-редактирование, мост `postMessage` для sync выбора с живым preview.
- **v3**: AI-генерация (MCP `create-form`), другие каталоги/дизайн-системы, кроссбраузерность (Node-бэкенд-fallback).

## 3. Модель «вход → редактор → выход» (ядро)

```
        ВХОД                          РЕДАКТОР                        ВЫХОД
┌────────────────────┐      ┌───────────────────────────┐   ┌──────────────────────┐
│ каталог компонентов│─────▶│ canvas (дерево/preview)   │──▶│ JsonFormSchema        │
│  = компоненты      │      │ палитра  ·  инспектор     │   │ (renderer-agnostic)   │
│  + props-схемы     │      │ свойств (виджеты x-doc)   │   │                       │
├────────────────────┤      │                           │   ├──────────────────────┤
│ [режим B]          │      │ состояние билдера         │   │ [режим B] запись      │
│ файлы проекта +    │─────▶│  ⇄ round-trip ⇄           │──▶│ обратно в тот же файл │
│ его JSON-схемы     │      │                           │   │ (round-trip)          │
└────────────────────┘      └───────────────────────────┘   └──────────────────────┘
                                        │
                                        ▼  preview (в билдере)
        схематичный (метаданные) · runtime (renderer-json в билдере)   →   живой результат: dev-сервер разработчика (save→HMR)
```

🔗 `JsonFormSchema`: `{ version, $schema?, root: JsonNode }`; узлы — `field` (`value: '$model(path)'`),
`array` (`{ array, item: { $template } }`), `container` (`{ component, children }`); операторы
`$model / $component / $dataSource / $html / $fn / $locale`.
🔗 JSON → живая форма: `convertJsonToM1Tree(json, registry, model)`
(`packages/reformer-renderer-json/src/converter/json-to-render-schema.ts`).

**Чего билдер НЕ знает** (важно для чистоты архитектуры): конкретных React-компонентов, ui-kit,
model/validation/behavior. Он оперирует именами (`$component(Input)`) и props-схемами.
🔗 **Вход формализован как контракт** (раунд 7, разд. 13): UI-Builder владеет JSON-Schema-контрактом
описания компонентов; ui-kit поставляет **каталог-JSON** по контракту (версионированный). Ядро — JSON-native.

❓ Открытые: как в UI отражать `$dataSource`/`$fn`/`$locale`-операторы (значения приходят из кода
проекта, билдер их не резолвит)? Показывать как «ссылку на источник из проекта»?

## 4. Проектная интеграция (режим B) — сердце dev-инструмента

Сценарий (со слов пользователя): разработчик запускает наш билдер-dev-сервер → выбирает каталог
проекта → видит файловую структуру и все JSON-схемы UI → правит и сохраняет → dev-сервер _его_
проекта делает hot-reload → он видит обновлённую форму у себя.

### 4.1. Доступ к файловой системе — ⚖️ главная развилка

| Вариант                       | Как                                                                                            | ➕                                                     | ➖                                                |
| ----------------------------- | ---------------------------------------------------------------------------------------------- | ------------------------------------------------------ | ------------------------------------------------- |
| 💡 **Node-fs бэкенд**         | наш билдер = локальный dev-сервер с Node-процессом, REST/WS для read/write файлов              | кроссбраузерно, полный доступ, watch                   | нужен наш сервер рядом с проектом                 |
| 💡 **Vite-плагин-панель**     | плагин в проект разработчика открывает билдер как панель/оверлей, fs через vite dev middleware | один dev-сервер, живёт внутри проекта, HMR «бесплатно» | инвазивно (правим конфиг проекта), только Vite    |
| 💡 **File System Access API** | `showDirectoryPicker()` в браузере, без бэкенда                                                | ноль инфраструктуры                                    | только Chromium, трение с правами, нет file-watch |

✅ **Решение (раунд 1, Q2): File System Access API** — билдер это браузерное приложение без бэкенда.
Следствия:

- ⚠️ **Chromium-only** (Chrome/Edge); Firefox/Safari не поддерживают → кроссбраузерность через
  Node-бэкенд-fallback отложена в v3 (✅ Q12 — Chromium-only приемлемо для MVP).
- **HMR без нашего watch**: билдер пишет реальный файл на диск через FS Access API → Vite _проекта_
  сам видит изменение и делает hot-reload. Собственный file-watch для этого пути не нужен.
- **Связанный preview остаётся возможен**: разработчик отдельно запускает dev-сервер своего проекта,
  билдер его iframe-ит (см. 4.5). «Наш dev-сервер» из исходной формулировки сводится к браузерному
  приложению билдера + отдельно живущему dev-серверу проекта.

### 4.2. Обнаружение схем

💡 Скан каталога проекта, файл считаем «схемой UI», если:

- `$schema` указывает на `form-schema.schema.json`, **или**
- содержимое — объект вида `{ version, root }` с валидными операторами.
  🔗 Валидация: `@reformer/renderer-json/validate` → `validateFormSchema`; мета-схема
  `packages/reformer-renderer-json/src/schema/form-schema.schema.json`.
  💡 UI: дерево файлов проекта, найденные схемы подсвечены/отфильтрованы; клик → открыть в редакторе.
  ❓ Ограничивать скан (напр. `src/**/*.schema.json`) или показывать всё дерево и метить схемы?

### 4.3. Round-trip / сериализация (было «белым пятном», теперь ядро)

⚖️ Путь JSON→форма готов, **обратного (форма→JSON) в библиотеке нет** — проектируем сами.
💡 Требования к сериализатору:

- Стабильный, diff-friendly вывод (сохранять порядок ключей, отступы — чтобы git-diff был чистый).
- Сохранять строки-операторы как есть (`$model(...)`, `$dataSource(...)`).
- Идемпотентность: открыл и сохранил без правок → файл байт-в-байт прежний (иначе шумные диффы).
  ❓ Держать в состоянии билдера исходный AST/форматирование для минимальных диффов, или
  переформатировать целиком по стабильному принтеру (напр. Prettier с фикс-настройками)?

### 4.4. HMR

💡 Билдер только **пишет файл**; hot-reload делает dev-сервер самого проекта (Vite при
`import schema from './x.schema.json'` перезагружает модуль). Билдеру не нужно ничего перезапускать.
❓ Что если проект не на Vite (webpack/другое)? Fallback — наш собственный watch + сигнал, или
явно «поддерживаем Vite-проекты» в MVP.

### 4.5. Preview — два режима в билдере + внешний dev-сервер

✅ **Решение (раунды 1/5/12): превью билдера = ДВА in-builder режима** с переключателем; «живая правда»
= собственный dev-сервер разработчика (внешне), НЕ встроенный iframe.

| Режим               | Где             | Рендерит                                                               | Требует                                                         | Интерактив   |
| ------------------- | --------------- | ---------------------------------------------------------------------- | --------------------------------------------------------------- | ------------ |
| **Схематичный**     | в билдере       | боксы из метаданных каталога (label + тип)                             | ничего (agnostic)                                               | нет          |
| **Runtime**         | в билдере       | renderer-json + встроенный registry (ui-kit); модель из `$model`-путей | встроенный рендерер+registry; мок `$dataSource`/`$fn`/`$locale` | да           |
| **Живой результат** | **вне билдера** | приложение разработчика (его dev-сервер, отд. вкладка)                 | dev-сервер + `save→HMR`                                         | да (реально) |

- ✅ **Q4/Q18/раунд 12**: в билдере — схематичный + runtime. «Живой» **не встраиваем** iframe'ом: билдер
  пишет схему в файл → HMR dev-сервера → разработчик видит форму в СВОЁМ dev-сервере.
- ⛔ **Q14 / мост postMessage — отклонено (раунд 12, разд. 18)**: встроенный live-iframe + sync избыточны,
  раз результат и так виден в dev-сервере разработчика. Опц. plain-iframe dev-сервера как удобство (без моста).
- ✅ **Q13**: схематичный рисуется из метаданных каталога, без реальных компонентов → ядро agnostic.
- ✅ **Q17**: runtime — **renderer-plugin поверх agnostic-ядра**; дефолт = renderer-json + `@reformer/ui-kit`.
  `$dataSource`/`$fn`/`$locale` → мок-заглушки; модель — пустые сигналы из `$model`-путей. ⚠️ registry
  билдера может расходиться с проектом → точное совпадение даёт dev-сервер разработчика.
  🔗 Runtime рендер: `convertJsonToM1Tree(json, registry, model)` + `<JsonFormRenderer>`
  (`packages/reformer-renderer-json`).

### 4.6. Безопасность / надёжность

💡 fs-доступ строго локально; подтверждение перед перезаписью; авто-бэкап файла перед записью
(undo на уровне файла); показ diff перед сохранением.

## 5. UX и взаимодействие

💡 Классическая раскладка редактора:

- **Слева**: (режим B) навигатор файлов проекта + список схем; **палитра компонентов** из каталога.
- **Центр**: **canvas** — дерево формы и/или WYSIWYG-preview; drag-drop для добавления/реордера.
- **Справа**: **инспектор свойств** выбранного узла — поля генерятся из props-схемы, виджет по
  `x-doc.kind` (`boolean`→switch, `enum`→select, `number`→number-input, `text`→input); секция
  **«привязки»** на фокусе — `$model`-путь и `$dataSource`-имя (разд. 17).
- **Тулбар**: переключатель preview (схематичный · runtime), сохранить, undo/redo, валидировать.

💡 Спец-узлы: `container`/`Section`/`Box` (вложенность), `array` (`FormArray` — повторяющиеся группы,
🔗 drag-reorder обсуждался в `docs/plans/modular-meandering-moth.md`), `wizard`/`Step` (шаги).
🔗 Палитра field-типов (~20): `Input, Textarea, Select, Combobox, RadioGroup, Checkbox, Switch,
Slider, DatePicker, FileUpload, InputMask, InputOTP, NativeSelect, Toggle/ToggleGroup, …`.

✅ **Решение (раунд 3, Q5): гибрид** — дерево структуры + drag-drop по превью одновременно.
⚖️ Нюанс: drag-drop реалистичен по **схематичному** preview (и дереву) — там билдер владеет DOM.
runtime-рендер — только просмотр; «живой результат» на dev-сервере разработчика — внешний, не холст.

## 6. Developer Experience (DX)

Раз режим B — это **dev-инструмент**, DX не «приятный бонус», а метрика успеха: если правка схемы
через билдер медленнее/страшнее, чем руками в редакторе, — им не будут пользоваться.

- **6.1. Запуск и онбординг** — ⚖️ zero-config CLI (`npx @reformer/builder` в корне проекта → открылся
  браузер → текущий каталог уже выбран → сразу видны схемы) против Vite-плагина (глубже интеграция,
  но правим конфиг проекта — выше трение). Минимум шагов «хочу → редактирую». Пересекается с Q2.
- **6.2. Петля обратной связи** — 💡 `edit → save → HMR → результат` за <1s. Явный save или автосейв с
  дебаунсом? Быстрый цикл — главная ценность dev-tool.
- **6.3. Доверие к правкам файлов** — 💡 чистые git-диффы (идемпотентная сериализация, 4.3),
  diff-preview перед записью, авто-бэкап/undo на уровне файла. Разработчик должен доверить тулу свои
  исходники — без этого dev-tool мёртв. ✅ (раунд 3, Q10) **явный save (Cmd+S) + diff-preview** перед
  записью — подтверждено как модель сохранения.
- **6.4. Escape hatch / двусторонность** — 💡 split-view «визуальный ⇄ raw-JSON» (Monaco); правка в
  любой панели видна в другой. Билдер не «запирает» — рукопашная правка JSON остаётся валидной.
- **6.5. Discoverability** — 💡 палитра и инспектор показывают inline-доки из `x-doc` (описание пропа,
  enum-значения, дефолты); разработчик учит API формы прямо в тулзе. 🔗 доки машиночитаемы в
  props-схемах; можно тянуть и через `@reformer/mcp` `get_symbol_docs`.
- **6.6. Ошибки и устойчивость** — 💡 битая/невалидная схема не роняет билдер: показывается как ошибка
  с якорем на узел, `validate_json_schema` инлайн; ошибка в одной схеме не блокирует остальные.
- **6.7. Совместимость с их тулчейном** — 💡 уважать TS-типы модели, их registry и data-sources; не
  навязывать свой ui-kit. Идея: читать сгенерированный проектом `form-schema.schema.json`
  (`gen:form-schema`), чтобы палитра = ровно их зарегистрированные компоненты. Билдер — дополнение к
  воркфлоу, не замена.
- **6.8. Скорость / keyboard-first** — 💡 хоткеи, командная палитра (Cmd+K), быстрый поиск
  компонента/поля/схемы.

❓ Открытые: онбординг (Q9), автосейв vs явный save + diff-preview (Q10), split-view в MVP (Q11).

## 7. Белые пятна и вызовы

- ⚖️ **Round-trip fidelity** (см. 4.3) — стабильная сериализация, чистые диффы.
- ✅ **Валидаторы/behaviors** (раунд 3, Q6): билдер **генерит TS-заготовки** (`validation.ts`/
  `behavior.ts` со стабами по конвенции), разработчик дописывает логику; layout правится в JSON,
  эффект виден в живом preview. ⚖️ Тонкость: layout-ядро остаётся agnostic, а stub-генерация — это
  **ReFormer-специфичный адаптер** поверх (знает `defineValidationSchema` и 10 behavior-операторов).
  Держим это отдельным слоем, чтобы не «заразить» ядро. Пересекается с Q7 (codegen).
- ⏸ **Codegen в `.tsx`** — детерминированной генерации кода из схемы в библиотеке нет (только AI/MCP).
  Нужен ли билдеру экспорт в код, или JSON — достаточный выход?
- ❓ **Персистентность/undo-redo/версионирование** состояния билдера.

## 11. Синтез: MVP-концепция и следующий шаг

### 11.1. Что за продукт (одним абзацем)

`reformer-builder` — **браузерный визуальный редактор JSON-схем форм ReFormer**, technology- и
ui-kit-agnostic. Ядро оперирует каталогом компонентов (`defaultPropSchemas`) и правит единственный
сериализуемый артефакт — `JsonFormSchema`. Главный сценарий — dev-инструмент: открыть реальный
проект (File System Access API), найти его схемы, визуально править и сохранять обратно, а
hot-reload делает Vite самого проекта. Плюс лёгкий standalone-режим «создать с нуля → экспорт JSON».

### 11.2. Скоуп MVP (всё ✅ по раундам 1–5)

- **Платформа**: браузерное приложение, без бэкенда, **Chromium-only** (FS Access API), hosted как
  статическая страница (+ локальный запуск в монорепо); каталог persist в IndexedDB («Переоткрыть»).
- **Режим B (первичный)**: выбрать каталог → дерево + найденные JSON-схемы (скан по конфигурируемым
  globs; матч строгий `$schema` + эвристика shape, с бейджами уверенности; каталог по `$schema`-ссылке) →
  визуальный редактор → **явный save + diff-preview** → запись в файл → Vite проекта делает HMR.
- **Режим A (минимальный)**: «новая схема» → экспорт/скачать JSON.
- **Каталог компонентов** (контракт-first, разд. 13): UI-Builder владеет JSON-Schema-**контрактом**;
  ui-kit поставляет **каталог-JSON** (с полем `role`), билдер его валидирует. Версия контракта — в
  каталоге (свитчер версий рендереров/ui-kit — v2).
- **Редактор**: гибрид — дерево структуры + drag-drop по схематичному превью; палитра из каталога;
  инспектор свойств из props-схем (виджеты по `x-doc.kind`); **split-view raw-JSON (Monaco)**.
- **Preview-тоггл (2 режима в билдере)**: схематичный (метаданные, agnostic) · **runtime** (renderer-json
  - ui-kit внутри билдера). «Живой результат» = dev-сервер разработчика (save→HMR, внешне); встроенного
    iframe/моста нет (раунд 12).
- **Валидаторы/behaviors в MVP**: только layout в JSON; валидацию/поведение оставляем коду (живой
  preview показывает эффект). Генерация TS-заготовок — **v2** (отдельный `*.builder.ts` + композиция, разд. 16).
- **Round-trip** (Стратегия A, разд. 12): модель (порядок ключей + passthrough неизвестных) + вывод
  через `prettier/standalone` с `.prettierrc` проекта → идемпотентно, diff-friendly.
- **Гейт**: `validate_json_schema` перед сохранением (валидация, не AI-генерация).
- **Выход**: `JsonFormSchema` + сгенерированные TS-заготовки. Полного `.tsx` codegen нет.

6. **Runtime-preview registry** — встроенный ui-kit может расходиться с registry/данными проекта →

## 12. Глубокий разбор: round-trip сериализация (узкое место #1)

### 12.1. Задача и критерии успеха

Цикл режима B: файл `.json` → состояние билдера → правки → запись **в тот же файл**. Критерии (по
убыванию важности):

1. **Идемпотентность** — открыл и сохранил без правок → файл байт-в-байт прежний (нулевой diff).
   Без этого разработчик не доверит тулу свои исходники (риск #1).
2. **Локальность diff** — правка одного поля → минимальный локализованный diff, не переформат всего файла.
3. **Без потери данных** — то, что билдер не редактирует (и даже не понимает), сохраняется точь-в-точь.

### 12.2. Что именно надо сохранить (из реального формата)

🔗 Реальные `json-schema.json` — **Prettier, 2 пробела**, порядок ключей естественный
(`selector, component, componentProps, children` / `value, component, componentProps`), операторы —
строками. Значит сохранять надо:

- **порядок ключей** внутри узла (Prettier его НЕ сортирует → если навяжем свой порядок, получим diff
  на каждом файле);
- **строки-операторы дословно** (`$model(loanAmount)` — без нормализации пробелов в скобках);
- **произвольные `componentProps`** (числа, className-строки, вложенные объекты) нетронутыми;
- **неизвестные/форвард-ключи** (будущие операторы, `x-*`-метаданные) — опасность №1: наивная модель
  их ДРОПНЕТ (тихая порча файла).

### 12.3. Стратегии

| Стратегия                          | Как                                                                                                                                                                                           | Идемпотентность                                  | Сложность                          | Потеря данных               |
| ---------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------ | ---------------------------------- | --------------------------- |
| **A. Модель + prettier-принтер**   | parse → типизированная модель (сохраняет порядок ключей + «мешок» неизвестных ключей на узел); сериализация = собрать объект в исходном порядке → `prettier.format(…, projectPrettierConfig)` | ✅ для Prettier-проектов (репо — такой)          | средняя                            | нет (если есть passthrough) |
| **B. CST-хирургия (jsonc-parser)** | хранить исходный текст; из diff модели вычислить точечные правки (JSON Pointer → значение) → `jsonc-parser.modify/applyEdits`, сохраняя всё форматирование                                    | ✅ даже для не-Prettier файлов                   | высокая (особ. add/remove/reorder) | нет                         |
| **C. Наивный canonical-printer**   | parse → модель → `JSON.stringify(obj, null, 2)`                                                                                                                                               | ❌ переформат/переупорядочивание при первом save | низкая                             | да (дропает неизвестные)    |

⚖️ **Вывод**: (C) отпадает — даёт ровно тот шумный diff, которого боимся.

💡 **Рекомендация MVP — Стратегия A**:

- целевые проекты форматируют JSON Prettier'ом → если билдер эмитит **тем же Prettier**
  (`prettier/standalone` + json-плагин в браузере) с конфигом, **прочитанным из проекта** (`.prettierrc`
  через FS Access API), вывод совпадает с тем, что проект сам бы записал → open+save идемпотентны
  **без всякой нормализации**;
- сохранение порядка ключей + passthrough неизвестных ключей → нет потери данных и лишних диффов;
- существенно проще CST; 🔗 `convertJsonToM1Tree` уже даёт парс JSON→дерево (для рендера), нам нужен
  обратный принтер модель→JSON — **его в библиотеке нет, пишем сами**.
- **Стратегия B** — потолок точности для проектов БЕЗ Prettier / с нестандартным форматированием;
  отложить в v2, если A где-то «шумит».

### 12.4. Тонкости

- **Формат-авторитет**: билдер браузерный (нет Node) → бинарь prettier проекта не прогнать, но
  `prettier/standalone` работает в браузере; читаем `.prettierrc`/`.editorconfig` проекта для совпадения.
- **Структурные правки** (add/remove/reorder узла) — в A локальный diff за счёт сохранения порядка
  соседей; reorder = перестановка элементов `children[]`.
- **diff-preview** (Q10): показываем ровно то, что уйдёт на диск (наш принтер vs исходный текст) —
  «что видишь, то и коммитишь».
- **`$schema` и `version`** — сохранять как есть (относительный путь к мета-схеме проекта).

### 12.5. Открытые под-вопросы (раунд 6)

- **Q20**: стратегия round-trip для MVP (A / B / A сейчас + B в v2).
- **Q21**: формат вывода (под `.prettierrc` проекта / фикс-стиль билдера / отдать их pre-commit'у).
- **Q22**: неизвестные билдеру ключи/операторы (passthrough / предупреждать / блокировать сохранение).

### 12.6. Решение (раунд 6)

- ✅ **Q20 = Стратегия A** (модель + prettier-принтер) для MVP; CST-хирургия (B) — v2, если A «шумит»
  на не-Prettier проектах.
- ✅ **Q21 = формат под `.prettierrc` проекта** — bundled `prettier/standalone` читает конфиг проекта
  (`.prettierrc`/`.editorconfig` через FS Access API) → вывод байт-в-байт как у самого проекта.
- ✅ **Q22 = passthrough неизвестных** ключей/операторов нетронутыми (форвард-совместимость, ноль потери данных).
- **Итог по узкому месту #1**: идемпотентность достигается тем, что билдер эмитит JSON **тем же
  форматтером и конфигом, что и проект**, сохраняя порядок ключей и неизвестные ключи. Принтер
  модель→JSON (в библиотеке отсутствует) — предмет реализации; нужен парный gate-тест
  «open→save = identity» на реальных схемах репо.

## 13. Глубокий разбор: каталог компонентов (контракт входа)

### 13.1. Что такое «каталог» (формально)

Каталог — то, чем оперирует agnostic-ядро: множество записей, каждая описывает один тип узла для
палитры и инспектора. Минимальная запись:

```
CatalogEntry {
  name          // имя в схеме: $component(name)
  propsSchema   // JSON Schema (draft-07) редактируемых пропсов + метки виджетов
  role          // field | container | array — как узел ведёт себя в дереве
  category?     // группировка в палитре
}
```

Палитра = список `name`; инспектор = форма по `propsSchema`; `role` решает, куда узел можно положить.

### 13.2. Что уже готово в ReFormer (сильная опора)

🔗 `@reformer/ui-kit/meta` → **`defaultPropSchemas: Record<registryName, PropsSchema>`** —
сгенерировано `scripts/generate-meta.mjs` из всех `*.props.ts` с `x-registryName`.
🔗 `PropsSchema` (`packages/reformer-ui-kit/src/fields/props-schema.ts`) = JSON Schema (subset) + расширения:

- **`x-registryName`** — имя в реестре renderer-json (= `$component(name)`).
- **`x-doc: { group, type, kind }`** — `group` (Control/Options/Textfield/Behavior/State) для секций
  инспектора; `kind` (`boolean|text|number|enum|readonly`) — **виджет редактора**; `type` — TS-тип для показа.
- **`x-runtimeProps`** — пропсы, которых НЕ бывает в `componentProps` (`value/onChange/onBlur/disabled` —
  их резолвит seam) → **инспектор их скрывает**.
- Остальное — стандартные ключи: `properties`, `enum`→options, `default`, `minimum/maximum/multipleOf`, `description`.
- **Ключевой факт**: `*.props.ts` **React-free** (их грузит даже голый Node в MCP) → метаданные каталога
  отвязаны от самих компонентов. Билдеру для палитры/инспектора нужны ТОЛЬКО props-схемы; реальные
  компоненты — лишь для runtime-preview (renderer-plugin, разд. 4.5).
  🔗 `mergeFieldPropsSchema(variant)` — полный контракт `componentProps` field-узла = props враппера
  (label/hint/error) + вариант. Инспектор поля показывает **merged**-схему.
  🔗 Реестр рантайма: `defineRegistry` + `getComponentNames(registry)` — второй источник имён; должен
  совпадать с `x-registryName` каталога.

### 13.3. Откуда билдер берёт каталог (режим B) — ⚖️ развилка

| Источник           | Как                                                                               | ➕                                          | ➖                                                           |
| ------------------ | --------------------------------------------------------------------------------- | ------------------------------------------- | ------------------------------------------------------------ |
| **Bundled ui-kit** | билдер везёт `defaultPropSchemas`                                                 | всегда есть, ноль настройки                 | не знает кастомных компонентов проекта; drift версий         |
| **Из проекта**     | читать сгенерир. `form-schema.schema.json` / catalog-файл проекта (FS Access API) | точное совпадение с зарегистр. компонентами | нужна конвенция; meta-schema несёт имена, но не весь `x-doc` |
| **Hybrid**         | bundled ui-kit + overlay кастомов проекта                                         | точность + zero-config для стандартных      | сложнее                                                      |

⚖️ Та же природа, что риск #6 (registry runtime-preview): bundled vs проектное. Идея: у проекта уже есть
`form-schema.schema.json` (`gen:form-schema`) — источник **точного списка имён**; богатый `x-doc` (виджеты)
билдер добирает из bundled ui-kit по совпадающим именам, а для кастомов — из catalog-файла проекта.

### 13.4. Пробелы контракта (надо доопределить)

- **Роль узла** (`field`/`container`/`array`) в `defaultPropSchemas` **явно не выражена** — renderer-json
  определяет роль по СТРУКТУРЕ узла (`value`→field, `children`→container, `array`→array), а не по компоненту.
  Билдеру же роль нужна ДО постановки узла (палитра, drop-правила) → нужен явный `role` в каталоге (или
  эвристика: Box/Section=container).
- **Merge wrapper+variant** — инспектор поля обязан брать `mergeFieldPropsSchema`, иначе не покажет label/hint.
- **Скрыть `x-runtimeProps`** — уже помечены, просто не рендерим.
- **Версионирование/drift** — bundled каталог может расходиться с версией ui-kit проекта (новые/удалённые пропсы).
- **Источники `options`** (`enum` vs `$dataSource(NAME)`) — часть пропсов ссылается на данные проекта; в
  инспекторе это «ссылка на источник», не редактируемый список.

### 13.5. Открытые под-вопросы (раунд 7)

- **Q23**: источник каталога в MVP (bundled ui-kit / из проекта / hybrid).
- **Q24**: как задаётся роль узла (явный `role` в контракте / эвристика / вывод из props-схемы).
- **Q25**: контракт каталога — `PropsSchema` напрямую vs нейтральный `CatalogEntry`-адаптер (agnostic-чистота).

### 13.6. Решение (раунд 7): контракт-first, каталог как JSON

Направление **инвертировано** (ключевой сдвиг): не билдер ест TS-`defaultPropSchemas`, а:

1. **UI-Builder владеет КОНТРАКТОМ** — это **JSON Schema**, описывающая, как выглядит «каталог
   компонентов» (запись: `name`, `propsSchema`, **`role` (field/container/array)**, `category`, …).
   Контракт **версионирован** (поле версии контракта).
2. **UI-kit (любая дизайн-система) по контракту формирует КАТАЛОГ** — отдельный **JSON-файл**,
   соответствующий контракту. ReFormer ui-kit генерит его из `defaultPropSchemas` (адаптер
   `props-схемы → каталог.json`, аналогично `generate-meta.mjs`).
3. **Билдер валидирует** каталог ui-kit против контракта и **даёт рекомендации** (линт каталога:
   пропущенный `role`, неизвестный виджет, битая ссылка на `$dataSource`).
4. **Переключатель версий** (вероятно v2): поле версии контракта позволяет работать с разными версиями
   рендереров/ui-kit; поле закладываем сразу (дёшево), сам свитчер — позже.

✅ **Q23** = контракт-first: билдер грузит **каталог-JSON** (bundled известные + из проекта),
провалидированный против контракта. ✅ **Q24** = **`role` — явное поле** в JSON-описании компонента.
✅ **Q25** = контракт **JSON** (JSON Schema), не TS → ядро полностью JSON-native и agnostic.

⚖️ Следствия:

- Вход билдера теперь **сериализуемый и версионируемый** (как и выход) — симметрия JSON↔JSON.
- Новый артефакт: **контракт-мета-схема UI-Builder** (`component-catalog.schema.json`) — отдельно от
  `form-schema.schema.json` (та валидирует ЭКЗЕМПЛЯР формы, эта — КАТАЛОГ компонентов).
- ReFormer ui-kit получает build-шаг «сгенерировать каталог.json из `*.props.ts`».
- `role` придётся проставить в props-компаньонах ui-kit (сейчас его нет) — часть адаптера.

## 14. Глубокий разбор: обнаружение схем (режим B)

### 14.1. Задача

При «открыть каталог» найти файлы-схемы форм, отсеять прочий JSON, показать в дереве (подсветить/
отфильтровать), связать каждую схему с применимым каталогом.

### 14.2. Сигналы (по силе) — на реальных файлах

- **`$schema` → `…/form-schema.schema.json`** — сильнейший (явный opt-in). НО не у всех:
  🔗 `renderer.schema.json` (mcp v20) `$schema` **не имеет** — только `{version, root}`.
- **Shape**: top-level `{ version: "1.0", root: <node> }`, где `root` — объект-узел
  (`component`/`value`/`children`), операторы-строки `$model(...)`/`$component(...)`.
- **Имя** (`json-schema.json`, `renderer.schema.json`, `*.schema.json`) — **ненадёжно** (именование
  разнится; `form-schema.schema.json` — вообще МЕТА, не форма).
- **Подтверждение**: провалидировать кандидата против мета-схемы (`form-schema.schema.json` проекта,
  если рядом, или bundled контракт).

### 14.3. Ложные срабатывания — что отсеять

- 🔗 **сама `form-schema.schema.json`** — это JSON Schema (draft-07): `$schema: …/draft-07/…`, `$id`,
  `properties`/`definitions`; её `root` лежит ПОД `properties`, а не как узел. Надёжный дискриминатор:
  `typeof json.root === 'object' && (json.root.component || json.root.value || json.root.children)`
  → у меты `false`, у формы `true`.
- `package.json`/`tsconfig.json`/конфиги, обычные JSON Schema, фикстуры/моки, `_generated`.

### 14.4. Скоуп и производительность

- Игнор `node_modules`, `dist`, `build`, `.git`, `_generated` (+ уважать `.gitignore`).
- Фильтр по расширению (`.json`/`.jsonc`) и размеру; парсить и классифицировать (дёшево для мелких JSON).
- Большие деревья: фоновый/ленивый скан (дерево показать сразу, классификация в воркере), кэш;
  опционально конфигурируемые globs (`src/**/*.schema.json`).

### 14.5. Связь схема ↔ мета ↔ каталог (стыкуется с разд. 13)

- **`$schema`-путь связывает форму с её мета-схемой** → из меты берём точный enum зарегистрированных
  компонентов → знаем применимый каталог для ЭТОЙ схемы. Нет `$schema` → fallback на bundled/проектный каталог.
- **Sibling-файлы** в той же папке (`registry.ts`, `model.ts`, `render-behavior.ts`, `data-sources.ts`)
  — «бандл формы»; нужны для живого/runtime preview и генерации TS-заготовок (разд. 6/7). Обнаружение
  по конвенции соседства.

### 14.6. Открытые под-вопросы (раунд 8)

- **Q26**: скоуп скана (всё дерево с игнором / конфигурируемые globs / ручной выбор папки-файлов).
- **Q27**: критерий «это схема» (строгий `$schema`→form-schema / эвристика по shape / оба с бейджами уверенности).
- **Q28**: применимый каталог для схемы (по `$schema`-ссылке на мету проекта / всегда bundled / спрашивать).

### 14.7. Решение (раунд 8)

- ✅ **Q26 = конфигурируемые globs** — скан по паттернам (разумный дефолт, напр. `**/*.schema.json` +
  `src/**/*.json`, с игнором `node_modules/dist/build/.git/_generated`); пользователь может сузить/расширить.
- ✅ **Q27 = оба критерия с бейджами уверенности** — строгий (`$schema`→form-schema) = высокая; эвристика

- ✅ **Q28 = применимый каталог по `$schema`-ссылке** — из `$schema` формы → мета-схема проекта → точный

- Дискриминатор «мета vs форма» (`json.root` как узел, 14.3) остаётся обязательным фильтром от ложных.

## 15. Глубокий разбор: FS Access API UX (режим B)

### 15.1. Модель доступа

- `window.showDirectoryPicker({ mode })` → `FileSystemDirectoryHandle` (нужен user-gesture/клик).
- Право **read** vs **readwrite**, **per-handle, per-origin**. Грант действует **на сессию**; при
  перезагрузке страницы грант **не восстанавливается автоматически** — нужно перезапросить.
- `handle.queryPermission()` / `requestPermission({ mode })` — проверить/перезапросить.

### 15.2. Persist handle между сессиями

- `FileSystemDirectoryHandle` **сериализуется в IndexedDB** (structured clone) → можно сохранить и
  на след. визите не заставлять выбирать папку заново («Переоткрыть <папка>»).
- ⚠️ НО **сам грант не persist'ится**: после перезагрузки `requestPermission()` (жест + промпт браузера
  «разрешить сайту редактировать файлы в X?»). Поток UX: persist handle → кнопка «Переоткрыть» →
  `requestPermission` → доступ восстановлен без повторного пикера.

### 15.3. Права на запись

- readwrite запрашивать **upfront** (при выборе папки) или **лениво** (перед первой записью).
- **Первый write** в сессии = промпт браузера; дальше в той же сессии — молча.
- Это ОТДЕЛЬНО от нашего **diff-preview + явный save** (Q10): браузерный промпт — про доступ, наш —
  про содержимое правки.

### 15.4. Потеря доступа и внешние изменения (нет file-watch)

- ⚠️ FS Access API **не даёт слежения за файлами**. Файл на диске мог измениться извне: `git pull`,
  другой редактор, тулинг проекта, prettier pre-commit. Риск: наша in-memory версия устарела → save
  **затрёт чужие правки**.
- Митигация: хранить `File.lastModified` при загрузке; **перед записью re-read + сравнить**; конфликт →
  предупредить (перечитать / смёржить / перезаписать). Периодически (на focus окна) сверять и
  показывать баннер «файл изменён на диске».
- Инвалидный handle (папку удалили/переместили/переименовали) → `NotFoundError` → graceful: пометить,
  предложить re-pick.

### 15.5. Открытые под-вопросы (раунд 9)

- **Q29**: persist handle между сессиями (да, IndexedDB + «Переоткрыть» / нет, выбирать заново каждый раз).
- **Q30**: права на запись (readwrite upfront при выборе папки / лениво перед первой записью).
- **Q31**: внешние изменения файла (детект конфликта по `lastModified` перед записью + предупредить /
  периодический re-read + баннер / игнорировать — последняя запись побеждает).

### 15.6. Решение (раунд 9)

- ✅ **Q29 = persist handle в IndexedDB** + кнопка «Переоткрыть <папка>» (`requestPermission` одним кликом,
  без повторного пикера).
- ✅ **Q30 = readwrite upfront** при выборе папки (`showDirectoryPicker({ mode: 'readwrite' })`) — один промпт.
- ✅ **Q31 = детект конфликта перед записью** по `lastModified` (re-read + сравнить) + предупредить
  (перечитать/смёржить/перезаписать). Затирание чужих правок недопустимо.

## 16. Глубокий разбор: генерация TS-заготовок (validation/behavior)

### 16.1. Реальность файлов (важно приземлить ожидания)

🔗 `validation.ts` / `form.behavior.ts` (v20-бандл) — **полны рукописной бизнес-логики**: custom rules
(`mustBeTrue`, `digitsExact`, `phoneValid`), математика (`annuity`, `computeAge`), импорты
`./data-sources`/`./types`; композиция `apply(...steps)` / `defineFormBehavior(...)`, контракты
`@reformer/core/validation` и `@reformer/core/behaviors`. **Билдер это НЕ сгенерирует целиком.**

### 16.2. Что билдер РЕАЛЬНО может генерить

Только **декларативную часть, на которую есть UI**:

- **валидация**: списки правил по каталогу валидаторов (`required/email/min/max/minLength/maxLength/
pattern/phone/url/…`) → `validate(model.$.path, [required(), email()])` из тумблеров инспектора;
- **behaviors**: простые операторы, которым билдер даёт UI (`enableWhen/disableWhen/copyFrom`, простой
  `compute`); сложная логика (annuity-подобная) — рукописная.
- Пути известны из JSON: `$model(path)` → `model.$.path` (TS выведет тип, знать `types.ts` не обязательно).

### 16.3. Проблема co-ownership и подходы

Билдер и разработчик **совместно владеют** файлом → регенерация не должна затирать рукописное.
| Подход | Как | ➕ | ➖ |
|---|---|---|---|
| **B. Отдельный файл + композиция** | билдер владеет `validation.builder.ts`; рукописный `validation.ts` композит: `apply(builderSteps, …hand)` | ноль риска затирания; билдер-файл целиком регенерируем; ложится на `apply()`/`defineFormBehavior` | нужна конвенция композиции; 2 файла |
| **A. Managed regions** | маркеры `// <builder:generated> … </builder:generated>`; регенерим только внутри | один файл | нельзя править внутри маркеров; шум в коде |
| **C. AST-merge** | ts-morph/babel: точечно править узлы билдера, остальное беречь | бесшовно | тяжело в браузере (bundle), риск мис-мёрджей |
| **D. Create-only** | сгенерить скелет один раз, дальше не трогать | ноль риска | нет синка при добавлении полей |

💡 **Рекомендация — B**: отдельный `*.builder.ts` + композиция через `apply()`/`defineFormBehavior`
идеально ложится на ReFormer, даёт полную регенерируемость билдер-части и нулевой риск затирания.
A (managed regions) — запасной «однофайловый» вариант. C — избыточно для MVP.

### 16.4. Тонкости

- **Тип модели** — не нужен явно: генерим `model.$.<path>` из `$model(path)`, тип выведется.
- **Осиротевшие правила** при удалении/переименовании поля — билдер-файл управляемый → чистим их там
  же (в отдельном файле это безопасно).
- **Только то, на что есть UI**; остальное — комментарий-маркер «оставлено разработчику».
- **Форматирование** — тем же `prettier/standalone` с конфигом проекта (разд. 12), чтобы TS-вывод не «шумел».
- **Запись TS** — через тот же FS Access API + diff-preview + детект внешних изменений (разд. 15).

### 16.5. Открытые под-вопросы (раунд 10)

- **Q32**: механизм co-ownership (B отдельный файл+композиция / A managed regions / D create-only).
- **Q33**: объём генерации (только декларатив с UI / декларатив + TODO-стабы для сложного).
- **Q34**: генерация TS-заготовок в MVP или v2.

### 16.6. Решение (раунд 10)

- ✅ **Q32 = отдельный файл + композиция** (B): билдер владеет `*.builder.ts`, рукописный файл композит
  через `apply()`/`defineFormBehavior`. Ноль риска затирания, полная регенерируемость.
- ✅ **Q33 = декларатив + TODO-стабы**: генерим декларативные правила/behaviors с UI; для сложного —
  пустой stub с `// TODO` и сигнатурой, чтобы разработчик дописал.
- ✅ **Q34 = v2**: в MVP генерации TS НЕТ (только layout в JSON; валидацию/поведение оставляем коду,
  живой preview показывает эффект). Генерация — v2, когда layout-цикл устоялся.

## 17. Глубокий разбор: схематичный preview

### 17.1. Роль

Всегда доступный, **agnostic**, **non-interactive** wireframe из метаданных каталога (разд. 13) + дерева
JSON. Он же — **drag-drop холст** (Q5, разд. 5). Риск #4: должен быть достаточно **читаем**, иначе им не
будут пользоваться (переключатся на runtime).

### 17.2. Что рисуем по типам узлов

- **field** — labeled box: `label` из `componentProps`, глиф по типу (см. 17.4), под ним — тип
  (`Input (text)`, `Select`).
- **container** (`Box`/`Section`) — рамка + `title`, вертикальный стек детей.
- **array** — индикатор повтора (`▤ repeats`) + один item-шаблон.
- **wizard/steps** — табы/заголовки шагов.
- Операторы: `options: $dataSource(NAME)` → подпись «▾ NAME» (значения не резолвим); `$model(path)` —
  опц. подпись пути (17.6/Q37).

### 17.3. Уровень фиделити — ⚖️ развилка

| Уровень               | Что                                                                                                     | ➕                               | ➖                                   |
| --------------------- | ------------------------------------------------------------------------------------------------------- | -------------------------------- | ------------------------------------ |
| **L1 outline**        | дерево с отступами, тип+label                                                                           | дёшево, всегда читаемо           | не похоже на форму                   |
| **L2 wireframe**      | серые боксы по типу виджета (input=бар, select=бар+chevron, checkbox=квадрат, textarea=высокий) + label | похоже на скелет формы, наглядно | больше работы                        |
| **L3 generic-styled** | нейтральные «настоящие» контролы (не ui-kit проекта)                                                    | близко к форме                   | размывает границу с runtime; сложнее |

💡 Рекомендация — **L2**: явно «не настоящее», но передаёт структуру и типы полей.

### 17.4. Глиф компонента (agnostic)

- Маппинг **`x-doc.kind`/`role` → набор глифов** (input-bar, dropdown, checkbox/toggle, textarea, group-frame,
  step-tabs); `kind: enum`→dropdown, `boolean`→toggle, `text/number`→bar, `role: container`→рамка.
- **Fallback** для неизвестных/кастомных компонентов — generic box + имя (`$component(MyWidget)`).
- Опция (в контракт, разд. 13): компонент может объявить `schematicHint` (глиф/форму) — тогда точнее.

### 17.5. Взаимодействие

- select / hover-highlight / drop-target (это **drag-drop холст**, Q5); клик синкает с деревом+инспектором.
- Форму НЕ заполняем (не интерактивна) — ввод показывает runtime preview; реальное поведение — dev-сервер разработчика.

### 17.6. Открытые под-вопросы (раунд 11)

- **Q35**: уровень фиделити (L1 outline / L2 wireframe / L3 generic-styled).
- **Q36**: глиф компонента (маппинг `x-doc.kind`/`role` + fallback / `schematicHint` в контракте / только generic box).
- **Q37**: служебные подписи на узлах (`$model`-путь, `$dataSource`-имя) — показывать / нет / переключатель.

### 17.7. Решение (раунд 11)

- ✅ **Q35 = L2 wireframe** — скелет формы: контейнеры как рамки, вертикальный стек, wizard как табы.
- ✅ **Q36 = generic box** — единый бокс на узел (label + имя/тип компонента), БЕЗ пер-виджетных глифов
  и без `schematicHint`. То есть L2-раскладка из одинаковых боксов (не L1-дерево, но и без глиф-системы).
- ✅ **Q37 = привязки в правом инспекторе на фокусе** — холст чистый (без `$model`/`$dataSource`-подписей);
  при выборе узла инспектор показывает секцию «привязки» (`$model`-путь, `$dataSource`-имя).
- Reconcile «L2 + generic box»: структурный wireframe из одинаковых боксов; читаемость даёт **раскладка
  и label**, а не форма глифа.

## 18. Глубокий разбор: мост postMessage (живой preview sync) — ⛔ ОТКЛОНЁН (раунд 12)

> ⛔ **Итог (раунд 12): мост НЕ делаем** — см. [18.9](#189-решение-раунд-12-мост-отклонён). Разбор ниже
> (18.1–18.8) сохранён как контекст на случай, если связанный режим понадобится позже.

### 18.1. Что и зачем

Двусторонний sync между билдером и **живым** iframe: клик по узлу в билдере → подсветка элемента в
живой форме; клик в живой форме → выбор узла в билдере. Превращает живой iframe из view-only в
связанный. **Это v2** (в MVP живой = plain iframe, Q14).

### 18.2. Cross-origin + требование bridge-скрипта

`postMessage` работает кросс-ориджин (билдер `builder.…` ↔ dev-сервер `localhost:3000`), НО живая
страница должна содержать **listener** → в приложение разработчика нужен **мини-скрипт/пакет-мост**.
Не zero-integration (как и отмечалось в Q14).

### 18.3. Адресация узел ↔ DOM (сильная опора в коде)

- 🔗 Узлы имеют `selector` (plain-id для override); renderer держит **`refRegistry`** (`selector` →
  живой ref → DOM) + `conditionRegistry`/`lifecycleRegistry`. Fallback — **индекс-путь модели**
  (`render-node.tsx`: «явный selector в приоритете, иначе индексный путь»).
- Мост переиспользует это: `schema.node(selector).getRef()` → DOM-элемент → подсветка/scroll.
- Опция: эмитить `data-reformer-selector` на узле (небольшая правка renderer) для прямого DOM-query.

### 18.4. Протокол и безопасность

- Сообщения (versioned, namespaced `{ source: 'reformer-builder', v, type, … }`): `handshake/ready`
  (мост объявляет готовность+версию), `select(selector)`, `highlight`, `hover`, `node-clicked(selector)`→билдер.
- Безопасность: мост проверяет `event.origin` (только ожидаемый dev-сервер), билдер шлёт с конкретным
  `targetOrigin` (не `*`).

### 18.5. Доставка моста — ⚖️ развилка

| Вариант                      | Как                                      | ➕                                                                  | ➖                   |
| ---------------------------- | ---------------------------------------- | ------------------------------------------------------------------- | -------------------- |
| **Встроить в renderer-json** | активируется при embed (флаг/handshake)  | renderer уже знает node↔DOM; zero-config для renderer-json проектов | правка renderer-json |
| **Отдельный пакет**          | `@reformer/builder-bridge`, dev импортит | явный, независимый                                                  | ручная интеграция    |
| **Vite-плагин**              | авто-инжект скрипта в dev                | авто                                                                | только Vite          |

### 18.6. Опция (амбициозно): live schema push

💡 Билдер шлёт **in-progress схему** в iframe через postMessage → приложение ре-рендерит **без записи
файла** → мгновенный preview до save. Требует, чтобы renderer принимал override схемы из моста.
Альтернатива — полагаться на `save → HMR` (медленнее, но проще). v2+/опционально.

### 18.7. Lifecycle / graceful

iframe грузится async; мост объявляет `ready`; нет моста/сервера → живой = plain iframe view-only,
sync выключен (не ломаемся).

### 18.8. Открытые под-вопросы (раунд 12)

- **Q38**: доставка моста (встроить в renderer-json / отдельный пакет / Vite-плагин).
- **Q39**: адресация узлов (selector из `refRegistry` + fallback индекс-путь / эмитить `data-reformer-selector` / требовать selector).
- **Q40**: live schema push (да — ре-рендер без save / нет — полагаться на save→HMR / опционально).

### 18.9. Решение (раунд 12): мост отклонён

⛔ Мост postMessage и встроенный «живой» iframe **не делаем**. Причина: разработчик и так видит живую
форму в **своём dev-сервере** (отдельная вкладка) через `save → HMR`; встраивать dev-сервер в билдер и
синхронизировать выбор — избыточная сложность (cross-origin, интеграция bridge-скрипта, протокол).

- Превью билдера = схематичный + runtime (оба in-builder, разд. 4.5).
- ✅ **Q40**: live schema push — опционально; если мгновенный preview понадобится, проще обновлять
  **in-builder runtime**, чем гонять схему в чужой iframe.
