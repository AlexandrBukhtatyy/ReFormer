# Сборка билдера под организацию

Билдер — одно приложение, а не набор дистрибутивов. Что в нём есть, решают четыре вещи, и все
четыре — данные, а не код:

| Что                               | Где                                         | Кто решает                    |
| --------------------------------- | ------------------------------------------- | ----------------------------- |
| состав встроенных плагинов        | `preset` и `profiles` конфига запуска       | тот, кто разворачивает билдер |
| между чем человек переключается   | `presetChoices` конфига запуска             | тот, кто разворачивает билдер |
| умолчания настроек (кит, тема, …) | `defaults` конфига запуска                  | тот, кто разворачивает билдер |
| платформа форм, движки, киты      | плагины приложения и `.ui_builder/plugins/` | сборка билдера и проект       |

Конфиг запуска — `.ui_builder/config.json` в каталоге, где запущен `npx reformer-builder`
(или `--config <path>`). Схема для автодополнения в IDE — `runtime-config.schema.json` пакета.
Всё, что здесь описано про состав, применяется только на уровне запуска: состав и умолчания
фиксируются при сборке приложения, до открытия проекта. Те же поля в конфиге проекта разбираются,
но не применяются. Записаны они там иначе, чем в конфиге запуска, — билдер говорит об этом
уведомлением; записаны так же — молчит: их уже применил запуск. Поэтому один
`.ui_builder/config.json` на оба уровня — запустили билдер в корне проекта и его же открыли —
предупреждений не даёт.

## Плагины приложения — едут вместе с билдером

Плагин попадает в билдер тремя путями, и различаются они тем, КТО его выбрал:

| Слой           | Откуда                                        | Кто выбрал                    | Когда работает                               |
| -------------- | --------------------------------------------- | ----------------------------- | -------------------------------------------- |
| встроенный     | собран в билдер (`src/plugins`)               | профиль состава               | всегда                                       |
| **приложения** | каталог `plugins/` рядом со сборкой           | тот, кто билдер развернул     | всегда: до открытия проекта, в любом проекте |
| проекта        | `.ui_builder/plugins/` открытого проекта, npm | человек, включивший в проекте | пока открыт проект                           |

Плагины приложения — пакеты того же вида, что плагины проекта (`manifest.json`, `main.js`),
собранные для поставки (`build:dist`). Билдер находит их по индексу `plugins/index.json` рядом
со своей сборкой и поднимает при запуске, сразу за встроенными. Доверие у них уровня запуска:
права из манифеста выдаются без вопроса, включено всё найденное, выключить такой плагин
из настроек нельзя — набор задаёт сборка. В разделе настроек «Плагины» они помечены «приложение».

Набор опубликованного билдера — список [`application-plugins.json`](../application-plugins.json):
основа (дерево файлов, редактор кода, предпросмотр markdown), платформа форм (реестр китов и превью-хост), оба движка форм и ассистент. Сборку раскладывает `npm run build:plugins` (после `npm run build`
и `build:dist` пакетов плагинов) — в `dist/plugins/`, сохраняя раскладку каталога плагинов.
Свой набор, не пересобирая билдер, называет флаг лаунчера:

```bash
npx reformer-builder --plugins ./my-plugins
```

Индекс каталога из флага лаунчер строит сам, на каждый запрос. Нет каталога и нет индекса —
слоя нет: так работает билдер под `vite dev`, где плагины остаются плагинами открытого проекта
(и перезапускаются по правке, если помечены «в разработке»).

Каталог, который сервер отдаёт с диска, — **живой**: его плагины пересобирают под работающим
приложением. Индекс такого каталога называет ещё и ревизию каждого плагина — отпечаток
содержимого его файлов. По возврату в окно билдер перечитывает индекс и перезагружает плагины,
чья ревизия изменилась: работающий — заново, упавший и только что появившийся — поднимает.
Пометок «в разработке» у слоя приложения нет: живой каталог наблюдается целиком. Живыми
бывают каталог из флага `--plugins`, каталог плагина dev-сервера приложения
([embedding.md](embedding.md)) и каталог dev-сервера самого билдера (ниже). Собранный в
`dist/plugins/` набор ревизий не несёт и не наблюдается.

Плагин проекта с тем же идентификатором, что у плагина приложения, не грузится: работает
экземпляр приложения, а строка в настройках помечена «перекрывает копию из проекта». Так
ведёт себя и проект-образец под собранным билдером: его каталог плагинов — исходники тех же
пакетов. Возможности плагинов приложения плагин проекта вправе требовать (`requires`) наравне
со встроенными.

## Движки форм — плагины

Встроенных движков форм у билдера нет, как нет и ничего другого про формы. Сам он — оболочка:
открытие проекта и сохранение, управление плагинами, выбор профиля.
Остальное приносят плагины: основу (дерево файлов, панель проблем, операции над записями,
редактор кода, предпросмотр markdown),
платформу форм (реестр китов и превью-хост — то, чем пользуется любой движок) и сами движки —
формат схемы, её редактор, поверхности превью, валидатор, генерацию кода, шаблоны, ассистента. Едут они вместе с приложением (см. выше) или лежат в `.ui_builder/plugins/`
открытого проекта. Без них файл формы открывается текстом.

Четыре готовых домена лежат в проекте-образце
([`projects/reformer-builder-playground`](../../reformer-builder-playground/README.md)), по пакету
на плагин:

| Домен    | Каталог                         | Плагины (идентификаторы)                                                                                                                                              |
| -------- | ------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| base     | `.ui_builder/plugins/base/`     | `reformer.files` — дерево файлов, панель проблем, операции над записями; `reformer.editor-monaco` — редактор кода; `reformer.editor-markdown` — предпросмотр markdown |
| forms    | `.ui_builder/plugins/forms/`    | `reformer.kits`, `reformer.preview` — платформа форм, общая для движков                                                                                               |
| ReFormer | `.ui_builder/plugins/reformer/` | `reformer.editor-schema`, `reformer.preview-runtime`, `reformer.validator-schema`, `reformer.codegen`, `reformer.templates`, `reformer.ai`                            |
| RJSF     | `.ui_builder/plugins/rjsf/`     | `reformer.rjsf.editor`, `reformer.rjsf.render`                                                                                                                        |

Каталог плагинов допускает один уровень вложенности. Подкаталог без `manifest.json`
и без `package.json` — **домен**; его подкаталоги с манифестом — плагины, а прочие (`core/` —
общий предметный код домена, `integration/` — проверки) билдер не трогает. Имя каталога плагина
в домене с идентификатором совпадать не обязано: идентификатор берётся из манифеста.

Под собранным билдером все четыре домена — плагины приложения и включены всегда. Там, где слоя
приложения нет (билдер под `vite dev`, свой набор без движка), основу, платформу форм и движок
включает проект — тем же списком, что любой свой плагин, в `.ui_builder/settings.json`:

```json
{
  "workspace.plugins.enabled": [
    "reformer.files",
    "reformer.editor-monaco",
    "reformer.editor-markdown",
    "reformer.kits",
    "reformer.preview",
    "reformer.editor-schema",
    "reformer.preview-runtime",
    "reformer.validator-schema",
    "reformer.codegen",
    "reformer.templates"
  ],
  "workspace.plugins.permissions": {
    "reformer.files": ["workspace.resources"],
    "reformer.codegen": ["workspace.save"],
    "reformer.templates": ["workspace.save"]
  }
}
```

Без `reformer.files` у проекта нет дерева файлов: открыть форму нечем. Без
`reformer.editor-monaco` нет редактора кода: текстовый файл открывается запасным полем ввода
плагина файлов, а исходник схемы и режим «рядом» у markdown показать нечем. Без
`reformer.editor-markdown` markdown-файл открывается исходником, без предпросмотра. Платформа форм нужна
любому движку: без `reformer.kits` форму нечем рисовать, без `reformer.preview` её негде показать. Остальное включается по одному: проекту без ассистента
достаточно не называть `reformer.ai`,
проекту с формами RJSF — назвать `reformer.rjsf.editor` и `reformer.rjsf.render`. Права, которых
просит плагин (`workspace.save` — писать файлы проекта), записываются туда же; без записи билдер
спросит их диалогом при первом включении.

Документ открывается тем редактором, чей движок успел подняться: открытие файла ждёт, пока
плагины проекта закончат загрузку.

## Встроенные профили

| Профиль        | Что внутри                                          |
| -------------- | --------------------------------------------------- |
| `builder`      | профиль по умолчанию: основа как есть               |
| `builder.base` | основа: проект, управление плагинами, выбор профиля |

Встроенные профили — тот же формат, что у своего профиля ниже: они лежат в
`src/application/profiles/builtin.config.json`, файле формата конфига запуска, вшитом в сборку.
Его `preset` называет профиль по умолчанию, так что этот файл — готовый образец для своего.

Без `preset` собирается `builder`. Неизвестное имя или состав, который не собирается
(опечатка в имени плагина, неразрешимое требование возможности), — предупреждение в консоли и
профиль по умолчанию: опечатка в конфиге не должна стоить инструмента.

Профиль называет только встроенные плагины. Плагин проекта или приложения в профиль не записать
и поправкой `plugins.enable` / `plugins.disable` не включить и не выключить: первое делают
настройки проекта, второе — набор, с которым собран билдер.

Дерево файлов, редактор кода, предпросмотр markdown, киты и превью-хост раньше были
встроенными, и их имена (`reformer.files`, `reformer.editor-monaco`, `reformer.editor-markdown`,
`reformer.kits`, `reformer.preview`, `files`, `editor-monaco`, `editor-markdown`, `kits`,
`preview`) могли остаться в чьём-то конфиге. Такое имя в профиле или поправке
пропускается с предупреждением в консоли — состав собирается без него, а не откатывается
к умолчанию.

## Рецепты

### ReFormer с HexaUI

Кит HexaUI — внешний плагин, пакет `@reformer/kit-hexa-ui`. Живёт он в каталоге плагинов
проекта-образца (`projects/reformer-builder-playground/.ui_builder/plugins/kit-hexa-ui`); его
[README](../../reformer-builder-playground/.ui_builder/plugins/kit-hexa-ui/README.md) — подробности
кита и образец кита, внесённого плагином. Сборка плагина:

```bash
npm run build:dist -w @reformer/kit-hexa-ui   # dist/: manifest.json, main.js, styles.css, chunks/
```

Содержимое `dist/` кладётся в проект как `.ui_builder/plugins/kit-hexa-ui/`. Включить плагин
можно в списке плагинов или настройкой проекта — файлом `.ui_builder/settings.json`:

```json
{ "workspace.plugins.enabled": ["kit-hexa-ui"] }
```

Кит выбирается в ячейке кита строки состояния или в палитре команд («Кит: Kaspersky HexaUI») —
или умолчанием организации, см. ниже. Тот же кит рисует и формы RJSF: киты — платформа, а не
часть движка.

Форму, напечатанную под HexaUI, приложение рисует само, пакетом `@reformer/kit-hexa-ui`. Страница
формы оборачивает `FormRenderer` провайдером кита — символом `kit.adapters.provider` каталога
(`KitProvider`), — так же, как превью билдера оборачивает форму рамкой кита. CSS HexaUI глобален
(ресет antd на `html`, `body`, теги), и приложение ограничивает его провайдером Vite-плагином
кита `hexaUiStyles()` из `@reformer/kit-hexa-ui/vite` — раздел «Стили — только внутри
`KitProvider`» README кита. Образец — страница `/contact-hexa` приложения
[`reformer-builder-host-example`](../../reformer-builder-host-example/README.md#второй-кит-hexaui).

Что под HexaUI есть в билдере:

- **полный каталог** — контракт `3.0`, полторы сотни записей, все компоненты входа пакета кита.
  Каталог не пишется руками: его генерирует `reformer-plugin catalog` из TypeScript-типов кита
  (рецепт ниже). В палитре — поля, контейнеры, отображение и действия. Оверлеи, навигация, табы,
  таблицы и тяжёлые компоненты — записи `limited`: в палитре они есть, превью рисует их
  подписанной заглушкой, кодоген печатает импорт. Инфраструктура кита (`FormField`,
  `KitProvider`, `FormWizard`…) в палитру не входит;
- **29 полей** с адаптерами формы. Имена записей — как у `@reformer/ui-kit` (`Input`, `Select`,
  `DatePicker`, `FileUpload`, …), поэтому одна схема формы рисуется обоими китами. Полей, которых
  у ui-kit нет, восемь: `CheckboxGroup`, `CodeEditor`, `InputSearch`, `RichTextEditor`,
  `TimeInput`, `TimeRange`, `ToggleButtonGroup`, `WeeklySchedule`. Вид значения поля
  (`Date | null`, `string[] | null`, …) билдер берёт из каталога — по нему кодоген печатает тип
  модели. Таблица соответствий полям HexaUI — в README кита;
- **визард** — `FormWizard` по протоколу визарда каталога `3.0` (`kit.adapters.wizard`). Поэтому
  под HexaUI есть встроенный шаблон «Пошаговая форма»: шаги рисует HexaUI `Wizard`, а переход
  делает поток формы — «Далее» не пускает дальше шага, пока его поля не прошли проверку.

Кит грузится по частям. Шапка (`id`, `label`, `package`) — значением: по ней кит виден в выборе.
Каталог (~0,5 МБ JSON, `chunks/catalog.js`) — динамическим импортом, когда кит выбран.
Пространство имён (HexaUI с antd и styled-components) — когда кит рисует форму; календари и
редакторы полей — при первой отрисовке такого поля. Стили плагина оболочка ставит с изоляцией
`scoped`: они действуют только в рамке кита в превью (`[data-rb-plugin="kit-hexa-ui"]`), и
всплывающие окна полей — списки, дерево, календари — кит открывает в той же рамке.

Ограничения (подробно — раздел «Ограничения» README кита):

- HexaUI объявляет React 16–18, а билдер работает на 19-м. Формы рисуются, но antd и
  styled-components внутри кита пишут предупреждения в консоль;
- `GlobalStyle` HexaUI кладёт CSS-переменные палитры и шрифты прямо в `<head>` — мимо изоляции
  стилей, когда кит впервые рисует форму;
- повторное включение плагина в той же вкладке даёт второй экземпляр styled-components —
  предупреждение в консоли до перезагрузки вкладки;
- подсказки самостоятельного `Tooltip` HexaUI открываются в `document.body`, вне стилей кита;
- локали провайдер кита не получает, и словарь HexaUI — английский по умолчанию: календарь и
  кнопки визарда, если схема не задала им подписи (`nextLabel`, `backLabel`, `submitLabel`).

### Свой кит: каталог из типов

Кит дизайн-системы организации вносится тем же путём, что HexaUI: плагином. Ни билдер, ни движки
о ките не знают — кит описывает себя каталогом и отдаёт компоненты пространством имён.

- **Плагин кита** — пакет с манифестом (`src/manifest.json`, в `requires` — служба китов
  `reformer.kit.catalog ^2`) и точкой входа, которая вносит кит в точку `KitSourcePoint`
  (`reformer.kit.source`) из `@reformer/builder-plugin-api`: шапку кита значением, каталог и
  пространство имён — загрузчиками (`catalog: () => import('../catalog.json')`). Стили — полем
  `styles` манифеста с изоляцией `scoped`. Образец — `src/builder-plugin.ts` кита HexaUI.
- **Поля** — обёртки над контролами дизайн-системы со статикой `reformerAdapter`
  (`FieldAdapter` из `@reformer/core/react`): адаптер сводит шов формы (`value`, `onChange`,
  `onBlur`) к контракту контрола. По этой статике генератор и узнаёт поле, поэтому тип пропсов
  обёртки должен быть точным: из него выводятся пропсы записи.
- **`catalog.config.mjs`** (с `// @ts-check` и `defineKitCatalog` из
  `@reformer/builder-plugin-cli/catalog-config`) говорит то, чего типы не знают: тип значения
  каждого поля, роли записей (палитра, `limited`, служебные), разделы палитры, переименования,
  части составных компонентов, решения по статикам. Остальное — пропсы, их типы, описания, enum —
  генератор берёт из TypeScript-типов входа пакета кита.
- **Генерация и проверка** — скриптами пакета:

  ```json
  {
    "scripts": {
      "catalog": "reformer-plugin catalog .",
      "catalog:check": "reformer-plugin catalog . --check"
    }
  }
  ```

  `catalog.json` лежит в репозитории кита. `--check` ничего не пишет: сверяет файл с типами и при
  расхождении печатает дифф с кодом выхода `1`.

- **Тест дрейфа** — тот же `--check` программно (`checkKitCatalog` из
  `@reformer/builder-plugin-cli/catalog`), как `src/catalog.test.ts` кита HexaUI. Обновили
  дизайн-систему, TypeScript или обёртку поля — тест падает с диффом, и каталог перегенерируют
  осознанно.
- **Визард** — по желанию: компонент по протоколу визарда каталога `3.0`, названный в
  `kit.adapters.wizard`. Без него кит работает, а «Пошаговой формы» среди встроенных шаблонов нет.

Сборка плагина (`reformer-plugin build`) проверяет каталог той же проверкой контракта, что реестр
китов билдера. Формат конфига, правила вывода пропсов и отказы генератора —
[README `@reformer/builder-plugin-cli`, раздел `catalog`](../../../packages/reformer-builder-plugin-cli/README.md#catalog-каталог---config-файл---check);
контракт кита, протокол визарда и словарь пропсов каталога — раздел
[«Киты» README `@reformer/builder-plugin-api`](../../../packages/reformer-builder-plugin-api/README.md#киты).

### Свой профиль

```json
{
  "preset": "acme",
  "profiles": [
    {
      "id": "acme",
      "name": "Формы Acme",
      "plugins": ["reformer.project", "reformer.profile-switch"]
    }
  ]
}
```

Это основа без управления плагинами. Профиль конфига — те же данные, что у встроенного: `id`,
`name`, `extends` (встроенный или другой свой профиль), `plugins` (встроенные плагины — свои
или сверх унаследованных), `providers` (выбор провайдера возможности, когда её дают двое). `id`
не может совпадать со встроенным — такой профиль пропускается с предупреждением. Прежние имена
плагинов работают: `project` вместо `reformer.project`, `stack-switch` вместо
`reformer.profile-switch`.
Поправки `plugins.enable` / `plugins.disable` применяются поверх выбранного профиля.

### Кит организации по умолчанию

```json
{
  "defaults": {
    "settings": { "plugin.kits.active": "hexa-ui" }
  }
}
```

`defaults.settings` — умолчания любых настроек: слой между выбором человека и умолчанием плагина.
Пока плагин кита не внёс кит, действует встроенный; как только внёс — реестр китов переключается
на кит организации сам. Выбор человека — в ячейке кита или в палитре — сильнее умолчания
и переживает перезагрузку.

### Проект организации целиком

```text
<каталог запуска>/.ui_builder/config.json        preset, profiles, defaults.settings
<проект>/.ui_builder/plugins/reformer/<плагин>/   manifest.json, main.js, styles.css — движок
<проект>/.ui_builder/plugins/kit-hexa-ui/         manifest.json, main.js, styles.css, chunks/ — кит
<проект>/.ui_builder/settings.json                включённые плагины и выданные им права
<проект>/forms/                                   формы
```

Запуск в корне проекта (`npx reformer-builder`) и открытие того же каталога сводят всё в один
`.ui_builder/`.

## Готовые конфиги: по одному на кит

Готовые файлы лежат в `projects/reformer-builder-playground/.ui_builder/presets/` — формат тот же,
что у любого конфига запуска, ничего сверх рецептов выше. Движка готовый конфиг не выбирает:
движки — плагины проекта, и включает их проект. Остаётся кит по умолчанию:

| Файл           | Кит              |
| -------------- | ---------------- |
| `ui-kit.json`  | ReFormer UI Kit  |
| `hexa-ui.json` | Kaspersky HexaUI |

```bash
# в разработке; preset:<имя> есть на каждый
npm run preset:hexa-ui -w reformer-builder-playground
# собранным билдером, из каталога пакета билдера
node bin/reformer-builder.mjs --config ../reformer-builder-playground/.ui_builder/presets/hexa-ui.json
```

Файлы — образцы репозитория и лежат в проекте-образце, а не в пакете билдера: в npm они не едут.
Вне репозитория то же самое — две строки своего `.ui_builder/config.json`.

Те же два пресета есть у приложения со встроенным билдером —
`projects/reformer-builder-host-example/.ui_builder/presets/`, с его заголовком. Там конфиг
запуска называет параметр `config` плагина `reformerBuilder()`: `vite.config.ts` приложения
берёт путь из `REFORMER_BUILDER_CONFIG` (от корня приложения), без переменной — `ui-kit.json`.
`npm run preset:hexa-ui -w reformer-builder-host-example` заодно собирает плагин кита в
`.ui_builder/plugins` приложения. `config.json` приложения — конфиг проекта, только с заголовком:
умолчания, записанные там иначе, чем в пресете, билдер показывал бы предупреждением при каждом
открытии проекта.

`hexa-ui.json` называет кит, но не привозит его: кит — плагин проекта. Пока проект с плагином
не открыт, формы рисует встроенный кит, а HexaUI включается сам, как только плагин его внесёт.
Проект для проверки — тот же проект-образец: пакеты плагинов лежат в его каталоге плагинов и уже
включены, остаётся их собрать (скрипты запуска образца делают это сами):

```bash
npm run plugins:build -w reformer-builder-playground   # сборка плагинов образца, не в git
```

В билдере — «Открыть папку…» и выбрать `projects/reformer-builder-playground`.

## Имя приложения

«ReFormer Builder» в шапке и строка в «О программе» — тексты приложения, а не оболочки: в словаре
оболочки они нейтральны («Приложение»), потому что оболочка — база для разных приложений. Свои
тексты приложение приносит вместе с составом (`ApplicationComposition.messages`, у билдера —
`src/application/identity.ts`), и ложатся они поверх словаря оболочки. Перекрыть так можно
только эти два ключа: приложение представляется, а не переписывает оболочку. Заголовок вкладки
браузера по-прежнему задаёт `branding.title` конфига запуска.

## Выбор профиля и кита

В строке состояния справа — две ячейки, и вносят их разные плагины.

**Профиль** — встроенный плагин `reformer.profile-switch`. Ячейка называет действующий профиль:
состав встроенных плагинов приложения. Когда предложенных профилей несколько, щелчок открывает
их список; те же пункты есть в палитре команд — «Профиль: …». Профиль один — ячейка остаётся
подписью: переключать не между чем.

**Кит** — плагин китов `reformer.kits` (платформа форм). Ячейка называет действующий кит
и приходит вместе с плагином: под собранным билдером она есть сразу, под `vite dev` — когда
открыт проект, включивший платформу форм. В списке — киты, доступные сейчас (кит плагина
появляется, когда плагин включён в открытом проекте); в палитре — «Кит: …». Кит один — ячейка
тоже подпись.

Движки ни в один список не входят: они не выбираются, а включаются — сборкой билдера или
настройками проекта, — и редактор файлу подбирается по его формату.

- **Кит меняется на лету.** Это настройка, общая для всех движков.
- **Профиль меняется перезагрузкой**, и перед ней билдер спрашивает: состав встроенных плагинов
  фиксируется при сборке приложения. Профили, требующие перезагрузки, помечены в списке.
- **Выбор человека сильнее конфига запуска** — у обеих ячеек, и он переживает перезагрузку.
  Поэтому готовый конфиг открывает «свой» кит только там, где человек не выбирал иного.
- **«Как в конфиге запуска»** — последний пункт каждого списка: снимает выбор своей оси, и билдер
  снова следует конфигу. Выбрать профиль конфига руками значит то же самое — такой выбор
  не хранится.

Что предлагать к выбору профиля, решает тот, кто разворачивает билдер, — полем `presetChoices`:

```json
{
  "preset": "builder",
  "presetChoices": ["builder", "acme"]
}
```

Без поля предлагается один `builder`, то есть выбора профиля нет. То же даёт одно имя или пустой
список. В списке называют встроенные профили и свои из `profiles`. Профиль, который
не собирается или не содержит плагин `reformer.profile-switch`, пропускается с предупреждением
в консоли: из состава без выбора профиля нельзя было бы вернуться. Убрать выбор профиля целиком —
поправкой состава:

```json
{ "plugins": { "disable": ["reformer.profile-switch"] } }
```

Без него в составе запуска выбора нет вовсе, и сохранённый раньше выбор профиля не действует:
конфиг собирает ровно то, что в нём написано. Ячейка кита от этого не зависит — её приносит
плагин китов.

## В разработке билдера

`npm run dev` отдаёт конфиг запуска так же, как лаунчер: файл из переменной
`REFORMER_BUILDER_CONFIG`, иначе `projects/reformer-builder/.ui_builder/config.json` (каталог
в `.gitignore`). Файл читается на каждый запрос — правка видна после перезагрузки страницы.
Путь в переменной отсчитывается от каталога пакета билдера; скрипты `preset:<имя>` проекта-образца
выставляют её на готовый конфиг из его `.ui_builder/presets/`:

```bash
npm run preset:hexa-ui -w reformer-builder-playground
```

Слой плагинов приложения под `npm run dev` есть по умолчанию — набор опубликованного билдера
(`application-plugins.json`) из сборок на месте каталога проекта-образца, те же плагины, что
у лаунчера в `dist/plugins/`. Поэтому открыть в dev-сервере можно любой каталог, а не только
проект-образец: дерево, редакторы и движки приходят слоем, копия того же плагина в открытом
проекте уступает экземпляру приложения. Плагины должны быть собраны — иначе сервер
предупредит, какие именно:

```bash
npm run plugins:build -w reformer-builder-playground
npm run dev -w @reformer/builder
```

Переменная `REFORMER_BUILDER_PLUGINS` называет другой слой — путь от каталога пакета билдера
к каталогу плагинов (отдаётся целиком, как у `--plugins`) или к файлу набора (корень и список
каталогов); пустое значение (`REFORMER_BUILDER_PLUGINS=`) выключает слой — так проверяют то,
что приходит плагинами открытого проекта.

Каталог живой: пересобранный плагин билдер перезагрузит сам.

Постоянный каталог для таких проб — [`projects/reformer-builder-playground`](../../reformer-builder-playground/README.md):
конфиг запуска, конфиг и настройки проекта, оба движка плагинами, кит и формы.
`npm run builder -w reformer-builder-playground` поднимает dev-сервер с его конфигом запуска
(порт 5184). Его же открывают e2e-тесты билдера —
[`projects/reformer-builder-playground-e2e`](../../reformer-builder-playground-e2e/README.md).
