# Как добавить поддержку нового UI-kit

Билдер умеет работать с несколькими дизайн-системами и несколькими версиями одной. Активный кит
один в момент времени; его выбирают в переключателе тулбара, смена — с перезагрузкой страницы.

Эта инструкция — про то, что нужно сделать, чтобы новый кит появился в этом переключателе и
рисовал живое превью.

---

## С чего начать: два пути

Выбор зависит от одного вопроса — **знает ли кит про конвенции ReFormer**.

|                      | Путь A                                                                                 | Путь B                                                                   |
| -------------------- | -------------------------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| Когда                | Другая версия `@reformer/ui-kit`, форк, внутренняя ДС по тем же конвенциям             | Сторонняя ДС (MUI, AntD, Kaspersky HexaUI)                               |
| Признаки             | Есть props-компаньоны (`*.props.ts`), поля называются `${Name}Field`, есть `FormField` | Ничего из этого нет                                                      |
| Объём                | Адаптер на 30 строк + сгенерированный каталог                                          | Отдельный пакет: адаптеры полей, обёртка поля, провайдер, каталог руками |
| Пример в репозитории | `src/kits/adapters/reformer-ui-kit-11.ts`                                              | `packages/reformer-kit-hexa-ui/`                                         |

Если сомневаетесь — попробуйте путь A. Генератор каталога честно скажет, что не нашёл `./meta`, и
это будет ответом.

---

## Две сущности, которые нельзя путать

**Дескриптор кита** — «что это за кит и как его рендерить». Поставляет САМ КИТ: опциональный блок
`kit` внутри его catalog-JSON. Правило резолва символа, infra-компоненты, адаптеры, категории
палитры, режим стилей, настройки кодогена.

**Реестр китов** — «между какими китами пользователь может выбирать». Поставляет БИЛДЕР:
`src/kits/registry.ts`.

Разделение вынужденное, а не эстетическое: у опубликованного `@reformer/ui-kit@11` вообще нет
`exports['./catalog']`, поэтому «где взять каталог» обязано быть свойством записи реестра, а не
пакета.

## Путь A: кит по конвенциям ReFormer

### 1. Поставьте пакет

Несколько версий одного пакета ставятся npm-алиасом — правок в самих пакетах не требуется:

```jsonc
// projects/reformer-builder/package.json
"devDependencies": {
  "@reformer/ui-kit": "*",
  "@reformer/ui-kit-v11": "npm:@reformer/ui-kit@11.0.0"
}
```

### 2. Получите каталог

Если пакет экспортирует `./catalog` — используйте его напрямую. Если нет (так у 11.x и раньше) —
сгенерируйте:

```bash
npm run generate:kit-catalogs --workspace @reformer/builder
# либо вручную для произвольного пакета:
node scripts/gen-kit-catalog.mjs <pkg> <kit-id> --label "Подпись" --out src/kits/generated/<kit-id>.catalog.json
```

Генератор собирает каталог из трёх источников по убыванию надёжности: `<pkg>/meta`
(`defaultPropSchemas` — записи с настоящими props-схемами), `package.json#exports` (список
компонентных subpath'ов) и именованные экспорты каждого subpath'а (части compound'ов). Что не
импортировалось — деградирует до записи без props, а не роняет генерацию.

### 3. Напишите адаптер

Единственная задача адаптера — отдать плоскую карту «имя экспорта → значение»:

```ts
// src/kits/adapters/<kit-id>.ts
import * as UiKit from '@reformer/ui-kit-v11';
import * as TableNs from '@reformer/ui-kit-v11/table';
import { FormWizard } from '@reformer/ui-kit-v11/form-wizard';
import type { KitNamespace } from '../types';

export const MY_KIT_NAMESPACE: KitNamespace = { ...UiKit, ...TableNs, FormWizard };
```

Subpath-модули подмешивают явно: тяжёлые компоненты за optional peer-deps в главный barrel не
попадают, и без этого они деградируют в заглушку «предпросмотр ограничен».

> ⚠️ **Именованный импорт, а не `import * as` со спредом,** если из модуля нужен один символ. Спред
> namespace-объекта отключает tree-shaking: на `form-wizard` это стоило +140 кБ в главном чанке.

### 4. Зарегистрируйте

```ts
// src/kits/registry.ts
{
  id: 'my-kit',
  label: 'My Design System',
  version: '11.0.0',
  catalog: myCatalog as unknown as CatalogJson,
  loadNamespace: async () => (await import('./adapters/my-kit')).MY_KIT_NAMESPACE,
}
```

> ⚠️ **`loadNamespace` обязан быть `import()`.** Статический импорт сложит все киты в главный чанк,
> и переключатель версий будет оплачиваться весом всех вариантов сразу.

Всё. Переключатель подхватит кит автоматически.

## Путь B: сторонняя дизайн-система

Кит становится **отдельным workspace-пакетом** со своими зависимостями. Билдер про него ничего не
знает — только перечисляет в реестре и грузит namespace. Эталон — `packages/reformer-kit-hexa-ui/`.

```
packages/reformer-kit-<name>/
  package.json      # свои зависимости на ДС; peer: react, @reformer/cdk, @reformer/core
  catalog.json      # каталог 2.0 с блоком kit
  src/
    fields.tsx      # адаптеры полей к seam ReFormer
    form-field.tsx  # обёртка поля поверх cdk
    provider.tsx    # провайдер темы + контейнер-скоуп
    namespace.ts    # плоская карта «имя → компонент»
    index.ts
```

`exports` указывайте на исходники (`"." : "./src/index.ts"`) — билдер компилирует их своим Vite,
отдельная сборка пакета не нужна.

### Адаптеры полей

Контракт формы ReFormer — **`value` + `onChange(value)` + `onBlur`**. Плюс служебный проп `control`,
который в примитив пускать нельзя. Задача адаптера — свести к этому API компонента ДС:

```tsx
export function InputField(props: FieldProps) {
  const { value, onChange, onBlur } = props;
  return (
    <Textbox
      {...rest(props)} // без value/onChange/onBlur/control
      value={(value ?? '') as string}
      onChange={(next: string) => onChange?.(next)} // лишние аргументы отбрасываем
      onBlur={onBlur}
    />
  );
}
```

Два правила, каждое из которых стоило отладки:

- **Снимайте пропсы обёртки** (`label`, `required`, `description`) перед спредом в примитив. Их
  читает `FormField` из cdk-контекста, а если оставить — ДС прокинет их в DOM, и в разметке
  появится `<input label="Сумма">`. React такие атрибуты не фильтрует, они строковые.
- **Контролы с собственной подписью** (чекбокс, тумблер) помечайте
  `Component.reformerLayout = 'inline-label'`, иначе обёртка нарисует вторую подпись сверху.

### Обёртка поля

Регистрируется под ключом `FormField` (он же `FIELD_WRAPPER` рендерера) и строится поверх headless
`@reformer/cdk/form-field`:

```tsx
<CdkFormField.Root control={control}>
  {/* внутри Shell: useFormFieldContext() → { label, required, error, componentProps, pending } */}
  <Shell />
</CdkFormField.Root>
```

Сам контрол инстанцирует `<CdkFormField.Control />` — руками его создавать не нужно.

### Провайдер и стили

Если ДС требует контекста (тема styled-components, i18n, конфиг портала) — объявите обёртку в
дескрипторе, и билдер завернёт в неё поддерево превью:

```jsonc
"adapters": { "provider": { "symbol": "KitProvider" } }
```

Символ ищется в namespace кита по имени. Киту на Tailwind-токенах обёртка не нужна — не объявляйте.

Для стилей есть два режима:

- **`tokens`** — ДС использует стандартный словарь CSS-переменных, достаточно переобъявить их
  значения на контейнере превью;
- **`standalone`** — ДС приносит собственный CSS с ресетом. Тогда кит рендерит контейнер
  `<div class="rb-kit-scope" style={{ display: 'contents' }}>`, а сборка билдера ограничивает
  глобальные селекторы этим контейнером (`vite-plugins/scope-kit-css.ts`, подключается в
  `vite.config.ts`). Добавьте свой пакет в `match`:

```ts
scopeKitCss({ scope: '.rb-kit-scope', match: /node_modules\/@kaspersky\// });
```

Плагин переписывает `html`/`body`/`:root` на контейнер (чтобы наследуемые свойства достались
поддереву), а `*` и голые типы — на его потомков.

> ⚠️ **Классовые селекторы скоупить нельзя.** antd и Radix рендерят выпадашки порталом в
> `document.body`, вне контейнера, и полный скоуп оставил бы их содержимое без стилей. В оболочку
> билдера классы кита и так не текут — там нет ни `.ant-*`, ни хешей styled-components.

## Справочник: блок `kit` в каталоге

Всё опционально. Отсутствие блока = «неявный кит»: билдер достраивает дескриптор своими дефолтами
и ведёт себя ровно как до появления контракта.

```jsonc
{
  "version": "2.0",
  "kit": {
    "id": "my-kit", // стабильный id, независимый от npm-алиаса
    "label": "My Design System",
    "package": "@acme/ds",
    "version": "2.1.0", // версия ПАКЕТА (не контракта каталога)
    "peerRanges": { "react": "^19" }, // подсказка человеку; решает символьная проверка
    "resolve": { "fieldSuffix": "Field" }, // Input → InputField
    "infra": { "fieldWrapper": "FormField", "asyncBoundary": "AsyncBoundary", "list": "List" },
    "adapters": {
      "wizard": { "symbol": "FormWizard", "subpath": "form-wizard" },
      "step": null, // null — кит такого не поставляет
      "provider": { "symbol": "KitProvider" },
    },
    "palette": { "categoryByName": { "Input": "Поля ввода" } }, // ЗАМЕЩАЕТ карту билдера целиком
    "styles": { "mode": "standalone", "href": "@acme/ds/styles.css" },
    "codegen": { "importSpecifier": "@acme/ds" },
  },
  "components": [
    /* … */
  ],
}
```

Поля записи компонента сверх нормативных (`name`, `role`, `propsSchema`):

| Поле         | Смысл                                                                                   |
| ------------ | --------------------------------------------------------------------------------------- |
| `exportName` | Точечный override правила резолва: `Chart` → `ChartContainer`                           |
| `subpath`    | Где искать символ, если его нет в barrel. Заодно даёт внятную причину, когда не нашёлся |
| `preview`    | `{ mode: 'live' \| 'limited', reason? }` — **жёсткий** запрет живого рендера            |
| `leaf`       | Компонент-лист: не drop-target, вложенных не держит                                     |

**`preview` и `subpath` — разные вещи, не путайте.** `preview: limited` проверяется ДО резолва:
оверлей нельзя рисовать, даже если он есть в namespace (Radix-корень без триггера даёт невидимый
узел). `subpath` — только объяснение, почему компонент не нашёлся; если кит его всё-таки поставит,
он обязан отрисоваться.

Ключи `FormField` / `AsyncBoundary` / `List` — это **ключи реестра**, которыми схемы адресуют
компоненты; они не меняются со сменой кита. Какими символами кит их поставляет, говорит `infra`.

## Что кит получает от билдера, а что обязан принести сам

Билдер владеет единственными инстансами `react`, `react-dom`, `@preact/signals-core`,
`@reformer/core`, `@reformer/cdk`, `@reformer/renderer-react`, `@reformer/renderer-json`. Кит их
**не тянет своих** — только объявляет в peer.

Это не стилистика: второй инстанс `@preact/signals-core` ломает `instanceof Signal`, и
`convertJsonToM1Tree` молча выдаёт «No form node for signal …» вместо рендера. Ровно поэтому в
`vite.config.ts` есть `resolve.dedupe`.

Следствие, о котором стоит знать заранее: **кит, собранный против другого мажора рантайма, не
поддерживается**. Гейт совместимости символьный, а не semver — при загрузке проверяется, что все
нужные символы есть, и при промахе кит не активируется, а показывает причину с именем символа.
Semver тут бесполезен: `@reformer/ui-kit@12` объявляет `@reformer/renderer-react: ">=1.0.0"`,
диапазон проходит — и следом падает жёсткий ESM link error.

## Проверка

1. **Каталог проходит контракт.** Это уже стережёт тест: `src/kits/registry.test.ts` валидирует
   каталог каждого кита из реестра. `npm test --workspace @reformer/builder`.
2. **Кит грузится.** Переключите его в тулбаре — страница перезагрузится. Если не активировался,
   будет тост с причиной, а билдер откатится на кит по умолчанию.
3. **Палитра и инспектор** показывают компоненты кита с его категориями.
4. **Живое превью.** Режим «Renderer»: поля должны рисоваться компонентами кита, а не плашками
   «предпросмотр ограничен». В DevTools проверьте, что подгрузились модули именно вашего пакета.
5. **Chrome билдера не поехал.** Для `standalone`-кита сравните шрифт оболочки до и после:
   `getComputedStyle(document.body).fontFamily` не должен измениться.
6. **Сборка.** `npm run build --workspace @reformer/builder` — адаптер кита обязан оказаться
   отдельным чанком, а не влиться в `App`.

## Грабли

Всё ниже — реальные случаи, а не гипотезы.

- **`import * as` со спредом убивает tree-shaking.** Нужен один символ — импортируйте именованно.
- **Пропсы обёртки текут в DOM.** `label`/`required` предназначены `FormField`, а не контролу.
- **Провайдер темы придирчив к типу аргумента.** У HexaUI `ConfigProvider` ждёт КЛЮЧ темы
  (`'light' | 'dark'`), а экспортируемые `LIGHT_THEME`/`DARK_THEME` — объекты для другого
  провайдера; передача объекта роняет рендер.
- **Нативный Node ESM не всё грузит.** Пакеты с директорными импортами (`antd/es/badge`) в голом
  Node не импортируются — проверять кит можно только через Vite.
- **`package.json` в этом репозитории врёт про версии.** `@semantic-release/git` не подключён,
  версия живёт в git-теге. Не берите версию кита оттуда.
- **Каталог, написанный руками, всегда беднее сгенерированного.** У `@reformer/ui-kit` 168 записей
  (из них 91 — части compound'ов), у ручного каталога HexaUI — 21. Палитра будет заметно короче, и
  это ожидаемо, а не поломка.

---

## Что пока не поддержано

- **Киты, требующие своего мажора рантайма ReFormer.** Нужен iframe с собственным стеком — см.
  `docs/plans/ui-builder-deep-sun.md`, §8.
- **Загрузка кита из `node_modules` проекта или с CDN.** Сейчас киты только вкомпилированные; для
  динамической загрузки кит должен публиковать собранный CSS, которого у `@reformer/ui-kit` нет.
- **Объявление своих китов через `reformer-builder.config.json`.** Реестр пока только вшитый.
