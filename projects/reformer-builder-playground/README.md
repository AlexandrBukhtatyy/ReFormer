# reformer-builder-playground

Проект-образец для [`@reformer/builder`](../reformer-builder): каталог, который билдер открывает
как рабочий. У него три роли:

- **дом плагинов приложения** — основа (дерево файлов), платформа форм (реестр китов,
  превью-хост) и движки ReFormer и RJSF живут здесь плагинами, по пакету на плагин: в самом
  билдере нет ни дерева файлов, ни чего-либо про формы. С собранным билдером они едут слоем
  плагинов приложения;
- **фикстура e2e** — [`reformer-builder-playground-e2e`](../reformer-builder-playground-e2e)
  открывает его в каждом тесте;
- **песочница** — на нём руками пробуют плагины, конфиги и формы, не заводя для этого
  каталог в `.tmp/`.

В npm не публикуется.

## Запуск билдера на этом проекте

```bash
npm run builder -w reformer-builder-playground        # dev-сервер билдера, http://localhost:5184
npm run builder:dist -w reformer-builder-playground   # собранный билдер под лаунчером, тот же порт
```

Дальше в билдере — «Открыть папку…» и выбрать `projects/reformer-builder-playground`. Нужен
Chromium-браузер (File System Access API).

Каждый скрипт запуска сначала собирает плагины проекта (`plugins:build`, см. «Плагины»): билдер
грузит их сборку, а в git она не едет.

`builder:dist` берёт готовый `projects/reformer-builder/dist` — сначала
`npm run build -w @reformer/builder`.

Порт 5184 — общий с e2e: сервер, запущенный здесь заранее, прогон тестов переиспользует.

## Конфиг и настройки

В `.ui_builder/` два файла, и отвечают они на разные вопросы:

| Файл            | Вопрос                   | Кто пишет                                  |
| --------------- | ------------------------ | ------------------------------------------ |
| `config.json`   | каким собрать приложение | человек: заголовок, локаль, тема           |
| `settings.json` | как настроен этот проект | билдер: включённые плагины, выданные права |

`config.json` билдер читает дважды: лаунчер — до сборки приложения, само приложение — открыв
проект. Здесь это один и тот же файл, раскладка «запустил в корне проекта и его же открыл»:
`builder:dist` запускает лаунчер в этом каталоге, и тот находит конфиг сам; dev-серверу, который
живёт в каталоге билдера, его называет `REFORMER_BUILDER_CONFIG`.

Состава (`preset`, `profiles`) конфиг образца не называет: собирается профиль по умолчанию —
основа конструктора и киты, — а движки приходят плагинами проекта. `preset`, `profiles`,
`presetChoices`, `plugins` и `defaults` применяются только на уровне запуска: разойдись они
в конфиге проекта с конфигом запуска, билдер при открытии предупредит, что эти поля не сработали.

`settings.json` называет включённые плагины (`workspace.plugins.enabled`) — все десять, оба движка
целиком — и права, выданные заранее (`workspace.plugins.permissions`): генерации кода, шаблонам
и редактору RJSF нужно писать файлы проекта (`workspace.save`). Без этой записи билдер спросил бы
права диалогом при первом открытии.

## Готовые конфиги: по одному на кит

В `.ui_builder/presets/` — два конфига запуска. Формат тот же, что у `config.json`; называют они
только кит по умолчанию — движок готовый конфиг не выбирает, движки включает проект.

| Скрипт           | Кит              |
| ---------------- | ---------------- |
| `preset:ui-kit`  | ReFormer UI Kit  |
| `preset:hexa-ui` | Kaspersky HexaUI |

```bash
npm run preset:hexa-ui -w reformer-builder-playground   # dev-сервер билдера, http://localhost:5174
```

Порт здесь обычный для dev билдера, 5174, а не 5184: на 5184 прогон e2e переиспользует
запущенный сервер, и готовый конфиг подменил бы умолчания, которые ждут тесты.

Открыв под готовым конфигом этот же каталог, вы увидите предупреждение о `defaults`:
`config.json` проекта просит свои умолчания, а запущен другой конфиг. Так и задумано.

`hexa-ui.json` называет кит, но не привозит его: кит — плагин проекта, см. «Плагины» ниже.
Подробности о составах — [composition.md](../reformer-builder/docs/composition.md) билдера; что
конфиги собирают именно своё, проверяет его тест `application/launch-presets.test.ts`.

## Плагины

Плагин, не входящий в состав билдера, — отдельный npm-пакет со своей сборкой. Пакеты плагинов
этого проекта лежат там же, где билдер их ищет, — в `.ui_builder/plugins/`, — и собираются
на месте. Сборок у пакета две, по скрипту на каждую:

| Скрипт       | Куда                    | Зачем                                           |
| ------------ | ----------------------- | ----------------------------------------------- |
| `build:dev`  | корень каталога плагина | её грузит билдер: `manifest.json`, `main.js`, … |
| `build:dist` | `dist/`                 | поставка: то, что идёт в архив пакета           |

Обе — один и тот же `reformer-plugin build src` с разным `--out`: разбор манифеста, один
`main.js`, «сухая» активация. Исходники вместе с их `manifest.json` лежат в `src/`. Собранное
в git не едет: сборку для билдера исключает `.gitignore` самого плагина.

```bash
npm run plugins:build -w reformer-builder-playground   # build:dev каждого пакета из .ui_builder/plugins
```

Пока плагин не собран, манифеста в корне его каталога нет, и билдер, открыв проект, скажет об этом
уведомлением «в каталоге … нет manifest.json». Скрипты запуска выше собирают плагины сами; если
билдер запущен иначе, после клона репозитория соберите их до того, как открывать каталог.
E2E собирает плагины перед каждым прогоном.

Сборку делает CLI автора плагина, а он работает из своего `dist/`. Плагины вкладывают в свой
`main.js` ещё три пакета — помощники печати, тему RJSF и ядро знаний MCP — и находят их тоже
по `dist/`. В свежем клоне всё это сначала собирают:

```bash
# по одному и в этом порядке: npm сам пакеты по зависимостям не сортирует
for pkg in @reformer/core @reformer/cdk @reformer/renderer-react @reformer/ui-kit \
           @reformer/renderer-json @reformer/form-registry @reformer/mcp \
           @reformer/builder-plugin-api @reformer/builder-toolkit @reformer/builder-plugin-cli \
           @reformer/rjsf-kit-theme; do
  npm run build -w "$pkg"
done
```

### Где лежит плагин: каталог или домен

Билдер ищет плагины на двух уровнях каталога `.ui_builder/plugins/`:

- подкаталог с `manifest.json` — плагин; имя каталога совпадает с идентификатором
  (`playground-hello`, `kit-hexa-ui`);
- подкаталог без манифеста и без `package.json` — **домен**: плагины — его подкаталоги
  с манифестом. Имя каталога здесь с идентификатором не связано: `reformer/editor` — это плагин
  `reformer.editor-schema`, идентификатор берётся из манифеста. Остальное в домене (`core/`,
  `integration/`) билдер не трогает.

Каталоги с точкой в начале (`.shared`) билдер пропускает.

### Домены: основа `base`, платформа форм `forms`, движки `reformer` и `rjsf`

`base` — то, чем работают с проектом, каким бы ни было приложение: дерево файлов, панель
проблем, текстовый редактор «на крайний случай» и операции над записями (`reformer.files`).
Раньше плагин был встроенным и получал от оболочки порт; теперь всё, что ему нужно, он берёт
службами SDK — панель дерева отдаёт возможность `reformer.workspace.tree`. Открыть папку
и сохранить умеет сама оболочка (встроенный плагин «Проект»), поэтому проект без `base`
открывается, но показать в нём нечего.

Второй плагин домена — редактор кода (`reformer.editor-monaco`, каталог `monaco-editor`):
подсветка, подсказки по схеме, разметка по находкам, поиск. Движок Monaco едет внутри плагина:
код — отложенным модулем сборки (`chunks/`), который оболочка исполняет при первом открытом
файле, а не при запуске; воркеры — текстом в том же модуле, запуск из Blob-URL; стили — таблицей
плагина под его скоупом (`--bundle-css`), шрифт значков — data-URL в ней. Тело редактора —
возможность `reformer.editor`: его одалживают предпросмотр markdown и редактор схемы, поэтому
скоуп стилей тело несёт само. Без плагина текстовый файл открывается запасным полем ввода.

Третий — предпросмотр markdown (`reformer.editor-markdown`, каталог `markdown-editor`): рендер, режим
«рядом», подсветка блоков кода, переход по ссылкам проекта. Текст он редактирует чужим
редактором — возможностью `reformer.editor`, которую даёт редактор кода, — а всё оформление
везёт сам: типографику и палитру подсветки (см. «Стили» ниже). Без него markdown-файл
открывается исходником.

`forms` — то, чем пользуется любой движок и что не знает ни одного из них: реестр китов
(`reformer.kits`: активный кит как служба, его выбор ячейкой строки состояния и палитрой,
встроенный кит `@reformer/ui-kit`) и хост превью (`reformer.preview`: живой вид, выбор
поверхности). Раньше оба были встроенными плагинами билдера; теперь билдер про формы не знает
ничего, а пакеты, общие для исполняемого кода форм (`@reformer/core`, рендереры, кит), отдаёт
плагинам его слой приложения. Движок без платформы не работает: проект, включающий движок,
включает и её.

Каждый плагин домена — пакет `@reformer/builder-<домен>-<роль>`, устроенный как
`playground-hello`: `src/` с манифестом и входом `main.ts`, `build:dev`, `build:dist`, `dev`,
`validate`, `test`, `typecheck`. Включаются плагины по одному: проекту без ассистента достаточно
не называть `reformer.ai` в `settings.json`.

Общий предметный код домена — формат схемы, операции над ней, каталог компонентов, печать кода —
лежит в `core/`: это пакет без манифеста и без сборки, плагины импортируют его относительным
путём, и сборка каждого плагина вкладывает нужную часть ядра в свой `main.js`. Соседний плагин
домена импортировать нельзя — только через точки расширения и возможности SDK; границу стережёт
корневой `eslint.config.js`.

```bash
npm run build:dev -w @reformer/builder-reformer-editor    # один плагин
npm run dev -w @reformer/builder-reformer-editor          # build:dev на каждое сохранение
npm test -w @reformer/builder-reformer-editor             # юниты плагина
npm run test:browser -w @reformer/builder-reformer-editor # его же тесты в Chromium

# весь домен разом: каталог домена называет все его пакеты
npm test -w projects/reformer-builder-playground/.ui_builder/plugins/reformer
```

`integration/` — не плагин, а проверки: плагины домена ставятся в настоящую оболочку билдера
(там, и только там, есть псевдоним `@` на исходники билдера) — состав, сессия проекта, клавиши,
превью, шаблоны.

**Корпус знаний ассистента.** `reformer.ai` перед сборкой гонит `generate:knowledge`: корпус
документации `@reformer/*` собирается из `@reformer/mcp` в `src/knowledge/generated/` (не в git).
Код импортирует его отложенно — `await import('./generated/….json')`, — и сборка выносит
корпус из `main.js` двумя модулями данных в `chunks/` (вместе около 3 МБ). Оболочка исполняет
их при первом вопросе про библиотеку, а не при включении плагина; сам `main.js` — около 2,6 МБ.

**Стили.** Плагин проекта пользуется классами оболочки и токенами кита, а своего CSS не имеет —
пока не выходит за то, что билдер уже собрал. Движки выходят: класс, которого нет в исходниках
билдера, остаётся без правила и молчит — вёрстка не падает, а теряет отступ или цвет. Поэтому
недостающие утилиты Tailwind плагин везёт сам: `generate:styles` (перед каждой сборкой) считает
разность «классы плагина − классы билдера» и пишет её в `src/styles.css` (не в git), а манифест
объявляет таблицу полем `styles`. Оболочка ограничивает её поддеревом плагина, поэтому:

- портал (диалог, меню) лежит в `document.body`, вне контейнера плагина, — его содержимое
  помечают скоупом сами: `{...pluginScopeAttributes(<id плагина>)}`;
- селектор скоупа совпадает только с потомками контейнера, поэтому размеры самого корня портала
  задают стилем, а не классом;
- поверхности превью монтирует чужая панель — элемент поверхности тоже несёт скоуп своего плагина.

Сборка в поставку (`build:dist`) у всех пакетов сжатая — `--minify`; сборка на месте — нет:
стек в ней должен читаться.

Генератор умеет ещё два случая — оба нужны предпросмотру markdown:

- `--plugin <пакет>` подключает плагин Tailwind (типографика). Классы, которые существуют
  только благодаря ему, плагин везёт всегда, а их правила ложатся слоем НИЖЕ утилит: под
  контейнером плагина типографика иначе стала бы сильнее утилит билдера, и, например, снятие
  ширины колонки перестало бы работать;
- `--include <файл>` дописывает постоянный блок CSS — правила, которые утилитами не выражаются
  (палитра подсветки стоит на классах чужой библиотеки). Блок ссылается только на токены кита
  (`--chart-2`), а не на переменные темы Tailwind (`--color-chart-2`): вторые билдер объявляет,
  только пока сам ими пользуется, и ссылка на необъявленную переменную молчит. Такую ссылку
  генератор не принимает.

Что плагин везёт таблицу тогда и только тогда, когда она ему нужна, проверяет
`integration/plugin-styles.test.ts` каждого домена.

### playground-hello

Шаблон `reformer-plugin create`: одна команда, подпись которой берётся из словаря плагина.
Включён настройкой проекта (`workspace.plugins.enabled` в `.ui_builder/settings.json`). Пакет —
workspace монорепозитория, скрипты у него свои:

```bash
npm run build:dev -w playground-hello    # сборка для билдера — в корень каталога плагина
npm run build:dist -w playground-hello   # сборка для поставки — в dist/
npm run dev -w playground-hello          # build:dev на каждое сохранение исходников
npm run validate -w playground-hello     # манифест и файлы — правилами оболочки
npm run typecheck -w playground-hello
npm test -w playground-hello
npm run pack -w playground-hello         # архив пакета для npm
```

Цикл правки: поменять исходник → `build:dev` → в палитре команд (`Ctrl+Shift+P`) «Плагины:
перезагрузить «Playground Hello»». Без ручных шагов — `npm run dev` в пакете и «Плагины:
наблюдать «Playground Hello» — режим разработки» в билдере: первый пересобирает на сохранение,
второй перечитывает плагин при возврате в окно.

### Новый плагин

Проще всего — от образца: скопировать каталог `playground-hello` под именем нового `id` (без
`node_modules` и собранного) и поменять `id` и `name` в `src/manifest.json`, `id` в
`src/main.ts` и `name` в `package.json`. Затем `npm install` в корне репозитория — пакет
подхватится как workspace — и `npm run build:dev -w <имя пакета>`. Включается плагин в списке
плагинов билдера или строкой в `.ui_builder/settings.json`.

### Кит HexaUI

Кит HexaUI — пакет `@reformer/kit-hexa-ui` в
[`.ui_builder/plugins/kit-hexa-ui`](.ui_builder/plugins/kit-hexa-ui): и сам кит (поля, обёртка
поля, провайдер темы, каталог компонентов), и плагин, который вносит его в билдер. Устроен как
`playground-hello` — `src/`, `build:dev`, `build:dist`, — только сборка его весит около 5 МБ:
внутри HexaUI с antd и styled-components.

```bash
npm run build:dev -w @reformer/kit-hexa-ui
```

Плагин включён заранее (`kit-hexa-ui` в `.ui_builder/settings.json`). Кит появляется в ячейке
«движок · кит» строки состояния и меняется на лету; готовый конфиг `hexa-ui` открывает его
сразу. Подробности — [README кита](.ui_builder/plugins/kit-hexa-ui/README.md).

## Что помнить

- **Каталог — фикстура.** e2e снимает с него копию перед каждым тестом, поэтому любое изменение
  здесь — изменение входных данных тестов. Поменяли форму, плагин или конфиг — прогоните
  `npm run test:e2e -w reformer-builder-playground-e2e`. В копию идёт то, что видит git,
  и сборка плагинов для билдера; кит HexaUI и ассистента (самые тяжёлые сборки) берут только
  тесты, которым они нужны.
- **Ручная работа меняет файлы.** Открытый руками проект билдер правит на диске: сохранённая
  форма, включённый плагин, подтверждённые права. Перед коммитом — `git status` на этот каталог.
- **`.ui_builder/settings.json` пишет билдер** — при каждом открытии, своим форматом. Файл
  исключён из prettier (`.prettierignore`), иначе открытие проекта давало бы diff.
- **Сборка плагинов исключена дважды.** `.gitignore` плагина prettier и ESLint не читают,
  поэтому те же файлы названы в корневых `.prettierignore` и `eslint.config.js` — на обоих
  уровнях каталога плагинов. Новый файл сборки в корне каталога плагина — строка и там.
- **Раскладку доменов стережёт тест.** Порог в 15 модулей на каталог, состав корня плагина
  и словарь в корне — те же правила, что у исходников билдера (`testing/structure` в его `src/`);
  проверяет их `integration/structure.test.ts` каждого домена. Каталог сверх порога делится
  по темам или получает исключение с причиной — в том же тесте.
