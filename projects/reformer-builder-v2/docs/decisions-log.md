> Решения, принятые **во время работы**, а не при планировании. Проектные решения —
> в [implementation-plan.md](implementation-plan.md) и контрактных документах.
>

### t0-2 · Границы слоёв · 🔀 развилка + ⚠️ уточнено

**Решение: `no-restricted-imports` по псевдониму `@/…`, без новой зависимости.**
Точное правило требует резолвера путей (`eslint-plugin-import` с `no-restricted-paths`);
заводить зависимость до первого реального нарушения не стали.

**Ограничение, которое надо знать:** правила ловят импорты через `@/…` и глубокие
относительные пути (`../../../`), но обход `../../` ровно на границе слоя не видят.
Если протечёт — добавляем `eslint-plugin-import`, а не чиним регулярками.

**⚠️ Уточнение к критерию приёмки.** В плане записано «нарушение границы валит `npm run lint`».
По факту **корневой `npm run lint` их не ловит**: в корне действует корневой конфиг, и правил
слоёв в нём нет. Валит только `npm run lint --workspace reformer-builder-v2`.
Обнаружено так: первая проверка пробником прошла «успешно» из корня и я чуть не засчитал
неработающее правило. Следствие — **в CI обязан быть workspace-level lint**, иначе граница
не проверяется вообще.

Проверено пробниками: импорт `@/lib/*` из `host/` и `@/host/*` из `plugins/` дают ошибку
с внятным сообщением. Пробники удалены.

### Общее решение по параллельной работе агентов · 🔀 развилка

Общие типы создаются **до** запуска волны агентов, а не внутри неё: `disposable.ts` написан
заранее, потому что его нужны сразу трём примитивам и параллельные агенты создали бы три копии.
Так же агентам запрещено трогать `package.json`, конфиги и барели `index.ts` — файлы, за которые
они бы передрались. Барели собираю сам после сдачи волны.

### s1 · Поле ID узла в схеме · ✅ подтверждено + ⚠️ уточнено

**Подтверждено экспериментом (10 тестов), не рассуждением.** Конвертер собирает render-узел
из фиксированного перечня полей — спреда исходного узла нет ни в одной из трёх веток
(`json-to-render-schema.ts`, ~285 array, ~308 field, ~321 container). Неизвестное поле на узле
отбрасывается до создания render-узла и до DOM не доходит: проверено `renderToString`.
Проверил независимо: спред в конвертере действительно отсутствует, репозиторий после спайка чист,
`$nodeId` нигде не занят.

**Имя поля: `$nodeId`, форма `^[0-9a-z]{8}$`.** Обоснование перенесено в контракты.

**⚠️ Уточнение к формулировке плана.** «Рантайм не меняется ни строкой» — верно (renderer-react,
cdk, form-registry, MCP-код не трогаются). Но аналогия с `$schema`/`id`/`meta` **неполна**:
те поля игнорируются конвертером **и объявлены** в мета-схеме, поэтому AJV их пропускает.
У нового поля совпадает только первая половина — без правки `form-schema.schema.json` схема
с полем **отвергается**, а без правки `types/json-schema.ts` рукописный литерал падает с TS2353.
Обе правки в плане и так перечислены; неточной была именно аналогия.

**❌ Опровергнута одна правка из плана.** Добавлять `$nodeId` в дискриминатор `looksLikeNode`
(`collect-schema-selectors.ts`) **не надо**: это превратило бы литеральные объекты в «узлы»
и сделало обход over-inclusive. Узел и так всегда несёт хотя бы один из ключей
`component|value|array|selector|children`.

**Найдено сверх задания:**

- Забыты две материализованные копии мета-схемы в `react-playground`; одна регенерируется
  скриптом `gen:form-schema`, вторая обновляется руками и разъедется молча.
- **Класть id в `componentProps` было бы опасно**: очистка пропсов для html-тегов — список
  запрещённого, а не разрешённого, поэтому поле село бы реальным атрибутом на каждый
  `$html(...)`-узел. Записано в контракты как обоснование выбора «поле на узле».
- `docs/plans/polymorphic-launching-mccarthy.md` фиксирует тот же факт про конвертер и делает
  **противоположный** вывод — потому что там маркеру надо было дойти до DOM. Противоречия нет,
  но склеить эти два вывода легко, и тогда получится «поле на узле не работает».

### s2 · Изоляция CSS плагина · ❌ опровергнуто

**Утверждение контракта «обёртка в `@scope` — текстовая операция, разбор не нужен» неверно.**
Проверено экспериментом в реальном Chromium 143, не рассуждением. Поддержка `@scope` при этом
не проблема (Chrome 118, приложение и так требует Chromium ради File System Access) — проблема
в том, что обёртка **не изолирует**:

- непарная `}` закрывает `@scope` досрочно, и всё после неё становится глобальным;
- `@keyframes`, `@font-face`, `@counter-style` проходят насквозь и регистрируются глобально;
- `@property` на чужой токен **убивает наследование во всём документе** — три строки ломают тему;
- `html`/`body`/`:root` никогда не совпадают и молча выбрасываются, то есть ресет плагина
  теряется целиком. Это не безопасность, а **регрессия против v1**, где postcss их переписывает.

**Решение: переписывание через CSSOM.** Парсер не нужен — он уже есть в браузере
(`new CSSStyleSheet().replaceSync()`). Функция `scopeSelector` из postcss-плагина v1
переиспользуется дословно и решает случай `html`/`body`/`:root` правильно: заменяет их
на контейнер, а не выбрасывает. Санитайзинг обязателен: `@property` вырезать, именованные
at-rules переименовать в пространство имён плагина.

**Shadow DOM отвергнут** с конкретными причинами: классы оболочки внутрь не достают, то есть
ломается основной путь «плагин без своего CSS выглядит родным»; `@font-face` не регистрируется;
порталы становятся хуже — узел уходит наружу теневого дерева и остаётся без стилей.

**Правило приёмки усилено.** «Плагин со своим ресетом не меняет вид оболочки» не поймало бы
ни `@keyframes`, ни `@property`. Добавлен кейс с коллизией имён.

**Найдено сверх задания — ответ на открытую задачу ReFormer-s0j.4** (утечка Radix-порталов
за пределы скоупа токенов): предложенное там лечение «дубль `data-rb-kit` на самом узле»
**не работает**, потому что голый селектор внутри области требует быть _потомком_ корня,
а не самим корнем. Работает только оборачивающий предок — то есть `portalContainer`,
лежащий внутри элемента со скоуп-классом. Верно и для `@scope`, и для переписывания v1.

Проверено независимо: `scopeSelector` в v1 действительно переписывает `html`/`body`/`:root`
в контейнер (не выбрасывает), артефакты эксперимента на месте, репозиторий не тронут.

### t1-1 · Resource · сдано (50 тестов)

Проверено независимо: tsc, vitest, eslint — чисто.

**🔀 Решения, принятые там, где контракт молчал:**

- `relativePath` работает в **файловой** семантике (`from` — файл, берётся его каталог), а не
  в каталог-к-каталогу как `path.relative` в Node. Пример из контракта сходится только так.
- Дефолт для неизвестного расширения — `text/plain`, а не `application/octet-stream`: файлы
  без узнаваемого расширения это `LICENSE`, `.editorconfig`, `.prettierrc`, а бинарные форматы
  расширение всегда носят. Обратный выбор сделал бы `readText('LICENSE')` отказом.
- Подсказка источника имеет приоритет, **но синтаксически невалидная отбрасывается** —
  иначе сервер, отдающий `application/octet-stream` на всё подряд, ломает определение типа.
- `\` в путь **не конвертируется**: обратный слэш легален в имени posix-файла, и молчаливая
  конвертация превратила бы имя в путь.

**⚠️ Требование, вытекающее из «идентификатор непрозрачен», но в контракте не записанное:**
любой производитель идентификатора **обязан** идти через `makeResourceId`, иначе `fs:./a`
и `fs:a` разъедутся как два ключа кэша на один ресурс.

**Исправлено расхождение в документации:** `project-structure.md` клал нормализацию путей
в `host/source/path.ts`, а задача Э1 — в `primitives/resource.ts`. Верно второе: нормализация
нужна раньше источника и не только ему. Структура поправлена.

**Открыто, вынесено в отдельную задачу:** тип для каталога (`mediaType` обязателен, а у каталога
его нет) и именованная операция резолва спецификатора — сейчас каждый потребитель напишет свою
композицию `joinPath(dirname(base), spec)`.

### t1-2, t1-3 · Service и ExtensionPoint · сдано (43 теста)

Проверено независимо: tsc, vitest, eslint — чисто.

**🔀 Повторная регистрация сервиса — бросает.** Обоснование сильнее, чем «так аккуратнее»:
молчаливая замена сделала бы действующую реализацию зависимой от порядка активации, а это
прямо противоречит правилу приёмки Э4 («активация в обратном порядке даёт то же поведение»).
Осмысленная замена при этом выразима — снять через `dispose()` и зарегистрировать заново,
ровно то, что делает перезагрузка плагина.

**🔀 Ключ реестра — строка `token.id`, а не идентичность объекта токена.** Причина не
стилистическая: плагины из каталога грузятся собственным линкером, и модуль с объявлением
токена может оказаться в памяти дважды. При ключе по объекту это дало бы «сервис есть,
но не находится» — худший вид отказа.

**✅ Правило «ни одна точка расширения не заполняется самим Host» стало структурным.**
`pluginId` не параметр `contribute`, а свойство вида реестра: `root.forPlugin(id)` отдаёт объект,
у которого происхождение подделать нечем. **У корневого реестра метода `contribute` нет вовсе** —
проверено чтением кода. Это ровно то, чего я хотел добиться правилом в контрактах, но получилось
лучше: не соглашение, а отсутствие пути.

**⚠️ Недосказано в контракте, требует согласования при Э4:** корневой тип реестра
(`RootExtensionRegistry`) в контрактах не описан, а Э4 обязан класть в `PluginContext`
именно вид `forPlugin(plugin.id)`, а не корень.

### s3 · Формат сообщений i18n · ⚠️ уточнено (оценка вдвое мимо)

**Оценка «примерно сотня строк» не сошлась: 196 строк чистого кода.** Причём вся недооценка —
в **разборе синтаксиса**, о котором в оценке не было ни слова. Плюрализация действительно почти
бесплатна: `Intl.PluralRules` — одна строка `select(n)`.

**Обоснование по весу пришлось поправить.** Измерено сборкой, а не взято из ощущения:
библиотека 32.4 КБ minified / **9.5 КБ gzip**, своя реализация 3.5 / 1.3 КБ. «Десятки килобайт»
верно для minified, но по проводу едет gzip — там разница ~8 КБ, и для инструмента разработчика
она решения не оправдывает. **Настоящий довод — контроль над поведением**, а не вес: отказ
на разборе словаря происходит в CI, а не у пользователя.

**✅ Страховка из контракта перестала быть декларацией.** «Если подмножества перестанет хватать,
библиотека подставляется под тот же вызов» проверено **дифференциальным тестом** против
`intl-messageformat` на общем корпусе: вывод совпадает посимвольно, 54 теста.

**🔀 Экранирование — апострофом, как в ICU, а не удвоением скобок.** Удвоение дешевле строк
на двадцать и понятнее автору словаря, но ломает ровно эту страховку: подстановка библиотеки
потребовала бы переписать все словари.

**🔀 Отсутствие ветки `other` — ошибка разбора, а не промах в рантайме.** Одна строка, а переносит
класс ошибок из «пользователь увидел пустую строку» в «CI не пропустил словарь». Русский тут
особенно уязвим: автор, думающий по-английски, естественно пишет `one`/`other` и получает `many`
без ветки на всех числах от 5.

**🔀 `select` берём сразу**, не откладываем: механизм веток уже написан ради `plural`, собственная
цена — около десяти строк. Отложить значит потом трогать парсер, словари и тесты ради тех же строк.

**Практическое следствие, которое ударит за пределами i18n:** `Intl.NumberFormat('ru')` разделяет
группы **неразрывным пробелом U+00A0**. Два теста упали на строках, выглядящих идентично.
Ожидаемые строки с числами нельзя писать литералом — их надо считать через `Intl`. Это же
касается CI-сверки словарей и любых golden-тестов интерфейса.

**Недосказано в контракте:** `t()` сверх форматирования обязан делать поиск ключа, маркер
`⟦files.title⟧` при промахе и откат на резервную локаль — это ещё ~40 строк поверх форматтера,
в 196 они не входят.

Прототип с тестами: `<scratchpad>/i18n-spike/` — идёт на вход задаче t4-3.

### t1-4, t1-5 · Command, WhenContext, Event · сдано (64 теста)

Проверено независимо: vitest и eslint чисты.

**🔀 Решения агента, которые стоит знать:**

- **Реестр принимает поставщика контекста**, а не требует контекст на каждом вызове. Иначе палитра,
  диспетчер и ассистент собирали бы «текущее состояние» каждый по-своему — ровно то расползание
  охранных условий, ради устранения которого `WhenContext` и заводится.
- **`execute` всегда возвращает промис, но `run` вызывается синхронно** до первого `await` внутри
  команды — иначе команда не укладывается в контур правки и в одну запись отмены. На это есть тест.
- **`agentCommands()` не фильтрует по применимости.** Набор инструментов уходит в каждый запрос
  к модели; если он меняется от фокуса пользователя, префикс запроса перестаёт кэшироваться.
  Применимость проверяется в момент вызова, тем же `execute`, что и у человека.
- **Упавший `enabled` = запрет.** Охранное условие, которое не смогло ответить, тем более
  не должно пропускать действие.

**⚠️ Две дыры в контракте, найденные реализацией, — закрыты:**

1. **`allowInEditable` упоминался в Э5, но не существовал в `CommandContribution`.** Добавлен
   в контракт полем команды, а не списком у диспетчера: список разъехался бы с набором команд
   на первой же новой команде, и разъехался бы молча.
2. **`WhenContext` не выражал третье охранное условие, которое сам же называет.** Из «фокус
   в поле ввода», «курсор на канвасе», «не на кнопке» первые два выражались, третье — нет:
   между `panel` и `editable` ничего не было. Добавлен вариант `control` — кнопка или чекбокс,
   элемент сам обрабатывает пробел и Enter. Это ровно тот случай «контракт ломается на первом
   же редакторе», о котором документ предупреждал применительно к режиму превью.

**❌ Отменена идея CI-проверки грепом.** Правило «примитив не знает слова „форма“» проверять
грепом нельзя: слово законно встречается в прозе («формат», «формируется», «схема формы»),
и наивная проверка дала бы ложные срабатывания на трёх файлах из пяти — проверено.
Настоящая граница — запрет импорта `lib/` и `plugins/`, и она уже проверяется линтером.
Формулировка в контракте исправлена.

**Урок оркестрации.** `tsc -p` проектный, поэтому незавершённая работа одного агента валит
проверку у другого: сдача Command/Event не прошла общий tsc из-за файла соседа, который ещё
писался. Проверять сданное надо изолированно (vitest + eslint по конкретным файлам),
а общий tsc гонять после схождения волны.

### t8-1 · host/modules · сдано (50 тестов) + ❌ дыра в контракте

Проверено независимо: vitest и eslint чисты, защищённый список в коде на месте.

**❌ Защищённый список был неполон, и это была настоящая дыра.** В контракте значились
`react`, `react/jsx-runtime`, `@reformer/*`, `@builder/sdk`. Не хватало **`@preact/signals-core`** —
а это ровно тот пакет, где живёт `instanceof Signal`, то есть его подмена ломает идентичность
**прямее, чем подмена самого ядра**. Плюс `react/jsx-dev-runtime`. Контракт исправлен.

**❌ Резолв подпутей отсутствовал в контракте.** В v1 он префиксный: `@reformer/ui-kit/*` ведёт
в неймспейс активного кита, `@reformer/core/validators` — в общий барель. Точный резолв,
описанный в контракте v2, потребовал бы регистрировать каждый подпуть руками и молча ломался бы
на первом новом. Контракт исправлен: сначала точное совпадение, затем самый длинный префикс.

**⚠️ Транспилятор: контракт объявляет `transpile` синхронным, в v1 он асинхронный** из-за
ленивой загрузки `typescript`. Это не косметика: асинхронный шаг нельзя вставить внутрь
CJS-`require`. Следствие для будущего TS-движка — **прогрев обязан быть отдельной фазой

### t6-6 · Журнал изменений · сдано (55 тестов, 1436 в проекте)

Проверено независимо: 257 тестов в `workspace`, tsc, eslint — чисто.

схлопывания.** Иначе правка, дописанная в предыдущую запись, делает уже лежащий снимок неверным,

отказ уборки проглатывается — вызывающий ждёт ошибку про квоту, а не про журнал.

### Тест на саму композицию: она была не покрыта ничем

Каждый плагин покрыт своими тестами, и все они зелёные — но проверяют они плагин **на своих
двойниках**. Ошибка сборки живёт между ними, и её не видит никто. Оба случая в проекте уже
происходили: порт, проглотивший аргумент (компилируется — реализация с меньшим числом
параметров присваивается функции с бо́льшим), и вклад, ушедший в точку-двойник (теряется молча —
точки сравниваются по идентичности объекта).

**❌ Первая версия теста прошла сразу, и это оказалось не заслугой, а дефектом.** Я проверял
пороги: «панелей не меньше четырёх». Мутация — подмена точки у плагина файлов на двойник —
**прошла незамеченной**: панелей от остальных плагинов хватало, чтобы порог выполнился, и вклад
терялся тихо. Порог тут бесполезен по устройству.

Переписал на **поимённый состав владельцев** каждой точки. Три мутации проверены:

- подмена точки на двойник → падает на конкретном пропавшем владельце;
- проглоченный третий аргумент в порту → падает тест шва;
- двойная регистрация плагина → падает пять тестов из восьми.

Отдельным тестом закреплено, что проверки **не пусты**: тест, проверяющий отсутствие нарушений
в пустом списке, проходит всегда и не значит ничего.

**Порты подставлены прокси, а не литералами с методами.** У семи портов вместе больше шестидесяти
методов; список здесь означал бы вторую копию контрактов вдобавок к тем, что уже есть, и правку
этого файла на каждое изменение любого порта.

### Пакет мелких долгов и перетаскивание · сдано. Две находки крупнее своих задач

**❌ Находка 1: ВСЕ три команды быстрых исправлений — фантомы.** `schema.set-component`,

написана целиком и **не работает ни одним концом**. Теперь валидатор их молча не публикует,
а в консоли появляется адресное предупреждение — **по одному разу на идентификатор**, потому что
проход идёт на каждой правке текста и без дедупликации предупреждение утонуло бы в себе.

Проверять решено **в момент показа, а не при регистрации**, и довод прямой: порядок активации
плагинов объявлен незначимым и закреплён тестом. Валидатор вправе подняться раньше редактора,
который владеет командой, — проверка на активации объявила бы законный порядок ошибкой.
Применимость команды при этом намеренно **не** спрашивается: «команды нет» и «сейчас недоступна» —

**❌ Находка 2, крупнее первой: `Journal` не создавался в композиции ВООБЩЕ.** `createJournal`

**правки человека и ассистента в журнале различимы**.

**✅ Отмена хода сделана на памяти моста, а не на журнале, и ограничение названо в коде.**
`txId` — тот же самый, что уходит в пометку, поэтому подключение журнала заменяет тело отмены
одним вызовом. Перекрытие правкой человека — **отказ с объяснением**, а не попытка: сравнивается
не «что было до», а что ход **оставил** в буфере. Правдоподобно испорченный текст хуже отказа,
а «потерял мою правку» хуже обоих.

оказалось неверно.** Резервная локаль — английская: ключа нет в ней — падать некуда, промах
доходит маркером; ключа нет в русской — в сборке английская фраза посреди основной локали.
Проверка живёт в композиции, а не рядом со словарём Host, потому что словари везут все девять
владельцев, а платформа не имеет права импортировать плагины. **И отдельно проверяется, что
список проверяемых не отстаёт от репозитория** — иначе проверка полноты сама была бы неполна.

**✅ Перетаскивание: точная обратимость сохранена полностью, ослаблять не пришлось нигде.**
Авто-сворачивание получило **свою** операцию, а не довесок к переносу, и она требует **ровно

### А вот зеркальная проверка нашла настоящую несогласованность

Экспорт без потребителя — тот же дефект, что поле без производителя, только с другой стороны.
Четыре имени в `@/sdk` не использует **ни один** плагин: `DocumentModelPoint`,
`SettingsServiceToken`, `ThemeServiceToken`, `NotificationsServiceToken`.

Первое объяснимо и намеренно: точку модели редактор схемы получает **параметром** от композиции,
чтобы в тестах подставлялся другой реестр.

Остальные три вскрывают вот что: **встроенные плагины получают платформенные вещи ПАРАМЕТРОМ,
а плагин из каталога может получить их только СЕРВИСОМ.** Плагин китов принимает настройки
опцией (`KitsPluginOptions.settings`), потому что композиция знает его в лицо. Внешнему плагину
композиция ничего передать не может — она о нём не знает; ему остаются только `ctx.services`.

Значит **путь, которым обязан пользоваться внешний плагин, сегодня не используется никем
и не проверен ни разу** — ни настройки, ни тема, ни уведомления. Диагностику и выделение через
сервисы берут (три плагина), а эти три токена — никто.

### Быстрые исправления заработали обоими концами, выделение — обеими половинами

**✅ Три команды-фантома зарегистрированы, и владельцем оказался ровно тот, кого назвал контракт.**
`schema.set-component`, `schema.rename-prop`, `rules.remove` внесены редактором схемы. Существующих
операций хватило НЕ полностью, и обе недостающие завелись по одной и той же причине — точная
обратимость:

- **`set-component`** нельзя было выразить через `set-prop`: тот правит `componentProps`, то есть
  содержимое компонента, а не сам компонент. Операция отказывается трогать узел, у которого не
  `$component(...)`, и это не перестраховка: обратная называет компонент ИМЕНЕМ, а `$html(div)`
  именем каталога не выражается — вернуть его было бы нечем;
- **`rename-prop`** не собирается составом из двух `set-prop`. Удаление с последующей вставкой
  уносит ключ в конец объекта, и обратная операция вернула бы его туда же: отмена МЕНЯЛА БЫ текст
  файла вместо того, чтобы его восстанавливать. Печать детерминированна, по её результату
  сравнивают буфер с моделью, — поэтому порядок ключей здесь не косметика. Своя операция
  переименовывает на месте, и обратная точна.

та же кнопка-обманка этажом ниже: команда есть, а править нечего. Сегодня сайдкар держит мост
ассистента и наружу не отдаёт — валидатор правил тоже не получает, поэтому осиротевших правил

аргументов не видит, а вся применимость именно в них: какой документ, какой узел, какое правило.
Сузить до «активна схема формы» нельзя — из панели проблем чинят находку НЕ активной вкладки, и
такой предикат запретил бы законный вызов (`execute` отвечает на запрет отказом `disabled`).
Оставлено самое широкое верное условие — «открыт хоть один документ», остальное проверяет `run`,

**✅ Показывающие спрашивают реестр ВТОРОЙ раз — и это видно тестом, а не только в комментарии.**

по содержимому значении, стор превью не уведомляет о совпадающем выборе — оставлены как есть, и
именно они гасят эхо на первом круге. Доказательство браузерное: щелчки туда-обратно десять раз,
и счётчик уведомлений канала растёт РОВНО на единицу за щелчок. Настоящую службу в тест плагина
не взять (`src/plugins/**` не видит `@/host`), поэтому двойник канала воспроизводит все три её
свойства, включая гашение повтора: двойник без него показал бы цикл там, где служба его
не допускает.

**⚠️ Сквозной проверки «настоящая служба + оба плагина» здесь нет и быть не может.** Оба плагина
и `@/host` одновременно видит только композиция, значит и тест такого рода принадлежит `src/app`.

### Быстрые исправления и зеркало выделения · сдано (+44 обычных, +12 браузерных)

**❌ Дефект, который прятался ЗА ТЕСТОМ — и это худший вид.** Заголовки **всех девяти** команд
редактора схемы не переводились: `titleKey: 'editor-schema.command.delete'` ищется внутри словаря
плагина **целиком**, а пространство имён — отдельное измерение, не приставка к ключу. В словаре
лежат голые `command.delete`, `palette.title`. Промах на каждой команде.

Тест палитры этого не ловил, **потому что в нём был записан правильный вариант, которого в коде
нет**. Он проверял выдуманный случай и потому оставался зелёным. Это опаснее отсутствия теста:
отсутствие видно, а зелёный тест читается как доказательство.

Починил ключи и добавил строки в оба словаря. Но главное — **завёл проверку, которая поймала бы
это**: заголовок каждой команды обязан разрешаться в словаре своего владельца. Словари читаются
динамическим импортом по идентификатору, а не статическим списком — список отстал бы от
репозитория молча. Проверено мутацией: возврат одного ключа к прежнему виду роняет тест.

**✅ Две новые операции завелись ради обратимости, а не удобства, и доводы точные:**

- замена компонента через правку свойств **невыразима** — те правят содержимое компонента,
  а не сам компонент; операция отказывается трогать узел, у которого не `$component(...)`,
  потому что обратная называет компонент **именем**, а `$html(div)` именем каталога не выражается;
- переименование свойства составом из двух правок **не собирается**: удаление с последующей
  вставкой уносит ключ **в конец объекта**, и обратная вернула бы его туда же — то есть отмена
  меняла бы текст файла вместо восстановления. Печать детерминированна, по её результату
  сравнивают буфер с моделью.

**✅ Команда «убрать правило» регистрируется УСЛОВНО** — только если композиция дала сайдкар
правил. Команда, которой нечем работать, — та же кнопка-обманка этажом ниже. Состояние сегодня
согласованное: правил нет → находки нет → команды нет.

**✅ Команды правят документ ПО АДРЕСУ ИЗ АРГУМЕНТОВ, а не активный сеанс** — из панели проблем
чинят находку неактивной вкладки, где сеанса канваса может не быть вовсе.

**✅ Отсутствие зацикливания доказано счётчиком в настоящем Chromium:** щелчки туда-обратно
десять раз, уведомлений канала ровно по одному на щелчок. Рассылка синхронная, поэтому круг
проявился бы переполнением стека на первом же щелчке.

**⚠️ Осознанное ограничение, названное прямо:** три команды исправлений видны в палитре и без
аргументов там ничего не делают. `enabled` аргументов не видит, а сузить до «активна схема формы»
нельзя — это запретило бы законный вызов из панели проблем. Флага «скрыть из палитры»
в контракте команды нет.

### Два последних шва проверены насквозь

**✅ Путь внешнего плагина перестал быть мёртвым.** Плагин китов теперь берёт настройки
из **реестра сервисов**, а не параметром от композиции. Параметр остался — но только для тестов,
и в композицию не передаётся. Это принципиально: пока встроенный плагин получал платформенные
вещи параметром, единственный доступный внешнему плагину путь оставался непроверенным.

Служба китов из-за этого создаётся **при активации, а не при объявлении плагина**: настройки
приходят из реестра, а реестр есть только у контекста. Деградация обязательна и проверена —
без службы настроек кит переключается, просто выбор не переживёт перезагрузку. Мутация ловится:
уберёшь чтение из реестра — падает тест.

**✅ Канал выделения проверен на НАСТОЯЩЕЙ службе.** Прежде отражение проверялось с обеих сторон,
но во всех тестах канал был **двойником**: плагин не видит платформу и не видит соседний плагин,
это держит линтер. Значит двойник оставался утверждением о службе, а не её проверкой — и такая
проверка могла жить только в композиции.

Четыре теста: оба плагина подключились к одной службе; эхо затухает; выделения разных ресурсов
независимы; снятие плагинов не оставляет живых подписок. Мутация — снятие гашения повтора —
роняет **три** теста, включая сквозной.

**Общий вывод обеих задач.** Двойник в тестах плагина — вынужденная цена границы слоёв, и он
честен ровно настолько, насколько верно воспроизводит оригинал. Проверить это может только
композиция: она единственная видит обе стороны. Значит **на каждый двойник платформенной вещи
должен приходиться сквозной тест в `app/`** — иначе двойник и оригинал разойдутся молча, как
уже разошлись копия точки расширения и копия синтеза мока.

### Панели доков: рейлы вместо стопки, как в v1

**Что было в v1 и что просили.** «Вкладки» в v1 — это **рейлы по краям**, а не горизонтальные
вкладки: узкая полоса с кнопкой на панель, открыта одна. Комментарий в v1 говорит прямо:
«правый рейл: вкладки правой зоны, как слева».

В v2 левый рейл уже был, а правый и нижний доки **складывали панели стопкой**. С тремя панелями
справа (свойства, ассистент, экспорт) колонка делилась на три, и каждая переставала помещаться.

**Сделано:** рейл обобщён на обе стороны, у каждого дока **свой** контроллер. Общий признак
«свёрнут» означал бы, что, закрыв инспектор, человек теряет дерево.

**❌ Первая версия браузерного теста была декоративной, и дважды.** Тело панели рендерило
**свой же заголовок** — «видно ли панель» стало неотличимо от «видно ли кнопку рейла», и тест
проходил бы, даже не отрисуйся тело вовсе. А проверка «правого рейла нет» искала его по ярлыку
из словаря Host, который в тесте **не загружен**: там маркер промаха, и проверка проходила всегда.
Обе переписаны: тело помечено отдельным текстом, рейлы ищутся по роли.

**❌ Мутация показала дыру, которой я не ждал.** «Убрать сторону у правого рейла» тест **прошёл**:
`side` управляет только рамкой, а положение задаёт место в разметке. Проверка положения сторону
не проверяет вовсе. Добавил проверку **вычисленного стиля** — рейл рисует рамку со стороны центра,
потому что отделяет себя от него, а не от края окна. Теперь ловится.

**Найдено попутно двойником:** мой снимок строки состояния отдавал новый объект на каждый вызов,
и React сказал ровно то, что говорил в этом проекте уже дважды: «результат должен кэшироваться».
Бесконечная перерисовка. Третий случай одной и той же ошибки в двойниках — стоит считать
её типовой.

**Заодно выровнены ярлыки рейлов:** было «Переключение левых панелей» против «Панели справа».
Два рейла делают одно и то же и описываться должны одинаково.

### Ассистент прижат к низу правого рейла

**Сделано полем контракта, а не порядком, и это не придирка.** Первое, что приходит в голову, —
дать ассистенту большой `order`. Не работает: **«последняя в списке» и «у нижнего края» совпадают
только пока рейл заполнен целиком.** С двумя панелями справа большой порядок поставит вкладку
второй сверху, а не у края.

Поэтому у панели появилось `railPlacement: 'top' | 'bottom'` — это не порядок, а принадлежность
к краю. Порядок расставляет панели ВНУТРИ группы, место говорит, к какому краю они относятся.

**Почему именно ассистент.** Инспектор и экспорт перебирают глазами по ходу работы, к ассистенту
приходят намеренно — и приходят тем чаще, чем надёжнее он на одном и том же месте. Постоянный
адрес у края даёт руке находить его не глядя, сколько бы панелей ни добавили сверху.

**Вкладка вынесена в отдельный компонент**, потому что групп на рейле стало две: рисуй их разными
выражениями — разъедутся видом на первой же правке одной из них.

Два браузерных теста, обе мутации ловятся: игнорирование места и снятие прижатия. Плюс тест
на умолчание — без объявленного места вкладка остаётся в основной группе, иначе каждая новая
панель прижималась бы к краю и «постоянное место» перестало бы быть постоянным.

### Нижний док: полоса вкладок. И дефект, который я сам же и внёс

**❌ У нижнего дока не было переключателя ВООБЩЕ.** Когда я заменил стопку панелей одной активной,
левый и правый доки получили рейлы, а нижний — нет: рейлы стоят по бокам и управляют только
своими доками. Активная панель нижнего вычислялась, но сменить её было нечем, и вторая панель
(превью рядом с проблемами) стала недостижима. Заметил это только сейчас, разбирая просьбу.

**✅ Полоса вкладок, а не рейл, и причина геометрическая:** вертикальная полоса у горизонтального
дока отнимала бы ширину у всего, что под ней, и заголовки в ней не помещались бы. Отсюда же
вкладки со СЛОВАМИ, а не значками: места по горизонтали хватает, а слово читается без наведения.

**✅ Полоса остаётся видимой, когда док свёрнут, и это несущее.** Исчезни она вместе с телом —
док закрывался бы навсегда: человек теряет панель и не понимает, куда она делась. Свёрнутый док
ужимается до высоты полосы, полоса и есть его след. Ровно этим он отличается от боковых доков,
чьи рейлы живут СНАРУЖИ и потому видны сами собой.

Три браузерных теста, обе мутации ловятся: исчезновение полосы вместе с телом и вкладки столбцом
вместо полосы.

### Нижняя панель по образцу привычных инструментов: закрытие, свёрнутый вид, сочетание клавиш

**Три состояния вместо булева «открыт», и третье нужно по-настоящему.** У бокового дока
свёрнутый и скрытый — одно и то же: его рейл живёт СНАРУЖИ и виден всегда. У нижнего вкладки
внутри, поэтому состояний три: полный вид, полоса вкладок, ничего. Модель это и выражает,
а «во что сворачивается» решает сам док — параметром, а не общим умолчанием.

**Сохранённая раскладка переживает правку.** Поле хранилось булевым и уже лежит у людей
в настройках. Читатель принимает и строку, и старое булево: отвергни он его — раскладка
сбрасывалась бы у всех разом и без объяснения.

**✅ Значок — КОМПОНЕНТ вклада, а не число.** Панель сама знает, на что подписаться и как часто
это меняется; верни она число, оболочке пришлось бы перевычислять его на каждый свой кадр либо
завести канал уведомлений ради одной цифры. **Ради значка свёрнутый вид и существует**: полоса
остаётся, чтобы ошибку было видно, не разворачивая. Убери значок — полоса из одних имён
не сообщает ничего.

Внутри значка счётчик сведён **в одно число, а не объект**: `useSyncExternalStore` сравнивает
по ссылке, и объект, собранный на каждый вызов, дал бы бесконечную перерисовку. **Эта ошибка
в проекте встречалась уже трижды**, поэтому здесь она предупреждена сразу.

**✅ Сочетание водит между полным видом и полосой, а не по трём состояниям.** Три в одну клавишу
не уложить, и я не пытался: это состояния РАБОТЫ — свернул освободить место, развернул прочитать.
Закрытие — действие другой силы, у него своя кнопка. **Но из закрытого сочетание разворачивает**,
иначе крестик был бы ловушкой, а панель — потерянной. Есть тест ровно на это.

Тон значка берётся по ХУДШЕЙ строгости: одна ошибка среди двадцати замечаний важнее двадцати
замечаний, и смешивать их в «в основном замечания» нельзя.

**⚠️ Наблюдение о самом прогоне:** один раз полный браузерный прогон завис после выполнения,
и обёртка принудительно вернула успех («No stdout for 60000 ms — forcing exit 0»). Мои тесты
в отчёт тогда не попали вовсе. Повторный прогон прошёл нормально, но **зелёный итог при зависании
означает, что часть файлов могла не отчитаться** — это стоит держать в голове и проверять число
тестов, а не только цвет.

Четыре браузерных теста, три мутации ловятся: крестик, сворачивающий вместо закрытия; неотрисованный
значок; сочетание, не возвращающее закрытую панель.

### Свёрнутый вид: полоса ужимается, панель отдаёт место

**❌ Скрыть содержимое было мало, и это выяснилось только просьбой пользователя.** Размер панели
раскладки читается **один раз при монтировании**: смена режима после этого убирала тело, но места
не отдавала — под полосой оставалась пустая площадь прежней высоты. Панель «свёрнута», а занимает
столько же. Схлопывание бывает только императивным.

**❌ И первая попытка чинить это уронила оболочку целиком.** Библиотека раскладки бросает
«Panel constraints not found», когда панель **снимается из группы**, а ручка на неё остаётся.
Симптом был обманчивым: пропадала не только нижняя панель, а весь интерфейс, и выглядело это
как ошибка моего эффекта. Настоящая причина нашлась только чтением необработанной ошибки прогона.

**✅ Лечение — не размонтировать панель вовсе.** Она живёт, пока есть хоть одна нижняя панель,
а режим меняет её РАЗМЕР: скрыт — схлопнута в ноль, свёрнут — прямой размер в высоту полосы,
полный — развёрнута. Схлопнутый размер объявлен нулём, а не высотой полосы: «скрыт» и «свёрнут» —
разные состояния, а двух схлопнутых размеров у панели не бывает.

**✅ Высоты объявлены одним числом на двоих** — их берёт и полоса, и раскладка. Разойдись они,
свёрнутый док либо обрезал бы полосу, либо оставил под ней пустоту.

Полоса ужимается с 34 до 22 пикселей вместе с вкладками, значками и кнопками; кнопка сворачивания
в свёрнутом виде не рисуется — сворачивать больше нечего.

Две мутации ловятся: размер, который не меняется, и полоса прежней высоты.

**⚠️ И отдельно, важнее самой правки: в этих файлах параллельно работают ДРУГИЕ СЕССИИ.** За время
работы `Shell.tsx` вырос на ~190 строк чужим кодом (строка меню, диалоги помощи), а `ResourceTree.tsx`
дважды показывал ошибки компиляции, исчезавшие сами через полминуты. **Я чуть не восстановил
`Shell.tsx` из своего снимка — это стёрло бы чужую работу**, и остановило меня только то, что
снимок оказался меньше файла на диске. Вывод на будущее: перед восстановлением из снимка
сверять размер, а «чужие» ошибки не чинить и не откатывать.

### Схематичный вид канваса (UX первой версии билдера) · 🔀 развилка

Просьба пользователя: «нравится конструктор схемы и его ux с первой версии — сделай так же».
В v1 редактирование шло по wireframe-канвасу: узлы коробками в РЕАЛЬНОЙ раскладке, зоны броска
axis-aware (`before`/`into`/`after` вдоль оси родителя, `beside-*`/`stack-*` поперёк — они
создают обёртку `$html(div)`). В v2 канвас был деревом строк с тремя положениями броска.

**Решение: второй ВИД одного редактора, а не второй редактор и не замена дерева.** Дерево
остаётся: на схеме из сорока полей оно читается, а полотно требует прокрутки в двух измерениях.
Переключатель — в панели инструментов канваса.

**🔀 Почему не третий режим документа.** `SchemaViewStore` (`design` | `code`) отвечает
на вопрос «чем нарисован документ», и у него пара взаимоисключающих кнопок в полосе вкладок.
Добавь туда `layout` — и «переключить конструктор и исходник» станет циклом из трёх состояний,
где кнопка не может сказать, что будет после нажатия. Поэтому измерения два, и вид конструктора
живёт в `canvas-prefs` со своим липким предпочтением (область `user`, как у режима документа).

**✅ Обёртка собирается из СУЩЕСТВУЮЩИХ операций.** У домена есть `wrapInRow`/`wrapPairInRow`,
и v1 звал именно их. Здесь так нельзя: словарь операций обязан быть обратимым по шагам, а
доменная мутация — одна непрозрачная правка, к которой обратной нет. Обёрточный бросок стал
составом: `batch([insert|move рядом с целью, (unwrap), group(пара, класс)])`. Отмена одним
Ctrl+Z получилась бесплатно, потому что каждая часть уже умеет отменяться.

Из этого же следует, что новому узлу адрес выдаётся ЗАРАНЕЕ (`insert` с `keepIds`): `group`
называет узлы адресами, а вставка с палитры их ещё не имеет.

**✅ Правило «две колонки одной обёртки» перенесено из v1.** Бросок колонки на соседнюю поперёк
переворачивает САМ контейнер (`flip` + при нужде `move`), а не вкладывает в него второй. Без
этого ряд из двух полей превращался бы в ряд, внутри которого столбец из тех же двух полей.

**❌ И по дороге вскрылся дефект, существовавший и у дерева: перестановка узла ВЛЕВО внутри
слота не отменялась.** `applyMove` записывал в обратную операцию прежний индекс, но позиция
в `move` называется в координатах ДО выреза, и та же компенсация применялась второй раз —
отмена возвращала узел туда, где он уже стоит. Обратимость `move` проверялась только между
разными слотами, поэтому дефект и дожил до сюда. Исправлено, покрыто тестом; в трекере —
`ReFormer-gfsq.7`.

**🔀 Скрытие `$html(div)`-обёрток — предпочтение, а не состояние документа.** Обёртки не часть
замысла формы, а след того, как её собирали: одному мешают видеть раскладку, другому нужны,
чтобы до них добраться. В модели отрисовки это `SchematicGroup` — прозрачный узел, у которого
есть ось и дети, но нет ни адреса, ни подписи: рамка исчезает, РАСКЛАДКА остаётся. Иначе
колонки схлопнулись бы в столбец, и вид перестал бы отвечать на свой единственный вопрос.

**✅ Переворот направления — команда, а не правка из компонента.** Кнопка на коробке зовёт
`editor-schema.flip` с адресом узла; выделение при этом не двигается. Аргумент важнее выделения
именно поэтому: щелчок по стрелке не должен уводить курсор с узла, над которым работают.

### Клавиатура: условие как данные, слои, области, аккорды, раскладка человека · сдано (+179 тестов node, +4 браузерных)

**❌ Опровергнуто допущение постановки «сочетаний одиннадцать».** Их двадцать пять:
`plugins/files/operations.ts` добавляет `f2`, `delete`, `mod+c/x/v`, а
`plugins/editor-schema/commands.ts` — восемь стрелок через `MOVE_KEYBINDINGS` и
`DUPLICATE_KEYBINDINGS`, которых не видно поиском по литералу. Вместе с ними вскрылся
настоящий дефект, а не гипотетический: **`delete` объявляли двое** — дерево файлов и редактор
схемы, — и разводил их только порядок регистрации, который по контракту рантайма
(`plugin/registry.test.ts`) не значит ничего. У `mod+d`, `mod+g` и всех стрелок предикат
вообще не смотрел на фокус, поэтому они срабатывали из дерева файлов и из любой панели.

**✅ Условие стало данными (`CommandContribution.when`), и это несущее решение всей работы.**
Предикат `enabled` отвечает на один вопрос — «доступна ли команда»; всё остальное, что нужно
клавиатуре, требует условие ПРОЧИТАТЬ: сравнить два (кто выигрывает), доказать непересекаемость
(это конфликт или разные места), записать в файл (манифест, раскладка), показать человеку.
Функцию прочитать нельзя. Отсюда `primitives/when-expr`: грамматика VS Code, AST, специфичность.

**🔀 Специфичность дизъюнкции — МИНИМУМ ветвей, а не максимум.** Выбрано по проверяемому
признаку: с максимумом приписка «или всегда» вставала бы ВЫШЕ исходного условия, совпадая при
этом со строго большим числом состояний, — то есть становилась бы способом перебить кого угодно.
Правило, срабатывающее чаще, не имеет права выигрывать у срабатывающего реже. Это несущий тест
модели разрешения конфликтов.

**⚠️ Уточнено: `when` проверяет ДИСПЕТЧЕР, а не реестр команд.** `isEnabled` и `execute`
условие не смотрят. Смотри его реестр — пункт контекстного меню «Переименовать» пропадал бы
ровно тогда, когда меню открыто правым щелчком без фокуса на строке, то есть когда он нужен.
Поэтому у пяти команд файлов проверка фокуса ОСТАЛАСЬ и в `enabled`: это одно ограничение
в двух независимых каналах, а не дублирование по недосмотру.

**❌ План предлагал условие `focus == canvas && hasSelection` для команд схемы — так делать
нельзя: `hasSelection` не пишет НИКТО.** Поле есть в контракте `WhenContext` с самого начала
и всегда равно `false`; поиск по `hasSelection:` даёт только объявление и нейтральное значение.
Такое условие сделало бы все клавиши схемы мёртвыми. Взято `focus == canvas`, а «есть что
удалять» осталось в `enabled` — и это ровно тот водораздел, который и требовался: `when`
отвечает «где», `enabled` — «есть ли чему».

**✅ Порядок разрешения: слой → специфичность → порядок регистрации.** Слой человека бьёт
всё, включая более специфичное правило плагина: переназначение, проигравшее чужому условию,
было бы переназначением, которое не сработало. Порядок регистрации сдвинут на третье место —
он и есть та случайность, от которой уходили. Прежний тест «первая подошедшая команда
выигрывает» переписан осознанно: правило изменилось.

**🔀 Снятие (`-command` в раскладке) действует на слои СТРОГО НИЖЕ своего.** Сначала было
«ниже либо равные», и на этом упал тест: тогда снятие убирало бы и другие записи самого
человека, то есть порядок строк в его файле становился бы значимым. Порядок строк в настройках —
не то, о чём человек должен думать, назначая клавишу.

**✅ Область (`scope`) даёт приоритет, а не исключительность.** Правило без области продолжает
срабатывать при открытом окне. Сделай область глушителем — получилось бы «пока открыт любой
диалог, клавиатура мертва»: `mod+shift+p` не открывал бы палитру из диалога, `mod+s` не
сохранял бы. Кому нужна исключительность, тот пишет `scope == своё` и выигрывает специфичностью.
Отдельно: **область не заменяет `stopPropagation`** — это ответы на разные вопросы («какое
правило выиграет» против «дойдёт ли событие вообще»), и смешать их значит снова сломать палитру.

**✅ Непопавшая вторая ступень аккорда НЕ переразбирается.** `mod+k`, затем `mod+s` не
сохраняет файл: ожидание снимается, не выполнив ничего. Переразбор дал бы человеку действие,
которого он не просил, — худший из возможных исходов, и он запрещён по построению.

**⚠️ `normalizeKeybinding` не менялась вовсе; рядом появилась `normalizeChord`.** Ловушка,
которую пришлось обойти: пробел ВНУТРИ ступени незначим (тест требует, чтобы `mod + alt + V`
давало одну ступень), поэтому наивное деление по пробелам сломало бы написание существующих
сочетаний. Правило: пробел у «плюса» — украшение, пробел между завершёнными ступенями —
разделитель. Все тринадцать канонических случаев прогоняются через `normalizeChord` отдельным
тестом — это гарантия, что ни одна работающая клавиша не сменила написания.

**🔀 Read-only таблица справки удалена вместе с модулем `ui/help.ts`.** Экран клавиш
показывает то же самое и позволяет править; держать рядом второй список, обязанный совпадать,
значило бы завести расхождение, которое обнаружится молча. Пункт меню «Горячие клавиши» ведёт
в редактор.

**✅ Поле записи нажатия слушает клавиатуру само, на своём элементе, в фазе ПОГРУЖЕНИЯ.**
Обычный `onKeyDown` не годится дважды: React делегирует события (и `mod+s` во время записи
успел бы сохранить файл), а Radix ловит Escape на `document` в погружении (и окно закрылось бы
раньше, чем компонент узнал о нажатии). Проверено браузерным тестом — в `node` порядок фаз
недоказуем.

**Проверено независимо:** 3456 node-тестов (было 3277), 156 браузерных (было 152), `tsc -b`
и `eslint` чисто. Единственный красный — `lib/kits/catalog-equivalence` (снимок каталога
компонентов), он падал и до работы: причина в незакоммиченных правках
`packages/reformer-ui-kit/component-catalog.json`, к клавиатуре отношения не имеет.

**Что ловится мутациями:** снятие `when` у `editor-schema.delete` немедленно роняет два теста
в `app/keybindings-wiring.test.ts` с внятным сообщением (проверено запуском); замена `min` на
`max` в специфичности дизъюнкции роняет несущий тест модели разрешения; жадная пересборка
указателя роняет счётчик сборок, забытый сброс кэша — проверку содержимого после регистрации.

### Экран клавиш: таблица с ключом команды · сдано (+3 браузерных теста)

**🔀 Список заменён таблицей из шести колонок: Команда, Ключ, Сочетание, Когда, Источник,
действия.** Ключ (`commandId`) выведен отдельной колонкой не для симметрии с VS Code: именно
им команда называется в раскладке человека, в `contributes.keybindings` манифеста и в обращении
к ассистенту. Строка «Сохранить — Ctrl+S» на вопрос «как эту команду зовут» не отвечает,
а переназначить или снять клавишу, не зная имени, нельзя.

**❌ Опасение «билдер сознательно не тянет `@reformer/ui-kit/table` из-за тяжёлой
`@tanstack/react-table`» не подтвердилось — проверено сборкой.** Барель таблицы экспортирует
и презентационный набор (`Table`/`TableRow`/…, без движка), и `DataGrid` (с движком). Vite
выбрасывает неиспользуемый `DataGrid` целиком: в `dist/assets/*.js` нет ни одного вхождения
`getCoreRowModel`, а единственное упоминание строки `@tanstack/react-table` — в базе знаний
ассистента, то есть текст описания кита, а не код. Сборка проходит за 25 секунд.

**❌ `ScrollArea` вокруг таблицы пришлось убрать — она ломала нажатия.** Обнаружено замером,
а не рассуждением: область просмотра Radix растягивается по содержимому, поэтому ширина
контейнера равнялась ширине таблицы (1382 px при окне в 347), `w-full` ограничивать было
нечему, и кнопки последней колонки уезжали за край экрана. `document.elementFromPoint` в центре
кнопки «Изменить» возвращал `undefined` — то есть клик физически не мог до неё дойти, и
браузерные тесты падали не на проверке, а на невозможности нажать. Заменено обычным блоком
с `overflow-y-auto`; горизонтальную прокрутку таблица приносит свою.

**⚠️ Обязательна фиксированная раскладка колонок (`table-fixed`) с процентными ширинами.**
Без неё `max-w` на ячейках не действует: при автоматической раскладке ширина колонки берётся
по содержимому, и таблица снова разъезжается. Это закреплено тестом, который сравнивает ширину
таблицы с шириной её контейнера, — иначе дефект вернулся бы незаметно, ведь при узком окне
он выглядит просто как «кнопка не нажимается».

**❌ Ширина окна клавиш задавалась классом, который молча не применялся.** Поставленный
`max-w-4xl` не действовал: у диалога кита объявлено `sm:max-w-lg`, слияние классов не считает
базовый и `sm:`-вариант конфликтующими, а в CSS правило с медиа-запросом идёт позже и
побеждает. Замер показал 497 px вместо ожидаемых 896 — то есть окно оставалось прежним, и
таблица из шести колонок ужималась в него. Исправлено на `sm:max-w-5xl` (тот же вариант, тот
же набор утилит — слияние заменяет). Закреплено тестом, который проверяет ФАКТИЧЕСКУЮ ширину
при широком окне, а не наличие класса: это второй случай подряд, когда вёрстка «выглядит
правильной» и не работает, и оба раза его ловил только замер.
