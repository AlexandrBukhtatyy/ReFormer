# Э1 — пять примитивов

Общее правило слоя: **ни один из пяти примитивов не знает слова «форма».** Это проверяется
грепом в CI, как в `@reformer/mcp` проверяется отсутствие node-глобалов в ядре.

## 1. Resource

### Решение: ресурс — это ссылка, а не содержимое

PWA-документ вешает `read()`/`write()` на сам ресурс. Так делать нельзя: объект с методами
привязан к живому источнику и начинает протекать по всему приложению — ровно то, что произошло
в v1, где `FileSystemFileHandle` разошёлся по стору, панелям, корпусу знаний и кодогену.

Поэтому ресурс — **описание**, а чтение и запись живут в Workspace. Идентификатор — строка,
и это осознанно: в локальной файловой системе это путь, у HTTP-источника — то, что вернул сервер,
и потребитель не должен их различать.

```ts
/** Непрозрачный идентификатор. Формат: `<sourceId>:<path>`. Сравнивать только целиком. */
export type ResourceId = string;

export interface ResourceRef {
  readonly id: ResourceId;
  readonly sourceId: string;
  /** Путь внутри источника, всегда с `/` и без ведущего слэша. */
  readonly path: string;
  readonly name: string;
  readonly kind: 'file' | 'directory';
  /** `application/json`, `text/typescript`, `text/markdown`, `image/png`… */
  readonly mediaType: string;
}

/** Свойства материализованного ресурса. Отдельно от ссылки: ссылка стабильна, это — нет. */
export interface ResourceStat {
  readonly kind: 'file' | 'directory';
  /** Непрозрачный маркер версии: ETag, mtime, хеш. Сравнивается только на равенство. */
  readonly revision?: string;
  readonly size?: number;
  readonly mediaType?: string;
}
```

### Решение: текст — основной API, байты — запасной выход

Развилка была: `read(): Uint8Array` как в PWA-документе, или текст.

Разбор по коду v1: текстовые ресурсы — это схемы, `.ts`-сайдкары, markdown, конфиги prettier,
каталоги компонентов, шаблоны. Байты нужны **ровно в одном месте** — картинки в предпросмотре
markdown. Байтовый API как основной означал бы кодирование и декодирование на каждом
текстовом пути ради одного бинарного.

Поэтому:

- `readText` / `writeText` — основной путь; кодировка UTF-8 решается **один раз в адаптере
  источника**, а не на каждом вызове;
- `readBytes` — только для ресурсов, чей `mediaType` бинарный;
- `readText` бинарного ресурса — **ошибка, а не набор мусорных символов**. Тихая порча данных
  хуже отказа.

## 2. Service

Типизированный токен вместо строки с приведением типа.

```ts
export interface ServiceToken<T> {
  readonly id: string;
  /** Только для вывода типов, в рантайме отсутствует. */
  readonly __type?: T;
}

export function defineService<T>(id: string): ServiceToken<T>;

export interface ServiceRegistry {
  register<T>(token: ServiceToken<T>, impl: T): Disposable;
  /** `undefined`, если сервиса нет. Вызывающий обязан деградировать. */
  get<T>(token: ServiceToken<T>): T | undefined;
  /** Бросает с внятным сообщением. Только для сервисов Host. */
  require<T>(token: ServiceToken<T>): T;
}
```

**Правило доступности.** Сервисы Host есть всегда — для них `require`. Сервисы плагинов могут
отсутствовать — для них только `get`, и отсутствие обрабатывается как штатная деградация,
а не как ошибка. Это прямое следствие принципа «работать без рантайма» из RFC-0001 и повторение
приёма из `@reformer/mcp`, где отсутствующий источник — это объявленная пустая заглушка,
а не исключение.

## 3. ExtensionPoint

Один обобщённый механизм вместо отдельного реестра на каждый вид вклада. В v1 таких мест
четыре, и все — литеральные массивы: панели слева, панели справа, встроенные киты, вызовы
генераторов.

```ts
export interface ExtensionPoint<T> {
  readonly id: string;
  readonly __type?: T;
}

export function defineExtensionPoint<T>(id: string): ExtensionPoint<T>;

export interface Contribution<T> {
  readonly id: string;
  readonly pluginId: string;
  readonly order: number;
  readonly value: T;
}

export interface ExtensionRegistry {
  contribute<T>(
    point: ExtensionPoint<T>,
    item: T,
    meta?: { id?: string; order?: number }
  ): Disposable;
  get<T>(point: ExtensionPoint<T>): readonly Contribution<T>[];
  /** Для реактивности UI: вызывается при добавлении и снятии вклада. */
  observe<T>(point: ExtensionPoint<T>, cb: () => void): Disposable;
}
```

Каждый вклад несёт `pluginId` — чтобы на вопрос «откуда здесь эта панель» отвечал реестр,
а не чтение всего кода.

**Что означает «реестры замораживаются».** Фиксируется только **встроенный** набор плагинов:
после старта в него ничего не добавляется. Плагины из каталога проекта включаются и выключаются
в рантайме, поэтому вклады обязаны быть снимаемыми — это же нужно и редакторам, которые вносят
панели на время своей активности.

## 4. Command

```ts
export interface CommandContribution {
  readonly id: string;
  /** Ключ i18n, не литерал. */
  readonly titleKey: string;
  readonly run: (args?: unknown) => unknown | Promise<unknown>;
  readonly enabled?: (ctx: WhenContext) => boolean;
  /** Например `mod+s`, `mod+alt+v`. `mod` = Cmd на macOS, Ctrl на остальных. */
  readonly keybinding?: string;
}
```

### Главное: команды и ввод — разные вещи

Это не стилистика, а вывод из разбора v1. Обработчик клавиш там занимает 192 строки,
и **командами является меньше трети**. Остальное — ввод, принадлежащий сфокусированному
редактору: стрелки с четырьмя комбинациями модификаторов, F6, аккорд из двух нажатий,
пробел как переход фокуса, Enter как быстрое добавление, Escape с тремя разными смыслами
в зависимости от места.

Если сложить всё это в реестр команд, получится та же цепочка условий, просто размазанная
по десятку файлов, и регрессы вида «Delete в инспекторе удаляет узел схемы».

Поэтому:

- **редактор сам обрабатывает свой ввод** и может пометить событие обработанным;
- **глобальный слой диспетчеризует только зарегистрированные сочетания** и только если
  событие не забрал редактор;
- в реестр попадает то, что имеет смысл вызвать из палитры команд, меню или ассистентом.

### WhenContext проектируется раньше реестра

Вторая причина монолитности в v1 — охранные условия: «фокус в поле ввода», «курсор на канвасе»,
«не на кнопке». Реестр команд их не убирает, он их прячет.

Проверка по коду уже проведена, и ответ отрицательный: условие «курсор на канвасе» **невозможно**
выразить, не обращаясь одновременно к режиму превью и режиму взаимодействия. Значит режим обязан
входить в контекст — иначе контракт придётся ломать на первом же редакторе.

```ts
export interface WhenContext {
  /** Куда направлен фокус: поле ввода, канвас, дерево, панель. */
  readonly focus: 'editable' | 'canvas' | 'tree' | 'panel' | 'none';
  readonly activeEditorId: string | null;
  readonly activeResourceKind: string | null;
  readonly hasSelection: boolean;
  /** Режим поверхности превью — без него не выражается «курсор на канвасе». */
  readonly previewMode: string | null;
}
```

## 5. Event

```ts
export interface EventType<T> {
  readonly id: string;
  readonly __type?: T;
}
export function defineEvent<T>(id: string): EventType<T>;

export interface EventBus {
  emit<T>(type: EventType<T>, payload: T): void;
  on<T>(type: EventType<T>, cb: (payload: T) => void): Disposable;
}
```

**Доставка синхронная.** Иначе события нельзя было бы publish-ить из контура правки, который
у нас обязан оставаться синхронным. Отсюда правило для подписчиков: обработчик обязан быть
дешёвым; всё тяжёлое планирует себя сам.

**Порядок между плагинами не гарантируется.** Если порядок важен — это не событие, а команда.
Событие сообщает о факте, а не запрашивает работу.

# Э2 — Workspace и хранилище

## Document против Resource

Различение несущее, и его легко потерять.

|            | Resource                    | Document                              |
| ---------- | --------------------------- | ------------------------------------- |
| Что это    | файл в источнике            | открытый ресурс с разобранной моделью |
| Живёт      | пока существует в источнике | пока открыта вкладка                  |
| Содержимое | текст или байты             | модель в памяти + состояние вида      |
| Истина     | файл в Workspace            | **модель в памяти**                   |

Это и есть развязка противоречия с PWA-документом: Workspace — истина для **ресурсов**,
модель в памяти — истина для **открытого документа**, а файл в Workspace является её
сериализацией. Запись в Workspace дебаунсится и нужна компилятору, валидаторам и соседним
файлам, но не редактору.

## Два множества, а не одно

```text
opened          явное действие пользователя, вкладки, закрепление
materialized    кэш содержимого, включая догруженные зависимости
```

`opened ⊆ materialized`. Разведение обязательно: без него «единица открытия» становится
неразрешимым вопросом — файл ломает компиляцию, каталог формы не покрывает импорт извне каталога.

## API

```ts
export interface Workspace {
  readonly id: string;
  readonly sourceId: string;

  // множество opened
  open(id: ResourceId): Promise<Document>;
  close(id: ResourceId): Promise<void>;
  openedResources(): readonly ResourceId[];

  // содержимое; материализует по требованию
  readText(id: ResourceId): Promise<string>;
  readBytes(id: ResourceId): Promise<Uint8Array>;
  writeText(id: ResourceId, text: string): Promise<void>; // в Workspace, НЕ в источник
  stat(id: ResourceId): Promise<ResourceStat | null>;
  list(dir: ResourceId): Promise<readonly ResourceRef[]>;

  // Workspace → Source
  save(id?: ResourceId): Promise<SaveResult>;
  revert(id: ResourceId): Promise<void>;

  isDirty(id?: ResourceId): boolean;
  onDidChange(cb: (e: WorkspaceChange) => void): Disposable;
}
```

`writeText` пишет в рабочую копию, а не в источник. Единственный путь наружу — `save`.
Это то, что позволяет ассистенту работать теми же операциями, что и UI, без отдельных прав:
он не может дотянуться до источника, минуя сохранение.

## Раскладка хранилища

```text
OPFS
└── ws/{workspaceId}/
    ├── files/<путь>        материализованное содержимое
    └── base/<путь>         содержимое, каким его отдал источник

IndexedDB
├── workspaces              дескриптор источника, настройки
├── opened                  вкладки, закрепление, состояние вида
├── stats                   revision и размер по пути
└── history                 снимки отмены, журнал операций
```

**Почему BASE хранится содержимым, а не хешем.** Для трёхстороннего слияния нужен исходный
текст. Хеша хватило бы только на обнаружение расхождения, а восстановить базу перезапросом
у источника нельзя: к моменту конфликта там уже другая версия — именно поэтому конфликт
и возник.

Удвоение объёма здесь допустимо, и это прямое следствие working set: рабочий набор мал
по построению, поэтому решение, неприемлемое для зеркала всего проекта, для него дёшево.

## Бюджет догрузки зависимостей

Открытие документа тянет за собой замыкание импортов. Без ограничителя импорт из файла-реэкспорта
втянет весь проект.

| Ограничение | Значение | Почему                                                                                 |
| ----------- | -------- | -------------------------------------------------------------------------------------- |
| Глубина     | 8        | Реальные формы укладываются в 2–3; 8 оставляет запас и всё ещё ловит цикл через барель |
| Файлов      | 200      | Каталог формы — единицы файлов; 200 означает, что мы зацепили чужое поддерево          |
| Байт        | 8 МБ     | Отсекает случайное втягивание сборочных артефактов                                     |

Следуем **только относительным** спецификаторам. Бэйр-спецификаторы (`react`, `@reformer/*`)
не догружаются вовсе — они резолвятся на модули оболочки, и это же ограничение защищает
идентичность сигналов.

**При превышении — остановиться и сказать.** Диагностика с указанием, на чём остановились.
Молчаливое усечение недопустимо: оно выглядит как «всё загрузилось», а форма потом не собирается
без объяснимой причины.

## Вытеснение

- **Открытые ресурсы закреплены** и не вытесняются никогда.
- **Догруженные зависимости** вытесняются по давности использования при превышении бюджета
  рабочей области, но **не раньше**, чем их перестанет требовать хоть один открытый документ.
- **`close` снимает закрепление**, а не удаляет. Физическое удаление ленивое — иначе
  закрыть и открыть тот же файл означало бы повторный поход в источник.
- **BASE живёт, пока ресурс материализован.** Выброшенный BASE означает потерю возможности
  слияния, поэтому вытесняются они парой.

# Э3 — Source

## Контракт

```ts
export interface Source {
  readonly id: string;
  readonly descriptor: SourceDescriptor;
  readonly capabilities: SourceCapabilities;

  read(path: string): Promise<{ text: string; revision?: string }>;
  readBytes?(path: string): Promise<{ bytes: Uint8Array; revision?: string }>;
  list(dir: string): Promise<readonly Entry[]>;
  stat(path: string): Promise<Stat | null>;

  write?(path: string, text: string, expected?: string): Promise<Written>;
  mkdir?(path: string): Promise<void>;
  remove?(path: string): Promise<void>;
  move?(from: string, to: string): Promise<void>;

  /** Отменяет обход дерева целиком, если источник умеет отдать список форм сам. */
  listForms?(): Promise<readonly FormRef[]>;
  watch?(glob: string, cb: (path: string) => void): Disposable;
}

export interface Entry {
  readonly name: string;
  readonly path: string;
  readonly kind: 'file' | 'directory';
}

export interface Stat {
  readonly kind: 'file' | 'directory';
  readonly revision?: string;
  readonly size?: number;
}

export interface Written {
  readonly revision?: string;
}

export interface SourceCapabilities {
  readonly write: boolean;
  readonly tree: boolean; // есть каталоги, или это плоский список
  readonly revisions: boolean; // возможен ли детект конфликта
  readonly executesCode: boolean; // можно ли компилировать сайдкары этого источника
  readonly auth: 'none' | 'session' | 'persistent';
}
```

## Три вещи, которые нельзя потерять

**`list` возвращает один уровень одним обращением.** В v1 обход читает **каждый** `.json`-кандидат
уровня, чтобы решить, форма ли это. Локально незаметно, по сети — N+1 на каждый каталог.
Классификация при этом чистая функция, её можно не звать вовсе, если источник ответил сам.

**`stat` заменяет проверку существования.** В v1 её делают два обращения — сначала как к файлу,
потом как к каталогу, — а генерация уникального имени делает до тысячи таких проверок подряд.
Заменяется одним листингом каталога и подсчётом в памяти; это улучшение и для локального случая.

**Конфликт — на равенстве ревизий, а не на «новее».** В v1 сравнение уже сделано на неравенство,
поэтому непрозрачный маркер подставляется без изменения логики. `write` с переданным `expected`
при расхождении бросает конфликт и возвращает текущую ревизию; без `expected` — перезаписывает.

## Отказы

Типизированные, потому что вызывающий обязан различать «нет файла» и «нет сети».

```ts
export type SourceErrorKind =
  | 'not-found'
  | 'conflict'
  | 'unauthorized'
  | 'forbidden'
  | 'unsupported' // возможности нет в capabilities
  | 'budget' // превышен лимит листинга
  | 'network'
  | 'aborted';

export class SourceError extends Error {
  readonly kind: SourceErrorKind;
  readonly path?: string;
  readonly revision?: string; // для conflict — текущая у источника
}
```

## Дескриптор и переоткрытие

```ts
export type SourceDescriptor =
  | { kind: 'fs'; handleKey: string } // сам дескриптор папки — в IndexedDB
  | { kind: 'memory'; label: string }; // тестовый двойник

export interface SourceFactory {
  readonly kind: string;
  restore(d: SourceDescriptor): Promise<Source | null>; // null — восстановить нельзя
}
```

Дескриптор сериализуем; живой объект — нет. В v1 переоткрытие держится на том, что дескриптор
папки переживает структурное клонирование; для остальных видов источника этого свойства нет,
поэтому восстановление идёт через фабрику по виду.

**Разрешения и вход — один и тот же шов.** В v1 переоткрытие отменяется, если у источника нет
модели разрешений; у источника с аутентификацией ровно там окажется запрос токена. Источник
без разрешений обязан отвечать «доступ есть», а не «метода нет».

## Тестовый двойник — вторая реализация контракта

HTTP-источник отложен, поэтому проверять контракт больше нечем. Двойник эту роль выполняет,
**только если устроен принципиально иначе**; копия файловой системы в памяти не проверяет ничего.

Обязательные отличия:

| Свойство    | File System Access       | Двойник                                                |
| ----------- | ------------------------ | ------------------------------------------------------ |
| Структура   | дерево каталогов         | плоское пространство имён, `tree: false`               |
| Ревизии     | время модификации, число | непрозрачная строка                                    |
| Задержка    | пренебрежимая            | настраиваемая, ненулевая                               |
| Отказы      | редкие                   | вводятся намеренно: конфликт, нет сети, нет прав       |
| Возможности | почти все включены       | часть выключена: `write: false`, `executesCode: false` |

**Правило приёмки Э3.** Один и тот же набор тестов проходит на обеих реализациях.
Ветвление теста по виду источника означает дырявый контракт — и это видно сразу,
а не через полгода на первом реальном сервере.

Прецедент, что приём работает, в v1 уже есть: тестовый двойник файловой системы реализует
тот же структурный контракт, и весь путевой слой исполняется над ним без единой правки.

# Решения по спорным местам

Приняты. Ниже — решения с обоснованием, чтобы их не переоткрывали заново.

## 1. Идентификатор для источников без путей

**Решение: путь синтезирует адаптер; ядро всегда работает с путём.**

Обоснование — от потребителя. Путь читают три места: листинг каталога, дерево файлов и **резолвер
импортов**. Последний решает: чтобы собрать `./validation` относительно
`src/forms/credit/schema.json`, нужна арифметика сегментов. Если путь непрозрачен для ядра,
арифметика невозможна, а без неё не собирается ни одна форма. Значит вариант «ядро не знает,
что такое путь» отпадает не по вкусу, а по устройству.

Плоский источник, отдающий формы по идентификатору, укладывается естественно: форма — это
несколько файлов, поэтому идентификатор `credit-app` становится синтетическим каталогом
`credit-app/` с `renderer.schema.json`, `validation.ts` и остальным.

**Важное различение, которое легко потерять:** `tree: false` означает «нет навигации по каталогам»,
а не «нет путей». Возможность управляет тем, что предлагает интерфейс — можно ли ходить по дереву,
создавать каталоги, — а не схемой адресации.

Нормализацию (posix-разделители, без ведущего слэша, запрет выхода за корень через `..`) держит
**ядро**: иначе два адаптера разойдутся в трактовке, и это вскроется на третьем.

## 2. Владелец `mediaType`

**Решение: расширение как основа, ответ источника как переопределение. Но сам вопрос
поставлен неточно — в нём смешаны две разные задачи.**

Разделять надо так:

|                       | Что решает                            | Кто отвечает                              |
| --------------------- | ------------------------------------- | ----------------------------------------- |
| `mediaType`           | текст или байты, подсветка синтаксиса | расширение; источник может переопределить |
| «что это за документ» | какой редактор открывает              | `canOpen` редактора, по успеху разбора    |

Смешение этих двух — источник проблемы, из-за которой вопрос и возник. `.json` действительно
бывает и схемой формы, и конфигом пакета, но это неоднозначность **не транспортного уровня**:
как `application/json` он однозначен, и читать его надо текстом в обоих случаях. Кто его откроет —
решается позже и не расширением. В v1 это уже так и работает: выбор редактора идёт по успеху
разбора, а не по имени файла.

Отсюда: таблица расширений в ядре, `Content-Type` источника имеет приоритет, при неизвестном
расширении определяем **только** текст против байтов. Угадывать «форма ли это» на этом уровне
нельзя — иначе неоднозначность вернётся туда, откуда её убрали.

## 3. Гранулярность `onDidChange`

**Решение: пакет всегда, одиночное изменение — пакет из одного.**

Массовые операции реальны и уже заложены: сохранение всего, вставка каталога, откат и —
самое крупное — материализация замыкания зависимостей, где бюджет допускает до 200 файлов.
Событие на ресурс означает 200 перерисовок дерева на одно открытие документа.

```ts
export interface WorkspaceChange {
  readonly changes: readonly {
    readonly id: ResourceId;
    readonly type: 'materialized' | 'written' | 'saved' | 'evicted' | 'removed';
  }[];
}
```

Подписчик фильтрует сам. Группировка — в пределах микрозадачи.

**Оговорка, чтобы не спутать с другим правилом.** Требование синхронности относится к контуру
правки модели, а не к уведомлениям Workspace: последние и так порождаются вводом-выводом,
который асинхронен по природе. Отложить их на микрозадачу можно, отложить мутацию — нельзя.

## 4. `watch` в первой версии

**Решение: оставить в контракте опциональным и не реализовывать.**

File System Access наблюдения не даёт вовсе, так что для единственного источника первой версии
реализовать его нечем. Вместо него — перепроверка при возврате фокуса в окно, и **только
у открытых ресурсов**: запрашиваем `stat`, сравниваем ревизию, содержимое не тянем. Расхождение
показываем как «изменён снаружи»; содержимое запрашиваем, лишь когда пользователь действует
или когда дело доходит до сохранения.

Это дёшево, покрывает основной сценарий и естественно ложится в трёхстороннее слияние на Э10.

## 5. Безопасный умолчательный ответ на отложенный Q4

Политика live-превью для удалённого источника отложена, и это не мешает Э3 — при условии,
что умолчание задано сразу: **`executesCode: false` для любого источника, кроме локальной
файловой системы.** Умолчание ничего не предрешает, снимается одним изменением возможности,
и до решения система не исполняет код, пришедший по сети.

## 6. Локали и локализация сообщений

**Решение по набору: `ru` и `en`, резервная — `en`.** Инструмент публикуется в npm,
поэтому английский нужен для тех, кто не читает по-русски; резервной делаем именно его.
Ключи — семантические (`files.panel.title`), а не английские строки: тогда ни одна локаль
не оказывается «главной».

**Решение по сообщениям об ошибках — важнее, чем набор локалей.** Диагностика валидаторов
и отказы источника не должны быть локализованными строками. Они должны нести **код и параметры**,
а локализация происходить при отображении:

```ts
{ code: 'component-not-registered', params: { name: 'Inptu' } }
```

Три причины. Ассистент разбирает код и чинится сам — по коду это возможно, по переведённой фразе
нет. Одна ошибка выглядит одинаково в интерфейсе, логе и тесте. И перевод не привязан к месту
возникновения ошибки.

Из этого следует оценка, которую стоит знать заранее: локализация сообщений — это не только
интерфейс оболочки, но и все диагностики валидаторов и отказы источника. В v1 они русскими
строками прямо в коде проверок, так что перевод их в коды — отдельная работа внутри Э4 и Э7,
а не побочный эффект.
