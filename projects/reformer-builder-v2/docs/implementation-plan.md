# UI Builder v2 — верхнеуровневый план реализации

> Рабочий документ и единственный живой источник по v2. Дополняем по мере обсуждения;
> цель — довести до точного плана.
>
> Опирается на разбор кода v1 (ключевые факты вынесены в раздел «Опорные факты») и на внешний
> документ «PWA Platform / UI Builder — архитектура Host + Plugins + Workspace».

## Контекст

v1 (`projects/reformer-builder`, ~45 300 строк) работает, но почти ничего в нём не заменяется:
оболочка на 617 строк с одним обработчиком клавиш, панели литеральными массивами, состояние
вкладки на 24 поля, три хранилища без общего слоя, единственный источник файлов — File System
Access API.

Решено ранее: **v2 пишется рядом, v1 замораживается**, публикация потом и из `reformer-builder`.
Домен (`model/`, `catalog/`, `kits/`, `codegen/`, `agent/`, компилятор) переезжает почти дословно
(~33k строк); заново пишутся оболочка, состояние и панели (~12k).

## Опорные факты по коду v1

Проверено чтением кода. На этих фактах стоят решения ниже — если какой-то опровергнут,
пересматривать надо соответствующее решение, а не план целиком.

- **Ссылочная идентичность схемы несёт корректность, а не оптимизацию.** `model/paths.ts:52-64`
  (`updateAt`) даёт structural sharing, и сравнение `!==` держит восемь мест: `isDirty`
  (`reducers.ts:972`), детект конфликта хода ассистента (`agent/apply.ts:49,66`), `hasChanges`
  (`changeset.ts:57`), кэш базовой линии гейта (`gate.ts:49`), автосохранение черновиков
  (`drafts.ts:33-45`), мемоизация канваса, детект no-op у разгруппировки, различение миграции
  формата. Разбор файла через `JSON.parse` каждый раз даёт новый объект и ломает все восемь.
- **Контур правки синхронный, и это несущее.** Перетаскивание вызывает `preventDefault()` только
  **после** синхронного хит-теста (`RuntimePreview.tsx:262-272`); гейт валидации срабатывает
  на каждой правке инструмента; все 25 write-инструментов ассистента — синхронные чистые функции.
  Асинхронная мутация означает переписывание `agent/core` (9.7k строк, намеренно без React
  и без состояния) на async.
- **Живое превью требует единственного экземпляра `@reformer/core`.** Линковщик подсовывает коду
  формы уже загруженные модули оболочки (`preview-runtime/live/module-registry.ts`); второй
  экземпляр ломает идентичность сигналов и поиск узла по сигналу (`live/link.ts:4-8`).
- **Рабочая копия в OPFS изолирует не всё.** От источника её отделены только живое превью,
  компиляция и редактор трёх схем. Мимо неё к диску ходят девять мест: сама схема формы
  (`io/save.ts:37,49-52`), code-вкладки Monaco, write-back схем, картинки markdown, переход
  по ссылке, все операции дерева, шаблоны, экспорт примера и корпус знаний ассистента.
  Именно они, а не рабочая копия, задают объём контракта источника.
- **Порт источника фактически уже существует и реализован трижды.** `io/fs-ops.ts:11-33` написан
  против структурных типов, а не против `showDirectoryPicker`; поэтому тот же path-слой работает
  над OPFS без правок (`io/opfs.ts:11-14`) и над тестовым двойником
  (`io/__fixtures__/fake-fs.ts:44-68`). Резать порт надо по **публичной сигнатуре** `fs-ops`
  (она уже путевая), а не по handle: обход по сегментам даёт N обращений на операцию.
- **Две ловушки производительности, безобидные локально и фатальные по сети.** `existsIn`
  (`fs-ops.ts:252-272`) делает два запроса на одну проверку; `uniqueName` (`:275-285`) —
  до тысячи последовательных проверок. Плюс обход каталога читает **каждый** `.json`-кандидат
  (`discovery.ts:178-193`). Лечится одним листингом каталога и подсчётом в памяти — это улучшение
  и для локального случая.
- **Детект конфликта обобщается почти бесплатно.** `io/save.ts:39` сравнивает время модификации
  **на неравенство**, а не «новее», поэтому любой непрозрачный токен (ETag, ревизия, хеш)
  подставляется без изменения логики — расширяется только тип.
- **Стабильного идентификатора узла нет ни в одном пакете.** Адресация идёт путём/указателем,
  который съезжает при вставке соседей. Поле `selector` на эту роль не годится: пользователь его
  правит, дедупликация меняет его при копировании, внутри шаблона массива он один на все строки,
  и он уже несёт публичный контракт (ключи шагов визарда и `validation.steps`).
- **Точек валидации не восемь, а четыре** — две из «восьми» проверяют конфигурацию, а не документ,
  и ещё две уже композируются внутри `io/validate.ts`.
- **Арифметика модульности.** Переход на реестры честно удаляет 350–400 строк и добавляет ~1050
  инфраструктуры. Гибкость через вклады — это всегда `+N` за `−M`, где `N > M`, пока вкладов мало.
  Чистое упрощение в v1 лежит не в архитектуре, а в объёме: `save-actions.ts` 709 строк,
  `FilesPanel.tsx` 559, `Inspector.tsx` 531, шаблоны 900 — 2700 строк, которым не нужен ни один
  новый слой.

| Идея                                                                   | Решение                                                                                                                                                                                                               |
| ---------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

| **Workspace = working set, а не зеркало проекта**                      | **Берём, и это лучше моего исходного предложения.** Я предлагал зеркалить дерево проекта целиком; working set экономнее и обязателен для удалённых источников                                                         |

## Где документ сталкивается с измеренными ограничениями

Это не возражения против идей, а места, где нужно явное решение — иначе план молча отменит то,
что уже проверено по коду.

### 1. «Workspace — единственная рабочая модель» против источника истины документа

Документ (§3) требует, чтобы редакторы работали только через Workspace API. Если понимать это
буквально как «истина — файлы в OPFS», мы возвращаемся к варианту, который уже отвергнут
с доказательствами: на ссылочной идентичности схемы (`model/paths.ts:52-64`, structural sharing)
стоит **корректность** в восьми местах — от `isDirty` до детекта конфликта хода ассистента;
а перевод правки в асинхронную ломает перетаскивание (`RuntimePreview.tsx:262-272`,
`preventDefault()` после синхронного хит-теста) и требует переписать `agent/core` — 9.7k строк
чистого синхронного кода — на async.

**Развязка:** Workspace — истина для **ресурсов**; открытый **документ** имеет модель в памяти,
которая является истиной, пока он открыт, а файл в Workspace — её сериализация. Ровно модель
VSCode: `TextDocument` в памяти, файл на диске. Запись в Workspace дебаунсится и нужна
компилятору, валидаторам и соседним файлам, а не редактору.

### 2. Preview в iframe против идентичности модулей

Документ (§21) перечисляет `iframe-preview` и `remote-preview` наравне с остальными. Ограничение,
которое это отменяет: линковщик обязан подсунуть коду формы **те же объекты модулей**, что
использует рендерер (`preview-runtime/live/module-registry.ts`, `link.ts:4-8`). Компилятор
в Host + рендер в iframe = второй экземпляр `@reformer/core` = сломанная идентичность сигналов
и неработающий поиск узла по сигналу.

Плюс отдельный факт: **iframe-превью и выбор узла кликом взаимоисключающи** — токены `rbnode-*`
дописывает `annotateSchema` в эфемерную копию схемы, а чужое приложение рендерит форму из своего
файла, так что токенов там нет вовсе.

**Развязка:** превью описывается не типом, а **возможностями** — `interactive`, `hitTest`,
`dragSource`, `executesCode`, `sameRealm`. Оболочка обязана уметь работать при `hitTest: false`.
Плагин поставляет **транспилятор** (чистая функция `(code, file) => js`), но не линковщик
и не реестр модулей.

### 3. Внешние плагины по URL против принципа «никакого удалённого кода»

Документ (§30) предлагает грузить плагины с `https://plugins.example.com/`. RFC-0001, принцип P4,
запрещает ровно это: _«Рантайм никогда не скачивает и не выполняет код из сети»_. Первым решением
было «только внутренний реестр контрибуций, стороннего кода не грузим» — **оно ниже пересмотрено,
см. «Обновление»**; разбор оставлен, потому что из него следует то, что осталось в силе.

Отдельно и важнее: билдер исполняет код в главном потоке, в том же realm, где живут FS-хендлы
проекта и ключ AI-провайдера. Плагин с React-панелью получает `localStorage`, то есть ключ.

**Развязка — и здесь документ сам себе даёт ответ, просто не связывает две главы.**
Плагин с React-компонентом в iframe жить не может: компонент не пролезает через `postMessage`.
Значит изоляция несовместима с императивным UI-плагином — но совместима с **декларативным**
(§32–33): плагин описывает UI как JSON, Host рендерит. То есть JSON-описание UI — не украшение,
а **единственное, что вообще делает недоверенные плагины возможными**.

**Обновление: динамические плагины принимаются, но не по URL.** Решено грузить их из локального
каталога проекта, по модели Obsidian. Это снимает противоречие целиком, а не обходит его:
P4 запрещает **скачивание кода из сети**, а плагин из папки рядом с проектом — это буквально
«уже установленный в рабочей области», о котором тот же принцип говорит как о допустимом.
Пересматривать P4 не требуется.

Что остаётся в силе: изоляция в iframe и в воркере по-прежнему несовместима с императивным
UI-плагином, поэтому её не делаем; плагин из каталога исполняется с полными правами, и это
объявляется, а не умалчивается. Механика — в
[plugin-and-shell.md](plugin-and-shell.md#динамические-плагины-из-каталога-проекта).

### 4. Масштаб «универсальной платформы»

Документ метит в PWA Application Platform, где тот же Host становится баг-трекером или системой
управления шлагбаумами. Оценка снизу: внутренняя модульность **одного только билдера** без единой
новой фичи оценена в 39–41 день с критерием «нулевая дельта поведения». Платформа — кратно больше,
и при этом v1 держит незакрытый MVP M2.

**Развязка:** строим билдер **как если бы он был плагином** — это почти бесплатно и сохраняет
дорогу к платформе. Но не строим маркетплейс, версионирование API, разрешения и песочницу,
пока нет второго приложения. Универсальность проверяется не декларацией, а **вторым Source**
(этап Э9) — это дешёвая и честная проверка того, что абстракция настоящая.

### 5. Мелочи, которые стоит знать заранее

- **i18n в списке сервисов Host — это новая работа, а не рефакторинг.** В v1 локализации нет
  вовсе, интерфейс русский строками в коде.
- **FTP и SSH отложены — решено.** Это и технически удачно: браузер этих протоколов не умеет
  вовсе, `ftp://` удалён из Chrome в 2021, так что любая их поддержка это всё равно HTTP-шлюз.
  FTP/SSH при необходимости появляются позже как конфигурация шлюза, без нового контракта.

  Позже отложен и HTTP-источник, поэтому реальная реализация остаётся **одна** — File System
  Access. Риск отсюда только вырос: проверять контракт нечем. Отсюда две страховки. Порядок
  Э2 → Э3 (Workspace раньше реального источника) из предпочтения становится обязательным,
  иначе контракт будет подогнан под File System Access. И роль второй реализации берёт на себя
  тестовый двойник, устроенный принципиально иначе.

- **Router в Host не используем — решено.** Всё происходит на одной странице, поэтому
  маршрутизации в списке сервисов Host нет, `routes` не входит в число точек расширения,
  и плагины вносят не маршруты, а виды и панели. Побочно это подтверждает, что мёртвая
  зависимость `react-router-dom` из v1 не должна вернуться.

  Что этим отдаём осознанно: глубокие ссылки на состояние и кнопку «назад» в браузере.
  В v1 их и так нет, так что регресса не происходит. Дешёвый запасной выход, если однажды
  понадобится «открыть форму по ссылке», — параметры в query или hash без маршрутизатора
  как библиотеки; это остаётся возможным и решения не требует.

```text

│                           HOST                              │
│  Theme · i18n · Settings · Storage · Notifications          │
│  Events · Commands · Permissions · Worker Pool              │
│                     Plugin Runtime                          │
└───────────────────────────┬─────────────────────────────────┘
                            │  Plugin API / SDK
   ┌────────────┬───────────┼───────────┬────────────┐
   ▼            ▼           ▼           ▼            ▼
 Sources     Editors    Validators   Preview        AI
   │            │           │           │            │
   └────────────┴─────┬─────┴───────────┴────────────┘
                      ▼
                 WORKSPACE  (working set: только открытое)
                      │
              ┌───────┴────────┐
              │ OPFS: файлы    │
              │ IDB: метаданные│
```

Направление зависимостей — строго сверху вниз. Плагины не связываются друг с другом напрямую:
только через Workspace, Commands и Events.

## Ключевые решения, которые план не переоткрывает

Приняты ранее и подтверждены разбором кода:

1. **Истина открытого документа зависит от его вида.** У документа с моделью (схема формы) истина —
   модель в памяти, а файл в Workspace её дебаунсенная сериализация. У текстового документа
   (`.ts`, `.md`) истина — буфер, модели нет. Уточнено при детализации Э6: структурная правка
   против текстового буфера означала бы разбор на каждое действие, а разбор каждый раз даёт новый
   объект и рушит structural sharing.
2. **Механизм истории выбирается по материалу.** У документа с моделью отмена на снимках —
   при structural sharing снимок это три указателя. У текстового документа история на патчах:
   разделять там нечего, а Monaco выдаёт готовые дельты. Содержимое в OPFS, история
   в IndexedDB. Журнал операций над моделью ведётся **дополнительно** к снимкам,
   как фундамент под совместную работу.
3. **Стабильный идентификатор узла — поле в схеме**, игнорируемое конвертером. Побочно чинит
   реальный дефект: правило видимости на обычном поле сейчас тихий no-op.
4. **Плагины грузятся из локального каталога проекта, но никогда из сети.** Обновлено: раньше
   здесь было «только встроенные». Модель — как в Obsidian: каталог рядом с проектом, каждый
   плагин включается явно. Принцип «никакого удалённого кода» это не нарушает — он запрещает
   загрузку по сети, а не из уже установленного в рабочей области. Замораживается только
   встроенный набор; плагины каталога включаются и выключаются в рантайме.
5. **Оболочка прибита к встроенному киту, превью — к активному.**
6. **Маршрутизации нет.** Приложение одностраничное; в Host нет `RouterService`, среди точек
   расширения нет `routes`. Плагины вносят виды и панели.
7. **Реализуем один источник — File System Access.** FTP и SSH отложены; HTTP-источник тоже
   отложен (см. Q3, Q4). Контракт обязан их допускать; вторая реализация на время отсутствия
   HTTP — тестовый двойник.
8. **Открытие — по ресурсу, материализация — по требованию.** Разведены «открытые ресурсы»
   (вкладки) и «материализованные» (кэш, включая зависимости). Резолвер импортов просит путь,
   Workspace достаёт его из Source, если в кэше нет. Нужен бюджет на глубину и количество
   догрузок; бэйр-спецификаторы не догружаются вовсе — они резолвятся на модули оболочки.
9. **ID узла — 8 символов base36, выдаётся при разборе, записывается при первом сохранении.**
   Счётчик отвергнут: коллизирует при слиянии, ради которого ID и нужен. В памяти ID есть всегда,
   поэтому нетронутый файл не получает шумный diff, а адресация работает с момента открытия.
10. **Секреты — в памяти сессии, опционально в изолированном пространстве IndexedDB.**
    `localStorage` не используем вовсе; ключ ассистента переезжает туда же.
11. **Полноценный i18n с первого дня** — до первой строки UI. См. отдельный раздел ниже.
12. **Связи с `@reformer/form-registry` не заводим** — ни общего контракта, ни зависимости.
13. **Сообщения об ошибках несут код и параметры, а не готовую строку.** Локализация — при
    отображении. Ассистент чинится по коду (по переведённой фразе не может), одна ошибка выглядит
    одинаково в интерфейсе, логе и тесте, перевод не привязан к месту возникновения.
14. **`executesCode: false` по умолчанию для всего, кроме локальной файловой системы.** Умолчание
    ничего не предрешает и снимает блокировку с Э3, пока Q4 отложен.
15. **Локали `ru` и `en`, резервная — `en`;** ключи семантические, чтобы ни одна локаль
    не была «главной».
16. **Форматирование — служба Host: свой prettier по умолчанию, проектный при наличии конфига.**
    Пользовательские файлы форматируются prettier'ом только если проект сам на нём; иначе —
    детерминированная сериализация, чтобы правка одного поля не переформатировала весь файл.
    Сгенерированный код форматируется всегда: он пишется целиком.
17. **Состояние превью живёт вне поверхности.** Мок-данные — в OPFS как авторский артефакт,
    эфемерное состояние вида — в IndexedDB. Поэтому поверхности можно свободно размонтировать
    при переключении, и держим одну.
18. **Журнал изменений — один поток в нейтральном формате.** Общий конверт на текстовые правки
    и операции над моделью; смещения в кодовых единицах UTF-16. Хранение в четыре шага:
    опорные снимки, схлопывание, удаление по возрасту, удаление по объёму — именно в таком
    порядке. Инвариант: в журнале всегда есть опорный снимок не позже самой старой записи,
    иначе воспроизведение не от чего вести.

## i18n — полноценный, с первого дня

Решено делать сразу и целиком: словари, переключение языка, плюрализация, ленивая загрузка локалей.
Обоснование простое — дошивать i18n в готовый UI дорого, а «потом пройдёмся и заменим строки»
обычно не случается. В v1 локализации нет вовсе, интерфейс русский строками в коде, так что это
новая работа, а не перенос.

Что из этого следует по устройству:

- **Появляется в Э4, до первой строки UI.** `I18nService` входит в сервисы Host и в `PluginContext`.
  Если UI начнёт писаться раньше, мы получим ровно тот сквозной проход по всем строкам, которого
  и хотели избежать.
- **Плагин везёт свои словари.** Каталог сообщений — часть вклада плагина, пространство имён
  по его идентификатору. Иначе Host снова начнёт знать предметные строки, а он не должен.
- **Плюрализация через `Intl.PluralRules`.** У русского три формы (`1 файл`, `2 файла`, `5 файлов`),
  и писать это руками не надо — платформа умеет.
- **Локали: `ru` и `en`, резервная — `en`.** Меньше двух не проверяет механизм вовсе. Резервной
  выбран английский: инструмент публикуется в npm, и промах должен оставаться читаемым для того,
  кто не знает русского. Ключи семантические (`files.panel.title`), а не английские строки —
  тогда ни одна локаль не оказывается «главной».
- **Отсутствующий ключ виден.** В разработке — заметный маркер, а не тихий откат к ключу:
  пропущенная строка должна обнаруживаться при написании, а не пользователем.
- **Сообщения об ошибках локализуются не как строки, а как коды.** Диагностика валидаторов
  и отказы источника несут `{ code, params }`, перевод происходит при отображении. Это важнее
  набора локалей: по коду ассистент чинится сам, а по переведённой фразе — нет.

  Отсюда оценка, которую лучше знать заранее: в v1 эти сообщения — русские строки прямо в коде
  проверок, поэтому перевод их в коды это отдельная работа внутри Э4 и Э7, а не побочный эффект.

**Важное разграничение, которое легко потерять.** Локализация интерфейса билдера и локализация
**содержимого формы** — две разные системы. Для содержимого в `@reformer/renderer-json` уже есть
оператор `$locale(...)`, он работает внутри схемы пользователя и к интерфейсу отношения не имеет.
Смешивать их нельзя: язык интерфейса выбирает тот, кто строит форму, язык содержимого — тот,
кто её заполняет, и это разные люди в разное время.

## Контракт источника — набросок

Один порт с объявленными возможностями, а не два понятия. Сервер форм, умеющий только список
и получение, — это источник, у которого выключено почти всё. Два понятия развели бы код на две
ветки в каждой точке, ровно как это уже случилось в v1 с режимом «проект не открыт»: около десяти
одинаковых `if (!root) { toast('Проект не открыт'); return; }`, ни один не выражен типом.

```ts
interface Source {
  readonly descriptor: SourceDescriptor; // сериализуемый, для переоткрытия
  readonly capabilities: SourceCapabilities;

  read(path: string): Promise<{ text: string; revision?: string | number }>;
  list(dir: string): Promise<Entry[]>; // один уровень, один запрос
  stat(path: string): Promise<Stat | null>; // заменяет двойную проверку existsIn

  write?(path: string, text: string, expected?: string | number): Promise<Written>;
  mkdir?(path: string): Promise<void>;
  remove?(path: string): Promise<void>;
  move?(from: string, to: string): Promise<void>;
  listForms?(): Promise<FormRef[]>; // отменяет обход дерева целиком
  watch?(glob: string, cb: (path: string) => void): Disposable;
}

interface SourceCapabilities {
  write: boolean;
  tree: boolean; // есть ли каталоги, или это плоский список форм
  revisions: boolean; // возможен ли детект конфликта
  executesCode: boolean; // можно ли компилировать и исполнять сайдкары этого источника
  auth: 'none' | 'session' | 'persistent';
}
```

Три вещи, которые нельзя потерять при проектировании:

- **`listForms` — не удобство, а ответ на N+1.** Если источник умеет отдать список форм сам,
  обход дерева не нужен вовсе; классификация в v1 чистая и просто не вызывается.
- **`executesCode` — граница безопасности.** У формы сайдкары это исполняемый код, который живое
  превью транспилирует и линкует в том же realm, где FS-хендлы и ключ ассистента. С диска
  пользователя это уровень доверия «`npm run dev`», с сервера — загрузка кода извне. Границу
  выражать типом, как это сделано в `@reformer/form-registry` (у источника кода варианта `http`
  нет **по типу**), а не проверкой в рантайме.
- **Разрешения и аутентификация — один шов.** В v1 переоткрытие проекта отменяется, если
  у источника нет модели разрешений; у HTTP-источника ровно там окажется вход по токену.
  Учётным данным не место рядом с ключом ассистента в общем хранилище.

Э9 стоит сразу после компилятора не случайно: **загрузчик плагинов и компилятор формы — один
и тот же механизм** (транспиляция плюс линковка с реестром модулей), поэтому после Э8 он почти
даром. Дорога не механика, а стабильность API: каждое её изменение ломает написанные плагины.
Поэтому загрузчик делаем рано, чтобы писать плагины самим, но **API объявляем нестабильным**,
пока не наберётся три-четыре собственных плагина против него.

Порядок Э2 → Э3 намеренный: сначала Workspace на памяти или заглушке, потом реальный источник.
Иначе контракт источника будет спроектирован под File System Access и не переживёт второй.

### Риск от переноса HTTP-источника за точку решения

HTTP-источник был единственной проверкой того, что абстракция Source настоящая. Отложив его,
мы остаёмся с одной реализацией — и рискуем спроектировать «универсальный контракт», который
на деле описывает File System Access.

**Страховка, стоящая почти нуля: вторая реализация — тестовый двойник, а не продукт.** В v1 такой
уже существует и доказал работоспособность приёма: `io/__fixtures__/fake-fs.ts` реализует тот же
структурный контракт, и весь path-слой работает над ним без правок. Но двойник обязан быть
**устроен иначе**, иначе он ничего не проверяет: плоский список вместо дерева, непрозрачные
строковые ревизии вместо времени модификации, искусственные задержки и отказы, отсутствующие
возможности (`write: false`, `tree: false`).

Правило приёмки Э3: один и тот же набор тестов проходит и на File System Access, и на двойнике.
Если тест приходится ветвить по виду источника — контракт дырявый, и это видно сразу, а не через
полгода на первом реальном сервере.

## Перенос домена из v1 — сквозная нить, а не отдельный этап

Раньше в плане этого не было вовсе, и это была настоящая дыра: список этапов описывал только
новое, а «остальное переезжает почти дословно» скрывало объём.

Перенос — не один этап, потому что его части нужны разным этапам: модель схемы требуется уже

## Чего не делаем

- **Маркетплейс и загрузка плагинов по сети** — не делаем. Плагины только из локального каталога;
  это и есть граница, проведённая принципом «никакого удалённого кода».
- **Изоляция плагинов в iframe или воркере** — несовместима с регистрацией React-панелей;
  альтернатива это декларативный UI, а он нужен только для недоверенных плагинов. Плагин
  из каталога пользователя доверенный по построению.
- **Политика совместимости Plugin API** — поле `apiVersion` в манифесте заводим сразу, но
  до появления чужих плагинов вся политика это отказ грузить при расхождении мажора.
- **Worker Pool с реальными задачами** — контракт заводим, наполняем когда появится тайпчек:
  валидация схемы синхронная, и на ней стоит гейт ассистента.
- **Полный тайпчек проекта** — требует чтения `.d.ts` из `node_modules` через источник, это
  отдельный проект.
- **Git/GitHub/Jira-плагины** — они в документе как иллюстрация универсальности, а не как задача.
- **FTP- и SSH-источники** — отложены. Контракт источника обязан их допускать, реализации нет.
  Браузер этих протоколов не умеет, поэтому появятся они как конфигурация HTTP-шлюза.
- **HTTP-источник** — отложен вместе с вопросами о его объёме и политике доверия (Q3, Q4).
  На время отсутствия вторая реализация контракта — тестовый двойник.
- **Любые связи с `@reformer/form-registry`** — ни общего контракта, ни зависимости, ни
  копирования сетевого слоя. Когда вернёмся к HTTP-источнику, решение принимается заново.
- **Маршрутизация** — не используем: всё на одной странице. Ни `RouterService` в Host,
  ни `routes` среди точек расширения; плагины вносят виды и панели, а не маршруты.

## Факт против оценки

Раздел дописан по завершении основного объёма работ. Он нужен затем же, зачем в плане была
записана вилка оценок: чтобы следующая оценка делалась не на пустом месте.

### Что получилось

|                     |                                                                                                                                                                                |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Файлов `.ts`/`.tsx` | **534**, из них **190** тестовых                                                                                                                                               |
| Строк               | **96 766**                                                                                                                                                                     |
| Тестов              | **2913** в обычном прогоне + **61** в браузерном                                                                                                                               |
| Плагинов            | **9** (файлы, два редактора, валидатор, киты, превью, ассистент, генерация, шаблоны)                                                                                           |
| Главный чанк        | **~1040 кБ raw / ~332 гzip**, при лениво загружаемых Monaco (3.7 МБ), TypeScript (3.5 МБ), каталоге кита (587 кБ), корпусе знаний (1.3 МБ), ajv (117 кБ) и самом ките (708 кБ) |

По слоям: платформа 41 973 строки, плагины 39 317, домен 10 400, композиция 4 780, SDK 147.

**Соотношение платформы к плагинам примерно один к одному** — и это, пожалуй, главный
количественный итог. Оно и означает, что архитектура сделала то, ради чего затевалась: половина
кода живёт за границей, которую можно пересечь только объявленным способом.

### Чего оценка не увидела

Плановая вилка (83–102 дня «сверху», 184 после декомпозиции) считала **написание** кода.
Дороже всего оказалось не оно, а три вещи, которых в оценке не было вовсе:

1. **Швы между слоями.** Порт, двойник контракта в тестах плагина, реэкспорт вместо копии —
   каждый такой шов это десятки строк, которых нет ни в одном пункте плана. Прямая цена
   границы слоёв измерена один раз честно: двойник ручки модели в тестах редактора схемы —
   **+118 строк**, и это не издержка, а плата за то, что плагин не видит платформу.
2. **Дефекты, найденные переносом.** Их оказалось больше, чем задач: латинское разбиение имён,
   ломавшее шаблоны для русских имён без единого сообщения; журнал, не создававшийся вовсе;
   команды-фантомы быстрых исправлений; валидатор, не срабатывавший ни разу; две ошибки
   в палитре команд, которые нашёл только браузерный прогон.
3. **Подключение.** «Плагин написан» и «плагин работает» разделяет порт композиции — и почти
   каждый из девяти обнаружил в контракте что-то недосказанное именно на этом шаге.

### Что стоит перенести в следующий план

- **Порт композиции — отдельный пункт оценки**, а не хвост задачи плагина.
- **Браузерный прогон — с самого начала.** Он был заведён поздно и немедленно нашёл две ошибки
  в коде, сданном часом ранее с зелёными тестами. Четыре агента независимо указали на эту дыру,
  прежде чем её закрыли.
- **Каждое утверждение о весе — контролируемым A/B**, а не разницей абсолютных чисел: в дереве
  одновременно работают несколько рук.
- **«Написано» не значит «вызывается».** Трижды за проект целые подсистемы оказывались
  не подключёнными. Дешёвая проверка — грепом по вызовам фабрики вне тестов.
