# Э6 — документы и редакторы

## Уточнение: документов два вида, а не один

В плане записано «истина открытого документа — модель в памяти». При детализации выяснилось,
что это верно не для всех документов, и разница принципиальна.

|           | `TextDocument`                                    | `ModelDocument`                                        |
| --------- | ------------------------------------------------- | ------------------------------------------------------ |
| Истина    | текстовый буфер                                   | разобранная модель                                     |
| Когда     | `.ts`, `.md`, всё, для чего нет провайдера модели | есть `DocumentModelProvider` — сегодня это схема формы |
| Редакторы | только Monaco                                     | Monaco и структурный, оба виды на одну модель          |
| Правка    | текстовая                                         | операциями над моделью                                 |

Почему нельзя обойтись одним видом: структурная правка против текстового буфера означала бы
разбор на каждое перетаскивание, а разбор каждый раз даёт **новый объект целиком** — и рушится
structural sharing, на котором в v1 держится корректность в восьми местах. Обратно: заводить
модель для произвольного `.ts` не на чем.

Это уточнение, а не отмена: у `ModelDocument` истина по-прежнему модель, а файл в Workspace —
её сериализация.

## Провайдер модели регистрируется на тип ресурса, а не на редактор

Иначе Monaco и структурный редактор одного и того же файла разойдутся в двух представлениях.

**Провайдер — это вклад плагина, а не часть Host.** Разбор схемы формы — предметное знание,
и оно не имеет права оказаться в платформе. Провайдер для схемы регистрирует
`plugins/editor-schema/`; появится другой формат — придёт со своим плагином.

Что при этом остаётся в `host/workspace/document.ts`: буфер, признак изменённости, обвязка
истории, состояние вида, переключение между двумя видами документа. То есть **машинерия
документа без единого знания о том, что за формат внутри**. Документ, для которого никто
не внёс провайдера, просто остаётся текстовым — это и есть определение `TextDocument`.

```ts
export const DocumentModelPoint =
  defineExtensionPoint<DocumentModelProvider<unknown>>('document.model');

export interface DocumentModelProvider<M> {
  readonly id: string;
  applies(ref: ResourceRef, probe: EditorProbe): boolean;
  parse(text: string): M;
  print(model: M): string;
  apply(model: M, op: EditOp): ApplyResult<M>;
}

export interface ApplyResult<M> {
  readonly model: M;
  readonly inverse: EditOp;
  /** Куда переехало выделение: узел мог сместиться или родиться. */
  readonly focus?: NodeId;
}
```

`focus` в результате — не удобство. В v1 выделение переносится на новый путь после каждой правки
отдельным механизмом, потому что вставка соседа смещает адрес. Со стабильными идентификаторами
смещения нет, но «куда смотреть после операции» всё равно знает только сама операция.

## Расхождение текста и модели

Пользователь может напечатать в Monaco нечто неразбираемое. Что происходит:

```text
буфер разбирается     → модель обновилась, всё согласовано
буфер не разбирается  → документ в состоянии «разошёлся»
                        · буфер держит то, что напечатал пользователь
                        · модель держит последнюю валидную
                        · структурные редакторы только на чтение
                        · диагностика показывает ошибку разбора
```

**Сохранение в состоянии расхождения пишет буфер, а не модель.** Пользователь сохраняет то,
что видит; незавершённый код — законное содержимое файла. Молча записать устаревшую модель
означало бы потерять его работу.

Обратное направление тоже нужно правило: когда модель меняется извне (структурная правка,
ход ассистента), текст в Monaco перерисовывается из `print(model)` — **но только если Monaco
не в фокусе**. Иначе редактор будет затирать то, что человек печатает прямо сейчас. В v1 этот
приём уже есть и работает; переносим.

## Стабильные идентификаторы узлов

```ts
export type NodeId = string; // 8 символов base36
```

**Имя поля в схеме — `$nodeId`, форма `^[0-9a-z]{8}$`.** Проверено спайком, альтернативы отвергнуты
по конкретным причинам: `$id` — ключевое слово JSON Schema, им пользуются сами мета-схемы формы,
и внутри узла оно читалось бы как «идентификатор схемы»; `id` уже занят **на корне** схемы
с другим смыслом; голый `nodeId` стал бы визуальным двойником `selector`, а их надо разводить —
`selector` пишет автор и адресует им поведение рендера, `$nodeId` выдаёт машина и в поведении
не адресуется. Префикс `$` у **ключа** в этом DSL уже означает служебную механику (`$schema`,
`$template`), и с операторами не конфликтует: операторы — это `$`-префиксные **значения**.

**Идентификатор кладётся на узел, а не в `componentProps`.** Это не вкусовщина: конвертер
отбрасывает неизвестные поля узла, а содержимое `componentProps` копирует поголовно, и очистка
пропсов для html-тегов устроена как список запрещённого, а не разрешённого. Поле в `componentProps`
доехало бы до DOM неизвестным атрибутом на каждом `$html(...)`-узле.

- **Выдаются при разборе.** Узел без идентификатора получает его сразу, поэтому адресация
  работает с момента открытия.
- **Записываются при первом сохранении.** Нетронутый файл не получает шумного diff.
- **Копирование выдаёт новые.** Вставка узла — это новый узел; сохранить идентификатор значило бы
  создать двойника, на которого сработают правила исходного.
- **Провайдер модели владеет выдачей.** Ядро о них знает только как о строках.

## Операции правки

```ts
export interface EditOp {
  readonly type: string; // 'insert' | 'move' | 'set-prop' | …
  readonly target?: NodeId;
  readonly params?: Record<string, unknown>;
}
```

Сериализуемость обязательна: то же описание уходит в журнал операций, который мы ведём как
фундамент под совместную работу. Функция `apply` при этом остаётся синхронной и чистой —
на этом стоит гейт ассистента.

## История

Две разные вещи, которые легко перепутать:

|                         | Отмена                    | Журнал операций                                |
| ----------------------- | ------------------------- | ---------------------------------------------- |
| Что хранит              | снимки модели и выделения | описания операций                              |
| Где                     | память документа          | IndexedDB, append-only                         |
| Зачем                   | Ctrl+Z                    | совместная работа, разбор поведения ассистента |
| Переживает перезагрузку | нет                       | да                                             |

Снимок при structural sharing стоит три указателя, поэтому отмена на снимках дешевле журнала
и остаётся снимками. Схлопывание мелких правок — по ключу совпадения, как в v1
(`ключ = свойство@узел`), иначе набор текста в поле забьёт стек.

**Ход ассистента — одна запись отмены.** Механизм в v1 уже такой и переносится.

## Вклад редактора

Контракт объявлен в [plugin-and-shell.md](plugin-and-shell.md#редакторы). Здесь только правило,
которое из него неочевидно:

**`viewState` — это прокрутка, свёрнутые ветки и позиция каретки. Выделение туда не входит.**
Выделение участвует в операциях правки (перенос на `focus` после вставки), читается командами
и входит в снимок отмены. В v1 это 270 строк навигации и блочных операций, которые читают
и модель, и выделение одновременно.

# Э7 — валидаторы и диагностика

## Адресация: размеченный союз, а не два адреса сразу

Раньше отвергнута «двойная адресация» — когда одна диагностика несёт и текстовый диапазон,
и структурный путь. Это остаётся отвергнутым. Но цель у диагностики бывает разной природы:

```ts
export type DiagnosticTarget =
  | { readonly kind: 'node'; readonly nodeId: NodeId }
  | { readonly kind: 'range'; readonly range: TextRange }
  | { readonly kind: 'resource' };

export interface Diagnostic {
  readonly source: string; // идентификатор валидатора
  readonly severity: 'error' | 'warning' | 'info';
  readonly code: string; // ключ i18n: errors.<code>
  readonly params?: Record<string, unknown>;
  readonly target: DiagnosticTarget;
  readonly fixes?: readonly QuickFix[];
}

export interface QuickFix {
  readonly titleKey: string;
  readonly commandId: string;
  readonly args?: unknown;
}
```

У одной диагностики цель **одна**. Синтаксическая ошибка разбора адресуется диапазоном — узла
ещё нет. Структурная ошибка адресуется узлом — и это лучше пути, потому что путь съезжает
при вставке соседей, а идентификатор нет.

Перевод «узел → диапазон» делает тот, кто рисует, в момент отрисовки, по тексту, который сейчас
в редакторе. Это снимает необходимость в отдельном механизме вычисления строки по пути:
в v1 такой механизм **симулирует** сериализацию и из-за этого врёт, а его убирает разбор
с позициями.

## Сообщение — это код и параметры

`code` плюс `params`, а не готовая строка. Причины уже записаны в плане: ассистент чинится
по коду, одна ошибка одинаково выглядит в интерфейсе, логе и тесте, перевод не привязан к месту
возникновения. `QuickFix` довершает картину: ассистент получает не только «что не так»,
но и «чем чинить», и чинит той же командой, что и человек.

## Два уровня валидации, потому что гейт синхронный

```ts
export interface ValidatorContribution {
  readonly id: string;
  applies(doc: DocumentRef): boolean;
  /** Быстрая проверка. Синхронная — на ней стоит гейт ассистента. */
  validate?(ctx: ValidateContext): readonly Diagnostic[];
  /** Дорогая проверка: с задержкой, отменяемая, результат вливается отдельно. */
  validateAsync?(ctx: ValidateContext, signal: AbortSignal): Promise<readonly Diagnostic[]>;
}
```

Разделение вынужденное и обосновано измерением: структурная валидация схемы в v1 синхронная,
и на каждой правке инструмента ассистента срабатывает гейт. Сделать всю валидацию асинхронной
означает сделать асинхронным цикл ассистента.

Дорогой уровень пока пуст. Он наполнится, когда появится проверка типов — и именно она станет
первым потребителем пула воркеров, а не валидация схемы.

## Служба диагностик

```ts
export interface DiagnosticsService {
  publish(resource: ResourceId, source: string, items: readonly Diagnostic[]): void;
  get(resource: ResourceId): readonly Diagnostic[];
  onDidChange(cb: (resource: ResourceId) => void): Disposable;
}
```

`publish` **замещает** результаты одного источника, а не добавляет: иначе исправленная ошибка
останется висеть. Это же даёт декорации на дереве ресурсов — файл с ошибкой помечается тем же
механизмом вкладов, что и «это схема формы».

# Э8 — модули, компиляция и превью

## Реестр модулей — неприкосновенная часть

Всё остальное в этом разделе обсуждаемо, это — нет.

```ts
export interface ModuleRegistry {
  resolve(specifier: string, fromPath: string): unknown | undefined;
  /** Только добавление. Попытка переопределить защищённый спецификатор бросает. */
  register(specifier: string, exports: unknown): Disposable;
}
```

Линковщик обязан подставлять коду **уже загруженные объекты модулей оболочки**. Второй экземпляр
`@reformer/core` ломает идентичность сигналов и поиск узла по сигналу — это измерено в v1
и зафиксировано там же в комментарии к линковщику.

Защищённые спецификаторы: `react`, `react/jsx-runtime`, `react/jsx-dev-runtime`,
`@preact/signals-core`, `@reformer/*`, `@builder/sdk`.

**`@preact/signals-core` в списке не за компанию.** Это ровно тот пакет, где живёт `instanceof Signal`,
то есть его подмена ломает идентичность прямее, чем подмена самого ядра. В первой редакции
контракта его не было — дыру нашла реализация.

**Резолв подпутей — префиксный, а не точный.** В v1 `@reformer/ui-kit/*` ведёт в неймспейс
активного кита, а `@reformer/core/validators` — в общий барель. Точный резолв потребовал бы
регистрировать каждый подпуть руками и молча ломался бы на первом новом. Порядок: сначала
точное совпадение, затем самый длинный подходящий префикс.
Плагин может **добавить** свой модуль, но не подменить эти. Проверка тривиальная — принадлежность
списку, — и она должна быть, а не подразумеваться.

## Транспилятор сменный, линковщик нет

```ts
export interface Transpiler {
  readonly id: string;
  applies(fileName: string): boolean;
  transpile(code: string, fileName: string): { js: string; map?: string };
}
```

Чистая функция без доступа к модулям — поэтому её замена безопасна. Именно так устроено в v1,
где транспиляция намеренно собрана в одном модуле с пометкой, что замена движка это правка
одного файла.

Линковщик заменять незачем и нельзя: его форма продиктована реестром модулей, и это сорок строк.

## Один механизм на два потребителя

Загрузчик плагинов и компилятор формы делают одно и то же: транспилировать при необходимости
и слинковать с реестром модулей. Поэтому механизм один и живёт в Host как служба:

```ts
export const ModuleLoaderToken = defineService<ModuleLoader>('host.moduleLoader');

export interface ModuleLoader {
  readonly registry: ModuleRegistry;
  /** Загружает набор файлов как связный граф модулей. */
  load(files: ReadonlyMap<string, string>, entry: string): Promise<LoadResult>;
}
```

Разные у них только входные данные: у плагина это его каталог, у формы — её файлы из Workspace.

## Компиляция читает Workspace, а не Source

Это то, ради чего вообще существует рабочая копия: компилятор получает материализованные файлы
и не знает, откуда они пришли. Замыкание импортов уже собрано на открытии документа, с бюджетом
и диагностикой при превышении.

Относительные спецификаторы резолвятся арифметикой путей внутри Workspace; bare-спецификаторы
идут в реестр модулей и **никогда** не догружаются из источника — это же ограничение защищает
идентичность.

## Поверхности превью

```ts
export interface PreviewSurface {
  readonly id: string;
  applies(doc: DocumentRef): boolean;
  readonly capabilities: PreviewCapabilities;
  mount(host: HTMLElement, ctx: PreviewContext): Disposable;
}

export interface PreviewCapabilities {
  readonly interactive: boolean;
  readonly hitTest: boolean; // выбор узла кликом
  readonly dragSource: boolean; // принимает дроп с палитры
  readonly executesCode: boolean;
  readonly sameRealm: boolean;
}
```

Ось — **realm**, а не «нужен ли компилятор». Рендер в iframe при компиляторе в оболочке даёт
второй экземпляр ядра, поэтому исполняющая поверхность обязана быть в том же realm.

Четыре поверхности первой версии:

| Поверхность   | hitTest | executesCode | Что это                                      |
| ------------- | ------- | ------------ | -------------------------------------------- |
| каркасная     | да      | нет          | схематичное дерево, без рендера              |
| рантайм       | да      | нет          | реальный рендерер по схеме, без сайдкаров    |
| компилирующая | да      | да           | сайдкары формы транспилируются и исполняются |
| внешняя       | **нет** | —            | чужой dev-сервер в iframe                    |

## Выбор узла кликом — почему это возможность, а не свойство

Механизм: в эфемерную копию схемы дописываются классы-токены, по которым элемент DOM
отображается обратно в узел. Для чужого приложения токенов **нет вовсе** — оно рендерит форму
из своего файла, а не из нашей аннотированной копии.

Поэтому внешняя поверхность и выбор кликом взаимоисключающи не из-за границы iframe,
а из-за отсутствия аннотации. Оболочка обязана нормально жить при `hitTest: false`:
палитра не предлагает перетаскивание, инспектор работает от выделения в дереве.

## Запрет исполнения по источнику

Поверхность с `executesCode: true` не монтируется, если у источника документа
`capabilities.executesCode === false`. Умолчание для всего, кроме локальной файловой системы, —
`false`.

Отказ **виден**: вместо компилирующего превью показывается рантайм-поверхность и сообщение,
почему исполнение недоступно. Тихая подмена режима хуже отказа — пользователь будет думать,
что видит результат своего кода.

# Поправка к структуре проекта

При детализации Э8 обнаружилось нарушение границы в раскладке, предложенной ранее.

Было: `lib/compiler/` — транспиляция и линковка. Но загрузчик плагинов живёт в `host/plugin/`,
а по правилу импорта **`host/` не имеет права импортировать `lib/`**.

Разбор показывает, что ошибка не в правиле, а в размещении: транспиляция TypeScript и линковка
модулей — механика платформенная, в ней нет ничего про формы. Предметное здесь другое: какие
файлы составляют форму и что считать точкой входа.

Поэтому:

```text
host/modules/          транспиляторы, линковщик, реестр модулей   ← платформа
  ├── registry.ts
  ├── linker.ts
  └── transpilers.ts

plugins/preview/       что именно компилировать для формы          ← предметное
```

`lib/compiler/` из раскладки уходит. Доступ для плагина превью — через службу
`ModuleLoaderToken`, как и для любой другой возможности платформы.

Побочная польза: правило импорта поймало ошибку проектирования до написания кода — ровно то,
ради чего оно и заводилось.

# Форматирование

Решено: **свой prettier как основа, с заложенной возможностью взять проектный.**

Форматирование — служба Host, потому что потребителей несколько (печать модели, генерация кода,
вывод плагинов), источник настроек переменный, а сам prettier асинхронный:

```ts
export const FormatterToken = defineService<FormatterService>('host.formatter');

export interface FormatterService {
  format(
    text: string,
    opts: {
      parser: 'json' | 'typescript' | 'markdown';
      /** Настройки резолвятся по расположению файла: у prettier они каталожные. */
      resource?: ResourceId;
    }
  ): Promise<string>;
  onDidChangeConfig(cb: () => void): Disposable;
}
```

Prettier грузится лениво: с плагинами это заметный кусок бандла, а до первого сохранения
он не нужен.

## Проектные настройки — ограничение переносится из v1

Читаются `.prettierrc*`, `.editorconfig` и `package.json`. **Исполняемые конфиги (`.cjs`, `.js`)
в браузере не выполнить** — в v1 на этот случай уже показывается отдельная плашка, и ограничение
переносится как есть: настройки берутся по умолчанию, а пользователю говорят почему.

## Правило, снимающее вопрос про шумный diff

Политика форматирования **разная для файлов, которые мы правим, и которые генерируем целиком**:

| Что                                 | Как форматируем                                                              | Почему                                                                                                                           |
| ----------------------------------- | ---------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| Схема формы (пользовательский файл) | детерминированная сериализация; prettier — только если у проекта есть конфиг | правка одного поля не должна переформатировать полторы тысячи строк. Если проект уже на prettier, вывод совпадёт и шума не будет |
| Сгенерированный код                 | всегда через prettier                                                        | файл пишется целиком, аргумента про diff не существует                                                                           |

Это и есть ответ на исходное опасение: первый save переформатирует весь файл только там,
где проект сам этого хочет.

# История: разные механизмы для разного материала

Решено: история файлов ведётся через OPFS плюс IndexedDB плюс патчи. Это дополняет, а не отменяет
решение про снимки — механизмы разные, потому что материал разный.

|                       | `ModelDocument`                                    | `TextDocument`                                              |
| --------------------- | -------------------------------------------------- | ----------------------------------------------------------- |
| Механизм отмены       | **снимки**                                         | **патчи**                                                   |
| Почему                | structural sharing делает снимок тремя указателями | у текста разделения структуры нет; снимки это полные строки |
| Откуда берутся дельты | из `apply(model, op)`                              | Monaco отдаёт их сам в событии изменения                    |
| Где содержимое        | OPFS                                               | OPFS                                                        |
| Где история           | IndexedDB                                          | IndexedDB                                                   |

Симметрия обманчива, и это стоит проговорить: **для модели патчи были бы хуже снимков,
а для текста — лучше**. Причина одна и та же — свойства данных. Модель разделяет неизменяемую
структуру, поэтому снимок почти ничего не стоит; текст не разделяет ничего, зато Monaco выдаёт
готовые дельты с диапазоном и вставкой бесплатно.

## Как это уживается с отменой в Monaco

У Monaco свой стек отмены, и подменять его не надо.

- **В пределах сессии** Ctrl+Z работает через Monaco — он для этого и сделан.
- **Журнал патчей — запись, а не второй стек.** Он переживает перезагрузку и даёт историю
  изменений как отдельный вид.
- **После перезагрузки** восстановление идёт из журнала как явная операция, а не подмешивается
  в свежий стек Monaco. Иначе получили бы двойную отмену: одно нажатие снимает две правки.

# Состояние превью живёт вне поверхности

Решено: состояние сохраняется, содержимое — в OPFS.

Это снимает исходный вопрос «сколько поверхностей держать смонтированными» целиком: **если
состояние не внутри компонента, поверхности можно свободно размонтировать при переключении**.
Держим одну.

Разделение, которое стоит сохранить:

| Что                                              | Где                                    | Почему                                                                 |
| ------------------------------------------------ | -------------------------------------- | ---------------------------------------------------------------------- |
| Мок-данные формы: значения модели и источников   | OPFS, рядом с рабочей копией формы     | это авторский артефакт, его можно выгрузить в файл и положить в проект |
| Эфемерное: прокрутка, текущий шаг визарда, режим | IndexedDB со состоянием вида документа | производное состояние, файлом не становится                            |

Первая строка — осознанное исключение из правила «OPFS для файлов, IndexedDB для состояния».
Мок-данные под него не подпадают: это не производное состояние, а то, что пользователь написал
руками и вправе забрать с собой.

# Журнал изменений

Решено: журнал нужен разным частям приложения, а не только восстановлению после перезагрузки.
Отсюда два следствия — нейтральный формат и осознанная политика хранения.

## Формат нейтральный, а не редакторный

Дельты Monaco привязаны к его модели. Раз журнал читают несколько потребителей — восстановление,
история изменений как вид, аудит хода ассистента, а в перспективе слияние правок, — хранить
надо в форме, не зависящей от того, кто правку породил.

```ts
export interface TextEdit {
  readonly offset: number; // в кодовых единицах UTF-16
  readonly removed: string; // что было — делает патч обратимым без исходника
  readonly inserted: string;
}
```

**Единицы измерения названы намеренно.** JavaScript и Monaco считают в кодовых единицах UTF-16;
потребитель, решивший, что это байты или кодовые точки, сломается на первом же эмодзи.
Написать это один раз дешевле, чем ловить потом.

**`removed` хранится, хотя для проигрывания вперёд не нужен.** Он делает запись самодостаточной:
шаг назад не требует поиска базы, а потребитель может понять правку, не имея документа.
Для набора текста это почти всегда пустая строка, так что цена низкая.

**Выгода оказалась больше заявленной.** Без `removed` невыполнимо схлопывание: смещения второго
пакета отсчитаны от текста _после_ первого, поэтому склейка списков `[...a, ...b]` даёт
правдоподобный, но неверный патч. Композиция двух пакетов в координатах основания требует знать,
что именно было удалено.

## Один конверт на модель и на текст

```ts
export interface JournalRecord {
  readonly seq: number;
  readonly resource: ResourceId;
  readonly ts: number;
  readonly origin: 'user' | 'agent' | 'external';
  /** Логический шаг: ход ассистента или мультикурсорная правка — одна запись. */
  readonly txId?: string;
  readonly payload:
    | { readonly kind: 'text'; readonly edits: readonly TextEdit[] }
    | { readonly kind: 'model'; readonly ops: readonly EditOp[] };
}
```

Конверт общий, начинка разная. Потребитель истории или аудита читает **один поток**, а не два —
иначе «покажи, что изменилось» пришлось бы собирать из двух источников с разными правилами
упорядочивания.

## Хранение: четыре шага, и первый из них не про удаление

Предложенный порядок — схлопывание, затем возраст, затем объём — верный, но в нём не хватает
опорных точек, и без них второй шаг ломает воспроизведение.

**0. Опорные снимки.** Каждые ~200 записей или ~1 МБ патчей кладётся полный снимок содержимого.

Зачем: журнал проигрывается **от снимка**, а не от начала времён. Если удалить старые патчи,
не имея снимка после точки удаления, восстановить состояние станет не из чего — останется
хвост правок без основания.

Инвариант, который держит всю политику. **Буквальная формулировка «снимок не позже самой старой
сохранённой записи» недостижима** — это выяснилось при реализации: `seq` монотонен по рабочей
области, а удаление вырезает префикс потока, поэтому одна граница не может совпасть со снимками
всех ресурсов сразу.

Равносильная выполнимая форма: **у каждого оставшегося в журнале ресурса есть опорный снимок,
и всё новее него сохранено целиком.** Вторая половина следует из префиксного удаления сама.

Отсюда же следствие, которого в первой редакции не было: **опорный снимок обязан закрывать хвост
схлопывания.** Иначе правка, дописанная в предыдущую запись, делает уже лежащий снимок неверным,
и восстановление тихо разойдётся с текстом.

**1. Схлопывание.** Соседние записи сливаются в одну.

Не сливаются никогда:

- через границу `txId` — иначе ход ассистента перестанет быть одним шагом;
- при смене `origin` — правка человека и правка ассистента обязаны остаться различимыми,
  в этом половина ценности аудита;
- если между ними прошло больше окна (~3 с) — иначе схлопнется то, что человек воспринимает
  как разные действия.

Схлопывание идёт первым, потому что оно **не теряет содержимого** — только промежуточные нажатия.
Удалять до него значит выбрасывать то, что и так сжалось бы почти в ничто.

**2. Возраст.** Записи старше ~30 дней удаляются — но не глубже ближайшего опорного снимка,
чтобы не осиротить хвост.

**3. Объём.** Пока журнал рабочей области больше ~32 МБ, удаляются самые старые записи вместе
с их снимками. Порядок величины взят из существующего в репозитории кэша схем, где потолок
такой же.

**Почему объём последним.** Возраст — это предпочтение («история за месяц»), объём — жёсткое
ограничение хранилища. Жёсткое обязано стоять последним, иначе после него снова может набежать
лишнее и гарантии не будет. В нынешнем порядке гарантия есть: что бы ни оставили предыдущие шаги,
последний доводит до потолка.

Журнал принадлежит рабочей области: удаление рабочей области удаляет и его.
