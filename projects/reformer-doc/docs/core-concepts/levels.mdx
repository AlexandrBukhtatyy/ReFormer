# Сигналы, прокси и уровни

Ядро ReFormer держится на двух механизмах. **Сигналы** хранят значения и сообщают об их
изменении. **Прокси** дают к сигналам удобный доступ: выглядят как обычные данные, а каждое
обращение переводят в чтение или запись сигнала.

Значения живут в одном месте — в [модели](./model.mdx). Всё остальное — **уровни** над ней.
Уровень смотрит на сигналы модели через свои прокси и добавляет своё состояние, но значений не
копирует. Форма — один из таких уровней. Рядом с ней может быть приложение и любой ваш уровень.

## Когда нужно

Эта страница — карта ядра. Она пригодится, когда вы:

- решаете, где держать состояние: только в форме или в модели всего приложения;
- не понимаете, почему `model.email`, `model.$.email` и `form.email` — разные объекты об одном
  значении;
- пишете свой уровень над моделью: автосохранение, синхронизацию с адресной строкой, свой
  рендерер.

Как описывать форму — модель, схему, правила и поведение — рассказывает
[архитектура M1](../intro.mdx#философия-архитектура-m1). Здесь — что из этих описаний получается во
время работы.

## Сигналы

Под каждым полем модели стоит [сигнал](/docs/reference/glossary) — ячейка, которая помнит значение
и сообщает подписчикам, что оно изменилось. Код внутри `computed`, `effect` или хука React
подписывается на сигналы сам, просто читая их. Запись будит только тех, кто читал это поле.

На этом стоит всё остальное. Ноды формы, правила, поведение и хуки не держат копий значений —
они читают те же сигналы. Поэтому запись в одном месте сразу видна во всех остальных. Подробно —
[Реактивность и сигналы](./reactive-state.md).

## Прокси

Сигналы лежат в дереве модели, а само дерево наружу не отдаётся. С ним работают через прокси.

| Прокси          | Пример                                     | Что даёт                                                               |
| --------------- | ------------------------------------------ | ---------------------------------------------------------------------- |
| значений модели | `model.user.name`, `model.user.name = 'А'` | значение поля: чтение подписывает на поле, присваивание пишет в сигнал |
| сигналов модели | `model.$.user.name`                        | сам сигнал поля — им схема, правила и поведение указывают на поле      |
| формы           | `form.name`, `form.$`                      | ноду поля: значение из модели плюс касание, замечания, доступность     |

Прокси кэшируются: одно и то же обращение всегда даёт тот же объект. Поэтому сигнал поля годится
как ключ — по нему сборка формы находит ноду поля, а правило `validate(model.$.email, …)` —
поле, которому положить замечание.

Вложенная группа модели — сама модель со своими прокси и методами:

```typescript
model.user.get(); // { name: '…', email: '…' } — значения группы
model.user.$.email === model.$.user.email; // true — один сигнал, два пути
```

## Уровни

Уровень — набор прокси и состояния поверх модели. Модель об уровнях не знает, поэтому их можно
добавлять, ничего в ней не меняя.

### Уровень модели

Модель — сама первый уровень: прокси значений, прокси сигналов и методы целиком (`get`, `set`,
`patch`, `reset`, `isDirty`). От формы и от React она не зависит. Это состояние на сигналах, и в
нём можно держать данные всего приложения: пользователя, корзину, настройки.

```typescript
import { createModel } from '@reformer/core';
import { computed } from '@reformer/core/signals';

type App = {
  user: { name: string; email: string };
  cart: { items: string[] };
  theme: 'light' | 'dark';
};

export const app = createModel<App>({
  user: { name: '', email: '' },
  cart: { items: [] },
  theme: 'light',
});

// Своё вычисление поверх двух значений из разных групп.
export const headerTitle = computed(() => `${app.user.name} · ${app.cart.items.length}`);
```

Компонент React читает модель хуком `useSignalSnapshot` и перерисовывается, только когда
меняется прочитанный сигнал:

```tsx
import { useSignalSnapshot } from '@reformer/core/react';

function Header() {
  const title = useSignalSnapshot(headerTitle);
  return <h1>{title}</h1>;
}

function ThemeSwitch() {
  const theme = useSignalSnapshot(app.$.theme);
  return (
    <button onClick={() => (app.theme = theme === 'light' ? 'dark' : 'light')}>{theme}</button>
  );
}
```

### Уровень формы

`createForm` строит над моделью уровень формы: [ноды](./nodes.md) `FormControl`, `FormGroup`,
`FormArray` над сигналами полей, прокси формы, дерево для рендера, проверку, шаги и отправку.
Своих значений у этого уровня нет: нода читает сигнал модели, а `setValue` пишет в него. Своё у
формы — состояние вокруг значений: касание, замечания, доступность, видимость узлов.

```typescript
import { createForm, type FormModel, type FormSchemaNode } from '@reformer/core';
import { Input } from '@reformer/ui-kit';

type Profile = { name: string; email: string };

const profileSchema = (model: FormModel<Profile>): FormSchemaNode => ({
  children: [
    { model: model.$.name, component: Input },
    { model: model.$.email, component: Input },
  ],
});

const { model, form } = createForm<Profile>({
  initial: { name: '', email: '' },
  schema: profileSchema,
});

model.email = 'a@b.c'; // запись через прокси значений модели
form.email.value.value; // 'a@b.c' — нода читает тот же сигнал
form.email.setValue('x@y.z'); // нода пишет в модель
model.email; // 'x@y.z'
form.email.touched.value; // false — касание есть только у ноды
```

Правила и поведение указывают на поле сигналом `model.$.email`, а не нодой. Ноду по сигналу
находит реестр, который сборка заполняет, когда строит ноды. Поэтому одни и те же правила
подходят к форме из кода и к форме из JSON.

### Свой уровень

Уровень — любой код, который читает сигналы модели. Ему не нужен отдельный API: хватает прокси
модели и `effect` или `subscribe`.

```typescript
import { effect } from '@reformer/core/signals';

// Автосохранение: подписка на группу целиком — сразу и при каждом изменении.
const stopDraft = app.$.user.subscribe((user) => saveDraft(user));

// Синхронизация с адресной строкой: эффект читает одно значение.
const stopUrl = effect(() => {
  const url = new URL(window.location.href);
  url.searchParams.set('theme', app.theme);
  window.history.replaceState(null, '', url);
});
```

Оба вызова возвращают функцию отписки — вызовите её, когда уровень больше не нужен.

## Пересечения прокси и значений

Прокси не делят модель на части. Один прокси указывает на одно значение или на несколько, к
одному значению ведут несколько прокси, и уровни пересекаются как угодно.

<ProxyOverlap />

- **Одно значение — несколько прокси.** `app.user.email`, `app.$.user.email`, `app.user.$.email`
  и нода `form.email` — входы в один сигнал. Запись через любой видна всем остальным.
- **Один прокси — несколько значений.** Сигнал группы `app.$.user` складывается из всех её полей,
  нода группы — из нод своих полей, `computed` — из всех значений, которые прочитал.
- **Уровни пересекаются.** Шапка читает `user.name`, форма профиля его пишет — шапка обновится, хотя
  о форме ничего не знает.

```typescript
app.user.name = 'Анна';
app.$.user.value; // { name: 'Анна', email: '' } — сигнал группы видит запись поля
headerTitle.value; // 'Анна · 0' — computed пересчитан
```

## Модель приложения и формы

Форма собирается над моделью приложения целиком или над её частью. Ноды встанут над сигналами
этой части, и ввод в поле сразу виден шапке и всем, кто читает модель.

```typescript
const profile = createForm<App['user']>({
  model: app.user,
  schema: userSchema,
  validation: userRules,
});

await profile.submission.submit(async (values) => {
  await saveUser(values); // значения уже в модели приложения — переносить их не нужно
});
```

Над одной моделью можно собрать несколько форм: форму профиля и форму настроек, или даже две формы
над одними полями. Значения у них общие, а ноды — свои: проверка формы кладёт замечания в её
ноды, поведение выключает её поля, рендерер рисует её ноды. Проверка одной формы не трогает
другую и не отменяет её идущую проверку.

## Подводные камни

- **Поле прокси формы — нода, а не значение.** `form.email = 'a@b.c'` не сработает: значение пишут
  `form.email.setValue('a@b.c')` или в модель — `model.email = 'a@b.c'`.
- **Прокси модели не заводит новых полей.** Состав полей задаёт начальное значение: присваивание
  полю, которого не было в `initial`, бросит ошибку.
- **Снимок группы — только для чтения.** `model.$.user.value` — общий снимок для всех читателей, в
  режиме разработки он заморожен. Пишите через поля или `model.user.patch(…)`.
- **Сброс формы сбрасывает её часть модели приложения.** Значения общие, поэтому
  `profile.form.reset()` вернёт `app.user` к его точке отсчёта, а остальную модель не тронет.
  После загрузки данных зафиксируйте точку отсчёта: `app.user.captureInitial()`.
- **`getNodeForSignal` при нескольких формах отдаёт ноду последней собранной.** Ноду конкретной
  формы берите у неё: `form.email` или `bundle.render.nodeOf(model.$.email)`.
- **Массив модели получает ноду, только если его описала схема.** Без узла в схеме `form.items` —
  `undefined`, а в режиме разработки консоль подскажет, как его привязать. Это касается и формы над
  моделью приложения.
