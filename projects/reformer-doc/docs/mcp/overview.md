# Обзор

MCP-сервер ReFormer — сервис для AI-ассистентов (Claude Code, Cursor, другой MCP-клиент): через
него ассистент создаёт и меняет формы на `@reformer/*`. Сервис ведёт план работы, собирает модуль
формы, проверяет типы и отвечает на вопросы по API, а ассистенту не нужно читать исходники
библиотеки.

Сервис закрытый и платный. К IDE его подключает открытый клиент [`@reformer/mcp`](#пакеты) (MIT):
справка, инструменты и сборка формы работают в сервисе, а всё, что касается ваших файлов, — на
вашей машине.

Форма собирается по единому контракту: модель → одна схема → одна сборка `createForm` → правила →
поведение → визард (поток шагов) → отрисовка. Набор инструментов (`REFORMER_SURFACE=tools`)
добавляет к сборке документацию пакетов как **ресурсы**, справочные **инструменты** (подбор API,
JSDoc-индекс публичных символов, рецепты, проверка кода) и workflow-**промпты**.

## Доступ

Сервис сейчас в раннем доступе: ключ `REFORMER_API_KEY` выдаётся по запросу. Напишите нам —
контакты (Telegram, почта) в подвале сайта.

Для команд, которым код и спецификации форм нельзя отправлять во внешний сервис, сервис
разворачивается у себя по лицензии — по договору. Клиент указывает на него переменной
`REFORMER_SERVICE_URL`.

## Зачем MCP — в цифрах

Тот же агент с сервером собирает и правит формы надёжнее, быстрее и дешевле, чем по одной
документации пакетов. На 180 прогонах Claude Sonnet с поверхностью `code-guided-dsl` — теперь она
по умолчанию — 97% прогонов прошли все проверки против 83% без MCP, работа шла в 2,6 раза быстрее и
стоила в 4,3 раза меньше.
Сводная инфографика и результаты по каждому сценарию — на странице
[Замеры: с MCP и без](./benchmark).

## Что такое MCP?

[Model Context Protocol](https://modelcontextprotocol.io/) — открытый стандарт от Anthropic для
интеграции AI-ассистентов с внешними инструментами и данными. MCP-сервер объявляет клиенту:

- **Resources** — доступ к документации и данным
- **Tools** — инструменты, которые AI может вызывать
- **Prompts** — готовые workflow-сценарии

## Подключение

Клиент запускается через `npx`, ключ передаётся переменной окружения. Регистрация в Claude Code:

```bash
claude mcp add --transport stdio reformer -e REFORMER_API_KEY=<ваш ключ> -- npx -y @reformer/mcp
```

Бинарь клиента называется `reformer-mcp`: после `npm install -g @reformer/mcp` вместо
`npx -y @reformer/mcp` можно писать `reformer-mcp`. Проверить подключение — `claude mcp list`.
Настройка других IDE (Cursor, Windsurf, Cline) — в [Быстром старте](./quick-start).

| Переменная             | Что задаёт                                                                                                   |
| ---------------------- | ------------------------------------------------------------------------------------------------------------ |
| `REFORMER_API_KEY`     | ключ сервиса; без него облачный сервис не отвечает, и клиент сразу об этом сообщает                          |
| `REFORMER_SERVICE_URL` | адрес сервиса без пути — для сервиса, развёрнутого у себя; по умолчанию облачный                             |
| `REFORMER_SURFACE`     | что сервер отдаёт ассистенту: `code-guided-dsl` (по умолчанию), `tools`, … — см. [поверхности](#поверхности) |
| `REFORMER_TRACE_FILE`  | журнал вызовов в файл (JSON Lines)                                                                           |

## Что остаётся у вас и что уходит в сервис

На вашей машине клиент:

- читает и пишет каталог формы;
- проверяет типы компилятором вашего проекта, с вашими версиями пакетов;
- читает спецификацию формы;
- сохраняет отчёты `report_issue` в `.reformer/issue_reports`.

С каждым вызовом клиент передаёт сервису только то, что нужно этому вызову: файлы каталога формы,
спецификацию, результат проверки типов и каталог компонентов `@reformer/ui-kit`, если он
установлен. Записи сервис возвращает операциями — на диск их пишет клиент. Без сети и без ключа
MCP не работает.

## Поверхности

Что сервер отдаёт ассистенту, выбирает переменная окружения `REFORMER_SURFACE`:

| Поверхность                      | Что видит ассистент                                                                                   | Когда брать                                                                            |
| -------------------------------- | ----------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| `code-guided-dsl` (по умолчанию) | два инструмента, `search` и `execute`; оба принимают JavaScript                                       | создать или изменить форму                                                             |
| `tools`                          | [набор инструментов](#инструменты-tools), [промпты](#промпты-prompts) и [ресурсы](#ресурсы-resources) | справка по API для своего кода, проверка кода `validate_form`, свой `form.intent.json` |
| `code`, `guided`, `code-guided`  | эксперименты: Code Mode (один `run_script`) и профили для малых моделей                               | замеры                                                                                 |

### По умолчанию: search и execute

Работу ведёт сервер. Ассистент начинает её в `execute` вызовом `reformer.formStart` с текстом
задания или спецификацией, а дальше меняет форму конструктором: цепочки методов записывают правки,
`save()` отправляет их, и сервер собирает модуль. Все файлы каталога формы — по ответу сервера —
пишет клиент, разметку JSX для `@reformer/core` тоже.

```js
// execute — правки конструктором
const f = reformer.form();
f.add('email', 'Email').required().email();
f.add('company', 'Компания')
  .required()
  .showWhen((m) => m.customerType === 'company');
console.log(await f.save());
```

Каждый ответ кончается строкой `Next:` с готовым кодом для `execute` — до ответа `Done`. `search`
только читает: текущую форму, задание и разбор спецификации, методы конструктора, план. Подробно — в
[Инструментах](./tools#по-умолчанию-search-и-execute).

### Набор инструментов

```bash
claude mcp add --transport stdio reformer -e REFORMER_API_KEY=<ваш ключ> -e REFORMER_SURFACE=tools -- npx -y @reformer/mcp
```

Набор нужен, если ассистент пишет свой код рядом с формой и ему нужна справка по API, если обвязка
сама пишет `form.intent.json` и зовёт `form_build` или если клиент работает через промпты.

## Инструменты (tools)

Этот набор сервер отдаёт при `REFORMER_SURFACE=tools`.

| Tool              | Роль                                                                                                                                       |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| `get_context`     | Собранный контекст для одного шага сборки формы: оператор, сигнатура, пример, правила и анти-паттерны в бюджете токенов.                   |
| `choose_api`      | Выбрать оператор под требование своими словами («поле B доступно, только когда заполнено A») — с примером и частыми путаницами.            |
| `get_symbol_docs` | Полный JSDoc публичного символа любого `@reformer/*`: сигнатура, параметры, все `@example`, исходник.                                      |
| `find_recipe`     | Рецепт по ключевому слову сценария (`wizard`, `form-array`, `json-schema`) или `@example` символа.                                         |
| `search_docs`     | Полнотекстовый поиск по документации всех пакетов, когда задачу можно описать, но не назвать.                                              |
| `list_symbols`    | Публичные символы по виду, пакету или части имени.                                                                                         |
| `plan_form`       | Черновик `<dir>/form.intent.json` по спеке формы (markdown): поля, правила из таблиц спеки, шаги, массивы. Готовый файл не перезаписывает. |
| `form_build`      | Модуль формы на диске из одного файла `form.intent.json`: компиляция, проверка типов и запись файлов; агент правит только intent.          |
| `validate_form`   | Проверка до запуска: код (`kind: "code"`), JSON-схема, циклы поведения, весь набор и имена файлов модуля (`kind: "layout"`).               |
| `report_issue`    | Сохранить найденную проблему и её решение отдельным JSON-отчётом в `<корень проекта>/.reformer/issue_reports`.                             |

Форма создаётся одним путём: грамматика `form_build {"grammar":"base"}` → свой
`<dir>/form.intent.json` (или черновик `plan_form` по спеке) → `form_build {"dir": …}`. Прежний
`generate_form` и псевдонимы `validate_json_schema`, `check_behaviors` удалены в 7.0.

[ИИ-ассистент билдера](/docs/builder/assistant) ходит в тот же сервис по тому же ключу: справку и
сборку формы по описанию он берёт у сервиса, а форму правит в редакторе. Подробно о каждом
инструменте — в [Инструментах](./tools).

## Пакеты

| Пакет                   | Лицензия | Для чего                                                                                                                                           |
| ----------------------- | -------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| `@reformer/mcp`         | MIT      | клиент сервиса для IDE, бинарь `reformer-mcp`: файлы формы, проверка типов, спецификация и отчёты — локально, остальное — в сервисе                |
| `@reformer/form-intent` | MIT      | контракт `FormIntent` для своих инструментов: типы, нормализация, печать правил валидации и поведения в код, типы документа раскладки, `findCycle` |

Компилятор `FormIntent` (разбор ответа модели, вердикт `form_build`, сборка модуля) — часть
сервиса, отдельным пакетом он не публикуется.

## Промпты (prompts)

Только в наборе `REFORMER_SURFACE=tools`: все промпты ведут через `form_build`.

- `start-here` — точка входа: канонический workflow единого контракта и карта, каким промптом,
  инструментом или ресурсом пользоваться на каждом шаге.
- `add-feature` — добавить в форму, собранную `form_build`, одну возможность: `feature` =
  `validation` | `behavior` | `array` | `wizard`.
- `to-renderer` — сменить способ отрисовки: `FormRenderer` по той же TS-схеме (`renderer-react`)
  или схема документом JSON формата 2 + реестр (`renderer-json`); модель, правила, поведение и
  вызов `createForm` остаются.
- `review` — кросс-пакетный чек-лист код-ревью.

Промпты доходят не до каждого клиента: у некоторых агентов `prompts/list` недоступен. Поэтому то же
содержание есть в инструментах (`get_context`, `plan_form`, `form_build` с `grammar`) и в ресурсе
`reformer://guide`. Разбор спецификации и создание формы по описанию — инструменты `plan_form` и
`form_build` или `reformer.formStart` в поверхности по умолчанию.

## Ресурсы (resources)

Только в наборе `REFORMER_SURFACE=tools`.

- `reformer://guide` — самодокументация сервера: workflow, раскладка файлов формы, какой
  инструмент и ресурс брать на каждом шаге.
- `reformer://catalog` — JSON-карта пакетов и их разделов (slug + заголовок) — откуда брать URI
  разделов.
- `reformer://status` — что клиент нашёл в проекте: пакеты `@reformer/*`, доступна ли проверка
  типов. Читать, когда инструмент жалуется на окружение.
- `reformer://docs/<pkg>` — документация одного пакета целиком, например `reformer://docs/cdk`.
  `<pkg>` — имя без префикса `@reformer/`: `core`, `cdk`, `ui-kit`, `renderer-react`,
  `renderer-json`, …
- `reformer://docs/<pkg>/<section>` — отдельный раздел по slug'у (список — в `reformer://catalog`).

> Списка символов и сигнатур в ресурсах нет — используй `list_symbols` / `get_symbol_docs`; для
> рецептов по сценарию — `find_recipe`, для поиска по словам — `search_docs`.
