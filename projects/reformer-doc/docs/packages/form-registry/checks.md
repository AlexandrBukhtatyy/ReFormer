# Проверки

Форма из реестра собирается из частей разного происхождения: схема могла прийти с сервера новее
кода, реестр компонентов — от другого микрофронтенда. Большинство таких расхождений ничем себя не
выдают: форма рисуется, а часть полей не проверяется. Реестр форм ищет их до сборки — это
проверки перед сборкой (preflight). Отдельно он умеет находить вторую копию библиотеки на странице.

## Когда это нужно

- Схема выкладывается отдельно от кода, и они могут разойтись.
- Шаги мастера, селекторы и пути модели правят разные люди в разных файлах.
- На странице несколько независимо собранных бандлов.

## Проверки перед сборкой

Загрузчик запускает их сам — для каждой формы, после загрузки частей и перевода документа в формат 2.
Проверяется документ вместе с частями (`parts`) против **составного** реестра: базового реестра
хозяина с наложенным реестром записи.

| Код                          | Что ловит                                                                           | Уровень |
| ---------------------------- | ----------------------------------------------------------------------------------- | ------- |
| `schema-version-drift`       | `version` схемы вне диапазона `compatibleSchema` записи: схему выложили раньше кода | error   |
| `schema-identity-mismatch`   | `id` схемы не равен `id` записи: пришла чужая схема                                 | error   |
| `missing-components`         | `$component(...)` нет в реестре                                                     | error   |
| `missing-data-sources`       | `$dataSource(...)` нет в реестре                                                    | error   |
| `missing-fns`                | `$fn(...)` нет в реестре                                                            | error   |
| `missing-parts`              | `$part(...)` не объявлена в `parts`                                                 | error   |
| `unknown-step-selectors`     | `id` шага в `flow.steps` не совпадает ни с одним `selector` документа               | error   |
| `unmaterialized-model-paths` | пути `$model(...)` документа, которых нет в начальных значениях                     | warn    |

- Проверка версии работает, только если у записи есть `compatibleSchema`, а у схемы — `version`.
  Диапазоны: `1.2.3`, `^1.2.0`, `1.x`, `>=1.0.0`, `*`.
- Проверка `id` работает, только если у схемы есть `id`.
- Пути модели проверяются, только если у записи есть `initial`. Пути внутри шаблонов строк массива
  не проверяются: они считаются от строки, а массив на старте обычно пуст. Пути внутри частей
  достраиваются от группы, к которой часть подключена.

Последняя проверка — самая коварная. Поля, которого нет в начальных значениях, нет и в модели. Правила
и поведение к нему не привяжутся, замечания молча пропадут — снаружи это выглядит как «валидация не
работает».

### Режимы

Режим задаёт `options.preflight` провайдера (или параметр `loadForm`):

| Режим   | Что происходит                                                                                                                |
| ------- | ----------------------------------------------------------------------------------------------------------------------------- |
| `error` | по умолчанию: при ошибках форма не собирается — `loadForm` бросает `FormPreflightError`, место показывает `loadErrorFallback` |
| `warn`  | форма собирается, проблемы уходят в `onDiagnostic`                                                                            |
| `off`   | проверки не запускаются                                                                                                       |

```tsx
<FormRegistryProvider
  registry={getFormRegistry()}
  baseRegistry={appComponents}
  context={context}
  options={{
    preflight: 'error',
    onDiagnostic: (d) => telemetry.warn(d.code, d.message, d.entry),
  }}
>
  <App />
</FormRegistryProvider>
```

Каждое сообщение называет все промахи сразу и перечисляет известные имена — например, доступные
селекторы для `unknown-step-selectors`. Результат проверок без React — в `loaded.preflight` у
`loadForm`.

## Проверка схемы мета-схемой

Проверки перед сборкой смотрят на имена и связи. Структуру документа проверяет мета-схема — вход
`@reformer/form-registry/manifest`:

```ts
import { assertSchemaValid, validateSchemaCached } from '@reformer/form-registry/manifest';

const { valid, errors } = validateSchemaCached(schema, { registry });
assertSchemaValid('mfe-orders/checkout@1.0.0', schema, { registry }); // бросает SchemaInvalidError
```

- Результат кэшируется по паре «схема + реестр», поэтому повторная проверка того же объекта ничего не
  стоит. Обычный `validateFormSchema` компилирует мета-схему на каждый вызов.
- Вход тянет ajv. Схемы из бандла выгоднее проверить в тестах, а в рабочей сборке проверять только
  схемы из сети: только они могут разойтись с кодом после выкладки.

Что именно проверяет мета-схема — на странице [Проверка документа](../renderer-json/document-check.md).

## Вторая копия библиотеки

Если два бандла на странице принесли по своей копии `@reformer/core` или `@preact/signals-core`,
форма ломается без единой ошибки: связи полей (`enableWhen`) перестают срабатывать, вычисляемые поля
затираются, реактивность между копиями пропадает. Тесты этого не ловят — там копия одна.

Вход `@reformer/form-registry/guard` находит дубли. Каждый бандл при загрузке ставит отметки:

```ts title="в каждом микрофронтенде"
import { CORE_RUNTIME_TOKEN } from '@reformer/core';
import { Signal } from '@reformer/core/signals';
import { stampRuntime } from '@reformer/form-registry/guard';

stampRuntime('@reformer/core', CORE_RUNTIME_TOKEN);
stampRuntime('@preact/signals-core', Signal);
```

Хозяин после загрузки всех микрофронтендов спрашивает результат:

```ts title="в хозяине"
import { reportRuntime } from '@reformer/form-registry/guard';

const { ok, duplicates, observed } = reportRuntime((d) => telemetry.error(d.message));
```

- Отметка — объект или функция, а не строка версии: две копии одной версии ломают форму так же, как
  копии разных. Подходят `CORE_RUNTIME_TOKEN`, класс `Signal`, `React.createContext`.
- Видны только копии, которые поставили отметку. Пустой `observed` значит «проверку не подключили», а
  не «дублей нет».
- По умолчанию дубль только сообщается. `setRuntimeStrict(true)` заставляет вторую отметку бросать
  исключение — удобно в CI и на стенде. `checkRuntime()` возвращает тот же результат без сообщений.

## Подводные камни

- **«Валидация не работает» на одном поле** — поля нет в начальных значениях. Включите `initial` в
  записи и посмотрите `unmaterialized-model-paths`.
- **Шаг мастера перестал проверяться** — шаг переименовали в документе, а в `flow.steps` остался
  прежний `id`. Ловится как `unknown-step-selectors`.
- **Форма собралась, но пишет не те поля** — пришла чужая схема. Задайте `id` в документе — его
  сверит `schema-identity-mismatch`.
- **`Component "…" not found in registry`** у сетевой схемы — схема ушла вперёд кода. Задайте
  `compatibleSchema` и держите `preflight: 'error'`.
