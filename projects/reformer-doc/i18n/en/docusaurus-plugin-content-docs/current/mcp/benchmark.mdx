# Measurements: with MCP and without

The `@reformer/*` packages ship with their documentation — `llms.txt`, `docs/llms`, types. Why an
MCP server then? To answer with numbers, the same agent — Claude Sonnet in Claude Code — solved the
same form tasks under two conditions:

- **No MCP** — file tools only and the installed packages with their documentation;
- **With MCP** — the same plus the `@reformer/mcp` server connected as is, with no settings: the
  agent builds the form with the server's form builder.

The same verifier checks every run: the build and types first, then the behavior of the form —
values, rules, reactions, wizard steps. The conditions are in [How it was measured](#how-it-was-measured).

Every chart has its own switches — the **model** (one, Sonnet and Opus together, or all) and the
**arm** (no MCP, with MCP, or both) — and they change only that chart; the scenario cards switch
above their tabs. The text describes the Claude Sonnet measurement — it has both arms and all ten
scenarios. Claude Opus ran the same full matrix; compare the two with the “Sonnet and Opus” option.
So far Qwen2.5-Coder 14B (LM Studio) has run the three registration scenarios in both arms, three
repeats each; Gemma 4 26B (Ollama) — only the arm with MCP on registration, one repeat each. Full
measurements of both local models are under way. Their cost is not counted, and a run is capped at
25 minutes. With several models the summaries and the spread use only the scenario × stack cells
every one of them ran; hover a model to fade the others.

## Summary

<McpSummary />

- **Creating a form is the main difference.** Without the server the agent writes the module by
  hand from the package docs and more often goes wrong in the file layout, the build and the types;
  on a large form from a spec that is about four minutes and over a dollar per run. With MCP the
  server does the plan, the build and the type check.
- **Editing and removing** in a ready form pass in both arms almost without failures, but with
  MCP it is faster and cheaper.
- **A stronger model does not replace the server.** Claude Opus passed 72 runs of 90 without MCP
  and 89 of 90 with it. Sonnet with MCP passed 87 of 90 for $10.99 — almost nine times cheaper than
  Opus without the server ($97.51). In every arm Opus costs 2–2.5 times as much as Sonnet.
- **The server carries a weak local model.** On registration Qwen2.5-Coder 14B passed 24 runs of
  27 with MCP and none of 25 without the server: the model writes a couple of files outside the
  module layout and stops.

Without the server 21 runs of 90 took longer than two minutes: 18 of them create a form, and half
of those eighteen failed the checks; three more turn a one-page form into a wizard. With MCP one
run took longer than two minutes — creating the wizard, 2.3 minutes, and it failed the checks. All
twenty most expensive runs of the measurement are without MCP.

Run time and cost grow together, so on one chart the arms spread along the diagonal: runs with MCP
sit in the lower left corner, runs without MCP stretch up and to the right. The median cost of
creating a form is $1.41 without MCP and $0.23 with it; on edits and removals the clouds are closer.

## How it was measured

- **Agent** — Claude Code in non-interactive mode, model `sonnet`, `opus` in the second
  measurement. Tools — file tools only (`Read`, `Write`, `Edit`, `Glob`, `Grep`) inside the working
  directory, no shell. The MCP server is
  connected only in the arm with MCP — in its default surface (`code-guided-dsl`); the harness
  checks this at the start of every run.
- **The working directory** is the same in every arm: the installed `@reformer/*` packages — exactly
  what is published to npm (the build with types, README, `llms.txt`, `docs/llms`); `spec.md` for
  the spec scenarios; a ready form for edits and removals.
- **The task** is the same in every arm: the task text, the delivery rules and the module layout —
  which parts of `createForm` go into which files. Without the layout the behavior check would not
  find a form written without the server.
- **Limits** per run are the same in every arm and set by the scenario: money, steps, time.
- **Local models** work in the harness loop: file tools `read_file`, `write_file`, `list_files`
  inside the working directory, plus the server tools in the arm with MCP. A run's time is the
  scenario limit adjusted for a slow model, but no more than 25 minutes: a model stuck in an edit
  loop would go on for up to 100 minutes a run. The cap does not touch the Claude models: the
  longest Sonnet run took 5.3 minutes, the longest Opus run 8 minutes.
- **The check** — static (types, stack, file layout) and behavioral: probes from the scenario
  contract fill the form and compare values, rule errors, reactions and wizard steps. A run
  **passes** when every required check passes; the **score** is the share of passed checks.
- **Order** — one run at a time, no parallelism; every “scenario × stack” cell goes through both
  arms back to back, so API speed changes over the hours of the measurement fall on both arms
  almost alike.
- **Cost and tokens** — from the Claude Code report of the run; it is an estimate at API prices.
  Input tokens include cache reads and writes.

Limitations: the full matrix so far only for Claude Sonnet and Claude Opus; edits and removals
start from a form the server built — this helps the arm without MCP, as the layout is already in
front of it.
