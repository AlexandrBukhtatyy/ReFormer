# DOM-контракт кросс-фреймворк проверки

Одна форма ReFormer рисуется в React, Vue и Angular — каждый раз настоящей библиотекой компонентов
своего стека. Сценарии не знают ни фреймворка, ни библиотеки: они находят элементы по
`data-testid` и читают состояние страницы из `window.__bench`. Этот документ — правила, по которым
хост стека размечает страницу, чтобы общие сценарии прошли на нём без правок.

Основа — DOM-контракт бенчмарка форм:
[BENCH-CONTRACT.md §4](../forms-benchmark/BENCH-CONTRACT.md#4-dom-контракт). Роли testid, пути
полей через дефис и состав `window.__bench` — оттуда. Ниже — только то, что добавляет работа с
библиотеками компонентов.

## Страница

- Адрес — `/cross/<форма>/` на сервере хоста; порты стеков — в [stacks.ts](stacks.ts).

  | Стек    | Хост                              | Библиотека компонентов | Драйвер списка                   |
  | ------- | --------------------------------- | ---------------------- | -------------------------------- |
  | React   | `react-playground`, Vite          | `@reformer/ui-kit`     | нативный                         |
  | Vue     | `vue-playground`, Vite            | Vuetify                | [vuetify.ts](drivers/vuetify.ts) |
  | Angular | `angular-playground`, Angular CLI | Taiga UI               | [taiga.ts](drivers/taiga.ts)     |

- Хост Angular ставит `window.__bench` позже события `load`: страница — отдельный чанк, а приложение
  стартует асинхронно. Поэтому POM, открыв страницу, сначала ждёт появления харнесса. Пакет
  рендерера Angular хост берёт из его `dist/` — перед запуском пакет должен быть собран.
- `window.__bench` ставит общий харнесс (`forms-benchmark/src/cross/page.ts`, `installBench`):
  хост передаёт ему только свои `mount` и `unmount`. Готовность первого экрана, покой, вызовы API
  и отправленные данные у трёх стеков считает один и тот же код.
- Заголовок первого уровня на странице один: сценарии снимают фокус с поля кликом по нему.
- Анимации библиотеки выключены: сценарий читает DOM сразу после покоя страницы.

## testid

| testid                             | Правило                                                         |
| ---------------------------------- | --------------------------------------------------------------- |
| `field-{path}`                     | корень поля — вместе с подписью и ошибкой                       |
| `label-{path}`                     | подпись поля                                                    |
| `input-{path}`                     | **нативный элемент** там, где он у виджета есть                 |
| `error-{path}`                     | элемент с текстом ошибки; пока ошибки нет, элемента нет в DOM   |
| `input-{path}-{value}`             | радиокнопка опции `value` — нативный элемент                    |
| `option-{path}-{value}`            | пункт открытой панели списка; пустой пункт — `option-{path}-`   |
| `computed-{path}`                  | вычисляемое значение, контрола у него нет                       |
| `captcha-image`, `captcha-refresh` | картинка и кнопка обновления капчи                              |
| `step-current`                     | заголовок текущего шага; номер шага — в `data-step`             |
| `btn-prev`, `btn-next`             | переходы визарда; `btn-prev` есть и на первом шаге — выключена  |
| `btn-add-{path}`                   | добавить строку массива `path`                                  |
| `btn-remove-{path}-{index}`        | удалить строку `index`; по этим кнопкам считаются строки        |
| `btn-submit`, `btn-reset`          | отправка и очистка; `btn-submit` визарда — только на последнем  |
| `submit-result`                    | подтверждение отправки; до успешной отправки элемента нет в DOM |

`input-{path}` на нативном элементе — главное правило. Библиотеки оборачивают `<input>` в свою
разметку, а `data-testid`, переданный компоненту, оставляют на его корне. Кит стека обязан донести
атрибут до внутреннего элемента: тогда `fill`, `pressSequentially`, `check`, `toHaveValue`,
`toBeChecked` работают в сценариях одинаково на всех стеках.

Элемент с ролью вместо нативного допустим, если Playwright ведёт его так же: флажок с
`role="checkbox"` и `aria-checked` отмечается через `check()` и читается через `toBeChecked()`.
Готовность экрана харнесс определяет тем же способом: `checked` нативного элемента либо
`aria-checked`.

`error-{path}` отсутствует в DOM без ошибки — сценарии собирают показанные ошибки запросом
`[data-testid^="error-"]`. Библиотека, которая держит пустой контейнер ошибки или оставляет
уходящее сообщение до конца анимации, нарушает правило: кит рисует элемент под условием.

`btn-next` — кнопка `type="button"`, `btn-submit` — `type="submit"`, и это разные элементы: кнопка,
которая меняет тип на последнем шаге, посреди клика по «Далее» отправила бы форму.

## Список

Список библиотеки компонентов — не `<select>`: в поле ввода стоит подпись выбранного пункта, а
пункты — всплывающая панель, которой нет в DOM, пока она закрыта. `selectOption` и `toHaveValue`
на таком списке не работают, поэтому сценарий ведёт список через **драйвер стека**
([drivers](drivers/index.ts)): выбрать значение, прочитать выбранное, перечислить пункты.

- Драйвер по умолчанию — нативный (`forms-benchmark-e2e/pom/control-driver.ts`): `<select>` и его
  `<option>`. Через него идёт стек, у которого список нативный.
- Драйвер библиотеки открывает панель, выбирает пункт `option-{path}-{value}` и ждёт, пока панель
  уйдёт из DOM. Значения списка он читает из пунктов открытой панели.
- Выбранное значение кит пишет в атрибут `data-value` на `input-{path}`. Его же читает харнесс,
  когда сверяет первый экран: у элемента с `data-value` значение — атрибут, а не `value`.
- Пустой пункт (`''`) стоит первым, как у нативного `<select>`: сценарии ждут его в списке.

## Значения

Значение поля — одно на всех стеках: пустое текстовое поле хранит `''`, флажок — `boolean`, число —
`number`, пустое числовое поле — `null`, список без выбора — `''`. Отправленные данные сравниваются
с эталоном целиком, поэтому адаптер контрола не подменяет пустую строку на `null` и не приводит
типы по-своему.

Число и дата — нативные `type="number"` и `type="date"` внутри поля библиотеки: поле с разделителями
разрядов или календарём показало бы другой текст, чем ждёт сценарий.

Поле «только чтение» — проп `readOnly`: его ставит поведение формы, имя одно на трёх стеках. Кит
доносит его до нативного элемента атрибутом `readonly`.

## Сценарии

Тела сценариев общие с conformance бенчмарка форм:
`forms-benchmark-e2e/scenarios/<форма>.ts` объявляет тесты для страницы, которую открывает
переданная функция. Conformance зовёт их по разу на каждую библиотеку форм, этот проект — по разу
на каждый стек (проект Playwright `<форма>:<стек>`).

```bash
npx playwright test                              # все стеки
npx playwright test --project=registration:react # одна форма на одном стеке
CROSS_STACKS=react npx playwright test           # сервер поднимается только для названных стеков
```
