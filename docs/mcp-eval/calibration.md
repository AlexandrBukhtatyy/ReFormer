# Калибровка `@reformer/mcp` по эталонным формам

> Замер 2026-10-27. Стенд — [packages/reformer-mcp/eval/calibration/](../../packages/reformer-mcp/eval/calibration/),
> запуск — `npm run mcp:calibrate` (с рантайм-проверкой — `npm run mcp:calibrate -- --e2e`).
> Метрики последнего прогона — [calibration-baseline.json](../../packages/reformer-mcp/eval/baselines/calibration-baseline.json).
> Задачи — эпик `ReFormer-j356` в bd.

## Зачем

[`mcp:evaluate`](README.md) меряет, отдаёт ли сервер нужное **знание**. Он не отвечает на вопрос,
**получится ли рабочая форма**, если агент пойдёт по пути, который сервер предлагает: спека →
`plan_form` → intent → `generate_form` → `validate_form`. Юнит-тесты пакета проверяют этот путь на
фикстурах, а с рабочими формами проекта его никто не сверял.

Калибровка сверяет. Эталоны — формы `projects/react-playground` с их e2e-наборами и наборы
кодогенерации ассистента конструктора. Цель — чтобы через сервер собирались и простые формы с
валидацией и поведением, и сложные многошаговые: визард, массивы, вычисляемые поля, условная
видимость.

## Два потребителя, два канала

| Канал                                                       | Кто пользуется                             | Как гоняется                                                                                 |
| ----------------------------------------------------------- | ------------------------------------------ | -------------------------------------------------------------------------------------------- |
| stdio `dist/index.js`, профиль `node`                       | внешние агенты (Claude Code и др.)         | MCP Inspector CLI 2.12.0                                                                     |
| бандл `.ui_builder/mcp/reformer/server.js`, профиль browser | ассистент конструктора через `mcp_call`    | тот же Inspector через переходник `worker-stdio.mjs`: бандл в `node:vm`, строка stdin ↔ кадр |
| `askReformer` / `validateCode` напрямую                     | `ask_reformer` и барьер записи кода модуля | импорт из `dist/core/…`, как в `mcp-reference.ts` ассистента                                 |

Inspector детерминирован, без модели в контуре. Аргументы длиннее предела командной строки
Windows идут тем же вызовом через SDK-клиент (`lib/client.mjs`).

## Эталоны

| Кейс           | Роль                           | Источник                                                                                                            |
| -------------- | ------------------------------ | ------------------------------------------------------------------------------------------------------------------- |
| `registration` | простая: валидация + поведение | `demo/registration-form-renderer-json` (8 полей, 19 правил, 2 асинхронных, `cross`, `onChange`)                     |
| `credit`       | сложная многошаговая           | спека `docs/specs/credit-application-form.md`, форма `demo/complex-multy-step-form` (6 шагов, ~75 полей, 3 массива) |
| `__golden__`   | код, который пишет ассистент   | 17 наборов `plugins/reformer/codegen/src/pipeline/__golden__/`                                                      |
| `insurance`    | holdout, **не подгоняется**    | `docs/specs/insurance-application-form.md`                                                                          |
| `loan`         | регрессия                      | `tests/fixtures/spec-loan-request.md`                                                                               |

У `registration` и `credit` есть `facts.json` (поля, шаги, массивы, правила, поведение — из кода
эталона) и `intent.json` — полная FormIntent эталона: ею проверяется выразительность
`generate_form` отдельно от разбора спеки. `operators.json` — 35 требований словами пользователя
→ ожидаемый оператор.

## Треки

- **Smoke** — протокол обоих каналов: `initialize`, `tools/list --strict`, ресурсы и шаблоны,
  промпты (только node), отказы на неверные аргументы (`isError`), паритет ответов каналов,
  отсутствие висящих процессов.
- **T1 спека → intent** (`plan_form`): полнота полей, шагов, массивов, правил по видам, условных
  правил, поведения — против `facts.json`.
- **T2 intent → бандл** (`generate_form`): кросс-проверка C1–C10, `tsc` бандла, `validate_form`
  `code`/`layout`; intent из `plan_form` и эталонная, три таргета.
- **T3 рантайм**: бандлы эталонных intent монтируются в playground
  (`src/pages/debug/mcp-calibration/`; папки форм — вывод стенда, в git не лежат), и по ним гоняются e2e эталонов: кредит — проекты `iter-*`
  с `MCP_ITER_VERSION=cal`, регистрация — свой спек с `REG_FORM_PATH`.
- **T4 подбор API**: `choose_api` по `operators.json` в обоих каналах, `askReformer` с бюджетом
  `ask_reformer`, `get_symbol_docs` по символам эталонов, рецепты.
- **T5 ложные срабатывания**: `validate_form kind=code` и `validateCode` по каждому файлу эталонов
  и `__golden__` — код рабочий, любая ошибка ложная; `kind=layout`, `kind=json-schema`.
- **T6 пригодность ответа**: есть ли главное в первых 1400 символах (`ANSWER_BUDGET` фасада
  `mcp_call`).

Сырые ответы и отчёт — `.tmp/mcp-calibration/<прогон>/` (`report.md`, `metrics.json`). Два
прогона подряд дают одинаковый `metrics.json`.

### Что осталось красным в T3 и почему

Кредит, renderer-react и renderer-json — 22 непройденных из 145, все объяснены:

- **15 — вычисляемые поля в сводке.** POM ищет `[data-testid="computed-<id>"]` — `<span>` в
  кастомных блоках `ConfirmationComponents.tsx` эталона. Сами значения считаются (`compute`
  в бандле есть), но FormIntent кастомный компонент не выражает (A18).
- **5 — слой приложения.** HP-002 и HP-003 рассчитывают на черновик, который эталон загружает
  из MSW при открытии (`loanPurpose` приходит с ним), HP-007-A/B — на загрузку заявки по
  `applicationId`, HP-006-A — на обработку ошибки отправки. Это A22, вне формы.
- **2 — пропущены самим спеком** (`test.skip`).

Без них: **123 из 123**. У core ещё 16 — все про видимость: генератор по контракту не печатает
`hideWhen` для core (разметку рисует консумент, условия — в JSX), а стенд рисует core тем же
`FormRenderer`. Это ожидаемо.

Регистрация, 7 из 12 красные — все про приложение вокруг формы: префилл через `AsyncBoundary` (3),
сброс к префиллу и статус после отправки (2 — без префилла пусты `username`, `email`, `fullName`,
`phone`), заголовки и колонки страницы (1), `PendingButton` (1). Валидация, `async`-проверки,
`cross` и `onChange` проходят.

### Объяснённое расхождение каналов

S17.4 (`find_recipe wizard`): текст ответов совпадает до символа, отличается место заголовка
первой секции. Рецепт воркера восстанавливается из `llms.txt`, где граница между вводным текстом
файла и его первой секцией не хранится. Smoke считает такое расхождение `info`, а не `fail`.

## Что поправлено в сервере

Задачи — дочерние `ReFormer-j356.4`. Каждая правка с юнит-тестом; полный набор пакета — 405
тестов.

- **Генератор (`generate_form`).** Словарь текстов `form.messages.ts` и `ValidationMessagesProvider`;
  `data-sources.ts` со значениями справочников; пропсы `FieldArray`; вложенная группа в строке
  массива; тип даты по компоненту; `form`/`schema` в области поведения; `onChange` без лишнего
  `(value)`; `async (value, { signal })` для загрузки; условие `copyFrom` через `expr`;
  транслитерация имён (`ZayavkaNaKreditForm`).
- **Разбор спеки (`plan_form`).** «Условное (при …)» — `required()` под условием; маска →
  проп `mask` и `pattern`; `pattern` с запятыми; условие по короткому имени → путь и литерал
  типа; варианты одного шага — секции одного шага; таблица зависимостей (очистка массивов,
  копирование по флагу, сброс полей, остальное — предупреждением с оператором); подсказка
  оператора у неразобранного правила; предупреждения — до JSON и сгруппированно.
- **Подбор API (`choose_api`).** Кириллица в признаках (`\w`, `\b` в JS — только латиница);
  правила для валидации, визарда, справочников, текстов ошибок, пропсов от других полей;
  релевантные антипаттерны.
- **Проверка кода (`validate_form`).** Операторы внутри функций-помощников; пакеты вне корпуса —
  в ограничениях, а не RF002; глубокие подпути и реэкспорты сторонних пакетов в индексе символов
  (в том числе через импорт); незнакомый проп компонента и шаг в отдельном файле JSON-схемы —
  предупреждения, а не ошибки.
- **Протокол.** `isError` на неверные аргументы всех инструментов; обязательные аргументы
  промптов (`InvalidParams`); `resources/templates/list`; тип у `validate_form.schema`;
  рецепты в профиле браузера.

Отступление от плана: правка генератора индекса `scripts/generate-llms-txt/index.js` (подпути,
реэкспорты) и перегенерация `llms.txt`/`llms-index.json` пакетов — без неё T5 не сходился.

## Что поправлено в стенде

- `onChange` в facts описан по записываемому полю, а в intent `target` — наблюдаемое поле:
  счётчик T1 берёт записываемые пути из выражения.
- T2 проверяет раскладку с файлами, которые манифест велит создать самому (`index.tsx`,
  `types.ts`, `api.ts`), — иначе RF012 был всегда.
- Паритет каналов отличает расхождение текста от расхождения разметки заголовков.

## Что осталось открытым

- `ReFormer-j356.4.21` — невыразимое в FormIntent: `when` у `compute`, поведение на группу
  (`apply`), `enableWhen` на группу, `severity: 'warning'`, параметры замечаний, кастомные
  компоненты (полный список — `cases/credit/notes.md`, раздел (a)).
- `ReFormer-j356.4.29` — `@reformer/form-registry` вне корпуса MCP (`FormEntry` без документации).
- T1 credit, правила 103/191: часть правил эталона спека не формулирует вовсе (длины и шаблоны
  ФИО, коды подразделений), это потолок разбора, а не пропуск; группа `residenceAddress.*`
  («аналогичная структура») и флаг `sameEmail`, не объявленный полем, уходят в предупреждения.
