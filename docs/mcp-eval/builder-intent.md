# Ассистент билдера: форма одним intent — `build_form`

> Эпик ReFormer-qsm8 (задачи `.15`, `.16`), план — [mcp-misty-graham.md](../plans/mcp-misty-graham.md),
> этап 2. Инструмент — [ai/src/tools/build-form/](../../projects/reformer-builder-playground/.ui_builder/plugins/reformer/ai/src/tools/build-form/index.ts),
> стенды — [assistant-scenarios-eval.test.ts](../../projects/reformer-builder-playground/.ui_builder/plugins/reformer/integration/assistant-scenarios-eval.test.ts)
> и [assistant-ab-eval.test.ts](../../projects/reformer-builder-playground/.ui_builder/plugins/reformer/integration/assistant-ab-eval.test.ts).

## Зачем

Внешним агентам `form_build` удешевил форму втрое: агент пишет FormIntent, сервер компилирует его
в модуль и отвечает диагностикой ([scenarios.md](scenarios.md)). Ассистенту билдера этот выигрыш
не достался. Он правил документ формы мелкими вызовами `insert_node`, `set_form_rules` и ещё
тринадцатью инструментами, и большую спеку не довёл ни один режим: на кредитной форме из 82 полей
— 0–23 поля при 150–520 тыс. входных токенов ([builder-files-mode.md](builder-files-mode.md)).

Воркер MCP в билдере форму собрать не может: его инструменты только читают, а файлов проекта он не
видит. Поэтому инструмент живёт в самом ассистенте и вызывает ядро MCP у себя в процессе, через
точку входа `@reformer/mcp/intent`.

## Как устроен

`build_form { intent?, parent?, index? }` — форма, шаг или блок одним FormIntent: поля, массивы,
шаги, правила, видимость, источники данных. Модель получает только диагностику.

- **Без `intent`** — грамматика с именами компонентов активного кита. На пустой форме она сразу
  приходит в затравке хода, и вызов без intent не нужен.
- **Сборка — не второй механизм правки.** Intent читает и раскладывает MCP (`readIntent`,
  `buildSchemaLayout`), план переводит имена в имена кита (визард, шаг, массив). Узлы ставит
  `insert_node` той же фабрикой каталога, правила — `set_form_rules`, видимость —
  `set_render_rules`. Отказ любого шага отменяет всё, ход получает одну запись для отмены.
- **Куда:** без `parent` — вся форма, только если она была пустой на начало хода (повторный вызов
  пересобирает её). С `parent` — в шаг или секцию; `parent` = визард — новые шаги.
- **Форма из двух и больше шагов — по шагам** (решение пользователя 2026-11-03): первый вызов — одни
  шаги, затем по вызову на шаг в адрес из ответа. Intent с несколькими шагами и полями сразу
  отклоняется, и отказ называет первый вызов. Один шаг с полями собирается сразу, в том числе в
  готовый визард.
- **Записи локальной модели** приводит к грамматике `lift.ts` до чтения intent. Модель часто
  описывает поле прямо в шаге или узле разметки, ключом `model` вместо `name`, массив — полем
  `type: "array"`, шаг — одним объектом, а тип `textarea` подставляет вместо компонента. Раньше
  такие поля пропадали молча.

`build_form` включён по умолчанию; `buildForm: false` у стека — набор без него, на нём снята база.
Поверхность инструментов выросла на 604 символа (`TOOL_SURFACE_BUDGET` 13050 → 13654): 515 — сам
`build_form` (intent — объект или JSON-строка), 89 — описание `expr` у связи `set_form_rules`.
Промпт с ним — 4100 символов против 4181 без него, потолок 4200.

## Методика

- **Сценарии** — 25 из [builder-form-scenarios.md](builder-form-scenarios.md) плюс три крупных,
  которые считают собранные поля и правила:
  - B.1 — средняя спека: 25 полей, 3 шага, 9 правил;
  - B.2 — шаг целиком в готовый мастер;
  - B.3 — два блока адреса с условным копированием.
- **Форма на 82 поля** — кредитная заявка `docs/specs/credit-application-form.md`, мера — ключи
  колонки «Ключ в форме» среди путей `$model(...)`. Ключи строк массивов (`properties[].type`, 15
  из 82) прежний счётчик не видел ни в одном плече: в шаблоне строки путь пишется от строки.
  Отдельный счётчик `coverage.rows` добавлен во втором раунде.
- **Модель** — `qwen3.8:27b-32k` через Ollama. Облачное плечо не снималось: ключа API нет.
- **База** — тот же код с `buildForm: false` (`EVAL_BUILD_FORM=0`): промпт, затравка и набор
  инструментов побайтно прежние.

Часть выигрыша полного набора дали сценарии без `build_form`: 10.2 (868 → 117 с) и 22.1
(826 → 246 с). Это разброс модели или новый промпт; без них создание — 37% времени базы, а не 31%.

**По критериям:**

- **B.1** — то же покрытие, медиана 64% базы: проходит.
- **Отказы** — 31% на первой версии, 8–13% после правок `lift.ts`: проходит.
- **Точечные правки** — ни одна не потеряна и не позвала `build_form`: проходит.
- **Форма на 82 поля** — 73–74% ключей (60 из 67 без строк массивов): проходит.
- **Молчание дольше 5 минут — сработал.** Форма на 82 поля: 32 минуты рассуждения (37 тыс.
  символов) до первого вызова, сам intent — ещё 16 минут. Совет промпта собирать мастер по шагам
  модель не выполнила. Отсюда сборка по шагам, обязательная для формы из нескольких шагов.
- **Облако** — не снято.

## Третий раунд — мастер по шагам, `build_form` по умолчанию

Тот же стенд на коде, где форма из нескольких шагов собирается по шагам. Время первых сценариев
(1.1, 1.3, 3.6) искажено: параллельно шёл прогон e2e.

| Сценарий               | Одним вызовом (раунды 1–2)                                   | По шагам (раунд 3)                                    | База                           |
| ---------------------- | ------------------------------------------------------------ | ----------------------------------------------------- | ------------------------------ |
| 5.4, мастер из 3 шагов | 84–122 с, 3–5 запросов, вход 12–24 тыс.                      | 82 с, 4 запроса, вход 18 тыс.                         | 141–210 с                      |
| B.1, 25 полей          | 333–450 с, 3 запроса, вход 13 тыс.                           | 258 с, 10 запросов, вход 69 тыс.                      | медиана 527 с, вход 49–54 тыс. |
| Форма на 82 поля       | 3058–3723 с, 60–61/82, строк массивов 0/15, вход 66–125 тыс. | 2281 с, 61/82 и строк 15/15 — 76 из 82, вход 139 тыс. | 3353 с, 23/82, вход 524 тыс.   |

- **Форма на 82 поля — лучший итог всех прогонов.** Собраны все три массива со строками, ход
  завершён, время — 68% базы. До первого вызова модель рассуждала 18 минут против 32 (рассуждение
  идёт в ленту с первой минуты), самый долгий вызов шага — 10 минут.
- **Цена — входные токены.** Каждый шаг — отдельный запрос, и он снова несёт затравку с
  грамматикой: на B.1 вход вырос с 13 до 69 тыс. и превысил базу. Для локальной модели решает
  время, для облачной это прямая цена. Если облачное плечо покажет то же, порог разбиения по числу
  полей вернёт короткий путь средним мастерам.
- **Полный набор — 23/25, время 70% базы.** Провалы — в ходах без `build_form`: 10.2 (модель сама
  добавила заголовки и удалила подключение части) и B.3 (модель пошла мимо `build_form` и потеряла
  копирование — ReFormer-qsm8.19, исправлено после раунда). Сценарии 10.2 и 22.1 в этом раунде шли
  414 и 1146 с против 117 и 246 во втором — разброс модели на перестройке формы. Без них создание —
  52% времени базы.
- **Отказы `build_form` — 3 из 19.** Правило в списке полей и поля без шага в визард (оба исправлены
  после раунда) и законный отказ гейта: у `InputNumber` нет `disabled`.

**Перепроверка провалов** на коде с этими правками и описанием `expr`: B.3, 10.2, B.2 и 21.4 по два
прогона — 8/8. B.3 оба раза с копированием адреса, B.2 оба раза одним вызовом за 2 запроса. Остались
два отказа, оба исправлены следом: поле в разметке голым именем `{ "name": "sameAddress" }` и
intent JSON-строкой (его отклоняла проверка аргументов). 10.2 шёл 463 и 1193 с — перестройка формы
без `build_form`, разброс модели.

## Что нашлось по дороге

- **Старый дефект билдера, ReFormer-qsm8.17.** Связь «копировать, когда…» печаталась, но не читалась
  обратно из кода. Сторож записи отклонял файл поведения, и вместе с ним молча пропадали все файлы
  правил формы. Ход сообщал об успехе — и через `set_form_rules` тоже.
- **ReFormer-gxv6 (MCP).** Поле `type: "array"` с `itemFields` читается полем `FieldArray`, строки
  теряются без отказа. Касается и `form_build`. В билдере обойдено в `lift.ts`.
- **ReFormer-qsm8.18.** Отказ генерации правил не доходит до хода: ход сообщает об успехе.
- **ReFormer-qsm8.19, исправлено.** У `expr` связи в `set_form_rules` не было описания. Модель
  искала `when` у `copyFrom` и теряла условное копирование: B.3 мимо `build_form` — 0 из 3.
- **Лишнее поле.** В 21.4 на «добавь поле телефона» модель добавила и «Дополнительный телефон».
  Проверка сценария лишнее поле не ловит.

## Ограничения

- Одна модель, локальная. На облачной не проверялось.
- По одному-три прогона на сценарий. Разброс модели велик: тот же 22.1 шёл от 246 до 1146 с.
- Проверки сценариев грубые: «поле есть», «правило есть». Лишние поля и смысл правил они не видят.

## Как повторить

Из `projects/reformer-builder-playground/.ui_builder/plugins/reformer/integration`:

```bash
# с build_form (по умолчанию) и база без него
EVAL_MODEL=qwen3.8:27b-32k npx vitest run assistant-scenarios-eval.test.ts
EVAL_MODEL=qwen3.8:27b-32k EVAL_BUILD_FORM=0 npx vitest run assistant-scenarios-eval.test.ts

# форма на 82 поля
EVAL_MODEL=qwen3.8:27b-32k EVAL_MODES=structured EVAL_SCENARIOS=spec EVAL_PAGES=0 \
  EVAL_SPEC=../../../../../../docs/specs/credit-application-form.md \
  npx vitest run assistant-ab-eval.test.ts
```

`EVAL_ONLY=B.1,B.2` — только эти сценарии, `EVAL_DUMP=<каталог>` — тела запросов и ответы модели
файлами: по ним видно, с каким intent пришёл отклонённый вызов. Облако — `EVAL_KIND`,
`EVAL_API_KEY`, `EVAL_BASE_URL`. Записи для `mcp:compare` — `npm run mcp:import-builder`.
