# Ассистент билдера: новая форма по описанию — куда идёт ход и что в неё попадает

> Задача ReFormer-9a9c, план [elegant-gliding-platypus](../plans/elegant-gliding-platypus.md).
> Харнесс —
> [assistant-scenarios-eval.test.ts](../../projects/reformer-builder-playground/.ui_builder/plugins/reformer/integration/assistant-scenarios-eval.test.ts),
> сценарии N.1–N.4.

## Зачем

Жалоба пользователя: разные описания форм дают похожую форму, к которой потом что-то дописывается.
Захардкоженной формы в коде нет. Есть две причины.

1. **Ход идёт в открытую форму.**
   - Мост выбирает форму хода по вкладке, а не по тексту запроса.
   - После `create_form` новая форма открыта на переднем плане, поэтому следующий запрос «сделай
     форму X» правит предыдущую.
   - Промпт правки о новой форме молчит, а отказ `build_form` на непустой форме советует дописать
     её в шаг или секцию.
2. **Образец грамматики `build_form` копируется.** Затравка каждой пустой формы несёт
   `BUILD_FORM_EXAMPLE`: email, kind, inn, sameEmail/billingEmail, price/qty/total, массив children,
   секция Passport. Нигде не сказано, что это только синтаксис.

Прежний замер ([builder-form-scenarios.md](builder-form-scenarios.md),
[builder-intent.md](builder-intent.md)) этого не видел, по трём причинам:

- стартовая анкета `CLIENT` и B.1 говорят на словаре образца (email, kind, inn, price, qty, total,
  billingEmail);
- сценария «новая форма, когда открыта другая» не было;
- проверки «полей не меньше N» не замечают лишних полей.

## Что добавлено в стенд

- **Сценарии N.** Предметы не пересекаются со словарём образца, ключи полей названы в запросе:

  | №   | Старт           | Запрос                                        | Засчитан, если                                                  |
  | --- | --------------- | --------------------------------------------- | --------------------------------------------------------------- |
  | N.1 | анкета `CLIENT` | новая форма записи к ветеринару, 5 полей      | создана одна форма, анкета не изменилась, в новой ровно 5 полей |
  | N.2 | анкета `CLIENT` | анкета отзыва о ресторане, 4 поля («Нужна …») | то же для 4 полей                                               |
  | N.3 | формы нет       | запрос N.1                                    | создана форма, ровно 5 заказанных полей                         |
  | N.4 | пустая форма    | запрос N.2                                    | форма не создана, в пустую легли ровно 4 поля                   |

- **Метрики результата** — в JSON прогона и в записях `mcp:import-builder`:
  - `extraFields` / `quality.extraFields` — поля сверх заказа. У 1.1, 1.3 и 21.4b заказ известен
    только числом, поэтому для них — только число;
  - `leakedExample` / `quality.leakedExample` — поля образца грамматики среди лишних;
  - `createdForms` / `process.createdForms` — сколько форм создал ход.
- **`EVAL_REPEATS=n`** — каждый сценарий n раз в одном JSON. `mcp:compare` складывает повторы в
  долю прошедших.

## Критерии — записаны до прогона

| Условие                                                                                                    | Решение                                                                            |
| ---------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| N.1+N.2: создана форма и анкета не изменилась — в ≥ 5 из 6 прогонов B                                      | правка маршрутизации принята                                                       |
| То же — меньше 5 из 6                                                                                      | промптом не лечится: детерминированная маршрутизация в мосте — отдельная задача    |
| `leakedExample` в N.1–N.3 плеча B — 0 во всех прогонах                                                     | правка грамматики принята; иначе — образец из затравки убрать, отдавать по запросу |
| N.4 и точечные правки (4.1, 4.2, 7.1, 8.1, 17.1, 20.2, 21.3): ни одной лишней формы, прохождение не ниже A | обратного перекоса нет                                                             |
| Полный набор: прохождение не ниже A с поправкой на разброс                                                 | регрессий нет                                                                      |
| Медиана входных токенов на сценарий выросла не больше чем на 5%                                            | цена приемлема; иначе — сжимать добавленные строки                                 |
| Постоянная часть запроса выросла не больше чем на ~400 символов (~100 токенов)                             | то же                                                                              |

## Методика

- **Плечо A** — код до правок маршрутизации и грамматики, но уже со сценариями N и метриками.
- **Плечо B** — с правками.
- **Модели** — те, что стоят локально:
  - `qwen3.5:4b` — поставлена накануне жалобы, на ней эффект и наблюдался;
  - `gemma4:26b` — вторая модель прежних замеров.

  Эталонной модели прежних замеров `qwen3.8:27b-32k` на машине нет, поэтому числа с прежними
  отчётами напрямую не сравниваются.

- Канал — Ollama через `providers/byok.ts`, рассуждение — по умолчанию канала.
- **Токены** — из `usage` провайдера по каждому запросу хода (`forms/ai/src/session/telemetry.ts`).
  Ollama отдаёт их сама; если `usage` нет, вход оценивается по телу запроса.
- **Постоянная часть запроса** — временный скрипт `.tmp/eval/static/measure.ts`: символы промпта,
  затравок и грамматики MCP, токены — как символы / 4.

- **Маршрутизация.** На базе в провалах N.1/N.2 модель сначала зовёт `build_form` без `parent`.
  Отказ «pass parent — the step or section to add to» она понимает буквально и достраивает анкету
  клиента. Затем через `ask_user` спрашивает «где добавить новые поля», не предлагая варианта
  «новая форма». С правками в 10 из 12 ходов `create_form` — первый вызов, и ход укладывается в 3
  запроса.
- **Цена.** Медиана входных токенов на ход упала с 68,6 до 15,4 тыс. (−78%), медиана запросов — с
  12 до 3. Экономит не длина промпта (он вырос), а исчезнувшие цепочки отклонённых вызовов.
  Каждый лишний запрос заново несёт промпт, затравку и историю.
- **Единственный провал B (N.2 #2)** — `create_form` с путём вместо имени:
  `forms/eval/schema/restaurant-review`. Отказ «kebab-case latin» модель не исправила и достроила
  открытую форму: 47 запросов, 344 тыс. токенов. После этого `create_form` берёт последний
  сегмент пути, если он годное имя, и говорит модели об этом. Проверка — прогон B2 ниже.
- **Образец грамматики.** На этой модели ни в одном ходе обоих плеч поле образца не попало в
  форму (`leakedExample` = 0). Вторая гипотеза жалобы не подтвердилась: оговорка в грамматике и
  предупреждение `build_form` остаются дешёвой страховкой, а не лечением.
- `mcp:compare`: при трёх повторах значим только переход 0/3 ↔ 3/3. Рост N.1 с 1/3 до 3/3 даёт
  p = 0,4 — направление видно, строгого вывода нет.

### B2: N.1 и N.2 после правки `create_form`, 3 повтора

**6/6.** Во всех шести ходах `create_form` — первый вызов. В пяти ходах по 3 запроса и ~11,9 тыс.
входных токенов. Один ход (N.1 #2) дошёл до цели через шесть отклонённых `build_form`: 10
запросов, 62 тыс. токенов. Вместе с B по N.1/N.2 — 11 из 12, медиана входа 11,9 тыс. токенов.

## Чего замер не говорит

- **Одна модель.** Замер снят на `qwen3.5:4b`; на `gemma4:26b` и облачной модели — нет. Крупная
  модель, вероятно, и в базе реже достраивает чужую форму, поэтому выигрыш на ней может быть
  меньше.
- **Мало повторов.** По 2–3 на сценарий. Статистически значимых переходов нет (p ≥ 0,4), видно
  только направление. Разброс модели велик: N.2 в одном плече — от 83 до 1073 с.
- **Полный набор (25+ сценариев) не прогонялся.** Покрыты создание (N, B2) и точечные правки.
  Мастер (5.3), части (10.2) и крупная сборка (B.1–B.3) в этом замере не проверены. Правки
  промпта и затравки задевают и их: строка в затравке непустой формы видна в каждом ходе правки.
- **Внешние агенты через MCP.** Правку грамматики `form_build` проверяют только тесты пакета.
  A/B на `mcp:scenarios` не снимался.
- **Образец грамматики.** На этой модели он не копировался ни в базе, ни с правками. Значит,
  гипотеза «образец переписывается в форму» здесь не подтверждена, а предупреждение
  `build_form` не проверено в бою.
- Проверки сценариев N строгие по ключам полей: поле, названное моделью иначе, чем в скобках
  запроса, считается и пропавшим, и лишним.

## Как повторить

Из `projects/reformer-builder-playground/.ui_builder/plugins/reformer/integration`:

```bash
# новые сценарии, по три повтора
EVAL_MODEL=qwen3.5:4b EVAL_ONLY=N.1,N.2,N.3,N.4 EVAL_REPEATS=3 \
  npx vitest run assistant-scenarios-eval.test.ts

# защитный набор: точечные правки не должны звать create_form
EVAL_MODEL=qwen3.5:4b EVAL_ONLY=4.1,4.2,7.1,8.1,17.1,20.2,21.3 EVAL_REPEATS=2 \
  npx vitest run assistant-scenarios-eval.test.ts

# записи и сравнение плеч — из корня репозитория
npm run mcp:import-builder -- .tmp/eval/form-scenarios-<A>.json
npm run mcp:import-builder -- .tmp/eval/form-scenarios-<B>.json
npm run mcp:compare -- <батч A> <батч B>
```

Ollama слушает `localhost:11434`. В песочнице Claude Code этот адрес закрыт, поэтому прогон идёт
вне её.

**База — отдельный worktree на HEAD.**

- В worktree кладётся только новый файл стенда.
- Корневой и вложенные `node_modules` основного дерева подключаются симлинками.
- Плечи гоняются строго по очереди: на одной Ollama параллельные прогоны искажают время.

Скрипт цепочки этого замера — `.tmp/eval/run-chain.sh`; он не коммитится.
