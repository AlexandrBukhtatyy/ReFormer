# Профиль `guided`: сервер ведёт, малая модель правит

> Реализация 2026-11-13, эпик `ReFormer-f2fs`. План и исследование —
> [docs/plans/lucky-popping-wall.md](../plans/lucky-popping-wall.md). Замеры на qwen3.5:4b:
> калибровка связки `code-guided` на старой лестнице L1–L3 (2026-11-13…14) и первый замер на новом
> наборе сценариев (2026-11-14) — в конце документа.

## Зачем

Малая локальная модель (эталон — qwen3.5:4b) почти не собирает формы через обычную поверхность:
`bare` — 1 из 15 на L1–L2 ([аудит](audit-2026-11.md)), Code Mode поднял средний счёт с 0.287 до
0.460, но целиком прошёл 1 сценарий из 11 ([code-mode.md](code-mode.md)). Типовые провалы: модель не
выходит на путь intent → `form_build`, переписывает intent целиком и не успевает, повторяет
отклонённый вызов, объявляет успех без сборки.

Та же модель в ассистенте конструктора, где работа идёт мелкими типизированными правками, проходит
11 из 12 новых форм ([builder-new-form-routing.md](builder-new-form-routing.md)). Профиль `guided`
переносит этот режим в MCP-сервер, не опираясь на клиента.

## Как устроено

Включается `REFORMER_SURFACE=guided`; умолчание не меняется. Справка по инструментам —
[02-tools.md](../../packages/reformer-mcp/docs/llms/02-tools.md), раздел «Guided profile».

|                        | Обычная поверхность                                                              | `guided`                                                                     |
| ---------------------- | -------------------------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| Инструменты            | 10: шесть справочных, `validate_form`, `plan_form`, `form_build`, `report_issue` | `form_start`, `form_edit`, `form_status`, `form_build`                       |
| `tools/list`           | ≈ 2564 токена                                                                    | ≈ 1195 токенов                                                               |
| Инструкции сервера     | 486 знаков                                                                       | 382 знака                                                                    |
| Кто пишет intent       | модель, целиком                                                                  | сервер, по плоским правкам модели                                            |
| Кто решает, что дальше | модель                                                                           | сервер: план в `form.plan.json` и строка `Next:` в каждом ответе             |
| Кто говорит «готово»   | модель                                                                           | сервер: `Done`, только если сборка прошла на текущих файлах и типы проверены |

- **План.** `form_start` раскладывает задачу на этапы по словам задания или по разбору спеки: поля,
  массивы, шаги, валидация, связи полей, поведение, разметка (только core). Ненужные этапы в план не
  попадают; лишний модель снимает через `form_status {skip}`. Этап считается сделанным по содержимому
  intent, а не по словам модели.
- **Правки.** `form_edit` принимает список плоских правок с перечислениями в схеме (`op`, виды правил
  и поведений). Каждая правка применяется отдельно: отклонённая говорит, как исправить, остальные
  принимаются. Сервер сам заполняет то, что знает: компонент по типу, коды замечаний при `message`,
  источники вычисления из выражения, таргет из плана. После правок — та же сборка, что у
  `form_build`, со строкой `✓`/`✗ form_build` в ответе.
- **Разметка core.** `{"op":"markup"}` — сервер пишет JSX в `index.tsx` и обновляет её при следующих
  правках. Чужой `index.tsx` не перезаписывается: только заготовка или файл с меткой сервера.
- **Следующий шаг.** `Next:` всегда один готовый вызов: исправить сборку, собрать, выполнить
  следующий этап (с примером на полях самой формы) или `Done`.

## Автофиксы: корпус записанных intent

Из записанных прогонов стенда (`.tmp/mcp-runs`) вытащены все `form.intent.json`, которые модели
передавали на сборку, — первые и промежуточные. Каждая запись прогнана через чтение и судью до и после
автофиксов. Новые классы чтения — в [реестре кодов](../../packages/reformer-mcp/docs/llms/08-diagnostic-codes.md):

| Код                  | Что делает                                                                                |
| -------------------- | ----------------------------------------------------------------------------------------- |
| `meta-dropped`       | Отбрасывает ключи без формы: `version`, `$schema`, пустой `components`, обёртку `intent`  |
| `wizard-as-list`     | Шаги списком в `wizard` читает как `steps`                                                |
| `json-schema-lifted` | JSON Schema вместо полей — поля и правила из её `properties`                              |
| `value-coerced`      | Расширен: `pattern`/`minLength`/`maxLength` на поле и правило-словарь становятся вызовами |

| Модель     | Первая запись прогона принята |  Все записи приняты |
| ---------- | ----------------------------: | ------------------: |
| qwen3.5:4b |               0/39 → **7/39** | 42/154 → **63/154** |
| sonnet     |             166/196 → 166/196 |   373/403 → 373/403 |

Регрессий нет: ни одна запись, принятая до автофиксов, не отклоняется после. У sonnet нечего чинить
этими классами — её отказы другие (`lost-message` 20 из 30).

Что остаётся у 4B после автофиксов (записей с кодом среди отклонённых):

| Код             |  До | После |
| --------------- | --: | ----: |
| `unknown-key`   |  62 |    35 |
| `invalid-value` |  19 |    18 |
| `not-json`      |  15 |    15 |

Рост `lost-message` — записи, которые раньше отклонялись на чтении, теперь доходят до судьи. Невалидный

## Связка с Code Mode: `code-guided`

`REFORMER_SURFACE=code-guided` кладёт тот же API в один инструмент `run_script` (песочница QuickJS):
`reformer.formStart`, `formEdit`, `formStatus`, `formBuild`. Сервер переписывает строки `Next:` в
готовый код (`await reformer.formEdit({…})`). Скрипт, который ничего не напечатал, получает ответ
последнего вызова. Ответ со следующим вызовом без `Done` напоминает, что код в сообщении ничего не
запускает. Справочных ресурсов в профилях guided нет.

Перед `Done` сервер сверяет форму с заданием:

- числа задания, которые не использует ни одно правило;
- умолчания;
- обязательность и видимость по окну поля в тексте;
- потерянные поля, чужие маски и границы, варианты не у того поля.

Расхождения приходят готовой правкой. Первое подтверждение при расхождениях не принимается, второе
принимается: эвристика может ошибиться. Этап поведения закрывается, только когда у readonly-поля и у
цели формулы задания есть вычисление, которое читает все поля формулы.

- `!model.x === v` читается как `!==`;

### Почему проваливается

1. **Правка готовой формы идёт мимо профиля** (8 из 9 правок и удалений). Модель читает
   сгенерированные файлы и переписывает их сама. Это `form.intent.json` целиком (до 20 тысяч знаков),
   `model.ts`, валидация и поведение. Итог — ошибки `tsc`, форма не грузится, а в конце «Форму
   доработал». В `order-edit` на `renderer-react` модель 11 раз собирала форму в цикле «правит
   `form.behavior.ts` руками — сборка затирает правку». Инструкции сервера говорят только о создании
   формы: «To create a ReFormer form: formStart…». О правке готовой — ни слова.
2. **Механика создания мешает правке.** Единственная правка путём guided — `registration-delete` на
   `renderer-json`, счёт 0.737:
   - `remove_field` поля, которое задание велит удалить, ответил «the task names this input — put it
     back»;
   - сверка с текстом правки сочла `minLength`/`maxLength` выдуманными, и модель сняла верные правила;
   - пример этапа `cross` на настоящих полях (`email equals login`) модель вставила дословно;
   - сверка пожаловалась, что подписи «Email» нет в задании.
3. **Заказ по спецификации собирается без неё** (`order-create`, 3 из 3).
   - Модель читает `spec.md` и вызывает `formStart` только с текстом задания, без `specPath`.
     Черновика intent по спеке нет, и около 30 полей модель вводит правками по одной (около 22 с на
     шаг). Она упирается в лимит 80 шагов: 0–5 правил, ни одного поведения, 1.1–1.9 млн входных
     токенов на прогон.
   - На core план из текста без массивов 10 раз отказал в `add_array` («the plan has no rows»). Сервер
     выдал `Done` при счёте 0.1.
   - На `renderer-react` модель перечислила поля в задании, и массивы прошли. Но типы не заданы у 7
     полей, а в строке товара нет `price` — образец падает исключением модели.
4. **Нечем выразить.**
   - Асинхронная проверка (капча-заглушка) — модель пыталась `computeFrom` с `fetch`.
   - Кнопка отправки — модель добавляет поле `submit`. В одном прогоне этого хватило, чтобы уйти в
     ручные файлы: `disableWhen` по строкам дал ошибку типов.
   - Переименование поля (`customerType` → `payerType`, `login` → `username`).
   - Правки шагов мастера: переименовать шаг, перенести поле, удалить шаг.
5. **Шум модели**:
   - 9 пустых `run_script {}` подряд (`order-edit` на core);
   - `import fs` в скрипте;
   - скрипты в файлах `form/01-fields.js`;
   - 18 чтений одних и тех же файлов подряд;
   - один шаг до 13 минут — запись большого файла.

### Дефекты, найденные замером

- **Стенд** (`ReFormer-mhsh.6`). Затравка правки на core рисует форму через `FormRenderer` из
  `@reformer/renderer-react`, как эталон для браузерной стадии. Гейт `static.stack` падает до старта
  агента во всех 7 ячейках правки на core. В этом батче это `registration-edit`, `registration-delete`,
  `order-edit` и `order-delete` на core.
- **Сервер** (`ReFormer-f2fs.13`):
  - фраза в `rule` без других проверок стала регуляркой `pattern(/length >= 6 && …/)`;
  - повторный `equals` добавляет второе правило, а не заменяет первое;
  - ложные расхождения сверки: «123» из `ABC123`, «300» из «ответ через 300 мс»;
  - `remove_field` предупреждает о поле, которое задание велит удалить.
- **`Done` честен только относительно плана.** План, собранный без спеки, закрывается без массивов
  (`ReFormer-f2fs.11`).

### Что дальше — по охвату

1. **Путь правки** (`ReFormer-f2fs.10`): 9 из 15 измеренных ячеек и 9 из 14 непрогнанных
   (`wizard-split/edit/delete`). Нужно:
   - строка инструкций про форму, которая уже лежит в каталоге;
   - план правки из существующего intent, этапы по дельте;
   - сверка только того, что называет задание;
   - примеры-заглушки вместо настоящих полей.
2. **Спецификация** (`ReFormer-f2fs.11`): `order-create` и `wizard-create`, 6 ячеек. Нужно:
   - `formStart` берёт `*.md` из задания как `specPath`;
   - `add_array` и `add_step` добавляют этап в план вместо отказа.
3. **Недостающие операции** (`ReFormer-f2fs.12`): асинхронное правило, кнопка отправки,
   переименование полей и шагов.
4. **Дефекты** `ReFormer-f2fs.13` и стенд `ReFormer-mhsh.6`.

Перемер — сначала узко: `registration-*` и `order-create`, 12 ячеек, около 2 часов. Затем полный набор
ночью.

## Чего это пока не говорит

- Новый набор измерен одним повтором на ячейку и без мастера. Это направление, а не оценка.
- На новом наборе нет сравнения с `bare` и `code-mode`. Цифры старой лестницы с ним не сравнимы:
  сценарии другие, а правок в старой лестнице не было вовсе.
- Корпус автофиксов меряет только чтение и судью на записях, которые модели уже написали. К тому же
  это те же прогоны, по которым выбирались классы автофиксов: настройка, а не проверка.
