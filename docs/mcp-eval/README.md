# Eval `@reformer/mcp` — метод и baseline

Харнесс: [packages/reformer-mcp/eval/](../../packages/reformer-mcp/eval/). Запуск — `npm run mcp:evaluate`.
Baseline: [baseline.json](baseline.json).

## Что он меряет и чего не меряет

Один вопрос: **отдаёт ли сервер знание, нужное для задачи, за сколько вызовов и токенов.**
Не «написала ли модель правильный код» — это зона клиента, недетерминированная и непригодная
для CI-гейта. Сервер контролирует именно извлечение, его и меряем.

46 задач в шести категориях (`eval/corpus/*.json`). У каждой — формулировки, которые агент
реально напишет (`queries`, первая — самая естественная), и `expectAny`: имена API, появление
которых означает, что знание получено.

| метрика         | смысл                                                                                         |
| --------------- | --------------------------------------------------------------------------------------------- |
| `static`        | `tools/list` + `resources/list` + `prompts/list` — цена ПОДКЛЮЧЕНИЯ, до любой полезной работы |
| `hitRate`       | доля задач, где нужное имя API вообще всплыло                                                 |
| `firstPassRate` | доля задач, где оно всплыло с **первой** формулировки — главный KPI                           |
| `tokensPerTask` | median и p95 стоимости задачи                                                                 |
| `callsPerTask`  | сколько обращений к серверу потребовалось                                                     |

Токены оцениваются как `chars / 4`. Грубо, но стабильно и сравнимо между прогонами — важна
дельта между версиями сервера, а не абсолютная точность.

> Числа `static` здесь меньше, чем `wc -c` по выводу `scripts/mcp-call.mjs`: харнесс считает
> сам payload (`JSON.stringify(result)`), а `mcp-call.mjs` печатает его с отступами и в
> JSON-RPC-обёртке. Внутри каждого способа счёт последователен; сравнивать надо однородные.

## Baseline (v7)

Стратегия по умолчанию — `v6-choose`: рекомендуемый путь агента, `choose_api` первым, дальше
`find_recipe` → `search_docs` → `resources/read`. Стратегии `v6` (без decision-слоя) и `v7`
(только `get_context`) остались для A/B: `npm run mcp:evaluate -- --strategy v6`.

```
задач 46
static           3 686 tok   (tools 2 168 · resources 520 · prompts 998)
hit rate         100.0%
first-pass rate   95.7%
токенов/задача    median 299 · p95 1 437 · всего 26 386
вызовов/задача    median 1 · p95 3
```

### Как менялись цифры

Все прогоны — один корпус, одна стратегия. Сборку «до Фазы 0» снимали с ревизии из `HEAD`
(`--server` у раннера позволяет померить чужую сборку).

|                        | до Фазы 0 | Фаза 0 | Фаза 2 | Фаза 4 |         v7 |
| ---------------------- | --------: | -----: | -----: | -----: | ---------: |
| static                 |    24 781 |  4 375 |  4 375 |  4 665 |  **3 686** |
| hit rate               |     97.8% |  97.8% |  95.7% | 100.0% |   **100%** |
| first-pass             |     80.4% |  80.4% |  80.4% |  95.7% |  **95.7%** |
| токенов/задача, median |     1 119 |  1 040 |    916 |    299 |    **299** |
| токенов/задача, p95    |    24 749 | 24 749 |  4 845 |  1 437 |  **1 437** |
| токенов, всего         |   194 842 | 185222 | 62 428 | 26 807 | **26 386** |
| вызовов, median        |         2 |      2 |      1 |      1 |      **1** |

Итог: **−85% статики, −86% токенов на корпус, first-pass +15 пунктов, ни одной нерешённой
задачи.** Худший единичный ответ инструмента — 2 877 токенов против прежних 20 591.

### Что дала каждая фаза

**Фаза 0** — починка дефектов и хирургия по токенам подключения; качество она и не должна была
двигать. `find_recipe` перестал упираться в тупик (68% → 0% промахов на естественных
формулировках), но в этой стратегии тупик и раньше компенсировался переходом на `search_docs`.

**Фаза 2** — билд-тайм индекс `llms-index.json` в каждом пакете, BM25 вместо счёта частот,
переход «формулировка → каноническое имя». Хвост стоимости исчез (p95 −80%). Ценой две задачи
перестали находиться — и это было записано в пробелы, а не спрятано. Попутно закрыт давний
дефект: генератор читал только `src/index.ts` и терял **весь DSL** `behaviors` и `validation`
(62 символа `@reformer/core`) — их не было и в самом `llms.txt`.

**Фаза 4** — `choose_api`. Ровно те две задачи и закрылись, вместе с семью, не бравшимися с
первой формулировки.

**Фаза 3** — бюджет и потолки выдачи; про отрицательный результат `get_context` — ниже.

**Фазы 5–6** — `plan_form`/`generate_form` с кросс-проверкой бандла и `validate_form` с кодами
`RF0xx`. На корпусе не измеряются: он про извлечение знания, а эти инструменты про генерацию и
проверку. Их гарантии закреплены юнит-тестами (каждый код C1..C9 и RF0xx — отдельным кейсом).

**Фаза 7** — сжатие поверхности: описания инструментов, `enum` пакетов убран из четырёх схем
(взамен принимаются короткие имена), промпты 11 → 7 схлопыванием семейств с одинаковой формой
аргументов. Статика −24% без потери качества.

### Отрицательный результат: «один большой `get_context`» проигрывает точному вопросу

Внешняя рекомендация ставила `get_context` первым по важности: один вызов вместо цепочки.
Проверено стратегией `v7` (единственный вызов `get_context`, тот же корпус):

|                        | `choose_api` + поиск | только `get_context` |
| ---------------------- | -------------------: | -------------------: |
| hit rate               |               100.0% |               100.0% |
| first-pass             |            **95.7%** |                69.6% |
| токенов/задача, median |              **299** |                  680 |
| токенов, всего         |           **26 386** |               36 675 |

Причина видна в трассах: собранный ответ на 500–900 токенов чаще промахивается мимо нужного
имени, чем точный ответ на 300. Плюс сборщик первой версии подавал ДОГАДКУ в той же уверенной
форме, что и знание — на «показать текущее количество строк массива» выдача начиналась блоком
`## API` с `isGroupNode`, хотя правило не сработало ни разу.

Что из этого сделано:

- форма ответа теперь отражает уверенность: символ попадает в `## API`, только если его выбрало
  правило ЛИБО он реально упомянут в найденной секции; иначе выдача честно говорит «правило не
  сработало» и ведёт секциями со сниппетами;
- `get_context` оставлен, но НЕ как точка входа: его описание прямо отсылает к `choose_api` для
  точечного вопроса. Рекомендуемый путь — `choose_api` первым;
- машинерия бюджета из этой фазы применена там, где выигрыш бесспорен, — к потолкам выдачи.

Оговорка, без которой цифры читаются неверно: корпус измеряет извлечение ОДНОГО факта.
Инструмент, собирающий контекст под целый шаг, на таком корпусе выиграть не может в принципе.
Вывод «`get_context` не заменяет `choose_api`» обоснован; вывод «`get_context` не нужен» — нет,
для него нужен другой корпус.

### Потолки выдачи инструментов

До Фазы 3 у ответов инструментов не было потолка вообще:

| вызов                     |       было |     стало |
| ------------------------- | ---------: | --------: |
| `list_symbols({})`        | 20 591 tok | **2 877** |
| `find_recipe("cookbook")` |  4 283 tok | **2 241** |

Это ответы, которые агент получает НЕ ГЛЯДЯ, в отличие от явного `resources/read`, поэтому
потолок для них обязателен. Обрезка всегда помечена и говорит, чем сузить запрос или где
дочитать: молча усечённый список агент примет за полный и решит, что символа не существует.

### Три раза прибор оказывался хрупким

Каждый раз ошибка была в измерении, а не в сервере, и каждый раз это выглядело как результат.

1. **Слишком общее ожидание.** Корпус ждал `["cross"]` и `["registry"]`. Тупиковый ответ
   `find_recipe` печатает список рецептов и алиасов — а в нём есть и `cross`, и
   `renderer-json/registry`. Задача засчитывалась решённой, хотя агент получил тупик. Лечится
   `isEmptyAnswer` + `assertStrongExpectations`.
2. **Слишком конкретное, но выдуманное ожидание.** Задача про блокировку submit ждала
   `isValid` и `FormStatus`, которых в ReFormer нет: `isValid` совпадал как ПРЕФИКС реального
   `isValidating` (25 вхождений против 1). Непопадание сервера записали ему в пробелы
   ошибочно. Лечится `auditExpectations` — ожидание-идентификатор обязано существовать либо
   как символ, либо как упоминание в документации.
3. **Гейт смотрел не туда.** Сравнивалась только МЕДИАНА токенов, и рост p95 с 24 749 до
   41 488 (после того как в `llms.txt` добавился ранее терявшийся DSL) прошёл мимо. Добавлены
   p95 и сумма.

**Вывод: корпус и гейт — такие же измерительные приборы, как сервер, и ломаются так же тихо.**

### Что осталось незакрытым

1. **Две задачи не берутся с первой формулировки** (`arrays/length`, `renderer-json/schema`) —
   кандидаты на правило в `choose_api`.
2. **`resources/read` не имеет потолка выдачи.** Один вызов может вернуть 37k токенов, если
   агент прочитает `API Reference` напрямую. Оставлено сознательно: это ЯВНЫЙ запрос
   именованного ресурса, и молча урезать его значило бы нарушить контракт. Потолки поставлены
   там, где выдачу агент получает не глядя, — в ответах инструментов.
3. **`get_context` не окупает себя на этом корпусе** (см. выше). Нужен другой корпус — на
   задачах «собери целый шаг», а не «найди один факт».
4. **`plan_form` / `generate_form` / `validate_form` корпусом не покрыты.** Он про извлечение
   знания, а эти инструменты про генерацию и проверку; их гарантии держатся на юнит-тестах
   (каждый код `C1..C9` и `RF0xx` — отдельным кейсом).

   > Здесь раньше стояло «полноценная проверка — прогон сгенерированной формы через e2e».
   > Это оказалось неверно: поведение формы ReFormer наблюдаемо headless (`createForm` не
   > требует схемы, `validateModel` возвращает boolean, узлы отдают `disabled`/`errors`).
   > `tests/form-from-spec.test.ts` доводит спеку до живой формы и проверяет поведение
   > юнит-тестом — без браузера. За e2e остаётся только рендер.

## Как пользоваться

```bash
npm run mcp:evaluate                                   # прогон (стратегия v6-choose) + сравнение
npm run mcp:evaluate -- --strategy v6                   # A/B: тот же корпус без decision-слоя
npm run mcp:evaluate -- --json .tmp/eval.json          # полный отчёт с трассами
npm run mcp:evaluate -- --save docs/mcp-eval/baseline.json   # обновить baseline
npm run mcp:evaluate -- --server <path/to/dist/index.js>        # померить другую сборку
```

Гейт падает, если против baseline упал hit/first-pass либо выросли статика или медиана
токенов/вызовов. Осознанное изменение — обновить baseline тем же прогоном.
