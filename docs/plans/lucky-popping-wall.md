# Малые локальные модели собирают сложные формы: профиль `guided`

## Итерация 3 (2026-11-15): профиль `code-guided-dsl` — конструктор форм в `run_script`

### Context

Идея пользователя: модели хорошо пишут код, а сервер и так отдаёт им TypeScript-объявление API, по
которому модель пишет скрипт для `run_script`. Пусть в этом объявлении будет **конструктор форм**:
объект с методами и цепочками вместо JSON-правок со свободными выражениями.

**Как код модели становится формой сейчас (code-guided):**

1. **Подача.** Сервер отдаёт один инструмент `run_script` с описанием:
   - преамбула;
   - TS-объявление `declare const reformer: {…}`: `GUIDED_MEMBERS` и союз правок `editDeclaration()` из
     реестра `src/core/guided/edit-spec.ts`.
2. **Скрипт модели.** Это тело async-функции.
   - `quickjs-sandbox.ts` оборачивает его в `async function __reformer_main__(){…}` и исполняет в
     QuickJS (120 с, 64 МБ).
   - Глобальные имена — только `console` и `reformer`.
   - После `SyntaxError` скрипт повторяется через `ts.transpileModule`, а `syntaxPlace` показывает
     место ошибки.
3. **Вызов `reformer.formEdit({dir, edits})`.** Хост получает аргумент через `context.dump`, поэтому
   функции через границу не проходят. Дальше `applyEdits` (`edits.ts`) правит FormIntent:
   - 18 плоских операций;
   - выражения `when`, `expr`, `cross`, `showWhen` и `async` — свободные строки JS;
   - их правят эвристики на регулярках: `withScope`, `unknownNames`, `conditionOf`, `crossOf`.
4. **Сборка.** Intent проходит `judgeIntent` и `planBuild`, затем `tsc` (strict). Результат —
   `model.ts`, `form.validation.ts`, `form.behavior.ts`, схема и `index.tsx`. Строки выражений
   попадают в TS **дословно** (`builders.ts`): `validate`, `cross((values)=>…)`, `compute`, `hideWhen`.
5. **Ответ.** В нём строки ✓/✗ по каждой правке, `Plan:`, `Next:` — готовый `await reformer.formEdit(…)`
   (это переписывает `asScriptCalls`) — или `Done`.

**Что ломается в замерах qwen3.5:4b и что из этого лечит язык:**

| Класс провала | Лечит ли конструктор |
| --- | --- |
| синтаксис скрипта: кавычки, запятые, скобки вложенного JSON | да — короткие цепочки без вложенных объектов |
| аргументы вызова теряются в разборе XML у Ollama (`run_script {}` 25 раз подряд) | частично — скрипты короче и проще |
| область выражений (`values.x` в поведении) | да — параметр лямбды переименовывается деревом TS |
| смысл шаблонов (`^[0-9].*$` на «хотя бы одну цифру») | да — `.digit()` |
| обход сервера: файлы руками, 0 вызовов MCP | нет |
| ложный «Done», неверное прочтение задания | нет |
| дыры возможностей: операции не хватает | нет — методы 1:1 с операциями |

Поэтому 100% одним языком не достичь. Ожидание на qwen 4b — от 0 до +15 п. п. прохождения при заметном
падении синтаксических ошибок и ошибок области. Решение пользователя — отдельный профиль
`code-guided-dsl` рядом с `code-guided`: code-guided не меняется, замеры сравнимы.

**Канал контекста, как у Cloudflare.** В [Code Mode MCP](https://blog.cloudflare.com/code-mode-mcp/)
ровно два инструмента, и оба принимают код:

- `search` — код над объектом `spec`. Сама спецификация в контекст не попадает: модель видит только то,
  что вернул её код;
- `execute` — код, который вызывает API.

Поверхность — около 1000 токенов при 2500 эндпоинтах. В первой статье ([Code Mode](https://blog.cloudflare.com/code-mode/))
инструмент один, и всё API лежит в контексте.

У нас малой модели не хватает не справки по API — оно маленькое, — а **данных**: какие поля и правила
уже есть, что сказано в задании и спецификации. Сейчас это приходит только текстом в ответах и теряется,
когда стенд усекает старые ответы. Справку как инструмент из guided убрали сознательно: qwen читала
`reformer://docs` по десять раз вместо сборки. Решение пользователя (2026-11-15): **два инструмента,
как у Cloudflare** — `search` для чтения данных и `execute` для правок.

### Решение

**Два инструмента профиля.** Оба принимают `code`: тело async-функции или async-стрелку (принимаются оба
вида).

| Инструмент | Что видит код | Что возвращает |
| --- | --- | --- |
| `search` (только чтение) | замороженные объекты (см. ниже) | возвращённое значение и `console.log`, не больше 4000 знаков; длиннее — обрезка с советом сузить фильтр |
| `execute` | `reformer.formStart` и конструктор `reformer.form()` | ответ сервера |

Объекты `search`:

- `form` — снимок текущей формы: поля (`name`, `label`, `type`, `component`, `mask`, `options`,
  `step`, `rules`, `readonly`), массивы с колонками, шаги, поведения, видимость, кнопка отправки;
- `task` — текст задания плана и, если есть спецификация, её разбор: разделы и таблицы полей из
  `analyzeSpec`;
- `api` — методы конструктора: сигнатура, описание, пример, операция;
- `plan` — этапы, текущий этап, последний `Next:`.

`search` до `formStart` отвечает «плана ещё нет», и сервер даёт вызов `execute` с `formStart`.

Описание `execute` — короткие сигнатуры конструктора, примерно 1,5–2 тыс. токенов. Полные описания и
примеры лежат в `api` и находятся через `search`. Строки `Next:` всегда ведут в `execute`, чтобы малая
модель не бродила в `search`. В ответах `search` есть строка «смотреть больше не нужно — измени форму
через `execute`».

**`execute`: конструктор живёт в песочнице, проверка — на хосте.**

**Конструктор живёт в песочнице, проверка — на хосте.**

- Прелюдия (JS-строка) исполняется в QuickJS до скрипта модели.
- Цепочки синхронны и только **записывают** правки — те же объекты `{op,…}`, что сегодня.
- `await f.save()` отправляет их **одним** `formEdit`. Дальше путь прежний: `applyEdits`, план, сверка,
  сборка. `edits.ts`, `plan.ts`, `guided.ts` не меняются.

**Лямбды.** QuickJS сохраняет исходник функции — проверено: `String((m) => m.x === "a")` возвращает
ровно этот текст.

- Прелюдия отправляет `{ $lambda: String(fn), $scope }`.
- Хост разбирает текст деревом TypeScript (`lowerLambda`):
  - ровно один параметр; тело — одно выражение или один `return`;
  - параметр переименовывается в `model`, `values`, `value` или `item`, как бы модель его ни назвала;
  - разрешённый набор: литералы, `?.`, `??`, арифметика, сравнения, логика, тернарный оператор,
    `Math.*`, `Number`, `String`, методы строк и массивов (`trim`, `includes`, `reduce`…);
  - отказ с подсказкой: присваивание (вместо `===`), `new`, `this`, `await`, свободные имена (замыкание
    на переменные скрипта), неизвестные вызовы.
- Результат — та строка, которую `applyEdits` принимает уже сейчас.
- Пакет `typescript` в пакете — необязательная зависимость. Платформа передаёт модуль в каталог
  инструментов (`loadTypescript` из `quickjs-sandbox.ts`).

**Сохранение.**

- Неизвестный метод перехватывает `Proxy`: он записывает ошибку «нет `.regex` — может, `.pattern`?»,
  а скрипт идёт дальше.
- Эпилог после основной функции:
  - есть несохранённые правки и скрипт завершился чисто — сохранить и напечатать ответ;
  - была ошибка выполнения — не сохранять и сказать, сколько правок потеряно.
- В песочнице одно необязательное изменение: `ScriptSandbox.run(code, functions, { prelude, epilogue })`.

**Результат — против цепочки.** У каждой записанной правки есть `$via`, текст цепочки. Хостовая обёртка
`dslScriptCall` подставляет его в строки ✓/✗: `✗ f.field("phone").options([…]): …`. Ошибки лямбд и
неизвестных методов встают на свои места. Если строки ответа не совпали по числу, ответ остаётся как
есть.

**`Next:` кодом конструктора.** `asBuilderCalls` переписывает ответ слоем каталога инструментов, как
сегодня `asScriptCalls`; `plan.ts` не трогается.

- `form_edit {json}` превращается в блок `const f = reformer.form(); f.field(…)…; console.log(await f.save())`.
- В выражениях `model.` → `m.`, `values.` → `v.`, `item.` → `r.`.
- `pattern "\\d"` печатается как `.digit()`.
- Операция без метода печатается как `f.edit({…})`.
- `form_status` превращается в `await f.confirm(…)` или `await f.skip(…)`.

### API конструктора (около 42 имён, у каждого JSDoc и `@example`)

| Метод | Правка |
| --- | --- |
| `f.add(name,label)` / `f.field(name)` | `add_field` / свойства → `set_field`, проверки → `add_rule` |
| `.label .type .options .mask .readonly() .initial .component` | одноимённые ключи |
| `.toStep(title)` | новое поле — `add_field.step`, существующее — `place` |
| `.required(msg?) .email .min(n) .max(n) .optional()` | `add_rule`: проверки копятся в группу, сообщение закрывает группу |
| `.pattern(re,msg?)` / `.digit(msg?)` | `pattern` (RegExp → `/src/flags`) / `pattern "\\d"` |
| `.sameAs(other,msg?)` | `add_rule{equals}` |
| `.check(v=>…,msg)` / `.asyncCheck(v=>…,{delay,message})` | `cross` (область `values`) / `async` (область `value`) |
| `.when(m=>…)` | `when` у каждого правила цепочки |
| `.showWhen(m=>…)` / `.hideWhen(m=>…)` | `add_visibility` |
| `.enableWhen(m=>…)` / `.resetWhen(m=>…)` / `.compute(m=>…)` / `.copyFrom(src, m=>…?)` | `add_behavior`; `compute` на колонке — область `item` |
| `.rename(to,label?)` / `.remove()` / `.removeRule(name?)` / `.removeBehavior(kind?)` | `rename_field` / `remove_field` / `remove_rule` / `remove_behavior` |
| `f.array(name,label,{min,max})` / `.column(name,label)` | `add_array` / `add_item_field` |
| `f.step(title).fields(…)` / `.rename(to)` / `.remove()` | `add_step` / `rename_step` / `remove_step` |
| `f.title` / `f.submit(label)` / `f.markup()` / `f.edit({op,…})` | `set_form` / `submit` / `markup` / сырая правка |
| `f.save() f.status() f.confirm(s) f.skip(s) f.build()` | `formEdit` / `formStatus` / `formBuild` |

`reformer.formStart` остаётся: объявление берётся из `GUIDED_SCRIPT_SURFACE` как есть. `formEdit`,
`formStatus` и `formBuild` в объявлении скрыты, но установлены — ими пользуется прелюдия.

### Риски

- Форматы строк ответа и `Next:` может поменять параллельная сессия. Защита — запасной путь (ответ без
  изменений) и тесты, фиксирующие формат.
- Модели могут выдумывать методы в духе zod (`.regex`, `.nonempty`). Их ловит `Proxy` с подсказкой;
  псевдонимы добавлять по журналам.
- Объявление станет больше. Потолок обоих описаний вместе — как у code-guided.
- Малая модель может бродить в `search` вместо правок, как раньше со справкой. Защита:
  - `Next:` всегда ведёт в `execute`;
  - ответ `search` кончается строкой «измени форму через `execute`»;
  - стенд считает поиски подряд без правки.

  Если блуждание подтвердится на замере, `search` убирается из подачи для малых моделей.
- Конструктор не лечит обход сервера, ложный `Done`, сбои канала Ollama и нехватку операций. Их ведут
  ReFormer-f2fs.15, f2fs.22, f2fs.23 и стенд.

## Итерация 2 (2026-11-14): контракт `code-guided`, правка готовой формы, форма по спецификации

### Context

Первый замер `code-guided` на новом наборе сценариев (батч `20261114T113832Z-68e8`, qwen3.5:4b,
[guided.md](../mcp-eval/guided.md#первый-замер-на-новом-наборе)) дал 0 из 15 при среднем счёте
0.495. Провалы такие:

- правки и удаления в 8 из 9 случаев идут мимо профиля: модель руками переписывает
  `form.intent.json` и файлы модуля;
- форма заказа по спецификации собирается без неё: `specPath` не передан ни разу из 3;
- модель шлёт по одной правке за вызов и упирается в лимит шагов;
- типовые ошибки ключей: фраза в `rule`, `component: "input"`, `options: ["textInput"]`.

Гипотеза пользователя: вводный абзац сервера неполон, а TS-контракт `run_script` слабо
документирован и слабо типизирован. Описание, которое реально видит модель, это подтверждает.

- **Инструкции** говорят только «To create a ReFormer form…». О форме, которая уже лежит в каталоге,
  и о `specPath` в них ни слова.
- **Преамбула `run_script`** общая с обычным Code Mode. Она говорит «write files with your own file
  tools», что противоречит «never write module files yourself». Пример в описании `code` —
  `formBuild({ grammar: "base" })`, хотя в guided грамматики нет.
- **`edits`** — один объект с 38 необязательными ключами и `op`-перечислением. Какие ключи у какой
  операции, видно только из однострочной сводки в описании.
- **Ключи без документации:** `rule`, `when`, `expr`, `cross`, `component`, `options`.
- **Результат** — голый `Promise<string>`: формат ответа (`✓`/`✗`, `Next:`, `Done:`) не описан,
  примеров вызова нет.

Решения пользователя (2026-11-14):

- контракт и серверные правки f2fs.10 (путь правки) и f2fs.11 (спецификация) — в одной итерации;
- контракт усиливается только для `code-guided`: обычный `code` и `guided` (инструменты) не меняются,
  их замеры остаются сравнимыми.

### 1. Контракт `code-guided`

**Реестр правок — один источник.** Новый `src/core/guided/edit-spec.ts`:

- по каждой операции — обязательные и необязательные ключи, строка описания, пример с заглушками
  вместо имён;
- по каждому ключу — описание: что значит и какой синтаксис.

Из реестра выводятся:

- `EDIT_OPS` и `EDIT_KEYS`;
- плоская JSON Schema `form_edit.edits.items` — та же, что сейчас. Снимок `tools.guided.json`
  меняется только новыми операциями из разделов 2–3: так проверяется, что вывод из реестра верен;
- однострочная сводка операций в описании `edits`;
- TS-объявление для Code Mode.

**Типизированное объявление.**

- `ToolDefinition` получает необязательное `codeDeclaration`. `apiDeclaration`
  (`src/core/codemode/declaration.ts`) берёт его вместо разбора JSON Schema. Инструменты обычного
  Code Mode его не задают и не меняются.
- В `guided.ts` четыре функции объявляются из реестра. `edits: Edit[]`, где `Edit` —
  размеченное объединение `AddField | SetField | AddRule | …` по `op`, с описанием каждой операции и
  каждого ключа. Типы точные: `type?: "string" | "number" | "boolean" | "date"`, у `options` —
  варианты задания, от двух.
- Ключи-выражения описаны с синтаксисом:
  - `when`, `showWhen`, `hideWhen`, `expr` — JS над `model.<поле>`;
  - `cross` — над `values.<поле>`, `true`, когда значение верно;
  - `rule` — только вызов валидатора вроде `minLength(2)`, фраза идёт в `message`;
  - `component` — не задавать (сервер выберет по типу) либо имя из кита: Select, RadioGroup,
    Switch, Slider, Textarea, DatePicker, InputMask.
- У каждой функции `@returns` — раскладка ответа: строки правок `✓`/`✗` с исправлением, `✓ form_build`
  или ошибки, строка `Plan:`, затем `Next:` с кодом или `Done:`.
- `@example` на заглушках, без имён из сценариев:
  - `formStart` — три входа: задание, спецификация, правка готовой формы;
  - `formEdit` — несколько операций одним вызовом.

**Преамбула по поверхности.** `runScriptToolDefinition(tools, { preamble, codeExample })`
(`src/core/codemode/run-script.ts`), передаёт её `tool-catalog.ts`. Преамбула `code-guided`:

- все файлы каталога формы пишет сервер — не писать и не переписывать их своими инструментами,
  `form.intent.json` тоже;
- правки этапа — одним вызовом `formEdit` со списком;
- без импортов, `require` и `fs`;
- ошибка инструмента — исключение с текстом ответа.

Пример в описании `code` — вызов `formStart`.

**Инструкции `CODE_GUIDED_INSTRUCTIONS`** (`src/platform/cli/server.ts`) называют три входа:

- новая форма — `formStart` с заданием;
- задание ссылается на спецификацию — `formStart` с `specPath`;
- форма уже лежит в каталоге — `formStart` с заданием правки, дальше только `formEdit`.

Лимит длины — тестом.

**Снимок.** `tests/__golden__/surface/tools.code-guided.json` и потолок токенов в
`surface-golden.test.ts`.

### 2. Правка готовой формы (`ReFormer-f2fs.10`)

- **Режим правки.** `formStart` при читаемом `<dir>/form.intent.json` пишет план с `mode: "edit"` и
  одним этапом `edit`. Ответ называет поля формы и говорит: каждое изменение задания — через
  `formEdit`, файлы руками не трогать. Черновик по спецификации при готовом intent заново не
  строится — как и сейчас.
- **Этап `edit` закрыт**, когда выполнено всё:
  - с начала плана принята хотя бы одна правка;
  - сборка прошла на текущих файлах, типы проверены;
  - модель подтвердила `formStatus({ confirm: "edit" })` после сверки.

  Сверка в режиме правки — только по дельте, точность важнее полноты:
  - имя в обратных кавычках или скобках, фраза со словами удаления (убери, удали, remove, delete),
    а поле ещё в форме → расхождение «still there»;
  - фраза со словами добавления, а поля нет → «missing»;
  - пара переименования (`a` → `b`, «переименуй `a` в `b`», «ключ `b` вместо `a`»): старое имя ещё
    есть или нового нет → расхождение.

  Проверки создания — числа, подписи, потерянные поля, окна полей — в режиме правки не
  запускаются. Мягкий гейт тот же: первое подтверждение при расхождениях отклоняется.
- **Операции правки**, без которых сценарии правки не выполнимы. Это часть f2fs.12; асинхронное
  правило и кнопка отправки остаются там.
  - `rename_field {name, to, label?}` — переписывает путь везде: правила, поведение (цели, источники,
    `expr`/`when`), видимость, раскладку, `values.x`/`model.x` в выражениях;
  - `rename_step {title, to}`;
  - `remove_step {title}` — шаг вместе с его полями и их правилами.
- **Дефекты, которые мешают правке:**
  - `remove_field` не предупреждает «the task names this input», если фраза задания про это поле
    содержит слова удаления (f2fs.13, п. 4);
  - примеры в строках `Next:` — только заглушки, никогда пары настоящих полей: пример этапа `cross`
    `email equals login` модель вставила дословно.
- **`formEdit` без плана при готовой форме** — отказ, как сейчас, но `Next:` ведёт в `formStart` с
  заданием правки.

### 3. Форма по спецификации (`ReFormer-f2fs.11`)

- **`specPath` из задания.** Если `specPath` не передан, а задание называет файл `*.md` и
  `k.spec.read` его находит (как написано или внутри `dir`), `formStart` берёт его как `specPath` и
  пишет строку `"specPath" taken from the task: …`. Дальше путь прежний: черновик intent по спеке
  через `plan_form` и список «Finish by hand».
- **Мягкий гейт строк.** Повторный `add_array` с тем же именем после отказа «the plan has no rows»
  добавляет этап `arrays` в план и применяется — как второе подтверждение сверки. На core модель
  10 раз подряд получала отказ и не вызывала `form_status {"add":"arrays"}`.

## Итерация 1 (2026-11-13, реализована)

### Context

Цель — чтобы малые локальные модели (эталон — qwen3.5:4b через Ollama) безошибочно собирали сложные
формы через MCP-сервер `@reformer/mcp`. Сейчас этого нет:

- терминал, `bare`: **1 из 15** на L1–L2 (sonnet на тех же сценариях 10/10), батч `ad08`,
  [audit-2026-11.md](../mcp-eval/audit-2026-11.md);
- Code Mode: средний счёт 0.287 → 0.460, полностью прошёл 1 из 11, сцеплений вызовов в скриптах нет
  ([code-mode.md](../mcp-eval/code-mode.md)).

Как модель проваливается (из того же аудита и [scenarios.md](../mcp-eval/scenarios.md)):

- не выходит на путь intent → `form_build`: 6 из 15 прогонов пытались собрать, остальные запросили
  грамматику и писали модуль руками;
- пишет модуль руками и придумывает API (`createReForm`, `FormModel`…);
- ломает форму после ✓: переписывает `index.tsx` после сборки или меняет стек;
- повторяет отклонённый вызов: 4 одинаковых отказа подряд из-за неверного `target`;
- ложный успех: 7 из 14 проваленных прогонов кончаются словами «форма успешно собрана»;
- переписывает intent целиком: 1.3–2 тыс. токенов на шаг при ~6 ток/с, лимит времени кончается до
  сборки (L5-registration в Code Mode);
- первые intent отклоняются на одинаковых ошибках: 13 из 27 — один `message` на несколько правил.

Контрпример: ассистент конструктора в режиме мелких типизированных правок проходит **11 из 12** новых
форм на той же qwen3.5:4b (формы на 4–5 полей). Большую форму, собранную по шагам, он доводит до 76 из
82 полей (целиком — 60), но это уже qwen3.8:27b. Плоские списки правок убрали сбои разбора вызовов в
Ollama (замечено на gemma4:26b)
([builder-new-form-routing.md](../mcp-eval/builder-new-form-routing.md),
[builder-intent.md](../mcp-eval/builder-intent.md)). Значит, решает не только размер модели, но и
форма работы, которую навязывает инструмент.

Решения пользователя (2026-11-13):

- в первую итерацию — план от MCP, плоские правки и автофиксы;
- помогать любым MCP-клиентам: всё живёт в сервере, на клиента не опираемся;
- отдельный профиль `REFORMER_SURFACE=guided`, умолчание не меняется.

## Решение: профиль `REFORMER_SURFACE=guided`

Набор инструментов профиля: `form_start`, `form_edit`, `form_status`, `form_build`. `form_build`
остаётся, чтобы работали стенд и replay. Справочные инструменты в профиль не входят. Инструкции
профиля — `GUIDED_INSTRUCTIONS`, не длиннее 500 знаков (тот же лимит, что у `SERVER_INSTRUCTIONS`
в `tests/surface-golden.test.ts`).

### 1. План и следующий шаг

- **`form_start {dir, target, task? | specPath?}`.** Определяет тип задачи детерминированно:
  - по спеке — `analyzeSpec` (`src/core/spec/analyze.ts:1027`);
  - по тексту — признаки: валидация, условия, вычисления, массивы, мастер, связи между полями.
    Правила `choose_api` (`src/core/decide/api-decision.ts`) переиспользуются, где подходят.
- По типу задачи собирается план из этапов: поля и раскладка → валидация → поведение → разметка
  (только core). Этапа без нужды в плане нет. План пишется в `<dir>/form.plan.json`.
- По спеке `form_start` сразу делает черновик через существующий `plan_form` (`src/core/tools/plan-form.ts`).
  Модели остаётся только список «Finish by hand» — он становится шагами плана.
- **Шаг плана** — ровно один готовый вызов `form_edit` с заполненными `dir` и `target`. К нему:
  - нужные секции грамматики, логика как у `sectionsFor()` в `src/prompts/plan-form.ts:115`;
  - один пример правки.

  Примеры не берутся из эталонов сценариев: holdout и настроечные эталоны — это прибор.
- **Каждый ответ профиля кончается блоком `Next:`** с одним вызовом. Он вычисляется по плану и
  результату сборки. `Done` сервер ставит сам, только когда все этапы собраны, типы проверены и на
  core есть разметка. Иначе ответ прямо говорит «не готово: …».
- **`form_status {dir}`** перечитывает план и состояние. Это на случай, если модель потеряла контекст.

### 2. Плоские правки `form_edit`

- **Вход:** `{dir, edits: [{op, …плоские поля}]}`. Операции: `add_field`, `set_field`,
  `remove_field`, `add_rule`, `add_behavior`, `add_array`, `add_item_field`, `add_step`, `place`
  (поле в шаг или группу). Ключи плоские, глубокой вложенности нет: это урок разбора вызовов Ollama
  из ассистента конструктора.
- **Перечисления в JSON Schema:** `op`, виды правил, виды поведения (тот же список, что
  `BEHAVIOR_KINDS` в `set-form-rules.ts` ассистента), компоненты кита. Имена полей схема перечислить
  не может, их проверяет сервер и подсказывает ближайшее имя.
- **Сервер применяет правки и сразу собирает.** Каждая правка проверяется отдельно:
  - чтение — `readIntent`/`normalizeIntent` (`src/core/generate/form-intent.ts:2265`, `:370`);
  - судья — `judgeIntent` (`src/core/generate/judge.ts`).

  Ответ по каждой отклонённой правке — что исправить. Принятые правки пишутся в `form.intent.json`.
  Затем идёт тот же конвейер, что у `form_build` (`planBuild` и проверка типов в
  `src/core/tools/form-build.ts`). Модель никогда не пишет intent целиком.
- **Ответ короткий:** строка ✓/✗ в контракте `form_build` (по ней разбирает стенд), сводка
  «полей / правил / поведений», затем `Next:`.
- **Из ассистента конструктора** (`projects/reformer-builder-playground/.ui_builder/plugins/reformer/ai/src/tools/`)
  берём словарь и уроки, но не код: он правит модель конструктора, а не FormIntent.

### 3. Автофиксы под замеренные ошибки

1. **Корпус.** Из `.tmp/mcp-runs/*/*/transcript.jsonl` вытащить все записанные `form.intent.json`
   (первые и промежуточные) и прогнать через текущие `readIntent` и `judgeIntent`. Получится
   список классов ошибок, которые всё ещё отклоняются, с частотой. Многое уже нормализуется:
   синонимы ключей, `each-lifted`, `prop-lifted` и т. д.
2. **Чинить классы по частоте:**
   - один `message` на несколько правил (13 из 27) — раздать каждому правилу или принять с
     предупреждением;
   - `target`, расходящийся с планом, — взять из плана с предупреждением;
   - ручная правка сгенерированного файла на renderer-таргетах — явный ответ «шаг не принят» с
     указанием, как сделать через `form_edit`.

   Каждый фикс помечается предупреждением своего кода, как сейчас в `IntentWarningCode`.
3. **Фикстуры корпуса** — в регрессионные тесты (`tests/`), без путей и сырья. Только минимальные
   intent-фрагменты.

### Не в этой итерации

- Дообучение (TinyAgent), каскад моделей.
