# Малые локальные модели собирают сложные формы: профиль `guided`

## Context

Цель — чтобы малые локальные модели (эталон — qwen3.5:4b через Ollama) безошибочно собирали сложные
формы через MCP-сервер `@reformer/mcp`. Сейчас этого нет:

- терминал, `bare`: **1 из 15** на L1–L2 (sonnet на тех же сценариях 10/10), батч `ad08`,
  [audit-2026-11.md](../mcp-eval/audit-2026-11.md);
- Code Mode: средний счёт 0.287 → 0.460, полностью прошёл 1 из 11, сцеплений вызовов в скриптах нет
  ([code-mode.md](../mcp-eval/code-mode.md)).

Как модель проваливается (из того же аудита и [scenarios.md](../mcp-eval/scenarios.md)):

- не выходит на путь intent → `form_build`: 6 из 15 прогонов пытались собрать, остальные запросили
  грамматику и писали модуль руками;
- пишет модуль руками и придумывает API (`createReForm`, `FormModel`…);
- ломает форму после ✓: переписывает `index.tsx` после сборки или меняет стек;
- повторяет отклонённый вызов: 4 одинаковых отказа подряд из-за неверного `target`;
- ложный успех: 7 из 14 проваленных прогонов кончаются словами «форма успешно собрана»;
- переписывает intent целиком: 1.3–2 тыс. токенов на шаг при ~6 ток/с, лимит времени кончается до
  сборки (L5-registration в Code Mode);
- первые intent отклоняются на одинаковых ошибках: 13 из 27 — один `message` на несколько правил.

Контрпример на той же модели: ассистент конструктора в режиме мелких типизированных правок проходит
**11 из 12** новых форм, а большую форму, собранную по шагам, доводит до 76 из 82 полей (целиком — 60).
Плоские списки правок убрали сбои разбора вызовов в Ollama
([builder-new-form-routing.md](../mcp-eval/builder-new-form-routing.md),
[builder-intent.md](../mcp-eval/builder-intent.md)). Значит, решает не только размер модели, но и
форма работы, которую навязывает инструмент.

Решения пользователя (2026-11-13):

- в первую итерацию — план от MCP, плоские правки и автофиксы;
- помогать любым MCP-клиентам: всё живёт в сервере, на клиента не опираемся;
- отдельный профиль `REFORMER_SURFACE=guided`, умолчание не меняется.

## Связка: провал → рычаг

| Провал 4B | Рычаг |
| --- | --- |
| Не выходит на путь сборки, бродит по справочным инструментам | В профиле справки нет; первый же ответ — план и один следующий вызов |
| План в начале теряется: стенд держит целиком только 4 последних ответа | План лежит на диске (`form.plan.json`), каждый ответ заново называет следующий шаг |
| Переписывает intent целиком, медленно, ломает JSON | Плоские правки `form_edit`; intent пишет сервер |
| Неверный `target`, повторы одного отказа | `target` и `dir` берутся из плана; повторы ловит существующий `repeat-calls.ts` |
| Пишет модуль руками и переписывает после ✓ | Ответ о сборке говорит «правь через `form_edit`»; ручная правка сгенерированного файла — явная ошибка шага |
| Ложный успех | Статус «готово» выдаёт только сервер: все этапы собраны, типы сошлись, на core есть разметка |
| Типовые ошибки первого intent | Автофиксы по классам, которые записаны в прогонах |

## Решение: профиль `REFORMER_SURFACE=guided`

Набор инструментов профиля: `form_start`, `form_edit`, `form_status`, `form_build`. `form_build`
остаётся, чтобы работали стенд и replay. Справочные инструменты в профиль не входят. Инструкции
профиля — `GUIDED_INSTRUCTIONS`, не длиннее 500 знаков (тот же лимит, что у `SERVER_INSTRUCTIONS`
в `tests/surface-golden.test.ts`).

### 1. План и следующий шаг

- **`form_start {dir, target, task? | specPath?}`.** Определяет тип задачи детерминированно:
  - по спеке — `analyzeSpec` (`src/core/spec/analyze.ts:1027`);
  - по тексту — признаки: валидация, условия, вычисления, массивы, мастер, связи между полями.
    Правила `choose_api` (`src/core/decide/api-decision.ts`) переиспользуются, где подходят.
- По типу задачи собирается план из этапов: поля и раскладка → валидация → поведение → разметка
  (только core). Этапа без нужды в плане нет. План пишется в `<dir>/form.plan.json`.
- По спеке `form_start` сразу делает черновик через существующий `plan_form` (`src/core/tools/plan-form.ts`).
  Модели остаётся только список «Finish by hand» — он становится шагами плана.
- **Шаг плана** — ровно один готовый вызов `form_edit` с заполненными `dir` и `target`. К нему:
  - нужные секции грамматики, логика как у `sectionsFor()` в `src/prompts/plan-form.ts:115`;
  - один пример правки.

  Примеры не берутся из эталонов сценариев: holdout и настроечные эталоны — это прибор.
- **Каждый ответ профиля кончается блоком `Next:`** с одним вызовом. Он вычисляется по плану и
  результату сборки. `Done` сервер ставит сам, только когда все этапы собраны, типы проверены и на
  core есть разметка. Иначе ответ прямо говорит «не готово: …».
- **`form_status {dir}`** перечитывает план и состояние. Это на случай, если модель потеряла контекст.

### 2. Плоские правки `form_edit`

- **Вход:** `{dir, edits: [{op, …плоские поля}]}`. Операции: `add_field`, `set_field`,
  `remove_field`, `add_rule`, `add_behavior`, `add_array`, `add_item_field`, `add_step`, `place`
  (поле в шаг или группу). Ключи плоские, глубокой вложенности нет: это урок разбора вызовов Ollama
  из ассистента конструктора.
- **Перечисления в JSON Schema:** `op`, виды правил, виды поведения (тот же список, что
  `BEHAVIOR_KINDS` в `set-form-rules.ts` ассистента), компоненты кита. Имена полей схема перечислить
  не может, их проверяет сервер и подсказывает ближайшее имя.
- **Сервер применяет правки и сразу собирает.** Каждая правка проверяется отдельно:
  - чтение — `readIntent`/`normalizeIntent` (`src/core/generate/form-intent.ts:2265`, `:370`);
  - судья — `judgeIntent` (`src/core/generate/judge.ts`).

  Ответ по каждой отклонённой правке — что исправить. Принятые правки пишутся в `form.intent.json`.
  Затем идёт тот же конвейер, что у `form_build` (`planBuild` и проверка типов в
  `src/core/tools/form-build.ts`). Модель никогда не пишет intent целиком.
- **Ответ короткий:** строка ✓/✗ в контракте `form_build` (по ней разбирает стенд), сводка
  «полей / правил / поведений», затем `Next:`.
- **Из ассистента конструктора** (`projects/reformer-builder-playground/.ui_builder/plugins/reformer/ai/src/tools/`)
  берём словарь и уроки, но не код: он правит модель конструктора, а не FormIntent.

### 3. Автофиксы под замеренные ошибки

1. **Корпус.** Из `.tmp/mcp-runs/*/*/transcript.jsonl` вытащить все записанные `form.intent.json`
   (первые и промежуточные) и прогнать через текущие `readIntent` и `judgeIntent`. Получится
   список классов ошибок, которые всё ещё отклоняются, с частотой. Многое уже нормализуется:
   синонимы ключей, `each-lifted`, `prop-lifted` и т. д.
2. **Чинить классы по частоте:**
   - один `message` на несколько правил (13 из 27) — раздать каждому правилу или принять с
     предупреждением;
   - `target`, расходящийся с планом, — взять из плана с предупреждением;
   - ручная правка сгенерированного файла на renderer-таргетах — явный ответ «шаг не принят» с
     указанием, как сделать через `form_edit`.

   Каждый фикс помечается предупреждением своего кода, как сейчас в `IntentWarningCode`.
3. **Фикстуры корпуса** — в регрессионные тесты (`tests/`), без путей и сырья. Только минимальные
   intent-фрагменты.

### Не в этой итерации

- Ограниченное декодирование: включает клиент; можно позже для нашего стенда и ассистента, отдельным
  плечом.
- Дообучение (TinyAgent), каскад моделей.
- Elicitation.
- Правки Code Mode: snake_case-псевдонимы, пустой `{}` (6 + 4 скрипта из 73) — отдельная задача.

## Замер

- **Сначала база.** Подсказки `11oe.25–.27` после `ad08` не перемерены.
- **Условия прогона:** qwen3.5:4b, подходы `bare`, `code-mode`, `guided`, по 3 повтора. Сценарии
  L1–L4 и L5-loan (L5-credit слишком длинный для 6 ток/с). Это 81 прогон, около 8 часов. Прогонять
  ночью, от сети, под `caffeinate` (ReFormer-gnm6).
- **Итоги каждого батча** — в историю: `npm run mcp:history -- add <батч> --tag guided-weak`.
  Профиль — событием `server`.
- **Метрики:**
  - pass k/n по ячейкам, средний счёт;
  - число модулей, записанных мимо сборки (цель — 0);
  - ложный успех: финальное «готово» без статуса `Done`;
  - итераций до ✓, повторы отказа, токены и время.
- **Гипотеза приёмки:**
  - `guided` — L1–L2 не ниже 2 из 3 на сценарий (действующий порог для малых моделей);
  - L3–L4 не ниже 1 из 3;
  - средний счёт выше `code-mode` по знаковому тесту.
- **Holdout** — контролем после выбора решения, только агрегатом.
- **Отчёт** — `npm run mcp:approaches -- <батчи> --save packages/reformer-mcp/eval/runs/approaches/guided-weak.json`
  и `docs/mcp-eval/guided.md`.

## Проверка реализации

- Модульные тесты:
  - `form_start` — тип задачи и этапы для текста и для спеки;
  - `form_edit` — каждая операция, отказ с подсказкой, запись intent и сборка;
  - `Next:` и `Done` — по состояниям;
  - автофиксы — на фикстурах корпуса.
- Снимок поверхности `guided` и лимит инструкций в `surface-golden.test.ts`.
- `npx vitest run` пакета, `eslint`, смоук-матрица на обычной поверхности —
  `npm run mcp:scenarios -- --matrix smoke`.
- Один ручной прогон Ollama: L1-feedback, `--approach guided`, затем `npm run mcp:log -- latest`.
  Проверить, что модель идёт по `Next:`.
- Задачи — эпиком в bd при старте реализации.
