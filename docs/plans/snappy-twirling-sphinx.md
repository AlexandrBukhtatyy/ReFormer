# Лёгкий запуск: код плагинов читается по требованию

> **Статус (2026-10-05).** Этапы 0–4 выполнены; этапы 5 и 6 отложены по замеру
> (ReFormer-eeq0.8.6, ReFormer-eeq0.8.7), найдена задача ReFormer-eeq0.11. Цифры и доводы —
> `projects/reformer-builder/docs/decisions-log.md`, раздел «Запуск: код плагинов приложения
> читается по требованию».

> Ниже, после черты, — выполненный план эпика ReFormer-eeq0 (этапы 1–7), оставлен для истории.

## Context

После эпика «оболочка как база» с билдером едут 13 плагинов приложения. Замер на собранном
билдере (ReFormer-eeq0.8): до готовности ~1,0 с локально, и до первого кадра читается **всё**:

| Что | Сейчас | Нужно для запуска |
| --- | --- | --- |
| JS плагинов | 10,8 МБ, 39 файлов | 0,81 МБ (13 `main.js` + 7 общих чанков) |
| CSS плагинов | 0,38 МБ (345 КБ — Monaco) | почти ничего |
| Запросы | 62, плагины строго по одному | — |
| Кэш | нет: лаунчер без `ETag`, клиент с `no-cache` | — |
| Чанки самой оболочки | ~0,9 МБ греются зря (каталог кита, ajv) | — |

Причина одна: `import()` в плагине откладывает **разбор**, но не **чтение** — `collectFiles`
берёт каталог целиком, потому что `require` синхронен (`B/src/shell/platform/plugin/loader.ts:278`).

Обозначения: `B` = `projects/reformer-builder`, `API` = `packages/reformer-builder-plugin-api/src`,
`CLI` = `packages/reformer-builder-plugin-cli/src`, `PG` = `projects/reformer-builder-playground`.

### Можно ли грузить плагины асинхронно — три разных смысла

| Смысл | Ответ |
| --- | --- |
| Код **внутри** плагина — по требованию | Да, это главный рычаг: −92 % чтения. Этап 3 |
| Активировать плагины **после первого кадра** | Можно, но не стоит — см. «Не делаем» |
| Активировать **по событию** (как VS Code) | Отдельный контракт: манифест сегодня объявляет только клавиши и словари |

## Этапы

Порядок — от дешёвого и независимого к главному. Этапы 5–7 решаются по цифрам этапа 0.

### 0. Замер

- `performance.mark/measure` всегда, печать сводки — по флагу. Точки: цепочка `ready`
  (`B/src/shell/boot/boot.ts:1037-1089`), фазы `load` (`plugin/loader.ts:481-595`), регистрация /
  активация / стили / словари (`plugin/catalog.ts:718-782`), первый кадр (`B/src/main.tsx:65`).
- В сводку — `performance.getEntriesByType('resource')` по `/plugins/` и `/assets/`.
- Отдельной мерой — `preparePluginStyles`: CSS разбирается дважды и переписывается по правилу
  (`plugin/styles.ts:292-322`); у Monaco это 345 КБ — кандидат на второе место после чтения.
- e2e только для dist (`PG-e2e/tests/startup.spec.ts`): печатает сводку и утверждает **состав**
  запросов до `ready`, а не миллисекунды; медленная сеть — CDP `Network.emulateNetworkConditions`.

### 1. Лаунчер: `ETag` и 304

- `B/bin/reformer-builder.mjs` `sendFile` (223-232): `ETag` из размера и `mtimeMs`, 304 на
  `If-None-Match` без чтения файла; `/assets/**` (имена с хэшем) — `immutable`; `index.html`
  и `plugins/index.json` — `no-cache`. Клиент и формат индекса не меняются.
- Тесты — `B/src/shell/boot/launcher.test.ts`.

### 2. Параллельное чтение, порядок активации прежний

- `plugin/loader.ts`: манифесты — `Promise.all` с сохранением порядка (на него опирается
  `withoutDuplicates`, 390-412); в `load` стили и словари читаются параллельно с кодом, а
  результаты разбираются в прежнем порядке (код отказа при двойной поломке не меняется).
- `PluginLoader.prefetch(found)` — только ввод-вывод: `WeakMap` по объекту `DiscoveredPlugin`,
  одноразовый; промис не отклоняется; запись хранит источник, `load` сверяет его с текущим.
- `plugin/catalog.ts` `restoreEnabled` (898-901): перед циклом — `prefetch` для включённых.
  Догрузочные проверки `enablePlugin` (667-704) выносятся в один предикат: перекрытые копии
  и плагины с неподтверждёнными правами не предзагружаются. Цикл активации остаётся
  последовательным.

### 3. Чтение чанков по требованию (главное)

Граница — сам `import()`: он уже асинхронен в коде автора. Собранный код зовёт хост-функцию,
она дочитывает файлы и исполняет их в **том же** графе модулей.

**SDK** (`API/plugin`): секция `build` собранного манифеста — граф файлов; тип, разбор, имя
хост-функции константой. Незнакомый `format` — секции нет (читаем по-старому), битая —
`manifest-invalid`. Неизвестные поля разбор уже пропускает, старые оболочки секцию не заметят.

```json
"build": { "format": 1, "files": {
  "main.js": { "imports": ["chunks/chunk-A.js"], "runtime": ["react", "@reformer/ui-kit/button"] },
  "chunks/monaco-runtime-X.js": { "imports": ["chunks/chunk-A.js", "chunks/chunk-B.js"] }
} }
```

**CLI** (`CLI/commands/build.ts`, между шагом ESM и переводом в CommonJS):
- `import("…")` переписывается лексером `es-module-lexer` (новая зависимость CLI; по диапазонам,
  а не подстрокой) в `__reformerImport("./<путь от корня плагина>")`; пакетный спецификатор —
  тем же вызовом с именем пакета; вычисляемый не трогается.
- Сверка: переписанные цели каждого файла равны его `dynamic-import`-рёбрам из `metafile`,
  иначе отказ сборки. После шага 2 — нет `require` на отложенную цель.
- Пролог в файлах с вызовом (дописывается после шага 2): запасная реализация для **старых**
  оболочек со встроенной копией `__toESM` — собранный каталог остаётся самодостаточным графом
  CommonJS, `dry-run.ts` и стенд `link()` в `build-chunks.test.ts` работают без правок.
- Граф и списки `runtime` (статические внешние + `requiredByCall`) — в манифест. Правка путей
  модулей данных `split/join` (603-607) удаляется. Сборка печатает «сразу / отложенно, байт».

**Оболочка:**
- `B/src/shell/platform/modules/loader.ts`: `LoadOptions.lazy = { closure, read, prepare? }`;
  набор файлов графа живой (линковщик уже держит ссылку на `Map`). Хост-функция кладётся
  в `ambient`: всегда асинхронная граница (иначе ложный `ModuleCycleError`), склейка
  одновременных чтений, `prepare`, `linker.load` в том же графе, интероп — точная копия
  `__toESM` с кэшем на путь. Пакетная ветка: `registry.warm([spec])` → `registry.resolve` —
  отложенные пакеты перестают греться при запуске. Отказ чтения не запоминается и приходит как
  `ModuleLinkError('resolve')`. Возможность `ModuleLoaderCapability` оборачивается, чтобы
  `lazy` не утёк в контракт плагинов.
- `plugin/loader.ts`: при `manifest.build` читает `main` и его замыкание, греет по спискам
  `runtime` (`B/src/shell/boot/plugin-modules.ts` — рядом с `warm` появляется `warmNamed`), без
  `list()` и без регулярок по тексту; предел файлов считается по манифесту. Только для слоя
  приложения; проект и установленные из npm читаются целиком, но той же хост-функцией.
- `plugin/catalog.ts`: карта графов по образцу `styles` (406), `dispose` при выключении
  и на ранних выходах после `load`; отказ отложенного чтения — через `onProblem` (тост).

**Документы:** запись-пересмотр к `B/docs/decisions-log.md` (чтение по требованию там было
отвергнуто в виде `ctx`-службы), `plugin-and-shell.md` (раздел про `chunks/`), README CLI,
шапки `build.ts` и `API/plugin/layout.ts`.

### 4. Устойчивость и фоновая дочитка

- Повтор чтения в хост-функции при сетевом отказе; обёртка с повтором для `React.lazy`
  (`rjsf/render/src/surface.tsx`, `base/markdown-editor/src/ui/MarkdownEditor.tsx` — они
  запоминают отказ навсегда; `monaco-setup.ts` уже нет).
- После первого кадра, в простое — дочитать отложенные замыкания слоя приложения (с учётом
  `saveData`): первый открытый файл не ждёт 4,7 МБ, а остановленный лаунчер не ломает редактор.
- Текст исполненного файла отпускается (ключ остаётся для резолва).

### 5. Отложенная таблица стилей — по замеру

`--bundle-css`: CSS, достижимый только из отложенных чанков, — в `styles.lazy.css`; ставится
через `lazy.prepare` перед исполнением чанка, **перед** основной таблицей (авторские правила
обязаны остаться позже); `styles` в каталоге становится списком; гонка «выключили во время
чтения» — проверкой, что граф не выгружен.

### 6. Тонкие точки входа редких плагинов — по замеру

После этапа 3 `import()` действительно откладывает чтение. Ассистент (157 КБ, из них 27 % —
движок базы знаний), кодоген (143 КБ), шаблоны (103 КБ): тяжёлое — за `import()` в обработчиках
команд и панелях. Порог «байт сразу» на плагин — в `.size-limit.json`.

## Не делаем

- **Активация после первого кадра.** После этапов 1–5 до кадра остаются линковка и `activate`;
  выигрыш — пустая рамка раньше, а дерево и редакторы появляются тогда же. Цена: вид документа
  решается один раз при открытии, сохранённая ширина дока не применяется к панели, смонтированной
  позже, панели и ячейки всплывают со сдвигом, клавиши до активации молча не работают. Нужен
  ранний кадр — статический скелет в `index.html`.
- **Активация по событию.** Требует декларативных команд, редакторов и панелей в манифесте —
  отдельный контракт; этап 6 даёт большую часть его пользы.
- `?v=`/`revision` в индексе (Pages не отдаёт `immutable`, ошибка в ревизии запирает старый
  код), сжатие в лаунчере, чтение по требованию для плагинов проекта.

## Ожидаемый эффект

До первого кадра: JS плагинов 10,8 → ~0,8 МБ, CSS 0,38 → ~0,03 МБ (после этапа 5), минус
~0,9 МБ чанков оболочки; запросы параллельно; повторный запуск под лаунчером — 304 без тел.
Время — по замеру этапа 0, обещать цифру до него нечем.

# Приложение. Выполненный план эпика ReFormer-eeq0 «Оболочка как база» (этапы 1–7)

## Context

Оболочка `projects/reformer-builder/src/shell` должна годиться базой для других приложений,
а не только конструктора форм. Движки форм уже вынесены в плагины проекта-образца
(`projects/reformer-builder-playground/.ui_builder/plugins/{reformer,rjsf}`), но во встроенных
осталось семь плагинов, часть из них знает про формы, а `boot` знает три из них по типам портов.
Кроме того, плагин проекта исполняется только после открытия проекта и только из его каталога:
опубликованный `@reformer/builder` и билдер на Pages остались без движков (ReFormer-er5o).

Итог работы: встроенными остаются три маленьких общих плагина, всё остальное — пакеты плагинов
с исходниками в проекте-образце, которые едут вместе с приложением новым слоем «плагины
приложения». `boot` не импортирует ни одного плагина, в словаре оболочки нет текстов про формы.

Обозначения: `B` = `projects/reformer-builder`, `API` = `packages/reformer-builder-plugin-api/src`,
`CLI` = `packages/reformer-builder-plugin-cli/src`, `PG` = `projects/reformer-builder-playground`.

## Решения владельца

- Уезжают в плагины: файлы, редактор кода, markdown, превью, киты.
- Встроенными остаются управление плагинами и маленький плагин выбора профиля.
- Общие модули форм (`@reformer/core`, рендереры, `ui-kit`, `cdk`) отдаёт слой приложения билдера.
- Доставка — новый слой «плагины приложения»: едут со сборкой, поднимаются при старте.
- Monaco — движок внутри плагина; сборщик плагинов дорабатывается.
- Объём — перенос плюс чистка предметного в оболочке.

## Целевой состав

| Где | Что |
|---|---|
| Встроенные, `B/src/plugins/base/` | `plugin-manager`; `profile-switch` (ось профиля из `stack-switch`); `project` — открыть папку, недавние, стартовая страница, сохранить / сохранить всё |
| Плагины приложения, исходники в `PG/.ui_builder/plugins/` | `base/files`, `base/editor-monaco`, `base/editor-markdown`, `forms/kits` (вместе с выбором кита), `forms/preview`, движки `reformer/*`, `rjsf/*` |
| Только плагины проекта-образца | `kit-hexa-ui`, `playground-hello` |

Идентификаторы плагинов и возможностей (`reformer.files`, `reformer.editor`,
`reformer.kit.catalog`, `reformer.preview.live`…) не меняются — `requires` соседей править не надо.

## Решения, принятые в плане (показать владельцу)

1. **«Проект» остаётся встроенным.** Открытие каталога нужно до любого внешнего кода; оболочка,
   которая не может открыть проект без скачанных плагинов, хрупка. Плагин будет без портов —
   позже его перенос сведётся к перемещению каталога.
2. **Сохранение — во встроенном «проекте»**, а не в файлах: вкладки и признак «изменено»
   принадлежат оболочке, сохранять должен уметь любой состав.
3. **При совпадении идентификатора побеждает слой приложения**, копия из проекта показана
   перекрытой и не грузится (как сейчас нельзя подменить встроенный). Альтернатива — «проект
   перекрывает приложение», ценой двойной активации при открытии образца.
4. **В dev-запуске образца слоя приложения нет**: плагины остаются плагинами проекта с прежним
   авто-перезапуском «в разработке». Слой приложения проверяют dist-прогон e2e и тесты.
5. **Выбор кита — в самом `forms/kits`** (ячейка строки состояния и пункты палитры), третьего
   плагина не заводим.
6. **Команды «проекта» переименовываются** `files.openProject|save|saveAll|openRecent|clearRecent`
   → `project.*`; сочетания клавиш те же.
7. **Опубликованный билдер везёт полный набор** (основа, формы, оба движка, ассистент) —
   этим закрывается ReFormer-er5o.

## Слой «плагины приложения» — конструкция

- **Набор — индекс рядом с приложением**: `<base>plugins/index.json`
  (`{ version, plugins: [{ dir, files[] }] }`). Нет файла — слоя нет. HTTP не умеет «список
  каталога», поэтому список файлов лежит в индексе.
- **Чтение — существующим загрузчиком.** Он уже отвлечён от источника (`PluginFilesSource`:
  `id`, `capabilities.executesCode`, `list`, `read` — `B/src/shell/platform/plugin/loader.ts:119`).
  Новый адаптер `createHttpPluginFiles` — по образцу `installed/files.ts`; `executesCode: true`.
- **Каталог — второй экземпляр** `createProjectPluginCatalog`
  (`B/src/shell/platform/plugin/catalog.ts:278`): включено всё найденное, права выдаются
  из манифеста без вопроса (доверие уровня запуска, как у встроенных). Активация — внутри
  `ready`, сразу после встроенных, до первой отрисовки.
- **Связь с каталогом проекта**: в `capabilities()` проектного каталога добавляются возможности
  включённых плагинов приложения; новый параметр `reserved` называет занятые идентификаторы.
- **Кто отдаёт индекс**: лаунчер (`B/bin/reformer-builder.mjs`) — `dist/plugins` либо каталог
  из `--plugins <dir>`; сборка — скрипт собирает `build:dist` пакетов из списка
  `B/application-plugins.json` в `B/dist/plugins/` и пишет индекс; Pages получает то же
  копированием `dist`.

## Этапы

Каждый этап — задача в beads под общим эпиком; после каждого билдер в образце и e2e зелёные.

### 1. Слой плагинов приложения

- **Изменения**: `B/bin/plugins-index.mjs` (обход каталога → индекс, общий для лаунчера
  и сборки); `B/scripts/collect-application-plugins.mjs` + `B/application-plugins.json`;
  `B/src/shell/platform/plugin/application/http-files.ts`; второй каталог и активация
  в `B/src/shell/boot/boot.ts`; `reserved` и слой `'application'` в `catalog.ts`; строки
  приложения в разделе «Плагины» (`B/src/shell/boot/settings/PluginsSettings.tsx`) — только
  чтение; `--plugins` в лаунчере; сборка плагинов и сбор в `release.yml`, `deploy-docs.yml`.
- **Состав на этом этапе**: движки `reformer/*`, `rjsf/*` — опубликованный билдер снова
  открывает формы.
- **Проверка**: тесты адаптера и каталога (отказ сети, перекрытие, права без вопроса);
  интеграционный тест `boot` со слоем из памяти; e2e `BUILDER_E2E_TARGET=dist` — форма
  открывается редактором без включения плагинов в проекте.

### 2. Платформа форм уезжает: превью, киты, выбор кита

- **Изменения**: `B/src/plugins/base/preview` → `PG/.ui_builder/plugins/forms/preview`;
  `B/src/plugins/kits/registry` → `forms/kits`; из `stack-switch` ось кита — в `forms/kits`,
  остаток — встроенный `base/profile-switch` (прежнее имя — в таблицу `canonicalPluginId`,
  `STACK_SWITCH_PLUGIN_ID` в `B/src/application/builder-application.ts`). Списки общих модулей

- **Риски**: изолированные стили Monaco против его же стилей в `document.head` — проверить
  глазами; запасной выход — режим изоляции «без скоупа» для слоя приложения. Размер:

- **Проверка**: тесты CLI на каждую доработку; браузерный тест редактора; e2e — открыть
