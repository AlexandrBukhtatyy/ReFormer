# Конструктор внутри приложения: вторая оболочка и превью самим приложением

## Коротко

**Как это выглядит для разработчика приложения:**

1. Подключает пакет и оборачивает приложение компонентом `<ReformerBuilder>`.
2. Запускает dev-режим, открывает нужную страницу.
3. Нажимает кнопку «Билдер» — поверх страницы открывается конструктор с тем же набором
   возможностей, что в самостоятельном режиме.
4. Один раз выбирает папку проекта (File System Access), дальше она восстанавливается сама.
5. Правит форму или любой файл проекта и сохраняет — файлы пишутся прямо на диск.
6. В панели «Превью» видит результат, который рисует **само приложение**:
   - **Форма** — только компонент редактируемой формы, без остальной страницы;
   - **Приложение** — страница целиком, с адресной строкой;
   - **↗** — то же приложение в отдельной вкладке, без конструктора.

Конструктор об устройстве приложения не знает ничего: превью — это запущенное приложение в рамке,
а обновляет его собственный dev-сервер после записи файлов.

**Внутри:**

```
        плагины билдера (файлы, редакторы, инспектор, кодоген…) — одни и те же
                              │
              общая платформа и сборка (файлы — File System Access)
                     ┌────────┴────────┐
              оболочка SPA       встроенная оболочка
           своя вкладка,          в дереве React приложения,
           форму рисует билдер    форму и страницу рисует приложение
```

**Что делается, по порядку:**

1. Отдельная рабочая копия от `develop`, эпик и задачи в beads.
2. Общая сборка получает окружение параметром; привязка к вкладке браузера уходит в оболочку SPA.
   Проверка, что SPA не изменился, — до следующего шага.
3. Встроенная оболочка и компонент `<ReformerBuilder>`: кнопка, оверлей, стенд одной формы.
4. Плагин «Превью приложением» — панель с тремя режимами.
5. Статический каталог плагинов и общие псевдонимы сборки для приложения.
6. Демо-приложение и e2e.
7. Документация.

**Не входит:** любое знание билдера о приложении — его реестр, источники данных, компоненты
в палитре, нотификации приложения на события билдера. Это будущий плагин сотрудничества.
Также не входят изоляция стилей, публикация в npm и прод-режим. Коммитов нет до явной просьбы.

## Context

Сейчас конструктор (`@reformer/builder`) — только самостоятельное SPA: формы в превью рисует он
сам, с данными-заглушками, и о приложении, для которого форма делается, ничего не знает. Нужно,
чтобы тот же конструктор запускался внутри разрабатываемого приложения, а результат был виден
в настоящем приложении — с его реестром, его API и его нотификациями.

Исходные сценарии закрываются без интеграции с приложением: словарь приходит из реального API,
потому что форму рисует приложение; тост при отправке формы показывает оно же; правка сервиса
во встроенном редакторе кода попадает на диск, и dev-сервер приложения обновляет превью.

Что есть в коде под эту постановку:

- Слои билдера разделены: `shell/platform/` — механизмы, `shell/boot/` — сборка, `application/` —
  состав плагинов (`projects/reformer-builder/docs/project-structure.md`).
- Кодоген билдера печатает в каталоге формы `index.tsx` с компонентом формы по умолчанию
  (`projects/reformer-builder-playground/forms/templates/reformer-simple-form/index.tsx:26`).
- Панели вносятся плагинами через `PanelPoint`, слоты фиксированы (`docs/plugin-and-shell.md:731-762`).
- Поверхности, которыми форму рисует сам билдер, вносит плагин `reformer/render`; без него
  «живой вид» редактора просто недоступен (`forms/preview/src/live/live-service.ts:86`).

## Принятые решения

| Вопрос | Решение |
|---|---|
| Два режима | Две оболочки над одной платформой: билдер — набор плагинов, оболочка — то, что их запускает |
| Размещение | Встроенная оболочка монтируется в дерево React приложения, общий React |
| Знание о приложении | Никакого. Сотрудничество с конкретным приложением — будущий плагин |
| Файлы проекта | File System Access в обеих оболочках. Vite-плагина и хранилища через dev-сервер нет |
| Запись на диск | По Ctrl+S, как сейчас; автосохранения нет |
| Превью формы | Рисует только приложение. Собственный живой вид билдера во встроенной оболочке отсутствует; структура правится деревом и схемой |
| Виды превью | Только форма; всё приложение; приложение в отдельной вкладке |
| Способ показа | Рамка (iframe) с адресом самого приложения: у формы настоящие стили и область просмотра, стили билдера в неё не попадают |
| Граница оболочек | Обе — каталоги внутри `projects/reformer-builder`, два входа |
| Потребление в первой итерации | Исходники через псевдонимы в конфиге сборки приложения; библиотечная сборка — этап упаковки |
| Где вести работу | Отдельная рабочая копия `D:/Work/ReFormer-builder-embedded`, ветка `feature/builder-embedded` от локального `develop` — как сделано для соседних работ. Без коммитов до явной просьбы |
| Ф9 (единый контракт) | Не пересекается: сборку превью билдера этот план не трогает |

## Устройство

Сокращения путей: B = `projects/reformer-builder`, PG = `projects/reformer-builder-playground`,
API = `packages/reformer-builder-plugin-api`, HOST = новый `projects/reformer-builder-host-example`.

### Две оболочки

```
B/src/
  shell/platform/     механизмы — общие
  shell/boot/         общая сборка; окружение получает параметром
  shell/standalone/   оболочка SPA: окружение вкладки браузера
  shell/embedded/     встроенная оболочка: окружение страницы приложения
  main.tsx            вход SPA
  index.ts            вход библиотеки
```

| Что | Оболочка SPA | Встроенная оболочка |
|---|---|---|
| Проект и файлы | File System Access | то же самое |
| Интерфейс | на всю вкладку | тот же, оверлеем на всю страницу, пока включён режим |
| Стили и признак темы | в документе всегда | подключаются при включении режима, снимаются при выключении |
| Заголовок документа | ставит | не трогает |
| Очистка хранилища origin, перезагрузка, выбор профиля | есть | нет: хранилище общее с приложением |
| Кто рисует форму | билдер (`reformer/render`) | приложение (плагин «Превью приложением») |
| Плагины приложения | рядом со сборкой | по адресу из пропа компонента |

Привязка к окружению в `shell/boot/boot.ts` — несколько мест (заголовок `:419-424`, корень темы
`:481-487`, перезагрузка `:511-513`, очистка хранилища `:1312-1324`); они переходят на порт:

```ts
export interface ShellEnvironment {
  /** Заголовок документа. Оболочка без своей вкладки метод не даёт. */
  applyTitle?(title: string | undefined): void;
  /** Куда ставится признак тёмной темы. */
  readonly themeRoot: ThemeRoot | null;
  /** Перезапуск приложения. Без него смена профиля недоступна. */
  readonly reload?: () => void;
  /** Обслуживание хранилища origin. Без него команда «Очистить кэш» не регистрируется. */
  readonly storage?: StorageMaintenance;
  /** Возможности, которые оболочка добавляет до активации плагинов. */
  registerCapabilities?(services: ServiceRegistry): void;
}
```

Правила импорта (линтер билдера): оболочки импортируют `shell/boot` и `shell/platform`, но не
`application/` и не друг друга. Состав плагинов с оболочкой соединяет только вход.

### Компонент `<ReformerBuilder>`

```tsx
// main.tsx приложения
createRoot(document.getElementById('root')!).render(
  <AppProviders>
    <ReformerBuilder pluginsUrl="/builder-plugins/">
      <App />
    </ReformerBuilder>
  </AppProviders>
);
```

| Где открыт документ | Что рисует компонент |
|---|---|
| Обычная страница, dev | приложение и кнопку «Билдер» |
| Режим включён | оверлей с конструктором; код конструктора подгружается в этот момент |
| Внутри рамки превью | только приложение, без кнопки |
| Внутри рамки превью, адрес стенда | только компонент формы — `index.tsx` из её каталога |
| Прод-сборка | только приложение |

Провайдеры, внутри которых стоит компонент, действуют и на форму в стенде. Состояние режима
переживает перезагрузку страницы. Необязательные пропы: префикс адреса для папки проекта (если
открыта не корневая папка dev-сервера) и своя функция загрузки модуля формы — для сборщиков,
которые не отдают исходники по адресу.

### Превью приложением

Плагин вносит панель «Превью» в правый док. Адреса ему даёт возможность, которую регистрирует
встроенная оболочка, — сам плагин о приложении ничего не знает:

```ts
// API/src/services/app-preview.ts
export interface AppPreviewService {
  /** Адрес страницы приложения, с которой включили режим билдера. */
  pageUrl(): string;
  /** Адрес, по которому приложение рисует одну форму; `null` — у документа нет модуля формы. */
  formUrl(documentPath: string): string | null;
}
export const AppPreviewCapability = defineCapability<AppPreviewService>({
  id: 'reformer.app.preview',
  version: '1.0.0',
});
```

- **Форма** следует за активным документом: берётся каталог открытого файла и его `index.tsx`.
  Нет модуля — панель говорит об этом и предлагает сгенерировать его командой кодогена.
- **Приложение** — рамка с адресной строкой и кнопкой обновления.
- **↗** открывает текущий адрес в новой вкладке без конструктора.
- Полоса в панели напоминает: показана сохранённая версия.

## Шаги

Порядок: 1 → 2 → 3; шаги 4 и 5 независимы от 2–3 и идут параллельно; 6 требует всех.

### Шаг 0. Рабочая копия и задачи

- **Рабочая копия.** `git worktree add -b feature/builder-embedded ../ReFormer-builder-embedded develop`
  и переход сессии в неё. Ветка берётся от локального `develop` (он на два коммита впереди
  `origin/develop`), а не от ветки по умолчанию `main`.
- **Подготовка копии:** установка зависимостей, сборка пакетов, которые билдер берёт собранными,
  сборка plugin-api и плагинов. До первой правки — прогон тестов билдера как точка отсчёта
  для критерия «SPA не изменился».
- **Задачи в beads** — эпик и по задаче на шаг, с зависимостями. Команды `bd` выполняются из
  основной копии `D:/Work/ReFormer`: база задач лежит там, а файлы `.beads` в ветке не трогаются.
- Копия этого плана кладётся в `docs/plans/` рабочей копии, чтобы он ехал вместе с веткой.

### Шаг 1. Возможность превью в plugin-api

`API/src/services/app-preview.ts`, экспорт в `API/src/index.ts` и `API/src/internal.ts`.
Переиспользуется `defineCapability`. После шага пересобрать `dist` пакета.

### Шаг 2. Общая сборка с портом окружения и оболочка SPA

- `shell/boot/environment.ts` и поле `environment` в `BootOptions`; прямые обращения к документу
  и окну уходят из `boot.ts`.
- `shell/standalone/`: окружение вкладки браузера, запуск (нынешнее содержимое `main.tsx`),
  корневой компонент (нынешний `App.tsx`). `main.tsx` остаётся входом Vite.
- `B/eslint.config.js`: зоны двух оболочек.
- Критерий: существующие юнит-, интеграционные и e2e-тесты SPA зелёные без правок тестов.

### Шаг 3. Встроенная оболочка и компонент

- `shell/embedded/`: окружение страницы приложения (стили и тема на время режима, без заголовка,
  без очистки хранилища и перезагрузки, регистрация `AppPreviewCapability`), запуск сборки по
  первому включению режима, оверлей.
- `ReformerBuilder.tsx`: кнопка, состояние режима, распознавание рамки превью, стенд формы
  (загрузка модуля по адресу, граница ошибок, сообщение при отсутствии компонента по умолчанию).
- `B/src/index.ts` — вход библиотеки: соединяет состав плагинов с встроенной оболочкой.
- Состав без выбора профиля и без установки плагинов из npm.
- `B/src/index.css`: явный источник классов на каталог билдера, чтобы набор утилит не зависел от
  корня сборки приложения; стили подключаются строкой и снимаются при выключении режима.
- Переиспользуются `applicationFromRuntime`, `loadApplicationFiles`, `useProjectSession`.
- Тесты: сборка встроенной оболочки (заголовок не тронут, команды очистки хранилища нет, стили
  и признак темы сняты после выключения), компонент (пять состояний из таблицы), `structure.test.ts`.

### Шаг 4. Плагин «Превью приложением»

- Новый пакет `PG/.ui_builder/plugins/base/app-preview/` по образцу соседних плагинов `base/*`:
  вклад в `PanelPoint` (слот правого дока), чтение `AppPreviewCapability`, активный документ —
  через службу документов.
- Без возможности (оболочка SPA) плагин ничего не вносит.
- Тесты: модель панели (режимы, адрес формы по активному документу, отсутствие модуля),
  браузерный тест панели.

### Шаг 5. Каталог плагинов и псевдонимы для приложения

- `B/scripts/collect-application-plugins.mjs` получает параметры: список плагинов и выходной
  каталог (сейчас зашиты `application-plugins.json` и `dist/plugins`).
- Список для встроенной оболочки: без `reformer/render` и `rjsf/render`, с `base/app-preview`.
- Псевдонимы из `B/vite.config.ts:213-240` выносятся в общий модуль для конфигов билдера
  и приложения. Временно — до библиотечной сборки.

### Шаг 6. Демо-приложение и e2e

- `projects/reformer-builder-host-example`: провайдер приложения, две страницы, форма
  `src/forms/contact/` (модуль, сгенерированный билдером) со словарём из `GET /api/cities` —
  честный эндпоинт dev-сервера приложения, собственные тосты на обычном CSS, скрипт сборки
  каталога плагинов в статику.
- E2E: цель `BUILDER_E2E_TARGET=embedded` в `projects/reformer-builder-playground-e2e`, тесты
  в `tests/embedded/`. Проект открывается существующим приёмом — диалог выбора папки подменён
  диском в памяти браузера (`tests/shared/playground-disk.ts`). Сохранённый файл тест переносит
  на настоящий диск сам, после чего проверяет превью. Сервер — над копией демо-приложения
  в `.tmp/e2e/host-example/`.

### Шаг 7. Документация

`B/docs/embedding.md`, запись в `decisions-log.md`, правка таблицы слоёв в
`B/docs/project-structure.md`. Имена утилитарных классов в документах билдера буквально не писать.

## Проверка

```bash
node ../../scripts/run-vitest.mjs [файлы]                       # в projects/reformer-builder
node ../../scripts/run-vitest.mjs -c vitest.browser.config.ts   # браузерные
```

Типы — только из каталога пакета (никогда `tsc -b` из корня). Линт — `npx eslint <файлы>` из корня
и `npm run lint -w @reformer/builder` (границы слоёв проверяет только он). Перед e2e —
`npm run plugins:dist -w reformer-builder-playground`.

E2E, цель `embedded`:

1. Кнопка включает режим; интерфейс конструктора тот же, что в SPA; проект открывается.
2. Панель «Превью», режим «Форма»: в рамке только форма, словарь пришёл из `/api/cities`.
3. Режим «Приложение»: в рамке страница целиком; переход по адресной строке работает.
4. Отправка формы в превью показывает тост приложения.
5. Правка схемы и сохранение — превью обновилось.
6. Правка файла сервиса во встроенном редакторе и сохранение — словарь в превью изменился.
7. Выключение режима: страница приложения выглядит как до включения (стили, тема, заголовок).
8. В рамке превью кнопки «Билдер» нет.
9. Существующий набор e2e самостоятельного режима проходит без правок.

Вручную (автотест подменяет диск памятью браузера): в настоящем Chromium выбрать папку
демо-приложения, поправить форму и сервис, сохранить — файлы на диске изменились, превью
обновилось; открыть приложение в отдельной вкладке кнопкой.

Скриншоты — в `projects/react-playground-e2e/screenshots/builder-embedded/`, временные файлы —
в `.tmp/`.

## Следующие этапы

1. **Плагин сотрудничества с приложением**: источники данных и компоненты приложения в инспекторе
   и палитре, нотификации приложения на события билдера, выбор узла кликом по форме в превью.
2. **Упаковка и изоляция**: библиотечная сборка и публикация, стили билдера без влияния на
   документ, пространство имён хранилищ, вынос платформы в пакет.
3. **Прод-режим**: проект поверх хранилища приложения, без исполнения кода.

## Риски

1. **Сохранение может перезагрузить страницу.** Билдер и приложение живут в одном документе:
   если изменённый файл формы уже загружен страницей и обновление «на лету» не применилось,
   dev-сервер перезагрузит всю страницу вместе с конструктором. Страховка — режим, проект
   и вкладки восстанавливаются после перезагрузки, а несохранённое лежит в рабочей копии.
   Проверяется вручную на шаге 6; если мешает — приложению рекомендуется ленивая загрузка страниц.
2. **Стили в одном документе.** Стили билдера на время режима действуют на весь документ
   (страница под оверлеем скрыта, рамки превью — отдельные документы), а глобальные стили
   приложения действуют на интерфейс билдера. Полная изоляция — следующий этап.
3. **Версия React.** Билдер исполняется на React приложения; в первой итерации поддерживается
   React 19.
4. **Стенд формы зависит от сборщика.** Загрузка `index.tsx` по адресу работает под dev-сервером
   Vite; для остальных — проп с функцией загрузки.
5. **Разбор `boot.ts`** затрагивает путь SPA; шаг 2 заканчивается полным прогоном тестов SPA.
6. **File System Access** — только Chromium, и браузер может заново спросить доступ к папке.
7. **Псевдоним приложения**, совпадающий с внутренним псевдонимом билдера, перехватит его
   импорты — до библиотечной сборки.
8. **Редактор формы без живого вида** (по чтению кода: служба отвечает «недоступно», когда
   поверхностей нет) — убедиться на шаге 5, что вид скрывается, а не показывает пустоту.

## Ограничения репозитория

- `docs/specs/` — только чтение. Коммит и пуш — только по явной просьбе.
- Незакоммиченные правки пользователя в основной копии (`PG/forms/contact/form.schema.json`,
  `PG/forms/templates/`) не трогать; в рабочую копию ветки они не попадают. Форма демо-приложения
  пишется заново в его каталоге, шаблон из основной копии служит только образцом для чтения.
- Основная копия и соседние рабочие копии (`ReFormer-unified-contract`,
  `ReFormer-core-contract-cleanup`) принадлежат другим работам — в них ничего не менять.
- В листингах — полные слова в именах, без сокращений.
