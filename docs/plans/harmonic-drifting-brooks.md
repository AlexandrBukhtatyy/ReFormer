# Code Mode для `@reformer/mcp`: можно ли внедрить, что даст, как мерить

## Context

Статья Cloudflare «Code Mode» (blog.cloudflare.com/code-mode) предлагает не отдавать модели
инструменты MCP напрямую. Схемы инструментов превращаются в TypeScript API с JSDoc. Модель получает
**один** инструмент «выполни код», пишет скрипт, который зовёт API, и скрипт исполняется в
песочнице (V8-изолят без сети, наружу — только через bindings). Промежуточные результаты остаются в
песочнице, модель видит только `console.log`. Аргументы авторов: модели лучше пишут код, чем
tool-calls, а цепочки вызовов не гоняют данные через контекст. **Цифр в статье нет** — значит,
решать будем своими замерами.

Почему это вопрос именно для нас (данные из `docs/mcp-eval/`):

- **Фасад** ([facade.ts](packages/reformer-mcp/src/core/facade.ts), в ассистенте — инструмент
  `ask_reformer`) — это уже Code Mode-скрипт, только написанный нами: каскад
  `choose_api → find_recipe → search_docs` одним вызовом. Замер 2026-08 (корпус 49 задач):
  он дешевле набора (28.9 тыс. токенов против 34.6 тыс., поверхность ~350 символов против 2858),
  но теряет 8 п.п. first-pass и 4 п.п. hit — модель **не может вести поиск**: переформулировать,
  ветвиться. Code Mode возвращает модели руль, не возвращая промахи в контекст.
- **Поверхность ассистента конструктора** — 20 инструментов, храповик `TOOL_SURFACE_BUDGET = 13667`
  символов, которые уходят в КАЖДЫЙ шаг хода
  ([types.ts:210](projects/reformer-builder-playground/.ui_builder/plugins/reformer/ai/src/model/types.ts#L210)).
  Пакетная правка уже однажды выиграла: `build_form` вместо десятков `insert_node` дал на qwen
  39 % времени и 56 % входных токенов. Code Mode — обобщение того же хода на чтение и правку.
- **Локальные модели тонут в контексте:** `reformer://guide` ~100 тыс. символов, у qwen 66–436
  усечений за прогон при контексте 32k.
- **Сборка формы уже декларативна:** агент пишет `form.intent.json`, `form_build` компилирует. Это
  «Code Mode на JSON», и он сработал (L5-credit: 60 → 11 ходов, 1/3 → 5/5). Этот путь не меняем:
  аудит 2026-11 (`docs/mcp-eval/audit-2026-11.md`) показал, что главная беда сервера — несколько
  несовместимых путей. Code Mode должен быть **другой поверхностью над тем же ядром**, а не новым
  путём создания формы.

Итог работы — ответ «внедрять / не внедрять / где именно», подтверждённый цифрами на существующих
стендах, и запись в `docs/mcp-eval/code-mode.md` в стиле `builder-toolset.md` (с отрицательным
результатом, если он будет).

**Решения, принятые с пользователем:**

| Вопрос                  | Решение                                                                                   |
| ----------------------- | ----------------------------------------------------------------------------------------- |
| Для каких моделей       | Claude **и** локальные (qwen3.8:27b, gemma4:26b). Сначала sonnet, затем локальные; в ассистент — только если локальные проходят порог H4 |
| Песочница               | QuickJS-wasm (`quickjs-emscripten`): один рантайм для stdio-сервера и воркера в браузере   |

## Гипотезы и что считать успехом

| #  | Гипотеза                                                                                                  | Где меряем                     | Порог «да»                                                       |
| -- | --------------------------------------------------------------------------------------------------------- | ------------------------------ | ---------------------------------------------------------------- |
| H0 | Скрипт в песочнице способен воспроизвести каскад фасада без потерь                                        | `mcp:evaluate`, без модели     | hit/first-pass скрипта = стратегия `builder-facade` побитно      |
| H1 | Поверхность `run_script` + объявление API меньше набора при том же покрытии                               | статика `tools/list`           | ≤ 1500 символов при покрытии всех read-only инструментов (полный набор — 8854 по замеру 2026-08) |
| H2 | Code Mode закрывает разрыв фасада: точность набора по цене фасада                                         | новый живой корпус (61 задача) | first-pass ≥ `v6-choose` − 2 п.п., токены ≤ фасада, сбоев скрипта ≤ 10 % (Claude) |
| H3 | На лестнице сценариев Code Mode не хуже `bare` и экономит ходы на длинных цепочках                         | `mcp:scenarios`, L1–L5         | вердикт не ниже (интервалы Уилсона пересекаются), медиана ходов и входных токенов L4–L5 −20 % |
| H4 | Локальные модели способны писать рабочие скрипты                                                          | те же стенды, qwen/gemma       | сбоев скрипта ≤ 25 %, пиковый контекст шага ниже, чем у набора    |

Порядок жёсткий: H0/H1 без модели и бесплатно → H2 → H3/H4 → (только если всё да) ассистент
конструктора. Провал на любом шаге — остановка и запись отрицательного результата.

## Что строим (минимум для эксперимента, за флагом)

### 1. API для скриптов — `packages/reformer-mcp/src/core/codemode/`

- `api.ts` — объект `reformer` с **структурными** результатами, а не markdown. Скрипт должен
  ветвиться по данным: `if (!hits.length) …`. Строится на существующих функциях ядра, ничего не
  дублирует:
  - `chooseApi(requirement, target?)` → `ApiChoice[]` — `chooseApi` / `chooseApiPerRequirement`
    из [decide/api-decision.ts](packages/reformer-mcp/src/core/decide/api-decision.ts);
  - `searchSymbols(query, pkg?, limit?)` → `SymbolHit[]` — `searchSymbols`/`rankSymbolsForQuery` из
    [index/search.ts](packages/reformer-mcp/src/core/index/search.ts);
  - `symbol(name, pkg?)` → `PublicSymbol` — `findOneSymbol` из `index/symbols.ts`;
  - `searchDocs`, `recipe(topic)`, `context(task)` — над теми же функциями, что
    `search-docs.ts`/`find-recipe.ts`/`get-context.ts`, с полем `text` для чтения и полями для
    ветвления;
  - `ask(task)` — сам фасад `askReformer`, чтобы у модели был «быстрый путь» одной строкой;
  - `validateForm(...)`, `formBuild({ dir })` → `{ ok, findings: JudgeFinding[] }` — для H3:
    скрипт сам фильтрует диагностику, наружу уходят только важные (лечит находку A8 аудита: «≤10
    предупреждений, важные тонут»).
- `api.d.ts` — компактное объявление для модели (сигнатуры + однострочные JSDoc). Пишется руками,
  сверяется с `api.ts` тестом типов (`tsc` на файле-образце), а не генерируется из JSON Schema: у
  нас структурные результаты, которых в `inputSchema` нет, и ручной текст короче.
- Перехват вызовов: каждый вызов binding пишется в `server-trace.jsonl` вложенной строкой
  (`call`, `inner`, имя, длительность, размер ответа), чтобы `mcp:log` показывал, что скрипт делал
  внутри. Без этого Code Mode — чёрный ящик для разбора прогонов.

### 2. Песочница — `codemode/sandbox.ts`

- **QuickJS (wasm)**, пакет `quickjs-emscripten` (решено). Довод: один и тот же рантайм работает
  и в stdio-сервере (Node), и в воркере конструктора (браузер) — тот принцип «одного пути», к
  которому ведёт аудит. Нет `fs`/`fetch`/`require`; наружу — только функции `reformer.*`,
  проброшенные хостом. Лимиты: время (interrupt handler, 5 с), память (32 МБ), размер вывода
  (бюджет ответа инструмента).
- Раскладка по слоям сервера: `core/` не трогает node-глобалы (`npm run check:no-node-globals`),
  поэтому в `core/codemode/sandbox.ts` — только интерфейс и логика bindings, а загрузка wasm —
  в `platform/cli/` (с диска) и `platform/worker/` (вшитый модуль, проверить размер бандла
  `scripts/build-worker.mjs`).
- Отвергнуто: `node:vm` — не граница безопасности; `isolated-vm` — нативный модуль, в браузер не
  едет; `ses` — тот же realm, бесконечный цикл не прервать.
- Язык скрипта — **JavaScript** (async-функция), `api.d.ts` показывает типы. TS не принимаем:
  транспиляция в браузере тянет esbuild-wasm, а для эксперимента разница не нужна. Если модели
  будут упорно писать TS — снимать типы `esbuild.transform` на стороне Node и отметить это в
  записи.

### 3. Инструмент `run_script` и флаг поверхности

- `codemode/tool.ts` — `run_script({ code })`: исполняет, возвращает вывод `console.log`, обрезанный
  `assemble()` из `context/budget.ts`, плюс ошибку со строкой и столбцом. Описание инструмента =
  абзац + `api.d.ts`.
- Регистрация в [server/tool-catalog.ts](packages/reformer-mcp/src/core/server/tool-catalog.ts) за
  переменной окружения `REFORMER_SURFACE=code`: `tools/list` = `[run_script, form_build]`
  (`form_build` остаётся отдельным — он пишет файлы, это не извлечение). По умолчанию поверхность
  не меняется, `tools/list` сервера без флага остаётся побитно прежним (проверка в тесте).

## Как мерим

Все записи — в общий формат `eval/records/` (`record.mjs`, `schema.json`), сравнение —
`mcp:compare`. Новые поля записи:

| Поле               | Смысл                                                                  |
| ------------------ | ---------------------------------------------------------------------- |
| `scripts`          | число вызовов `run_script`                                             |
| `scriptFailures`   | `{ syntax, runtime, timeout, limit }` — по видам                       |
| `innerCalls`       | вызовы `reformer.*` внутри скриптов (то, что модель НЕ видит)          |
| `peakStepInput`    | максимум входных токенов за один шаг модели (важно для 32k)            |

Остальное уже есть: вердикт и счёт, токены вход/выход, ходы, вызовы MCP, цена, время, усечения
Ollama, недействительные прогоны.

### Шаг 0 — без модели (H0, H1), CI-пригодно

- Стратегия `eval/strategies/code-facade.mjs`: эталонный скрипт, повторяющий каскад `v6-choose`,
  исполняется в песочнице через `run_script`. Должен дать те же hit/first-pass/токены, что
  `builder-facade`. Доказывает, что API и песочница не теряют знание.
- Статика: `measureToolSurface` (формула конструктора, `assistant-surface.test.ts`) для
  `run_script` и для `tools/list` с `REFORMER_SURFACE=code`.
- **Оценка выигрыша для редактора — тоже без модели.** Переписать текущие 20 инструментов
  ассистента как `.d.ts` (сигнатуры + однострочные JSDoc с той же информацией) и измерить той же
  `measureToolSurface`. Если `.d.ts` не короче JSON-поверхности хотя бы на 40 % — переводить
  редактор в Code Mode незачем, шаг 3 сводится к замене `ask_reformer`.

```bash
node packages/reformer-mcp/eval/runner.mjs --strategy code-facade --baseline .tmp/no-baseline.json
```

### Шаг 1 — живой корпус извлечения (H2)

Сейчас `mcp:evaluate` модель не запускает: стратегии подают готовые формулировки. Code Mode без
модели не проверить, поэтому нужен живой вариант того же корпуса:

- `eval/live/run.mjs` — задача корпуса (`task`, без `queries`) уходит агенту вопросом «какой API
  ReFormer решает это?». Засчитывается, если имя из `expectAny` есть в финальном ответе
  (`lib/match.mjs`, тот же матчер, что у стратегий). First-pass — имя всплыло в ответе первого
  вызова MCP (для `code` — в выводе первого `run_script`), по `server-trace.jsonl`. Запись —
  `harness: retrieval`, `agent.kind` настоящий, `approach.id` = поверхность.
- Три поверхности на одних задачах: `set` (`choose_api + find_recipe + search_docs`), `facade`
  (один `ask`), `code` (`run_script`). Агенты — существующие адаптеры `claude-code` и `ollama`,
  с `approach.withoutTools` и env сервера.
- Матрица в два захода, чтобы не жечь лимит: (а) sonnet × 3 поверхности × 61 задача × 1 повтор
  (183 коротких прогона); (б) повторы ×3 только для задач, где поверхности разошлись, плюс тот же
  набор на gemma4:26b. Оценка стоимости — до запуска, `--max-usd-batch`.

### Шаг 2 — лестница сценариев (H3, H4)

- Подход `code-mode` в [approaches.json](packages/reformer-mcp/eval/scenarios/approaches.json): тот
  же текст задания, что у `bare`, сервер с `REFORMER_SURFACE=code`. Сейчас подход умеет только
  `promptPrefix`, `serverPrompt` и `withoutTools` — добавить поле `serverEnv` и прокинуть его в
  env сервера в [claude-code.mjs:205](packages/reformer-mcp/eval/agents/claude-code.mjs#L205)
  (`mcp.json`) и в `ollama.mjs`; описать в `agents/types.mjs`. `approach.id` уже пишется в запись,
  так что `mcp:compare` разведёт подходы без правок.
- Матрица `code-mode.json`: L1-feedback, L3-order-total, L4-contacts-array, L5-loan, L5-credit ×
  {`bare`, `code-mode`} × sonnet × N=5; qwen3.8:27b-32k и gemma4:26b — L1–L3 × N=3.
- Итог — `mcp:compare <bare> <code-mode>` по ячейкам «сценарий × подход».

### Шаг 3 — ассистент конструктора (только если H2 и H3 — да)

- Заменить `ask_reformer`
  ([reformer-docs.ts](projects/reformer-builder-playground/.ui_builder/plugins/reformer/ai/src/tools/reformer-docs.ts))
  на `run_script` над тем же API. Справка вызывается функциями напрямую (`askReformer` из
  `dist/core/facade.js`), значит песочница едет в браузер тем же QuickJS-wasm.
- **Пробел замера, закрыть до шага 3:** записи `mcp:builder-ladder`
  (`eval/records/import-builder.mjs`) не несут токенов и `usage` — только число вызовов и время.
  Без них сравнение «ход дешевле» невозможно. Протянуть `usage` из AI SDK (`streamText` отдаёт его
  по шагам) в `ladder.json` и в запись.
- Перевод **редактора** в API для скриптов — только если оценка шага 0 дала ≥ 40 % экономии
  поверхности и H4 подтвердилась на qwen/gemma: это главный возможный выигрыш (13 667 символов в
  каждом шаге) и главный риск для локальных моделей.

## Где ещё может быть польза (проверяем попутно, не обещаем)

- **Прогрессивное раскрытие вместо `reformer://guide`:** скрипт ищет и печатает 2–3 секции вместо
  100 тыс. символов. Видно по `peakStepInput` и числу усечений у Ollama.
- **Самопроверка до сборки:** `reformer.symbol('ModelArray')` в скрипте показывает агенту, что у
  массива нет `.reduce` — находка qo9b.30 («запускать агенту нечем»).
- **Эталонные скрипты как регрессионные тесты API:** `replay`-агент исполняет сохранённые скрипты
  в CI — ломающее изменение API сервера краснеет без модели.

## Риски

- **Локальные модели пишут код хуже, чем зовут инструменты.** Поэтому H4 меряется отдельно и
  ассистент конструктора — последним шагом.
- **Второй путь.** Пока флаг не снят, поверхность экспериментальная. Если гипотезы подтвердятся —
  заменяем, а не добавляем; если нет — удаляем `codemode/` целиком.
- **Отладка.** Без вложенной трассы прогон нечитаем — трасса входит в шаг 0, а не «потом».
- **Песочница.** Нет `fs`/сети внутри; `formBuild` пишет только в `dir` рабочего каталога, как
  сейчас `form_build`. Отдельный тест: скрипт с `require`, `fetch`, `while(true)`, 100 МБ строки —
  все отказывают с понятной ошибкой.
