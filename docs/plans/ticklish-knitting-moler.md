# `@reformer/ai-kit` — встраиваемый ассистент приложения

## Context

Нужен новый пакет с AI-ассистентом. По уточнению постановки это **не** ReFormer-специфичный
ассистент и **не** MCP-инфраструктура:

> **ai-kit — это чат, который встраивают в разные приложения, чтобы работать с самим приложением;
> и, возможно, интегрировать его с внешними сервисами.**

Центр тяжести — **приложение-хост**. Чат живёт внутри него, читает его состояние, выполняет его
операции, водит пользователя по его интерфейсу. Внешние сервисы — второй слой, опциональный.
WebMCP и MCP — **способы объявить и подключить операции**, а не суть продукта: приложение обязано
уметь отдать себя ассистенту напрямую из кода, без единой строчки протокола.

**Почему это уместно именно здесь.** В монорепо три опоры, которых больше нигде не будет:

1. **Живой агент в билдере** — [projects/reformer-builder/src/agent/](../../projects/reformer-builder/src/agent/),
   ~8.3k строк, прошедший реальные прогоны на Anthropic/OpenAI/Ollama. Пользователь решил
   **писать ai-kit с нуля рядом, билдер не трогать**. Код не переиспользуем — но выводы обязаны
   переехать (§10), иначе заново оплатим уже оплаченное.
2. **Два RFC, спроектировавшие части этого** — [RFC-0002](../../projects/reformer-builder/docs/rfcs/0002-ai-chat-and-webmcp.md)
   (inbound/outbound, WebMCP, «единая поверхность — разные потребители») и
   [RFC-0003 §6](../../projects/reformer-builder/docs/rfcs/0003-schema-validation-and-worker-pool.md)
   (пул воркеров с дорожками, протокол, планировщик, отмена).
3. **Чат-примитивы в ui-kit** — `Message`/`MessageGroup`/`MessageAvatar`/`MessageContent`,
   `MessageScroller`, `Bubble` уже существуют и покрыты тестами.

**Что изменилось по сравнению с RFC-0002 (проверено 21.08.2026).** RFC писал, что обнаружение
инструментов (`getTools`/`executeTool`) помечено в черновике как TODO. Это устарело: по
[документации Chrome](https://developer.chrome.com/docs/ai/webmcp/imperative-api) обе операции
существуют, есть событие `toolchange`, снятие регистрации через `AbortSignal`, а
[`@mcp-b/webmcp-polyfill@4`](https://www.npmjs.com/package/@mcp-b/webmcp-polyfill) ставит API и на
`document`, и на `navigator`. То есть интероп-путь через WebMCP реализуем штатно и без зависимости
от флага и origin trial — но он остаётся **вторым**, а не первым.

## 1. Раскладка пакетов

```
packages/reformer-ai-kit/          @reformer/ai-kit
  src/
    core/          контракты, AppBridge, ToolHub, цикл хода, сессия, микро-стор — БЕЗ React и БЕЗ сети
    providers/     AiProvider + ленивые адаптеры (ai-sdk, server, byok, webllm, fake)
    sources/       ToolSource: app (local), page (WebMCP), mcp (remote), server, worker, dom
    react/         хуки + headless compound-компоненты
    ui/            стилизованная панель на @reformer/ui-kit
    element/       custom element <ai-chat> (сборка через preact/compat)
    testing/       fake-провайдер + сценарии

packages/reformer-worker-pool/     @reformer/worker-pool  (generic, zero-dep)
```

**Почему пул — отдельный пакет.** Билдеру он нужен под validate / prettier / codegen, где нет ни
байта AI ([RFC-0003 §6.10](../../projects/reformer-builder/docs/rfcs/0003-schema-validation-and-worker-pool.md)).
Заперев пул внутри ai-kit, мы заставим билдер тянуть SDK ради очереди задач.

**Сабпаты** (каждый — отдельная запись в [.size-limit.json](../../.size-limit.json)):
`.` · `/react` · `/ui` · `/element` · `/sources/page` · `/sources/mcp` · `/providers/byok` ·
`/providers/server` · `/providers/webllm` · `/pool` · `/testing`.

**Зависимости.** Ядро: ноль рантайм-зависимостей, и в него **не входит ничего протокольного** —
приложение подключается к ai-kit без WebMCP, без MCP и без полифилла. `/providers/byok`: `ai`,
`@ai-sdk/*` (peer, lazy-import). `/sources/mcp`: `ai` (`experimental_createMCPClient`).
`/sources/page`: `@mcp-b/webmcp-polyfill` (optional peer). `/ui`: `@reformer/ui-kit` + `react`
(peer). Ядро **не зависит от `@reformer/core`** — условие универсальности; свой микро-стор на
30 строк вместо сигналов ядра форм.

## 2. Мост приложения — центральный контракт

Это главный API пакета: то, чем приложение отдаёт себя ассистенту. Всё остальное — обвязка.

```ts
interface AppBridge {
  readonly id: string;

  /** Операции приложения. Объявляются из кода, типизированно, без протоколов. */
  tools: readonly AppTool[];

  /**
   * Снимок «что сейчас происходит»: маршрут, выделение, видимые данные.
   * Прикладывается к ходу как ДАННЫЕ (роль user + явный лид), не как инструкции.
   */
  context?(): AppContext | Promise<AppContext>;

  /** Состав операций или контекст изменились — пересобрать. */
  subscribe?(onChange: () => void): () => void;
}

interface AppContext {
  /** Человекочитаемый снимок. Обрезается хабом по бюджету. */
  summary: string;
  /** Структурированное — для UI и для ретривера, не для модели напрямую. */
  data?: unknown;
}
```

### 2.1. Контекст важнее инструментов

Измерено на вашем же агенте ([floofy-questing-papert.md](floofy-questing-papert.md)): за ход из
23 вызовов **15 (65 %) были чтением**, `get_form_outline` звался восемь раз, `get_form_node` —
четыре. Каждый такой заход — полный обход «модель → инструмент → модель» с пересылкой всего
контекста заново.

**Вывод, который переносится в контракт:** приложить снимок состояния к началу хода на порядки
дешевле, чем дать модели инструмент для его чтения. Билдер пришёл к этому эмпирически
([loop.ts](../../projects/reformer-builder/src/agent/core/loop.ts), `withOutlineSeed`); здесь это
становится обязательной частью API, а не приёмом.

Три правила, унаследованных оттуда же и не подлежащих переизобретению:

- Снимок идёт ролью **`user`**, а не в системный промпт: содержимое приложения — данные
  пользователя, и класть их в системное сообщение значит стереть границу, на которой держится
  защита от инструкций, спрятанных в подписи поля или в имени товара.
- Снимок идёт **в хвост** диалога: всё выше (промпт, определения операций, прошлые ходы) остаётся
  неизменным префиксом и потому кэшируемым.
- Снимок **не обновляется по шагам**: правка сообщения в середине диалога обнуляет кэш префикса на
  каждом шаге. Актуальность держат ответы операций — успешная мутация сама сообщает, что изменила.

### 2.2. Три класса операций

Билдер различал только `readOnly` / не-`readOnly`. Для ассистента приложения этого мало: политика
подтверждения и осмысленность отката у трёх классов разные.

| Класс | Пример | Approval по умолчанию | Откат |
| --- | --- | --- | --- |
| `read` | «что сейчас в корзине», «какие поля не заполнены» | авто | не нужен |
| `command` — мутация состояния | «добавь товар», «заполни поле», «примени фильтр» | спросить (настраивается) | нужен контракт (§2.3) |
| `effect` — навигация и UI | «открой страницу заказа», «подсвети поле», «прокрути к секции» | авто, но видимо в ленте | необратим по природе — не пытаться |

Класс `effect` — то, чего в билдере не было вовсе, и то, что для встроенного ассистента ценно само
по себе: «покажи мне, где это» — законный запрос, который ничего не меняет и не требует
подтверждения, но и откатывать его бессмысленно.

### 2.3. Откат — контракт, а не реализация

Ядро не знает семантики приложения и откатывать самостоятельно не может. Оно даёт две петли, и обе
опциональны:

```ts
interface ToolResult {
  ok: boolean;
  text: string;              // единственное, что уходит модели
  data?: unknown;            // структурированное — для UI
  /** Вернуло приложение — ai-kit рисует «Отменить» у этой строки ленты. Нет — кнопки нет. */
  undo?: () => void | Promise<void>;
  error?: { code: string; message: string; suggestions?: string[] };
}
```

Плюс **снимок на реплику пользователя** — приём билдера
([session.ts](../../projects/reformer-builder/src/agent/session.ts), `ChatEntry.snapshot`):
приложение может отдать состояние на начало хода, и тогда в ленте появляется «Восстановить»,
откатывающая весь ход разом. Хранится ссылка, не копия.

Почему именно так, а не «ChangeSet + Применить/Отклонить», как в билдере: подтверждать каждый ход
кнопкой дорого для внимания, и билдер сам от этого ушёл — правки применяются сразу, а отмена
доступна после ([run.ts](../../projects/reformer-builder/src/agent/run.ts), `finish`). Кнопка
остаётся ровно для конфликта. Для встроенного ассистента это тем более верно: приложение живёт
своей жизнью, и модальный предпросмотр на каждый чих сделает чат неюзабельным.

### 2.4. Как это выглядит у консумента

```ts
const bridge = createAppBridge({
  id: 'shop',
  tools: [
    tool.read('list_cart', 'Что сейчас в корзине', {}, () => cart.items),
    tool.command('add_to_cart', 'Добавить товар', SchemaAddToCart, ({ sku, qty }) => {
      const prev = cart.snapshot();
      cart.add(sku, qty);
      return { text: `Добавлено: ${sku} ×${qty}`, undo: () => cart.restore(prev) };
    }),
    tool.effect('open_product', 'Открыть карточку товара', SchemaSku, ({ sku }) => {
      router.push(`/p/${sku}`);
      return { text: `Открыта карточка ${sku}` };
    }),
  ],
  context: () => ({ summary: `Маршрут ${router.path}. В корзине ${cart.count} товаров.` }),
});
```

Схемы аргументов — сырой JSON Schema, как в [@reformer/mcp](../../packages/reformer-mcp/src/tools/)
(без zod). Это уже принятая в монорепо конвенция, и она же — формат WebMCP и MCP, то есть одна и та
же декларация уезжает во все три канала без конверсии. **Открытый вопрос для решения на Ф0:**
принимать ли дополнительно zod/valibot-схемы как сахар с выводом типов — DX заметно лучше, но
тянет зависимость в тот слой, который должен остаться нулевым.

## 3. Механизм подключения — `ToolSource`

Мост приложения — частный (и главный) случай источника. Источников несколько, они появляются в
рантайме, и часть из них **недоверенная** — поэтому единый механизм всё-таки нужен.

```ts
interface ToolSource {
  readonly id: string;                    // неймспейс вызовов
  readonly kind: 'app' | 'page' | 'mcp' | 'server' | 'worker' | 'dom';
  readonly trust: 'trusted' | 'untrusted';
  list(): Promise<readonly ToolDescriptor[]>;
  call(name: string, args: unknown, opts: { signal?: AbortSignal }): Promise<ToolResult>;
  subscribe?(onChange: () => void): () => void;
  connect?(): Promise<void>;               // OAuth, рукопожатие
  dispose?(): void;
}
```

`ToolHub` агрегирует источники и берёт то, что иначе продублируется в каждом:

| Обязанность | Почему в хабе |
| --- | --- |
| Неймспейс имён | Приложение и MCP-сервер легко дают одинаковый `search`. Формат `${sourceId}_${name}`; **имя WebMCP ≤ 30 символов** — при переполнении короткий алиас и карта алиас→(источник, имя) |
| Валидация аргументов по `inputSchema` | Модель врёт в аргументах; ajv ловит это до вызова приложения. Уходит в дорожку `compute` пула (§6) |
| Бюджет поверхности | Перенос `TOOL_SURFACE_BUDGET = 7700` из [core/types.ts](../../projects/reformer-builder/src/agent/core/types.ts): описания операций уходят в запрос **целиком на каждом шаге**. Приложение с 40 операциями плюс два MCP-сервера — уже неотправляемо |
| Отбор активного набора | Следствие бюджета: операции приложения — всегда, внешние источники — по выбору пользователя или ретривером |
| Политика approval | По классу операции (§2.2), с переопределением по источнику и по имени |
| Обрезка результата | `TOOL_TEXT_BUDGET`; суффикс обрезки — **с новой строки**, иначе обрубок структурного идентификатора читается моделью как валидный адрес (реальный баг билдера) |
| Аудит вызовов | Лента, «Отменить», экспорт для телеметрии |

## 4. Источники

### 4.1. Первая версия (все выбраны пользователем)

**`app` — приложение объявляет себя из кода.** §2. Первичный и обязательный путь: работает везде,
без полифилла, без протокола, с типами. Всё остальное — надстройки над той же поверхностью.

**`page` — WebMCP, inbound (интероп внутри страницы).**
`document.modelContext.getTools({ fromOrigins })` → дескрипторы; `executeTool(tool, jsonString, {signal})`
→ вызов; `toolchange` → пересборка списка. Разрешение API: нативный `document.modelContext` →
`navigator.modelContext` (deprecated с Chrome 150) → динамический импорт полифилла.

*Когда он нужен, если есть прямой мост:* когда операции регистрируют независимые части приложения
(виджеты, микрофронтенды, iframe'ы чужого origin), которые не имеют ссылки на ваш `AppBridge`.
Тогда `document.modelContext` работает как общая шина страницы.

Ловушки, закладываемые сразу: `executeTool` принимает вход **строкой JSON**, а не объектом;
возвращает `null` при навигации (это не ошибка, а «страница ушла»); кросс-оригинные инструменты
требуют `allow="tools"` на iframe и явного `fromOrigins`.

**Outbound-зеркало.** `publishToWebMcp(hub, { include })` — операции приложения публикуются в
`document.modelContext`, и их видит внешний агент браузера. Это «одна поверхность — разные
потребители» из RFC-0002: приложение декларирует себя **один раз**, а получают это и встроенный
чат, и внешний агент. Снятие — через `AbortSignal`, как требует спека.
Обязательная защита: публикуем только явно помеченные операции. Иначе внешний агент получит доступ
к подключённым пользователем MCP-серверам вместе с их OAuth-токенами.

**`mcp` — удалённые серверы (внешние сервисы).** `createMcpToolSource({ url, auth })` поверх
`experimental_createMCPClient` со Streamable HTTP. По
[спеке 2026-07-28](https://blog.modelcontextprotocol.io/posts/2026-07-28-release-candidate/)
транспорт стал POST-only с заголовками `Mcp-Method`/`Mcp-Name`, авторизация — OAuth 2.1 + PKCE +
Resource Indicators. **Честное ограничение:** из браузера работает только если сервер отдал CORS с
этими заголовками в allow-list. Не все отдадут → опциональный прокси через тот же endpoint, что и
server-транспорт (§5).

### 4.2. Другие возможности (по запросу — что ещё бывает источником)

| Источник | Что даёт | Цена / риск |
| --- | --- | --- |
| **`server`** — операции на бэкенде приложения, объявленные тем же endpoint'ом | Привилегированное (БД, платежи, внутренние API) без выставления в браузер. Естественная пара к server-транспорту | Требует бэкенда; офлайн-SPA неприменимо |
| **`worker`** — операции в дорожке пула | Тяжёлое без джанка: парсинг PDF/xlsx/docx, локальный поиск, эмбеддинги | Нужен пул (§6); данные ходят через structured clone |
| **`dom`** — универсальная автоматизация страницы (`read_page` по accessibility tree, `click`, `fill`) | Работает там, где приложение **ничего не объявило**. Фолбэк | 🔴 Главный вектор prompt injection и главный пожиратель токенов. Только явным включением, никогда по умолчанию |
| **iframe / cross-origin** | Операции встроенных виджетов чужого origin — уже в спеке WebMCP (`fromOrigins` + `allow="tools"`) | Требует кооперации хоста и виджета; `trust: 'untrusted'` обязателен |
| **Расширение браузера** — мост через [`@mcp-b/transports`](https://www.npmjs.com/package/@mcp-b/transports) (`TabClientTransport`, postMessage) | Обходит CORS целиком: соединение с удалённым MCP держит расширение. Плюс кросс-табные возможности | Требует установленного расширения — не для массового встраивания |
| **OpenAPI-адаптер** | Дескрипторы из OpenAPI/Swagger — подключение сервиса без MCP | Схемы бывают огромны; нужен фильтр операций и сжатие описаний |
| **`@reformer/mcp` in-process** | У вас уже есть MCP-сервер с 7 инструментами по докам ReFormer. Он stdio (L2 в RFC-0002 — «браузер не может его поднять»), но сами инструменты — чистые функции над `docs/llms`. Обёртка в `ToolSource` = справка по ReFormer прямо в чате, без stdio и без сети | Требует сборки парсеров доков под браузер |
| **Provider-native tools** (web search, code execution на стороне Anthropic/OpenAI) | Возможности, которых у нас нет | Исполняет провайдер: в ленте показывать иначе — без approval и без origin |
| **`ask_user` (elicitation)** | Модель вызывает «спроси у пользователя», ai-kit рисует форму, ответ уходит обратно. **Закрывает дыру спеки WebMCP** — user prompting там в открытых вопросах | Нужен UI-примитив; ход блокируется на ожидании |
| **Composite / macro** | Пользовательские рецепты из нескольких вызовов, сохранённые как одна операция | Только после того, как остальное устоится |

**Порядок:** `app` → `page` → outbound → `ask_user` → `mcp` → `worker`. `dom` и OpenAPI — отдельным
решением после. `ask_user` вклинивается рано намеренно: дёшев и резко поднимает качество ходов на
неоднозначных запросах, а для ассистента *внутри приложения* уточняющий вопрос — нормальный ход
диалога, а не сбой.

## 5. Модели и транспорт

**Контракт канала — свой, не тип из SDK.** Решение билдера
([providers/types.ts](../../projects/reformer-builder/src/agent/providers/types.ts)) правильное и
воспроизводится: адаптер SDK становится заменяемым файлом, а тесты получают провайдер без сети.
Поток событий: `delta` · `reasoning` · `tool_call` · `tool_result` · `step_usage` · `error` · `done`.

**Роли моделей вместо одного активного канала.** В билдере `activateProvider` делает
`resetProviders()` — активен ровно один. Для параллельных подзадач это тупик.

```ts
type ModelRole = 'chat' | 'fast' | 'reasoning' | 'vision' | 'embed';
interface ModelRouter { resolve(role: ModelRole): { provider: AiProvider; model: string } }
```

**Два транспорта (выбор пользователя — оба).**

| Транспорт | Кому | Что важно |
| --- | --- | --- |
| `server` — прокси на endpoint приложения | Прод, встраивание в продукт | Ключ никогда не в браузере. **Режим «тонкий прокси»: один HTTP-вызов = один шаг модели; цикл и исполнение операций остаются в браузере.** Иначе операции приложения недоступны — сервер не может ни вызвать `router.push`, ни прочитать состояние стора. Это требование к контракту endpoint'а, а не деталь реализации |
| `byok` — ключ пользователя в браузере | Локальные инструменты, dev, офлайн-SPA вроде билдера | anthropic / openai / google / openai-compatible (Ollama, LM Studio, OpenRouter, vLLM). Список моделей тянуть с `/models`, **не хардкодить**. В доке пометить явно: ключ доступен странице |

Плюс `webllm` (локальная модель в дорожке пула) и `fake` (детерминированные сценарии — публикуется
как `/testing`, чтобы консументы писали e2e без ключей).

**Второй режим хода — `streamObject`.** Для задач «извлеки структуру» (заполнить форму по тексту,
разобрать документ) один вызов structured output дешевле tool-loop на порядок. Ход получает
`mode: 'tools' | 'object'`.

## 6. Worker pool

Отдельный пакет `@reformer/worker-pool` по дизайну
[RFC-0003 §6](../../projects/reformer-builder/docs/rfcs/0003-schema-validation-and-worker-pool.md):
типизированный реестр задач, приоритеты `interactive > background > bulk`, latest-wins по
`dedupeKey`, кооперативная отмена с `terminate`-фолбэком, **дорожки с affinity**, inline-executor
для тестов и SSR, прогрев в idle, circuit breaker, размер `clamp(1, hardwareConcurrency - 2, 4)`.

**Почему не готовая библиотека.** Требование, которого не закрывает ни одна:

- [Comlink](https://github.com/GoogleChromeLabs/comlink) — эргономика RPC, но proxy-модель: очередей
  с приоритетами, dedupe и affinity нет, планировщик всё равно писать самим.
- [workerpool](https://github.com/josdejong/workerpool) — зрелый пул с отменой и таймаутами, но
  **безликий**: задача уходит первому свободному воркеру, резидентный кэш теряется. Для валидации
  измерено — 20 мс переразогрева на каждую миграцию.
- piscina — Node-only.

Свой пул по готовому дизайну — ~300 строк. Affinity здесь не украшение: пул без неё **вредит**.

| Дорожка | Резидентное состояние | Задачи | Приоритет |
| --- | --- | --- | --- |
| `compute` | скомпилированные ajv-валидаторы | валидация аргументов и результатов операций, diff, разметка markdown, счёт токенов | interactive |
| `index` | эмбеддинги + векторный индекс | ретривер по операциям приложения (когда их сотни) и по докам | background |
| `llm` | загруженная локальная модель | WebLLM / transformers.js — работа без сети и ключей | bulk |
| `generic ×N` | нет | параллельные подзадачи | по задаче |

**Честно про параллельные подзадачи.** Стриминг от модели сетевой — воркеры не ускорят его **ни на
миллисекунду**. Что пул реально даёт: очередь с приоритетами, отменяемость, dedupe и отсутствие
джанка в main. Этого достаточно, чтобы им пользоваться, но продавать как ускорение нельзя.
Настоящий CPU-выигрыш — только дорожки `llm` и `index`.

Пользователь по составу дорожек **не определился**, поэтому `compute` входит как обязательная (без
неё ajv едет в главный чанк), а `index` и `llm` вынесены в отдельную фазу и отбрасываются целиком,
не задев остального.

## 7. Безопасность — первого класса

Ассистент **внутри** приложения опаснее чата рядом с ним: он может нажимать кнопки. Плюс часть
операций и данных приходит из мест, которые приложение не контролирует.

1. **Граница доверия.** Контекст приложения, результаты операций, содержимое страницы — всё уходит
   ролью `user` с явным лидом «данные, не инструкции». Билдер это уже делает для карты формы
   ([loop.ts](../../projects/reformer-builder/src/agent/core/loop.ts), `OUTLINE_SEED_LEAD`) —
   переносим как обязательный механизм API. Название товара, введённое другим пользователем, —
   такой же вектор инъекции, как подпись поля.
2. **Approval по классу операции** (§2.2), с переопределением по источнику и имени. `command` из
   недоверенного источника — всегда спрашивать.
3. **Origin в интерфейсе.** WebMCP отдаёт `origin` в дескрипторе — показываем у каждого вызова.
   Пользователь видит, куда уходит вызов, до подтверждения.
4. **Outbound — только allow-list.** Иначе внешний агент получит доступ к подключённым
   MCP-серверам пользователя вместе с их OAuth-токенами.
5. **Токены и ключи — отдельное хранилище**, никогда в контексте модели и никогда в аудит-логе
   (приём из [keys.ts](../../projects/reformer-builder/src/agent/keys.ts)).
6. **`untrustedContentHint`** из аннотаций WebMCP — прокидывать в UI и в политику approval.

## 8. Слои интерфейса

Повторяем расслоение монорепо (core → cdk → ui-kit):

- **`/react`** — `useAssistant()`, `useAppBridge()`, `useToolSources()`, `useApprovals()` + headless

  CustomEvents как публичный API. Прецедент алиаса есть — `@preact/signals-core` уже в зависимостях
  билдера.

Голосовой ввод — Web Speech API в `Chat.Composer`, ноль байт бандла (RFC-0002 назвал это самой
дешёвой позицией всего документа).

## 11. Проверка

**Юниты** (`node ../../scripts/run-vitest.mjs`, `environment: 'node'` — как во всех пакетах):
ходы через `fake`-провайдер, сценарно; `AppBridge` (классы операций, приклейка контекста, `undo`);
`ToolHub` (неймспейс, коллизии, бюджет, обрезка, отказ ajv); политика approval; разбор
`finishReason` по таблице; планировщик пула (приоритеты, dedupe, отмена, circuit breaker) на
inline-executor.

**WebMCP** — тест с полифиллом: регистрируем операцию → `list()` её отдаёт → `call()` исполняет →
`toolchange` пересобирает список → `AbortSignal` снимает. Отдельный кейс: `executeTool` вернул
`null` (навигация) — это не ошибка.

**Демо + e2e**: приложение в [react-playground](../../projects/react-playground/) с настоящим
`AppBridge` — маршрутизация, стор, операции всех трёх классов, встроенный чат. Playwright-спека в
`projects/react-playground-e2e/tests/`, скриншоты — **строго** в
`projects/react-playground-e2e/screenshots/ai-kit/<scenario>.png` с явным `filename` (без него
playwright MCP пишет в корень репозитория).

**Гейты монорепо**: `npm run typecheck` (добавить оба tsconfig), `npm run lint`,
`npm run size:check` (записи на каждый сабпат), `npm run knip`, `node scripts/check-dist-deps.mjs`,
`node scripts/check-exports-dist.mjs`, `node scripts/check-peer-ranges.mjs`,
`node scripts/check-no-node-globals.mjs` — последний критичен: ядро обязано быть браузерным.
