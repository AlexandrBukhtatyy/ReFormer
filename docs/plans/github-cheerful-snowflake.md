# Форма обратной связи на GitHub Pages → создание GitHub Discussion

## Context

Задача: на статическом сайте (GitHub Pages) сделать форму обратной связи, которая
по обращению пользователя создаёт **GitHub Discussion**.

Главное ограничение, которое определяет решение:

- **GitHub Pages — чисто статический хостинг**, серверного кода нет.
- **Создать Discussion можно только через GraphQL API** (`createDiscussion` mutation);
  REST-эндпоинта для создания discussions не существует. Мутация требует
  аутентификации токеном с правом «Discussions: write».
- **Токен нельзя положить в клиентский JS** — любой посетitель GitHub Pages увидит его
  в исходниках/Network и сможет злоупотребить. Значит «форма сама дёргает API» без
  посредника-сервера невозможно.

**Выбранный путь (по ответам пользователя): redirect на предзаполненную страницу
создания discussion — 0 инфраструктуры, 0 секретов.** Форма не вызывает API напрямую,
а конструирует URL вида `.../discussions/new?category=&title=&body=` и перенаправляет
туда пользователя; тот (залогиненный в GitHub) подтверждает создание кнопкой
«Start discussion». Рецепт универсальный — не привязан к этому монорепо, подходит
любому статическому сайту (vanilla HTML, React, Vue, Docusaurus и т.д.).

Компромисс осознанный: отправитель обязан иметь GitHub-аккаунт и вручную нажать кнопку
(это «assisted», а не полностью автоматическое/анонимное создание). Для аудитории
разработчиков это приемлемо и даёт бесплатную защиту от спама (нужен аккаунт).

## Как это работает (поток)

```
пользователь заполняет форму
        │  submit (preventDefault — НЕ отправляем на сервер)
        ▼
JS собирает URL:
  https://github.com/{OWNER}/{REPO}/discussions/new
    ?category={slug}
    &title={encodeURIComponent(...)}
    &body={encodeURIComponent(markdown)}
        │  window.location.href = url
        ▼
GitHub открывает форму «New discussion» с предзаполненными полями
        │  пользователь (залогинен) жмёт «Start discussion»
        ▼
Discussion создан от имени этого пользователя
```

## Шаг 1. Настройка репозитория (обязательно, один раз)

Это не код, а действия в UI GitHub — без них форма откроет пустую/сломанную страницу:

1. **Включить Discussions**: репозиторий → **Settings → General → Features →** поставить
   галочку **Discussions**.
2. **Создать категории и узнать их slug**: вкладка **Discussions →** значок шестерёнки у
   списка категорий → создать нужные (например «Обратная связь», «Идея», «Вопрос»).
   `category` в URL — это **slug** категории: нижний регистр, пробелы и `&` заменяются на
   дефис (`Q&A` → `q-a`, `Show and tell` → `show-and-tell`). Проще всего подсмотреть slug,
   открыв категорию — он будет в адресной строке.
   - Если передать несуществующий slug — не ошибка: GitHub просто откроет форму без
     предвыбранной категории, пользователь выберет вручную.
3. **(опционально) Шаблон категории**: для категории можно задать template, чтобы задать
   структуру тела обсуждения на стороне GitHub.

## Шаг 2. Разметка + скрипт формы (self-contained рецепт)

Готовый к копированию vanilla-вариант (работает на любом статическом сайте; в React/Vue
логика та же — собрать `url` и сделать redirect в обработчике submit):

```html
<form id="feedback-form">
  <label>Тема
    <input name="title" required maxlength="120"
           placeholder="Кратко о проблеме или идее">
  </label>

  <label>Тип обращения
    <select name="category" required>
      <!-- value = slug категории Discussions в вашем репозитории -->
      <option value="obratnaya-svyaz">Обратная связь</option>
      <option value="ideya">Идея</option>
      <option value="q-a">Вопрос</option>
    </select>
  </label>

  <label>Описание
    <textarea name="description" required rows="6"
              placeholder="Что случилось / что предлагаете"></textarea>
  </label>

  <label>Шаги воспроизведения (необязательно)
    <textarea name="steps" rows="3"></textarea>
  </label>

  <button type="submit">Отправить в Discussions</button>
</form>

<script>
  const OWNER = 'AlexandrBukhtatyy';   // ← ваш owner
  const REPO  = 'ReFormer';            // ← ваш repo

  const form = document.getElementById('feedback-form');

  form.addEventListener('submit', (e) => {
    e.preventDefault();
    const data = new FormData(form);

    const title = data.get('title').trim();
    const category = data.get('category');

    // Собираем markdown-тело из полей формы (GitHub отрендерит его как Markdown)
    const parts = [data.get('description').trim()];
    const steps = (data.get('steps') || '').trim();
    if (steps) parts.push('', '### Шаги воспроизведения', steps);
    parts.push('', '---', '_Отправлено через форму обратной связи на сайте._');
    const body = parts.join('\n');

    const url = `https://github.com/${OWNER}/${REPO}/discussions/new`
      + `?category=${encodeURIComponent(category)}`
      + `&title=${encodeURIComponent(title)}`
      + `&body=${encodeURIComponent(body)}`;

    // Защита от переполнения URL (см. «Ограничения»)
    if (url.length > 6000) {
      alert('Слишком длинное описание — сократите текст.');
      return;
    }

    window.location.href = url;   // либо window.open(url, '_blank') — в новой вкладке
  });
</script>
```

Ключевые моменты кода:
- `encodeURIComponent` **обязателен** для `title` и `body` — иначе кириллица, `&`, `#`,
  переводы строк сломают URL.
- Тело собирается как Markdown: можно раскладывать несколько полей формы в заголовки/списки.
- `\n` после кодирования станет `%0A` — GitHub корректно покажет переносы строк.

## Шаг 3. (если форма на ReFormer) мостик к схеме

Пользователь выбрал «общий рецепт», поэтому основной вариант — vanilla выше. Если позже
захочется построить ту же форму на ReFormer: поля описываются схемой формы как обычно, а
весь код из обработчика `submit` переносится в `onSubmit` — вместо отправки данных
собирается тот же `url` и делается redirect. Паттерн обработчика submit можно посмотреть
через `mcp__reformer__find_recipe` (topic: «submit-and-reset»). Схему полей —
`mcp__reformer__find_recipe` (topic: «form»).

## Ограничения и тонкости (обязательно учесть)

- **Не анонимно и не автоматически.** Требуется GitHub-аккаунт + ручное подтверждение.
  Незалогиненного пользователя GitHub сперва попросит войти, затем вернёт к предзаполненной
  форме. Гарантии, что обсуждение будет создано, нет — пользователь может не дожать кнопку.
- **Длина URL.** Практический безопасный предел — несколько тысяч символов; очень длинный
  `body` может не поместиться. Отсюда guard `url.length > 6000`. Если нужен длинный текст —
  это сигнал в пользу serverless-варианта (см. «Альтернативы»).
- **category slug должен существовать** в репозитории, иначе категория не предвыберется.
- **Нет серверной валидации/капчи** — но необходимость GitHub-аккаунта сама по себе режет
  спам-ботов.

## Опциональные улучшения

- Клиентская валидация полей (required, maxlength) до формирования URL.
- Открывать в новой вкладке (`window.open(url, '_blank')`), чтобы не уводить пользователя с
  сайта.
- Кнопка-ссылка вместо JS: можно заранее сгенерировать `<a href="...discussions/new?...">`
  для типовых обращений (например «Сообщить об ошибке» с шаблоном body).
- Шаблон категории на стороне GitHub (Шаг 1.3) — тогда часть структуры тела зададут на
  GitHub, а форма передаёт только переменную часть.

## Альтернативы (кратко — если требования изменятся)

- **Нужны анонимные отправки / полный автомат без кнопки** → добавить маленький
  serverless-прокси (Cloudflare Worker / Vercel / Netlify Functions), который хранит секрет
  и вызывает GraphQL `createDiscussion`. Секрет лучше не как personal token, а как **GitHub
  App installation token** (короткоживущий, ограничен репозиторием). Потребует антиспам
  (rate-limit / капча). Это другая архитектура — вне текущего плана.
- **Issue вместо Discussion приемлемо** → тот же приём: `/issues/new?title=&body=&labels=`.
  Плюс у Issues есть REST API создания — проще, если позже понадобится автомат.

## Verification (проверка end-to-end)

1. Подставить реальные `OWNER`/`REPO` и slug'и категорий; убедиться, что в репозитории
   включены Discussions и созданы эти категории.
2. Открыть страницу с формой (локально файлом или на GitHub Pages), заполнить поля,
   нажать submit.
3. Убедиться, что произошёл переход на
   `https://github.com/OWNER/REPO/discussions/new?...` и что **title, body и категория
   предзаполнены**.
4. Проверить корректность кодирования на «злом» вводе: кириллица, символы `&`, `#`,
   несколько строк в описании — в форме GitHub они должны отображаться правильно.
5. Проверить, что выбранная в форме категория совпала с предвыбранной на GitHub (если нет —
   поправить slug).
6. Дожать «Start discussion» и убедиться, что обсуждение создалось в нужной категории.
7. (негативный кейс) Ввести очень длинное описание → должен сработать guard с alert.
