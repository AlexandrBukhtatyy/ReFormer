# Правила формы — в коде модуля, без `form.rules.json`

> Прежняя версия этого файла — план MCP-серверов ассистента (ReFormer-9dt2) — выполнена и
> закоммичена (`4f39340a`…`bc514a12`), текст — в истории git.

Сокращения: **RP** = `projects/reformer-builder-playground/.ui_builder/plugins`,
**SDK** = `packages/reformer-builder-plugin-api/src`.

## Контекст

Ассистент билдера на просьбу «сделай форму авторизации» создал `login/schema/form.schema.json` и
рядом `login/schema/form.rules.json`. Пользователь: этого файла быть не должно. Это так и по
контракту библиотеки: раскладка модуля ReFormer (рецепт `directory-layout` MCP) — «the set is the
whole module», правилам отведён код валидации, отдельного JSON-файла правил в нём нет.

Файл ввели 2026-10-23 (ReFormer-1a6r.2, `4c761f9c`): правила структурного режима жили в памяти
моста и терялись. Сейчас его читают ход ассистента (знание уже заданных правил), генерация кода
(`rulesOf`), валидатор (находки «правило без узла»), редактор (`rules.remove`), превью
(значения источников данных).

**Решение пользователя:** правила живут сразу в каноничных файлах кода модуля; код — единственный
источник истины. У билдера это папочная раскладка: `validation/form.ts`, `validation/<шаг>.ts`,
`behavior/index.ts` (перегенерируемые, пока маркер `// @reformer-generated <hash>` сходится),
`validation/messages.ts` (тексты по кодам) и `constants/<каталог>.ts` (значения источников) —
авторские, «пишутся один раз». **Объём записи — гибрид:** кода модуля ещё нет — ход генерирует
модуль целиком; есть — пишет только файлы правил.

Обратного чтения TS → `FormRules` в репозитории нет; AST TypeScript плагинам недоступен. Есть свой
структурный парсер JS без зависимостей — `RP/reformer/core/codegen/print/js.ts`: на нём строится
читатель.

## Архитектура

1. **Читатель правил из кода** — `RP/reformer/core/codegen/rules-code/`: из текстов файлов правил
   модуля собирает `FormRules` и происхождение каждого правила (файл; `generated` / `edited` /
   `handwritten`), чужие операторы — как есть (`foreign`, с позицией). Строится на сыром тексте с
   позициями: приватные сканеры `print/js.ts` (`scan`, `matchingClose`, `splitTop`, `topIndexOf`,
   `wholeString`, `isArrowHead`) выносятся в `print/scan.ts`. Узнаёт ровно то, что печатает
   генерация (`@reformer/mcp` `builders.ts`, шаблоны `core/codegen/templates/*.eta`, виды
   `core/codegen/view/*`):
   - валидация: `validate`, `validateAsync`, `cross(…(values) => (C ? null : { code }))`,
     `applyEach(model.$.E, ({ model: item }) => …)`, `validateWhen(() => W, () => …)` — во всех
     `validation/*.ts`, кроме `messages.ts` (шаг переименовали — старый файл тоже читается);
   - поведение: 12 видов связей, строки массива (`applyEach(…, defineFormBehavior(…))`), правила
     узлов `hideWhen` / `schema.node(s).patchProps({…})` / `onComponentEvent` в своих областях;
   - `message` = `formMessages[code]` из `messages.ts`; `dataSources` — `export const NAME = <литерал>`
     из `constants/`.

   Нормализация: `required` → `required()`, цели строк массива — полным путём, правило дробится по
   операторам, `code` простого правила — из `{ code }` единственного валидатора. Потери (порядок,
   `sources` у части связей — восстанавливаются по путям `model.`/`item.` в выражении, `code` у
   async) документируются и закрепляются тестом. Плюс загрузчик над портом чтения модуля и
   помощники точечной правки авторских файлов: `patchMessages(text, {code: text | null})` и
   `patchConstants(text, {NAME: value | null})`. Они меняют только свой литерал, остальное — байт в
   байт; незнакомую форму не трогают и говорят об этом.

2. **Генерация читает правила из кода.** `rulesOf` стека `RP/reformer/codegen` — через загрузчик, в
   `print()`, а не в `open()`. Вход печати — только правила из нетронутых файлов (из правленного
   руками `validation/form.ts` правило не переезжает дублем в файл шага). Страж: напечатанный файл
   правил обязан прочитаться обратно в то, что печатали, иначе файл не пишется и показывается
   проблема генерации. Осиротевший файл шага с живым маркером получает заглушку. Это заодно
   закрывает дыру шаблонов: правила, напечатанные шаблоном формы, больше не превращаются в
   заготовку при следующей генерации.

3. **Запись — генератором, через дверь хода.** SDK, аддитивно, `ModuleGeneratorCapability`
   1.0.0 → 1.1.0:
   - `GenerateRequest.only?: readonly string[]` — доставить только эти цели (переопределения
     проекта считаются ими);
   - `GenerateRequest.stackInput?: { stack: string; value: unknown }` — непрозрачный вход стеку
     документа, другие стеки его не видят;
   - `CodegenPrintRequest.input?: unknown`, `CodegenFile.merge?(current): string | null` (авторский
     файл: точечная правка вместо пропуска «authored»), `CodegenModule.check(delivered?)` — проверка
     по доставляемому подмножеству.

   Хост `RP/forms/codegen` (`run`, `generate-for`, `deliver`) фильтрует по `only` при доставке, а
   печатает весь модуль, — поэтому имена и импорты те же. Стек ReFormer берёт `input.rules` вместо
   правил из кода и для `messages.ts`/`constants` отдаёт `merge` на помощниках из п. 1, только при
   переопределении.

4. **Ход ассистента** (`RP/reformer/ai`): `load` читает правила кодом и запоминает тексты файлов
   правил. `land` пишет документ, затем, если правила изменились, зовёт генератор дверью хода с
   `stackInput: { stack: 'reformer', value: { rules } }`. Модуль без кода (нет `types/<каталог>.ts`) —
   генерация целиком, иначе — `only` = цели правил (`validation`, `step-validation`, `form-behavior`,
   `messages`, `data-sources`). Записанное — в `companions` с `before/after` (отмена хода и
   «Восстановить» уже умеют такие). Расхождение — сверка всех запомненных файлов правил. Созданный
   ходом файл правил при отмене возвращается к напечатанному из прежних правил тексту (сухой прогон
   генератора), а не к пустоте. Файлы правил в список отказа плагинам (`refuseWrite`) не попадают,
   иначе `generate_code` в том же ходе споткнётся. Правила меняются через `set_form_rules`, но файл
   правлен руками (маркер не сходится) или генератора нет — инструмент отказывает сразу с причиной,
   а в режиме файлов модель правит TS сама. Затравка хода перечисляет распознанное и запертое.
   `reformer.codegen.generator ^1.1` — необязательное требование манифеста. Память моста без
   файлового доступа остаётся.

5. **Остальные потребители — через читатель:** кэш правил модуля (`core/codegen/rules-cache.ts`,
   перечитывание при правке любого файла правил) у валидатора и редактора. Находки «правило без
   узла» адресуют правило файлом и ключом, а не индексом. `rules.remove` — тем же генератором с
   переопределением. `useRuleDataSources` превью читает `constants/`.

6. **Сайдкар уходит:** роль `'rules'` и `rulesSidecarNameOf` (`core/codegen/layout.ts`),
   `core/codegen/rules-file.ts`, ветка гейта и метка листинга режима файлов, `RULES_REFUSAL`.
   Миграции нет (файлу два дня); найденный `form.rules.json` — заметка «устарел, удалите».

## Тесты

- **Читатель:** по форме на каждый вид оператора; свойства на корпусе (12 видов × строки массива ×
  опции; валидация × `when`/`each`/`cross`/`async`/`code`/`message`; правила узлов × корень/строка/
  часть/шаг) и на всех 17 наборах `__golden__`. Проверяются три свойства:
  - `read(print(R)) ≡ normalize(R)`;
  - `print(read(print(R)))` байт в байт равен `print(R)` — с prettier и без;
  - вход, переформатированный prettier, читается так же.

  Отдельно — чужие операторы и правленые файлы; `patchMessages` / `patchConstants` не трогают
  остальной текст.
- **Генерация:** «сгенерировать дважды — то же самое» на золотых наборах; шаблон с правилами →
  повторная генерация не меняет `validation/form.ts`; визард с правленым `validation/form.ts` — без
  дублей; `RP/reformer/integration/codegen-run.test.ts`.
- **Хост:** `only` по идентификаторам и переопределениям, `merge`, `stackInput` — только своему стеку.
- **Ход** (`RP/reformer/integration/assistant-turn.test.ts`, `assistant-bridge.test.ts`):
  - правила ложатся в код, у новой формы модуль генерируется целиком;
  - отмена — и файла правил, созданного ходом, и после `generate_code` в том же ходе;
  - «Восстановить», расхождение, «Применить всё равно»;
  - отказ при правленом файле и без генератора;
  - `form.rules.json` не появляется.
- **e2e:** T12 — правила в `validation/form.ts`, следующий ход их видит, отмена; T13 — значения в
  `constants/<каталог>.ts` и в превью; `form-scenarios.spec.ts` и `SCENARIOS.md` — новые пути.

## Риски и ограничения

- Потери обратного чтения (порядок, часть `sources`, `code` у async) — проверка циклов и затравка
  чуть слабее; закреплены тестом.
- Правленый руками файл правил запирает структурную правку правил этой формы — только режим файлов.
- Нет генератора (плагин генерации выключен, нет кита, источник только для чтения) — ход не может
  записать правила и говорит об этом заранее.
- Отмена хода, создавшего модуль целиком, файлов не удаляет (у плагинов нет удаления) — как у
  `generate_code` сегодня.
- Имя формы, введённое в панели не по умолчанию, после перезагрузки забывается: печать только
  файлов правил возьмёт имена из импорта типа в существующем файле.
- `docs/specs/` не трогаются.
