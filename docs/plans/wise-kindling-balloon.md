# Ассистент билдера молча бросает сложный ход

## Контекст

На сложном запросе (мастер, несколько полей разом) ассистент заканчивает ход заметкой
«Ассистент вызывал инструменты, но форму не изменил и ничего не ответил», рассуждение при этом
обрывается на полуслове («Let me insert these into…»). Простой запрос — добавить или удалить одно
поле — проходит. Канал: локальный OpenAI-совместимый (Ollama), пределы в настройках канала не
заданы ни одного.

**Про веб-воркеры: их у ассистента нет.** Проверено по всем веткам — `git log -S "new Worker"`,
`-S "Comlink"`, `-S "postMessage"` по `src` дают ноль коммитов. Единственные живые воркеры проекта —
Monaco в [monaco-setup.ts:36-40](../../projects/reformer-builder/src/canvas/monaco-setup.ts#L36-L40),
они от 26 июля и к ассистенту не относятся. Есть
[RFC-0003](../../projects/reformer-builder/docs/rfcs/0003-schema-validation-and-worker-pool.md)
«пул веб-воркеров» со статусом «к реализации не приступали» — регрессию, похоже, приписали ему.
Ассистент целиком в main thread на async-генераторах, и менять это не требуется.

Регрессия по времени объясняется другим: за 23 августа в ассистента добавили справку по библиотеке
(`ask_reformer`, коммиты `81cd3b44`, `3ffa6e40`) и правила формы (`set_form_rules`, `048ad862`).
Поверхность инструментов выросла до `TOOL_SURFACE_BUDGET = 8946` символов, к ней прибавляются
системный промпт (`PROMPT_BUDGET = 4000`) и карта формы (`OUTLINE_SEED_BUDGET = 3000`). Постоянная
часть запроса — порядка 3.5–4 тысяч токенов ещё до первого ответа инструмента, а `num_ctx` у Ollama
по умолчанию 4096.

## Диагноз

Из кода следуют три жёстких факта о наблюдавшемся прогоне
([run.ts:200-227](../../projects/reformer-builder/src/agent/run.ts#L200-L227)): `reason !== 'error'`
(иначе показалась бы ошибка, а не заметка), `hasChanges(changeSet) === false`, `tools.length > 0`.
То есть ход завершился **штатно** — и именно это неверно.

Причин, складывающихся в один симптом, три. Все они проявляются только там, где вызовов инструмента
больше одного или JSON аргументов длинный, — отсюда асимметрия «одно поле живёт, двенадцать нет».

**1. Обрыв, который провайдер не назвал обрывом.**
[ai-sdk.ts:102-111](../../projects/reformer-builder/src/agent/providers/ai-sdk.ts#L102-L111) знает
только `length`, `content-filter`, `tool-calls`. Билдер собран на `ai@7.0.63` (вложенный
`node_modules`, не корневой `ai@5`), где `FinishReason = 'stop' | 'length' | 'content-filter' |
'tool-calls' | 'error' | 'other'`. У `@ai-sdk/openai-compatible` начальное значение —
`{ unified: 'other' }`: сервер, не приславший `finish_reason` (обычное дело при упоре в окно),
даёт `'other'`, а `'other'` и `'error'` в `BROKEN_FINISH` отсутствуют → `done: 'complete'` →
заметка вместо диагноза.

**2. Оборванный вызов инструмента не оставляет следа.**
`fullStream` несёт `tool-input-start` (`{ id, toolName }`), `tool-input-delta`, `tool-input-end` —
именно ими стримится JSON аргументов. В `switch`
[ai-sdk.ts:240-297](../../projects/reformer-builder/src/agent/providers/ai-sdk.ts#L240-L297) их нет:
обрабатывается только готовый `tool-call`. Если модель начала писать `insert_node` с двенадцатью
узлами и вывод кончился посреди JSON, `tool-call` не придёт **никогда** — ни записи в журнале, ни
сообщения, ни следа попытки. Системный промпт про этот риск
[модель предупреждает](../../projects/reformer-builder/src/agent/core/prompt.ts#L68-L71) («if it
gets cut off mid-way nothing is applied at all»), а кода, который это замечает, нет.

**3. Пакет отвергается целиком.** Когда JSON всё-таки дошёл, но битый, SDK отдаёт `tool-error` →
`tool_result { ok: false }` → `withOutcome` возвращает набор без изменений. Тот же эффект даёт
`additionalProperties: false` в `insert_node` и отказ гейта: шесть узлов — шесть независимых шансов
провалить весь вызов. В журнале строка есть, правок ноль — буквально текст заметки.

Диагностики нет ни на одном слое: `finishReason` и `rawFinishReason` никуда не пишутся,
`report()` печатает только шаги и токены, а `silentTurnNote()` в ветке «инструменты были» не даёт
ни одной подсказки — хотя в соседней ветке подсказка про `num_ctx` уже есть.

## Правки

### 1. `providers/ai-sdk.ts` — заметить и назвать обрыв

Отслеживать незакрытые вызовы: `Map<string, string>` (id → toolName), заполняется на
`tool-input-start`, чистится на `tool-call` (по `part.toolCallId`) и на `tool-input-end`. Остаток на
`finish` — это вызовы, которые модель начала и не дописала.

В ветке `case 'finish'` порядок причин: `exceededBudget` → **незакрытый вызов** → `BROKEN_FINISH` →
`reachedStepLimit`. Незакрытый вызов идёт раньше таблицы, потому что называет конкретное имя
инструмента, а не общий класс отказа. Текст сообщения — имя инструмента, факт обрыва аргументов и
две починки: окно контекста (`num_ctx` / `OLLAMA_CONTEXT_LENGTH`) и меньший пакет.

`BROKEN_FINISH` дополнить `'error'` — это безусловный отказ генерации. `'other'` **не** добавлять
слепо: для локального канала это значение по умолчанию при молчании сервера, и слепая ветка дала бы
ложные тревоги на исправных ходах. Считать `'other'` обрывом только вместе с признаком
незавершённости (незакрытый вызов), что и покрывается предыдущим абзацем.

Пробросить наружу диагностику: событие `done` получает `stopReason` (унифицированная причина) и
`rawStopReason` (`part.rawFinishReason` — сырая строка провайдера, есть в `ai@7`).

### 2. `providers/types.ts` — контракт события

`AiEvent` вариант `done` получает необязательные `stopReason?: string` и `rawStopReason?: string`.
Поля общие для любого канала, не SDK-специфичные, — граница «контракт не знает про Anthropic»
не нарушается.

### 3. `core/loop.ts` — донести до интерфейса

`TurnEvent` вариант `done` получает те же два поля. `TurnStats` получает `peakStepInputTokens` —
пик входа за шаг (не сумма): именно он показывает, во что упёрлось окно, тогда как сумма по ходу
об окне не говорит ничего. Считается в `addUsage`.

### 4. `run.ts` — перестать молчать

* `report()` печатает причину остановки и пик входа рядом с шагами и токенами.
* `silentTurnNote()` в ветке `tools.length > 0` получает диагностику того же качества, что и
  соседняя ветка: ход оборвался на полуслове, помогает большее окно контекста и меньшая задача.
* Заметка перестаёт быть единственным сигналом — при обрыве сообщение приходит из канала как
  ошибка и показывается вместо неё.

### 5. Устойчивость: одна автоматическая попытка докрутить

Тело `sendMessage` разделить: цикл событий выносится в приватную `runTurn(messages, base, opts)`,
возвращающую исход хода; `finish()` вызывается снаружи, как сейчас.

Если ход завершился обрывом на незакрытом вызове и пользователь не жал «Остановить» — сразу провести
**один** повторный ход по уже применённой схеме вкладки, с подсказкой «продолжай, вызови инструмент
меньшим пакетом», добавленной в `messages`, но **не** в ленту. Фантомной реплики пользователя быть
не должно: продолжается та же реплика ассистента, `startTurn` второй раз не вызывается. Повтор
ровно один — второй обрыв означает, что окно мало для задачи в принципе, и молотить по нему
бессмысленно.

База второй попытки — `activeTab(...).schema` после применения первой: карта формы строится заново,
контекст короче, и это ровно то, что пользователь делает руками словом «продолжай».

### 6. Тесты

* [ai-sdk.test.ts](../../projects/reformer-builder/src/agent/providers/ai-sdk.test.ts) — обвязка уже
  умеет проигрывать произвольные части (`play(parts)`), новых средств не нужно:
  `tool-input-start` + `tool-input-delta` + `finish` без `tool-call` → ошибка с именем инструмента;
  `finishReason: 'error'` → ошибка; `'other'` сам по себе → штатное завершение; проброс
  `stopReason`/`rawStopReason` в `done`.
  Тест «неизвестная причина остановки не превращается в ошибку» (строки 135-139) переписать:
  он закрепляет молчание и использует `'unknown'`, которого в `FinishReason` у `ai@7` уже нет.
* [providers/fake.ts](../../projects/reformer-builder/src/agent/providers/fake.ts) — новый вид
  `FakeStep`: вызов, начатый и не законченный. Без него режим обрыва не воспроизвести на уровне
  цикла — ровно та же дыра в покрытии, из-за которой коммит `5a781b32` завёл шаг `parallel`.
* [loop.test.ts](../../projects/reformer-builder/src/agent/core/loop.test.ts) — ход с обрывом:
  `done` несёт причину, набор изменений пуст, событие `done` приходит ровно одно.
* `run.ts` юнитами не покрыт (слой стора) — проверяется живым прогоном.

### 7. Среда — проверить окно модели

Не код, но без этого правки только назовут проблему. Постоянная часть запроса ≈ 3.5–4 тыс. токенов;
`num_ctx` Ollama по умолчанию 4096. Поднять окно: `OLLAMA_CONTEXT_LENGTH=16384` для сервера либо
`PARAMETER num_ctx 16384` в Modelfile. После правки 4 фактический пик входа виден в консоли строкой
`[agent]` — им и проверять, хватило ли.

## Проверка

1. `npm test -w @reformer/builder` (vitest) и `tsc` пакета — правки задевают контракт `AiEvent`,
   его потребители должны собраться.
2. Живой прогон на локальном канале, `num_ctx` оставить дефолтным: тот же сложный запрос обязан
   дать **внятное сообщение** («модель начала вызывать `insert_node` и не дописала аргументы…»)
   вместо прежней заметки, а в консоли — строка `[agent]` с причиной остановки и пиком входа.
3. Тот же запрос после `OLLAMA_CONTEXT_LENGTH=16384`: форма должна собраться целиком; если ход
   всё же оборвётся, автопопытка обязана его дотянуть — в ленте одна реплика ассистента, без
   фантомного «продолжай» от имени пользователя.
4. Регресс простого сценария: добавить одно поле, удалить одно поле — поведение не изменилось,
   лишних сообщений и лишних обращений к модели нет.
5. Отмена кнопкой «Остановить» посреди длинного вызова — автопопытка **не** запускается.

## Что уточнилось при реализации

План опирался на гипотезу «обрыв посреди JSON аргументов оставляет незакрытый вызов». Проверка на
подставном OpenAI-совместимом сервере (`.tmp/mock-llm/`) показала, что **для локального канала это
не так**: `@ai-sdk/openai-compatible` добирает вызов из накопленного буфера в `flush()`, разбор
падает, и приходит `tool-error`. Такой ход не тихий — ошибка видна в журнале, а цикл продолжается
и правку в итоге делает. Признак `truncatedCall` остаётся верным для каналов, которые вызов не
эмитят (Anthropic — `content_block_stop` не пришёл), но наблюдавшийся симптом ловит не он.

Наблюдавшийся симптом воспроизвёлся другим сценарием: модель уходит в рассуждение, обрывается и
закрывает поток, не прислав ни текста, ни вызова, ни `finish_reason`. Для SDK это `'other'`, для
нас было `done: complete`. Поэтому добавлен второй признак обрыва — **пустой конец хода**
(`AiStop.emptyFinish`): шаг, не давший ни ответа, ни вызова инструмента. По протоколу это аномалия
— модель либо отвечает, либо зовёт инструмент, — поэтому признак надёжен, а не эвристичен.
Рассуждение содержательным не считается: ход из одного рассуждения и есть оборванный.

Автопопытка срабатывает на оба признака. Проверено вживую: тихий обрыв → внятная ошибка канала →
второй ход по обновлённой форме → поле вставлено, в ленте ОДНА реплика ассистента без фантомного
«продолжай», в консоли `[agent] ход: шагов 1, остановка other` и следом `шагов 2, остановка stop`.
