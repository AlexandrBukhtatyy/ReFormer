# Композиция форм: переиспользование, динамический выбор, асинхронная загрузка

> **Статус: разбор вариантов, не план работ.** Решение принимает пользователь; план реализации пишется отдельно.
>
> Вход: «переиспользовать одну форму внутри другой + динамически выбирать какую когда использовать +
> загружать её асинхронно». Уточнения пользователя: набор под-форм **открыт** — любой микрофронтенд в любой
> момент регистрирует форму и её чанк подгружается; привязка данных **зависит от вида под-формы**;
> нужны **оба** слоя схемы (TS и JSON).

## Главный вывод

**Переиспользование layout уже работает** — и это меняет постановку задачи. В флагманском примере блок «адрес»
переиспользован **четырьмя** независимыми артефактами:

| Слой | Артефакт | Монтирование |
|---|---|---|
| layout | `addressNodes = (m: FormModel<Address>) => ({…})` — [schema.ts:104](../../projects/react-playground/src/pages/examples/complex-multy-step-form/schemas/schema.ts#L104) | вызов функции (`:440`, `:446`) |
| validation | `addressSchema: ValidationSchema<Address>` — [validation.ts:228](../../projects/react-playground/src/pages/examples/complex-multy-step-form/schemas/validation.ts#L228) | прямой вызов + `validateWhen` |
| behavior | `addressBehavior` — [behavior.ts:137](../../projects/react-playground/src/pages/examples/complex-multy-step-form/schemas/behavior.ts#L137) | `apply([model.$.reg, model.$.res], …)` |
| React | `AddressForm({control, testIdPrefix})` | JSX-проп |

Работает это потому, что `signalAt`/`$` на фасаде под-модели резолвятся **относительно**
([form-model.ts:336-346](../../packages/reformer/src/state/form-model.ts#L336-L346)), а `facadeCache` даёт
стабильную идентичность. То есть **относительный scope — уже существующий, рабочий примитив ядра**.

Значит настоящая проблема оси 1 — не «нельзя переиспользовать», а **четыре декларации, три разные идиомы
монтирования и четвёртая система адресации (`testIdPrefix` руками)**. Это задача про связывание, а не про
новую способность. Соответственно `defineFragment` из [stateful-sleeping-volcano.md](stateful-sleeping-volcano.md)
даёт не «возможность переиспользовать», а **префиксование селекторов + перенос способности в JSON-слой**.

Оси 2 и 3 — принципиально другие, и именно там лежит настоящая работа.

## Развилка: три оси — три разные проблемы

| Ось | Во что упирается | Настоящая цена |
|---|---|---|
| **1. Переиспользование** | Ни во что в ядре. Ноды порождаются формой **модели**, а не layout'ом, поэтому блок ничего не создаёт — только доносит конфиг. | Низкая. Дельта — унификация + JSON-слой. |
| **2. Динамический выбор** | В то, что **один бизнес-предикат пишется трижды в трёх несвязанных системах адресации**, и в то, что **payload включает выключенные поля**. | Средняя. Ядро придётся тронуть. |
| **3. Асинхронность** | В `createForm` как в единственную точку, где материализуются model-массивы и наполняется глобальный реестр сигнал→нода. | Высокая. Расслаивается на «слабую» (работает) и «сильную» (упирается в неизменяемость модели). |

Про ось 2 подробнее, потому что здесь чаще всего ошибаются. `hideWhen` **не выключает и не сбрасывает** ветку —
только `return null` в рендере ([render-node.tsx:664-682](../../packages/reformer-renderer-react/src/core/render-node.tsx#L664-L682)).
Чтобы «выбрать вариант» по-настоящему, надо синхронно держать три рычага:

```
hideWhen(schema.node('vehicle-section'), cond)            // адресация СТРОКОЙ-селектором
enableWhen(model.$.vehicle, cond, {resetOnDisable:true})  // адресация СИГНАЛОМ
validateWhen(cond, () => { … })                           // адресация ЗАМЫКАНИЕМ
```

Связи между ними в коде нет. `validateModel` слова `disabled` не знает вовсе (ноль вхождений в
[validation-schema.ts](../../packages/reformer/src/form/validation-schema.ts)) — **скрытая, но не выключенная
и не обёрнутая в `validateWhen` ветка завалит submit**. Это ровно то, что зафиксировано аналитически
в [2-resilient-wigderson.md](2-resilient-wigderson.md) (9 предикатов, написанных 28 раз).

Отдельно: `FormSchemaNode.when` задекларирован в JSDoc
([schema-node.ts:53](../../packages/reformer/src/form/types/schema-node.ts#L53)), но **не реализован нигде** —
мёртвая строка документации, опираться на неё нельзя.

## Установленные факты

Проверено чтением исходников (адверсарная проверка гипотез). Всё с указанием файла и строк.

### Ф1. Форма модели неизменяема — с оговорками

Ключ в объект-группу добавить нельзя: `children` наполняется только в конструкторе
([form-model.ts:106-117](../../packages/reformer/src/state/form-model.ts#L106-L117)); `GroupNode.set` итерирует
по **существующим** детям ([:129-138](../../packages/reformer/src/state/form-model.ts#L129-L138)); value-proxy
`set` на неизвестном ключе возвращает `false` ([:396-404](../../packages/reformer/src/state/form-model.ts#L396-L404)).
API присоединения готовой под-модели нет (`attach|graft|addField|merge|subModel` в экспортах — пусто).

Асимметрия, о которой стоит знать: `model.set({newKey})` и `model.patch({newKey})` — **тихий no-op**
(`set` и `patch` буквально одна функция, [:379-380](../../packages/reformer/src/state/form-model.ts#L379-L380)),
а `model.newKey = 'x'` — **TypeError** в strict mode. Тестов на это нет.

Опровергнуто «узлы рождаются только в `push`/`insertAt`»: `ArrayNode.set`
([:210-213](../../packages/reformer/src/state/form-model.ts#L210-L213)) пересобирает узлы через `buildNode`
и достижим из `model.set(…)`, `model.patch({rows:[…]})`, `model.reset()`, `ModelArrayNode.setValue`.
**Следствие: `model.reset()` на форме с массивом уничтожает идентичность сигналов строк** → промах `cache`
в `ModelArrayNode` → все per-item формы диспозятся и пересобираются, `touched`/`errors` строк теряются.

### Ф2. Инвариант «разворот на build» верен, но обоснован ложно

[stateful-sleeping-volcano.md](stateful-sleeping-volcano.md) запрещает «фрагмент = React-компонент» на том
основании, что теряются валидаторы. **Валидаторов в layout-дереве M1 нет вообще.** `harvestFieldConfig`
переносит ровно пять ключей ([create-form.ts:94-101](../../packages/reformer/src/form/create-form.ts#L94-L101)),
`validators` среди них нет — сам код это декларирует ([:149-151](../../packages/reformer/src/form/create-form.ts#L149-L151)).
Валидаторы теряются у **любого** листа M1 — это открытый баг `ReFormer-ixr`, а не свойство композиции.
JSDoc самой `createForm` ([:32](../../packages/reformer/src/form/create-form.ts#L32), `:172`) обещает обратное
и рассинхронизирован с кодом.

Более того, из пяти harvest-ключей **`updateOn` и `debounce` в M1 мертвы**: оба гейтятся собственными
валидаторами ноды ([field-node.ts:174,190,315,480](../../packages/reformer/src/form/nodes/field-node.ts#L174)),
которых в M1 не бывает. Реально переносятся `component`, `componentProps`, `disabled`.

**Честная формулировка инварианта:** *переиспользуемый блок обязан разворачиваться в тот же объект
`FormSchemaNode`, который передан в `createForm({model, schema})` — потому что именно этот вызов материализует
model-массивы в `ModelArrayNode` и наполняет глобальный реестр сигнал→нода.*

### Ф3. Инвариант расслаивается: массивы — жёстко, листья — мягко

Это ключ ко всей задаче.

- **Листовое поддерево над путями, которые уже есть в модели, — деградирует мягко.** Рендерится корректно
  (`component`/`componentProps` берутся из `RenderNode`,
  [render-node.tsx:159,176](../../packages/reformer-renderer-react/src/core/render-node.tsx#L159)),
  `validateModel` работает (он идёт от модели), selector-API работает целиком. Теряется только FieldNode-side
  конфиг: `label`/`required`/`description` в `FieldWrapper` (cdk `useFormField` читает их из
  `control.componentProps`) и детект inline-подписи. `componentProps` и `disabled` чинятся постфактум
  (`updateComponentProps`, `disable()`); **не чинится только `component`** — он `readonly`.
  `description` не чинится тоже: [form-field.tsx:114](../../packages/reformer-ui-kit/src/components/form-field/variants/base/form-field.tsx#L114) `peek`'ает его один раз.
- **Поддерево с узлом массива — ломается жёстко и молча.** `ModelArrayNode` материализуется только в
  `createForm` ([:220-234](../../packages/reformer/src/form/create-form.ts#L220-L234), `if (!itemFn) continue;`).
  Поздний массив: узла нет → `getNodeForSignal(rowLeaf) === undefined` → warn + `return null` →
  **строки рендерятся пустыми**; `applyEach` бросает «массив не материализован в схеме формы».
  Постфактум-API материализации нет.

**Ограничение сильнее, чем принято думать: массив материализуется ТОЛЬКО в корне формы.** `harvest` кладёт
item-фабрику по **абсолютному** `arr.__path` ([:88-90](../../packages/reformer/src/form/create-form.ts#L88-L90)),
а материализация ищет по **голому top-level ключу** ([:225](../../packages/reformer/src/form/create-form.ts#L225)).
Для корня они совпадают. Для под-модели строки `im.docs.__path === 'properties.0.docs'` ≠ `'docs'` → промах.
Значит массив не материализуется **ни внутри группы, ни внутри строки другого массива**. Блок
«адрес + список документов» не заработает нигде, кроме корня формы.

### Ф4. Селекторы: коллизия есть, но механизм не тот, что описан в плане

`createRenderSchema` **не обходит дерево ни разу** — создаёт пустые `Map`, наполняемые только вызовами
`.node(selector)` ([render-schema-proxy.ts:167-245](../../packages/reformer-renderer-react/src/core/render-schema-proxy.ts#L167-L245)).
Резолв — по строке в момент рендера. Следствие: **поздно собранное поддерево полностью адресуемо**.
Реальная проблема — плоский namespace: два инстанса блока читают один строковый ключ, **абсолютно молча**.

Две асимметрии, на которых легко попасться:
- `refRegistry` имеет фоллбэк `selector ?? __path` ([:701-705](../../packages/reformer-renderer-react/src/core/render-node.tsx#L701-L705)),
  а `hiddenOverrides`/`propsOverrides`/`conditionRegistry`/`lifecycleRegistry` — нет. `getRef()` может работать
  там, где `setHidden(true)` молча ничего не делает.
- `propsOverride` вычисляется для каждого узла, но **применяется только в контейнерной ветке** (`:737`).
  `patchProps` на лист или массив — тихий no-op.

### Ф5. Монтирование в scope родителя формально уже работает — и ломается в четырёх местах

`FormMountProps.model?: FormModel<T>` уже есть и проброшен до `createJsonForm`
([mounted-form.tsx:29,49-59](../../packages/reformer-form-registry/src/react/mounted-form.tsx#L29)), покрыт тестом.
Под-модель родителя — это буквально `FormModel<T>`. Значит
`<FormOutlet id="address" model={parentModel.registrationAddress} />` **компилируется и рендерится сегодня**.

Ломается тихо:

1. **Реестр сигнал→нода — глобальный `WeakMap` без ключа формы, last-write-wins**
   ([signal-node-registry.ts:18,42-44](../../packages/reformer/src/form/signal-node-registry.ts#L18)).
   Родитель уже имеет ноды на те же сигналы (они строятся из модели, а не из layout); под-форма создаётся
   позже и **перетирает**. Родитель агрегирует `valid`/`errors` по осиротевшим нодам, `validateModel` роутит
   ошибки в новые. Рассинхрон без единого warning. Это открытая задача `ReFormer-lx2`.
2. **Валидность не агрегируется вверх** — механизма нет (`scope|prefix|parent|subform` по form-registry пусто).
3. **Форма не диспозится нигде** — `.dispose()` даёт **ноль** вхождений в `renderer-json`, `renderer-react`,
   `form-registry`, `cdk`. Для независимой формы это утечка, умирающая с моделью; для под-формы сигналы
   принадлежат **родителю** и переживают unmount → `getNodeForSignal` возвращает ноду размонтированного
   поддерева. Это ровно сценарий переключения варианта.
4. **Preflight не видит хостовую модель**: `unmaterialized-model-paths` сверяет схему с `initial`
   ([preflight.ts:241-254](../../packages/reformer-form-registry/src/preflight.ts#L241-L254)), а проп `model`
   живёт ниже по течению; при `model` фабрика записи вообще не вызывается.

Плюс: `FormOutlet` **не может** быть зарегистрирован как `$component(...)` — он читает
`useFormRegistryContext()`, который бросает вне провайдера, а React-контекст границу бандла не пересекает
(тот же мотив, по которому `ComponentRegistry` передаётся пропом).

### Ф6. Payload включает выключенные поля

`GroupNode.getValue()` не проверяет `disabled` ([group-node.ts:239-246](../../packages/reformer/src/form/nodes/group-node.ts#L239-L246)),
`form-submitter.ts:137` отдаёт его как есть. Opt-out'а нет (`getRawValue|includeDisabled|skipDisabled` — ноль
вхождений), `pick`/`omit`/`toPayload` в ядре нет. `resetOnDisable` обнуляет **значения**, но не опускает ключи:
payload получит `{vehicle:{…пусто}, property:{…пусто}, health:{…}, travel:{…}}`.

При этом на `form.valid` выключенное поддерево не влияет
([aggregate-signals.ts:88-91](../../packages/reformer/src/form/aggregate-signals.ts#L88-L91)). То есть
`enableWhen` — рабочий рычаг для валидности, но не для payload.

Два JSDoc ядра противоречат друг другу: [behaviors-node.ts:32-34](../../packages/reformer/src/form/behaviors-node.ts#L32-L34)
честно предупреждает «мусор утечёт в payload», а [form-node.ts:363](../../packages/reformer/src/form/nodes/form-node.ts#L363)
утверждает «отключённые узлы не включаются в `getValue()`» — **это неверно**.

## Блокеры, которые придётся починить при любом варианте

Эти пять вещей не зависят от выбора варианта и лежат ровно на тех рычагах, на которые любой из них обопрётся.
**У них есть самостоятельная ценность:** после их починки чистый payload и рабочее выключение ветки становятся
доступны уже сегодня, вручную, без всякой композиции — плюс исчезает утечка подписок. Это разумная первая
работа независимо от того, какой вариант будет выбран.

1. **`enableGroup` течёт и может быть вечным no-op.** [behaviors.ts:349-366](../../packages/reformer/src/form/behaviors.ts#L349-L366):
   `effect(...)` без `onDispose` (в отличие от скалярной ветки `:333`), и `nodeByPath(g.__path)` резолвится
   один раз **до** effect — нет ноды на момент запуска ⇒ молчаливый no-op навсегда. Это ровно тот рычаг,
   которым выключается невыбранный вариант.
2. **`.dispose()` не вызывается нигде** в четырёх пакетах. Без этого переключение варианта копит мёртвые ноды.
3. **`form.submit(fn)` без `{skipValidation:true}` уничтожает результат schema-валидации**:
   `GroupNode.validate()` ([:324-339](../../packages/reformer/src/form/nodes/group-node.ts#L324-L339)) первым
   делом зовёт `clearErrors()`, стирая только что разложенные `validateModel` ошибки, и в M1 возвращает `true`
   всегда. `FormWizard` спасается только явным `skipValidation:true`.
4. **`apply()` даёт под-схеме деградированный фасад.** `applyEach` → настоящий `makeFormModel`
   ([behaviors.ts:460,466](../../packages/reformer/src/form/behaviors.ts#L460)), а `apply` → `nestedModel`
   ([:172-186](../../packages/reformer/src/form/behaviors.ts#L172-L186)) без `set`-трапа и без `ModelApi`,
   типизированный `as FormModel<T>`. Переиспользуемое поведение через `apply` **молча теряет** записи
   `model.field = x` и падает на `model.get()`. Чинится дёшево — `makeFormModel` уже существует.
5. **JSON-дерево реконвертируется на каждый рендер.** `FormRenderer` зовёт `render()` в теле компонента
   ([form-renderer.tsx:53](../../packages/reformer-renderer-react/src/core/form-renderer.tsx#L53)), а
   `createRenderSchemaFromJsonM1` возвращает `() => convertNodeM1(schema.root, model, registry)`
   ([json-to-render-schema.ts:397-403](../../packages/reformer-renderer-json/src/converter/json-to-render-schema.ts#L397-L403)).
   Значит **любое замыкание, созданное конвертером, получает новую идентичность каждый рендер**.
   `useCondition` построен на `useCallback([fn])` + `useSyncExternalStore` → отписка и новый `computed(fn)`
   на каждый рендер. Следствие для оси 2: **условие варианта нельзя класть на узел свежим замыканием** —
   его надо брать из кэша, живущего в замыкании `createRenderSchemaFromJsonM1` (оно создаётся один раз
   в `useMemo`). Тот же кэш попутно чинит сброс кэша строк массива, завязанного на идентичность item-фабрики.

## Разбор вариантов

Оси решаются разными механизмами, поэтому это **комбинируемые слои**, а не взаимоисключающие альтернативы.

### Вариант A — блок как типизированный кортеж функций (минимальная дельта)

Не новый вид узла, а формализация того, что уже написано четырьмя руками:
`FormPart<TScope> = (m: FormModel<TScope>) => { layout, behavior, validation }` + единая идиома монтирования +
обязательный `selectorPrefix`. Плюс `defineFragment`/`$fragment`/`$def` для переноса способности в JSON-слой
(это и есть [stateful-sleeping-volcano.md](stateful-sleeping-volcano.md)).

Выбор варианта — один дескриптор `FormVariant`, из которого выводятся три существующих рычага, чтобы
предикат был написан один раз.

| | |
|---|---|
| **Ось 1** | ✅ Решает полностью и в обоих слоях. |
| **Ось 2** | ⚠️ Дедуплицирует **авторство** предиката, но три механизма остаются тремя. Заклейка, не починка. |
| **Ось 3** | ⚠️ Только «слабая» половина: модель известна, по сети едет разметка. «Форма сейчас, вариант потом» требует `applyLateLayout` (~60 строк + `setComponent`) и запрета массивов. |
| **Цена** | Низкая. Semver MINOR, ломающих нет. Ценность после первой фазы — высокая. |
| **Не решает** | Открытый MFE-каталог. Чистый payload (нужен шов `getValue({skipDisabled})`). Массивы вне корня. |

### Вариант B — слот: узел, владеющий поддеревом модели

Обобщение **единственного существующего механизма ленивого построения дочерней формы** — `ModelArrayNode`.
Он строит форму строки через `createFormFromModel({model: itemModel, schema: itemFn(im)})`, кэширует по
идентичности под-модели, детерминированно диспозит выбывшие
([model-array-node.ts:105-147,278-283](../../packages/reformer/src/form/nodes/model-array-node.ts#L105-L147)).
Родитель в это поддерево не лезет — `buildModelConfig` массивы `continue`-ит
([create-form.ts:136-141](../../packages/reformer/src/form/create-form.ts#L136-L141)), **именно поэтому
коллизии реестра сигнал→нода там нет**.

`ModelSlotNode` — то же для одиночной под-модели, с билдером схемы, который может быть асинхронным и сменяемым.

| | |
|---|---|
| **Ось 1** | ➖ Ортогонален (переиспользование даёт A). |
| **Ось 2** | ✅ Смена варианта = смена схемы слота. `getValue()` слота отдаёт **только активную ветку** → payload чистится сам, без нового API. Валидность агрегируется как у `ModelArrayNode`. |
| **Ось 3** | ✅ Асинхронный билдер легален: разворот идёт через `createFormFromModel`, а не «после `createForm`» — значит массивы материализуются и реестр наполняется. |
| **Цена** | Высокая. Новый узел в ядре + ветка в `buildModelConfig`/`createForm` + вариант `RenderNode` + узел JSON. Ценность после первой фазы — низкая. |
| **Риск** | Требует существования под-модели `model.objectData` (Ф1). Надо проверить кэш `controlsRecord` в `form-proxy-builder` — он опирается на «поля фиксированы в конструкторе». |

### Вариант C — доделать реестр форм до монтирования в scope

Здесь надо жёстко развести две версии — они выглядят одинаково, но одна из них запрещена.

**C-scoped (рабочая).** `FormEntry.mount: 'root' | 'scoped'`, где scoped-запись **не строит вторую форму**,
а доставляет layout и конфиг в **уже существующее** дерево нод хоста. Конфликта владения не возникает.

**C-naive (запрещена).** `FormOutlet model={parent.vehicle}` — компилируется, рендерится и покрыта тестом
**сегодня**, и именно поэтому опасна. Второй `createForm` над **сигналами родителя** при глобальном
last-write-wins реестре молча перепривязывает листья: родитель агрегирует `valid`/`errors` по осиротевшим
нодам, `validateModel` роутит ошибки в новые — рассинхрон **без единого warning**. Плюс `dispose` не
вызывается нигде, поэтому после переключения варианта `getNodeForSignal` продолжает отдавать ноду мёртвой формы.

> **Правило, которое обязано попасть в контракт дословно: композиция НИКОГДА не создаёт вторую форму
> над сигналами родителя.** Либо scoped-доставка в существующее дерево, либо собственная модель — третьего нет.

| | |
|---|---|
| **Ось 1** | ❌ Плохо. Менять 60 строк memo-компонента `AddressForm` на JSON + запись реестра + `useFormResource` + preflight ради двух адресов в одной форме — избыточно. |
| **Ось 2** | ⚠️ Через `FormQuery {by:'variant'}` + дискриминатор в записи. Три рычага остаются. |
| **Ось 3** | ✅ Уже реализовано: `DataSource`/`CodeSource`, кэш, preflight, `FormResource`. |
| **Цена** | Низкая по объёму, но правки лежат **в ядре** (`signal-node-registry`) и задевают всех. |
| **Риск** | Scoped-запись физически **не может нести массив** (Ф3) и не может принести свою форму данных (Ф1). Требует `FormRegistryProvider` в host-shell: `useFormRegistryContext` бросает вне провайдера, а React-контекст границу бандла не пересекает. |

## Рекомендация

**A + C сразу, B — если понадобятся вариантные массивы.** Это не компромисс, а разграничение по критерию:

> Повторяющийся кусок layout **той же формы** → блок (A).
> Едет по сети или выбирается из каталога времени исполнения → реестр (C).
> Ветка со **своим массивом** или требующая чистого payload → слот (B).

Для сценария пользователя (MFE регистрирует форму, чанк подгружается) рабочая связка — **A + C**:
хост объявляет слот в `createModel`; MFE регистрирует scoped-запись с дискриминатором; при смене
`insuranceType` реестр отдаёт другую запись. Ограничение «код не едет по сети» сценарий **не задевает**:
behavior/validation/registry едут как `CodeSource.module` — динамический import из бандла самого MFE.

**Чего эта связка не закрывает и о чём надо знать заранее:** шаг 4 страховой спеки — это
**вариантные массивы** (водители / выгодоприобретатели / путешественники / история убытков). Ни A, ни C их
не покрывают: массив материализуется только в корне формы (Ф3). Это и есть единственный настоящий довод за B.

Перед началом любого варианта — четыре блокера из [раздела выше](#блокеры-которые-придётся-починить-при-любом-варианте).

## Что делать с неизвестной заранее формой данных

Модель неизменяема (Ф1), а MFE регистрирует форму, шейп которой хост не знает. Три честных пути:

| Путь | Как | Цена |
|---|---|---|
| **Заранее объявленный union** | Хост объявляет все ветки: `{vehicle:{…}, property:{…}, health:{…}, travel:{…}}`. Именно так написана [insurance-application-form.md](../specs/insurance-application-form.md) — четыре независимых поддерева при одном дискриминаторе. | Только **закрытый** набор. Для MFE не подходит. Payload грязный. |
| **Изолированная под-модель** | Слот/запись создаёт **свою** `FormModel` из `initial`; склейка на submit. | Снимает и неизменяемость, и коллизию реестра сигнал→нода. Цена: `compute`/`copyFrom` между родителем и веткой становятся ручными, кросс-валидация — через явный проброс. |
| **Слот как массив 0..1** | Существующий `ModelArrayNode` без нового узла: форма строки решается в рантайме из пушнутого значения — **единственное место в ядре, где это возможно**. | Работает, но: `ModelArray<U>` типизирован одним `U`; `signalAt` в «чужую» строку тихо отдаёт `undefined`; вложенный массив не материализуется; семантика вводит в заблуждение. Прототип, не контракт. |

Три уточнения, которые меняют оценку:

- **У изолированной под-формы конфликта владения нодами НЕТ вообще** — она работает над **своими** сигналами,
  глобальный `WeakMap` сигнал→нода не задевается. Это единственный путь, честно закрывающий по-настоящему
  неизвестную форму данных, и он не требует правки `signal-node-registry`.
- Слот-массив ограничен сильнее, чем кажется: `push()` **без аргумента** даёт `buildNode({})` — бесформенную
  строку без детей ([model-array-node.ts:177-179](../../packages/reformer/src/form/nodes/model-array-node.ts#L177-L179)),
  и это публичный API секции массива.
- Заранее объявленный union требует `resetOnDisable` на **каждой** ветке, иначе данные покинутой ветки
  уедут на submit даже с чистым payload по ключам.

**Вывод:** ответ пользователя «зависит от вида под-формы» — правильный, и два режима надо развести **в типах**:
**привязанный** к под-модели родителя (один payload, кросс-валидация работает, шейп объявлен заранее) и
**изолированный** (своя модель, склейка на submit объявляется явно). Смешивать нельзя — это прямой источник
тихих ошибок (Ф5).

### Решающая таблица

| Ситуация | Путь | Механизм |
|---|---|---|
| Повторяющийся кусок layout той же формы | — | блок / `$def` (A) |
| Взаимоисключающие варианты, набор известен | union | дескриптор варианта → три рычага (A) |
| Разметка едет по сети, ключи модели известны | union | резолв документа **до** `createForm` (C-scoped) |
| Форма данных неизвестна, нужна ОДНА модель | слот-массив | массив 0..1 **в корне формы** (B) |
| Форма данных неизвестна, граница приемлема | своя модель | `MountedForm` + агрегация через `onReady` |
| Под-форма над сигналами родителя | — | **запрещено** (C-naive) |

## Открытые вопросы

1. **Шов чистого payload — но не наивный `skipDisabled`.** Наивная версия опасна: node-level `disabled`
   означает «поле выключено», и как только его напишут на **вычисляемом** поле, из payload вылетят
   `totalPremium`/`age`/`bmi`. Безопасная формулировка — **опускать только выключенные ГРУППЫ, никогда листья**:
   вычисляемое поле всегда лист, ветка варианта всегда группа.
   ```ts
   // group-node.ts
   getValue(options?: { omitDisabledGroups?: boolean }): T {
     this._fields.forEach((field, key) => {
       if (options?.omitDisabledGroups && field instanceof GroupNode && field.disabled.peek()) return;
       result[key] = field.getValue(options) as never;
     });
   }
   ```
   Коллизия сегодня ещё не наступила только потому, что все `disabled: true` в playground лежат **внутри
   `componentProps`** ([schema.ts:634-672](../../projects/react-playground/src/pages/examples/complex-multy-step-form/schemas/schema.ts#L634-L672)),
   а не на узле. Это один коммит до проблемы. Вопрос к решению: принимаем ли группо-ориентированную семантику
   как контракт (и документируем «ветка варианта обязана быть группой»), или идём через submit-трансформ.
2. **Владелец в `signal-node-registry` (`ReFormer-lx2`) — в рамках этой работы или нет?** Не нужен для A и для
   scoped-версии C (одна форма — одно дерево нод), но без него закрыта дорога к «две формы над одной моделью»,
   то есть к изолированным под-формам. Если ответ «нет» — надо **явно записать в контракт**, что блок нельзя
   монтировать через `FormOutlet`/`createJsonForm`, иначе кто-то это сделает и получит тихий рассинхрон.
3. **Вариантные массивы шага 4 — что с ними?** (а) целиком в коде хоста, все четыре объявлены в build-схеме,
   переключение `enableWhen` — работает, payload грязный, кода не переиспользуется; (б) вариант B со
   слотом-массивом; (в) отдельная форма + ручная агрегация. Принципиальная развилка, решать до, а не после.
4. **Правим ли [stateful-sleeping-volcano.md](stateful-sleeping-volcano.md)?** Инвариант №1 обоснован ложно
   (Ф2), инвариант №2 — ужесточение, а не фиксация (сегодня нерезолвимый `$model` даёт `console.warn`),
   предпосылка про селекторы неверна по механизму (Ф4). Это план, а не спека, править можно — но стоит
   подтвердить, что он остаётся живым артефактом.
