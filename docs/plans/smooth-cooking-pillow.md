# Графики трейсов в отчёте бенчмарка форм

## Контекст

В trace-режиме бенчмарк пишет DevTools-трассу на участника и форму:
`projects/forms-benchmark-e2e/results/<run>/traces/<lib>-<form>.json` (≈110 МБ, baseline ≈8 МБ,
по одному событию на строку). Сейчас их можно открыть только по одной в DevTools → Performance —
сравнить участников между собой нельзя.

Цель: в HTML-отчёте (`report.html`) для каждой формы (credit, registration) показать, как
меняются **JS heap, DOM-узлы и обработчики событий** во времени. На каждом графике — все
участники, у каждого свой цвет; три графика друг под другом с общей осью X.

Решения пользователя:
- **Y** — три счётчика из событий `UpdateCounters`: `jsHeapSizeUsed`, `nodes`, `jsEventListeners`.
- **X** — выравнивание по фазам. Для этого в трассу добавляются метки фаз и бенч прогоняется
  заново. Старые трассы без меток не рисуются — вместо графика выводится пояснение.
- **Где** — новый раздел в HTML-отчёте (`scripts/report-html.mjs`).

Почему нужны метки: из меток в трассе сейчас только `bench:ready` и `bench:prefill`. Участники
проходят фазы с разной скоростью, а между фазами есть пауза `thinkMs`, ожидание простоя и GC.
Поэтому по сырому времени кривые разъезжаются, и «шаг 1» одной библиотеки оказывается напротив
«шага 2» другой.

## 1. Метки фаз в трассе — `projects/forms-benchmark-e2e/lib/session.ts`

- Приватный хелпер `mark(name)`: `page.evaluate((n) => performance.mark(n), name)` **только при
  `info.mode === 'trace'`**. Замеряемые прогоны (`timing`, `renders`) метки не получают и не
  меняются.
- Имена меток: `bench:phase:<id>:start` и `bench:phase:<id>:end`. Id фазы — в имени, а не в
  `detail`: в trace-событии `blink.user_timing` надёжно доходят только имя и `ts` (проверено:
  `bench:ready` лежит там как `ph: "I"` с `ts`).
- Где ставятся:
  - `phase()` — `start` сразу перед `action()`, `end` — после пост-`idle()`. Это то же окно, что у
    `__probe`.
  - `load()` — `start` перед `page.goto`. Метка встаёт в старом документе, но в трассе у неё общий
    clock. `end` — после `idle()`.
  - `remount()` — `start` до прогрева, `end` после цикла.
- Трассу включает `credit.bench.ts` / `registration.bench.ts`, их менять не нужно. Фазы
  `load-application` и `load-invite` идут вне трассы, поэтому на графиках их не будет.

## 2. Извлечение рядов — новый `projects/forms-benchmark-e2e/scripts/traces.mjs`

`export async function traceSeries(runDir, form)` → данные графиков формы.

- **Потоковое чтение**: `readline` по строкам, без `JSON.parse` всего файла (110 МБ × 7). Разбираются
  только строки, где есть `"UpdateCounters"`, `"blink.user_timing"` или `"thread_name"`; хвостовая
  запятая снимается.
- **Поток**: берутся только события главного потока рендерера (`thread_name = CrRendererMain`).
  Навигация может сменить процесс рендерера: тогда с первого события нового pid события старого
  pid отбрасываются.
- **Сегменты**: из меток получается `start` каждой фазы. Сегмент участника `k` = `[start_k,
  start_{k+1})`, то есть сама фаза и пауза/GC до следующей. Последний сегмент заканчивается на
  `end`.
- **Общая ось**: фазы берутся в порядке `PHASES[form]` (`scripts/metrics.mjs`). Ширина сегмента —
  максимум его длительности по участникам, `offset_k` — накопленная сумма. Отсчёт участника
  переводится в X так: `X = offset_k + (ts − start_k)`, в мс. Внутри фазы время реальное, просто
  начала фаз совпадают. У быстрого участника линия заканчивается раньше конца сегмента, между
  сегментами — разрыв линии.
- **Прореживание**: около 600 корзин на всю ширину оси. В каждой корзине — min и max в порядке
  времени, чтобы сохранить «пилу» GC и ступени узлов. Округление: X до 1 мс, heap — МБ с 2 знаками.
- **Участники**: `LIB_ORDER` из `scripts/aggregate.mjs`, без `CONTROL` (`reformer-core-aa`) — так
  же, как в ключевых графиках.
- **Результат**: `{ phases: [{ id, title, offset, width }], libs: { [lib]: { heap, nodes,
  listeners: [[x, y], …] } }, unmarked: string[] }`. В `unmarked` попадают участники, у которых
  трасса без меток.
- **Кэш**: `results/<run>/traces/series.json` с `{ version, files: { name: { size, mtimeMs } } }`.
  Если файлы трасс не изменились, ряды берутся из кэша, иначе пересчитываются. Без кэша на каждый
  `report` уходит около 0,7 ГБ чтения.

## 3. Отрисовка — `projects/forms-benchmark-e2e/scripts/report-html.mjs`

Перед вёрсткой загрузить скилл **dataviz**: палитра, валидатор, правила линий и взаимодействия.

- Сигнатура меняется на `renderHtml(summary, labels, traces = {})`. Третий аргумент
  необязательный, поэтому `compare.mjs` и другие вызовы не ломаются.
- В секции каждой формы, после «Ключевых метрик», добавляется `<h3>Трейсы: память и DOM во
  времени</h3>`:
  - короткое пояснение оси X: «начала фаз выровнены, внутри фазы время реальное; heap без
    принудительного GC — видна пила сборки мусора; значения после GC — в таблицах фаз»;
  - своя легенда с 6 цветами. Важно: в этом разделе цвет означает участника, а не роль, как на
    барах;
  - три `<figure class="chart">` друг под другом с общей осью X: «JS heap, МБ», «DOM-узлы»,
    «Обработчики событий». SVG собирается в Node, как `barChart`;
  - вертикальные правила на началах фаз с номерами; под графиками — список «номер → название фазы»
    из `PHASES`.
- Цвета — 6 категориальных токенов `--series-1..6` в `:root` с вариантами для тёмной темы (в
  стиле уже существующих `--accent` и `--rest`). Значения брать из палитры dataviz и проверять её
  валидатором в обеих темах.
- Взаимодействие на общем `#tip`:
  - наведение на элемент легенды или линию приглушает остальные серии;
  - перекрестие на графике: под курсором — фаза и значения всех участников. Данные для подсказки
  кладутся компактным JSON в `<script type="application/json">`, ряды те же, что в SVG.
- Если `unmarked` не пуст или трасс нет — вместо графиков `<p class="muted">` с подсказкой:
  перезапустить бенч с `BENCH_TRACE=1`.

## 4. Подключение — `projects/forms-benchmark-e2e/scripts/report.mjs`

- После `aggregate(runs)`: `traces[form] = await traceSeries(runDir, form)` для каждого прогона.
  Это не попадает в `summary` — иначе раздуется публикуемый `summary.json`, который форматируется с
  отступами.
- `renderHtml(summary, LABELS, traces)`. В `report.md` — одна строка: «графики трейсов — в
  report.html».
- `--publish` не меняется: копирует `report.html`, графики уже внутри.

## 5. Документация

- `projects/forms-benchmark/README.md`, раздел «Где что»: трассы теперь размечены по фазам и
  нарисованы в `report.html`; кэш `traces/series.json`.
- `projects/forms-benchmark/BENCH-CONTRACT.md`: метки `bench:phase:<id>:start|end` ставятся только
  в trace-прогоне и не влияют на замеры.

## Проверка

1. `npm run typecheck -w forms-benchmark-e2e`.
2. Короткий прогон только с трассами:
   `BENCH_ITERATIONS=0 BENCH_WARMUP=0 BENCH_RENDERS=0 npm run bench`. Убедиться, что `report.mjs`
   не падает без timing-данных; если падает — проверять на `--runs` с новыми каталогами.
3. В новых трассах есть метки:
   `grep -c 'bench:phase:' results/<run>/traces/rhf-credit.json` — по паре на каждую фазу.
4. `npm run bench:report -- --runs <credit-run>,<registration-run>`. Затем открыть
   `results/_reports/<stamp>/report.html` (`open` в песочнице заблокирован — открывает
   пользователь) и проверить:
   - на каждую форму 3 графика и 6 линий;
   - начала фаз совпадают по X у всех участников;
   - подсказка и подсветка работают;
   - тёмная тема читается;
   - ширина 375 px — без горизонтальной прокрутки.
5. Повторный `bench:report` берёт ряды из `series.json`: заметно быстрее, ряды те же.
6. Отчёт по старому прогону (без меток) показывает пояснение и не падает.
7. Полный прогон (`npm run bench`) и `--publish` — только по решению пользователя: прогон долгий,
   результат коммитится.
