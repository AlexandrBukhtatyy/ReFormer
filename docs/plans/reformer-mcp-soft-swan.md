# Knowledge-слой ReFormer в браузере: `core` / `platform` и подключение к ассистенту билдера

> Актуализировано 2026-08-22 после переработки `@reformer/mcp` (коммиты `987110c6`, `0d6ce064`,
> `937233cb`, `1fe780e0`). Цифры измерены на HEAD; ссылки — на реальный код.

## Context

`@reformer/mcp` работает **только по stdio** — браузер такой сервер поднять не может. При этом в
`projects/reformer-builder` уже есть зрелый AI-ассистент: BYOK прямо из вкладки, Vercel AI SDK v7,
свой agent-loop и 13 инструментов над layout-JSON, ничего не знающих про API `@reformer/core`.

Задача: сделать так, чтобы знания о библиотеке были доступны ассистенту билдера, **включая канал
GitHub Pages без Node-процесса**.

**Цели (все четыре, подтверждены):** (1) справка по библиотеке, (2) заполнение `validation.ts` /
`form.behavior.ts`, которые codegen эмитит моками, (3) форма целиком по спеке, (4) проверка
технической осуществимости переноса.

**Принятые решения:**

| Развилка | Решение |
| --- | --- |
| Граница «ядро / среда» | `src/core/` + `src/platform/{cli,browser}/` внутри существующего пакета |
| Как ядро получает источники | **Фабрика `createKnowledge(sources)`**, без глобального состояния |
| Корпус в браузере | `llms-index.json` **и** `llms.txt` |
| Набор инструментов для билдера | **Один фасад-инструмент**, каскад `choose_api → find_recipe → search_docs` внутри него. Выбран замером Э0, отчёт — [builder-toolset.md](../mcp-eval/builder-toolset.md) |
| Канал Pages | Обязателен |
| MCP-протокол в браузере | Нет; фасад из тех же `definition` + функция (обоснование — §4) |
| Web worker | По замеру, вторая обёртка над тем же фасадом (§4) |

## 2. Что осталось: ядро уже почти изоморфно, граница не проведена

**17 модулей — ноль Node-API:** `index/{search,symbols,types}`, `context/{budget,builder,profiles}`,
`decide/api-decision`, `generate/{builders,cross-check,form-intent,from-spec}`, `validate/{code,codes}`,
`utils/graph`, а также `tools/{search-docs,get-context,choose-api,validate-form,list-symbols,get-symbol-docs,check-behaviors}`.

Это не совпадение: [validate/code.ts](packages/reformer-mcp/src/validate/code.ts) намеренно разбирает
код регэкспами, а не TS-парсером — «тянуть его обратно значило бы отменить выигрыш Фазы 2».
Браузерная совместимость уже была проектным соображением под другим именем.

**Вся Node-зависимость — в 12 файлах, и почти вся это резолв путей:**

| Файл | Что именно |
| --- | --- |
| [index/loader.ts](packages/reformer-mcp/src/index/loader.ts) | `fs`, `path`, `url`, `__dirname`, `process.cwd()` ×2 |
| [utils/docs-parser.ts](packages/reformer-mcp/src/utils/docs-parser.ts) | то же + **`module.createRequire`** (единственное место в `src/`) |
| [tools/find-recipe.ts](packages/reformer-mcp/src/tools/find-recipe.ts) | `readdirSync` по `docs/llms` |
| [utils/prompt-template-loader.ts](packages/reformer-mcp/src/utils/prompt-template-loader.ts) | `node:fs` для 12 Handlebars-шаблонов |
| `utils/symbols-parser.ts` | `import * as ts from 'typescript'` — только фолбэк |
| `tools/report-issue.ts` | `writeFileSync` — **единственная запись на диск во всём сервере** |
| `utils/{project-detector,spec-analyzer}.ts`, `prompts/{plan-form,create-form}.ts`, `index.ts` | чтение проекта, `process.env`, stdio-бутстрап |

Два места, где граница проходит не гладко, и это надо назвать заранее:

- **`generate_form` едет в браузер целиком** — он не пишет на диск, а возвращает манифест файлов
  текстом (обоснование в его шапке: path traversal через `outputDir` от модели). Для билдера это
  прямо ложится на существующий `src/codegen/`.
- **`find_recipe` деградирует.** Первая стадия читает `docs/llms/*.md` через `readdirSync`; в браузере
  остаётся каскад в `search_docs` — он для этого и делался, но потеря должна быть в отчёте, а не
  обнаружиться потом.

### 3.1. `createKnowledge(sources)`

Фабрика вместо модульных синглтонов — решение принято сознательно, ценой правки тестов.
Что она даёт помимо чистоты: **два источника одновременно**. В Mode B билдер имеет папку проекта
через File System Access, а значит может прочитать `node_modules/@reformer/*/llms-index.json`
**пользователя** — то есть версии, реально у него установленные. Это ровно то свойство, ради
которого [loader.ts](packages/reformer-mcp/src/index/loader.ts) читает индекс у пакета, а не из
своего `dist`; глобальный синглтон его бы потерял.

Стоимость честно: сейчас `tools/*` зовут `getMergedIndex()` и `searchSections()` напрямую, а на
пакете 123 теста в 16 файлах. Правка механическая, но широкая — гейт на неё в §5, Э1.

### 3.2. Где живёт корпус в браузере

| Канал | Источник | Свежесть |
| --- | --- | --- |
| Pages / Mode A | артефакт, собранный при сборке билдера из `packages/*` | версия сборки билдера |
| Mode B (папка проекта открыта) | `node_modules/@reformer/*/{llms-index.json,llms.txt}` через FS Access | версии пользователя |

Объём: индекс 1 276 432 B + `llms.txt` 1 266 838 B = **2.54 MB raw**, порядка 600 KB gzip, лениво
отдельным чанком. Для сравнения в билдере уже есть `byok-*.js` 712 KB и App-чанк 1.81 MB.

**OPFS — только для второго случая.** Артефакт из бандла кэширует HTTP по immutable-хэшу бесплатно;
кэшировать между сессиями имеет смысл именно индекс, вычитанный из чужого проекта. Компоненты
готовы: [opfs.ts](packages/reformer-form-registry/src/storage/opfs.ts) + fallback на IndexedDB +
контракт, закреплённый `storage-contract.test.ts`.

## 4. Worker и MCP-протокол — почему не сейчас

Два независимых вопроса: worker про то, **где исполняется**, протокол — **как разговаривают**.

**Worker — по замеру.** Критерий RFC-0003: «оправдан бандлом, cold-джанком, отменяемостью — не
скоростью». Померить надо одно: `JSON.parse` 1.28 MB индекса. Порог наступит, когда в браузер поедет
`generate_form` (6 билдеров + кросс-проверка `C1..C9` — сотни мс). Worker — вторая обёртка над тем же
фасадом, не альтернативная архитектура. SharedArrayBuffer запрещён архитектурно (COOP/COEP не
настраиваются на Pages).

**MCP-протокол — нет, и это решение обратимо.** Асимметрия: фасад → протокол стоит ~50 строк поверх
тех же `xToolDefinition` + `xTool`; протокол → фасад стоит переделки всего, что на него оперлось.
Практическое: postMessage-транспорта в SDK нет (stdio / sse / streamableHTTP / websocket / inMemory) —
писать и тестировать самому, без продуктовой ценности. Единственный довод «протокол нужен, чтобы
eval мерил браузерную сборку» проверен и не работает: поверхность та же самая, стратегию `builder`
можно мерить на stdio-сервере с урезанным набором.

## 5. Ограничения, которые обязан соблюсти любой этап

1. **`TOOL_SURFACE_BUDGET = 7700`** ([types.ts](projects/reformer-builder/src/agent/core/types.ts)) —
   храповик, занятый на **7684 символа**: свободно шестнадцать (измерено Э0). Комментарий прямой:
   «его СНИЖАЮТ, поднимать нельзя». Единственное историческое повышение было оплачено измеренной
   экономией. Именно эта цифра, а не соображения вкуса, отсекает перенос набора инструментов MCP:
   самый дешёвый набор требует освободить 840 символов, самый качественный — 2858.
2. **`TOOL_DESCRIPTION_BUDGET = 500`.** `choose_api` имеет `description` = 824 — если он поедет,
   описание придётся сжать. Правка полезна и самому MCP: описание уходит в контекст при каждом
   подключении.
3. **`TOOL_TEXT_BUDGET = 1500`** и обрезка `clamp` в
   [registry.ts](projects/reformer-builder/src/agent/core/registry.ts). У `get_context` свой бюджет
   в токенах (`Math.ceil(chars/4)`) — два потолка надо согласовать, иначе `clamp` дорежет уже
   урезанное и собьёт пометку «обрезано».
4. **Юнит-тесты билдера в CI не запускаются** — `test.yml` гоняет только пакеты. Значит храповик
   поверхности сегодня охраняется лишь локально ([registry.test.ts:114](projects/reformer-builder/src/agent/core/registry.test.ts#L114)).
5. **Pages не ломать** — DoD F2 из RFC-0002 требует ещё и «размер начального чанка не вырос».
6. **P4 «No remote code»** (RFC-0001 §3.2): корпус — данные и часть сборки; загрузка кода по сети
   исключена.
7. **`sourcePath` в индексе** считается как `path.relative(process.cwd(), …)` — зависит от каталога
   запуска генератора. Для артефакта, который поедет в бандл, это надо сделать детерминированным.

### Э4 — цели 2 и 3 · ✅ выполнено 2026-08-23

**Главная находка: словарь и эмиттеры уже написаны.** Проектировать «декларативную модель
поведения» с нуля не нужно — она есть в MCP как `FormIntent`:

| нужно билдеру | есть в MCP |
| --- | --- |
| правила валидации | `ValidationRuleIntent { target, each?, when?, rules[], async? }` |
| реактивные связи | `BehaviorIntent { kind, target, sources[], expr? }` — 10 видов |
| условная видимость | `VisibilityIntent { selector, condition }` |
| генерация файлов | `buildValidationTs`, `buildBehaviorTs`, `buildRenderBehaviorTs`, `buildBundle` |
| проверка согласованности | `crossCheckBundle` (C1..C9), `findCycle` |

Формула хранится как `expr?: string` — «тело выражения на TS, вставляется как есть», а `sources`
перечислены отдельно. Это осознанный размен: произвольную формулу декларативно не выразить, но
граф зависимостей всё равно известен, и проверка циклов работает.

**Модель обязана быть сайдкаром — проверено.** В `JsonFormSchema` её положить некуда:
`additionalProperties: false` и на корне схемы, и внутри `meta` (там только `name` и
`description`). Расширять контракт `@reformer/renderer-json` план запрещает: набор операторов
закрыт в шести синхронизированных местах.

**Дублирование, которое придётся развести.** Эмиттеров два комплекта: `src/codegen/emit-*.ts` в
билдере и `core/generate/builders.ts` в MCP. Билдерские богаче по обвязке (prettier, импорты
кита, имена файлов), MCP-шные — по содержанию (у билдера `validation.ts` и `form.behavior.ts` —
заглушки с TODO, у MCP они собираются из правил).

**Упирается в тот же бюджет.** Свободно 14 символов. Любой новый write-инструмент над правилами
стоит 600–900 — то есть Э4 начинается не с модели, а с решения, откуда взять место. Замеченный
резерв: `get_form_outline` (263) и `get_form_node` (306) отвечают на близкие вопросы; слияние в
один с необязательным `ref` дало бы около 220 символов.

**Решения приняты (2026-08-23):** сайдкар в `TabState` с историей; гибрид эмиттеров — MCP для
правил, билдер для остального; бюджет поверхности поднимать только под замер.

**Сделано:**

- `model/rules.ts` — `FormRules { validation, behavior, visibility }`. Типы взяты из
  `FormIntent`, а не придуманы заново: второй словарь для того же самого разошёлся бы с первым
  на первой же правке, и разошёлся бы молча. Ни полей, ни раскладки там нет — это уже в схеме.
- Правила вошли в `TabState` и в `HistorySnapshot`: правка правил откатывается тем же Ctrl+Z,
  что и правка схемы. Вынести их за историю (как `mock`) означало бы, что испорченное агентом
  правило вернуть нечем.
- `codegen/emit-rules.ts` — `validation.ts` и `form.behavior.ts` собираются билдерами MCP, когда
  правила есть; пустые правила дают прежние заглушки с примерами. Одна несостыковка адаптируется

  Проверки на вхождение подстрок не отличают валидный код от мусора — этот тест отличает.

1. **Баг MCP-билдера:** `ValidationRuleIntent.rules` документирован как «`required`, `email`,

**Инструмент `set_form_rules` (1259 символов) и повышение потолка 7686 → 8946.** Отчёт —
[builder-rules.md](../mcp-eval/builder-rules.md). Повышение оплачено не экономией шагов, а тем,
что происходит БЕЗ инструмента, и это главный результат замера:

| | с инструментом | без него |
| --- | --- | --- |
| «сделай email обязательным» | `set_form_rules` ✅ | `set_node_prop`, ход завершён успешно, **валидации нет** |

Первая строка и есть довод. Агент ставит проп на узел, отчитывается об успехе, форма выглядит
изменённой — а `required` в ReFormer живёт в `validation.ts`, а не в свойствах компонента.
Ложное «готово» обнаружится у пользователя при сабмите формы, которая обязана была не пройти.
Явный отказ обошёлся бы дешевле. Выбор инструмента верен 4/4, включая нецелевые задачи — плата
за поверхность не растеклась на соседние ходы.

**Условной видимости в инструменте нет — намеренно.** Правило видимости адресует узел по
`selector`, а селекторы проставляются только при экспорте и только секциям, массивам и кнопкам;
обычное поле его не получает, и задать селектор не умеет ни один инструмент агента. Принятое
правило видимости было бы no-op — ровно тот случай, который C6 в `crossCheckBundle` называет
худшим: ни ошибки, ни эффекта. Убрано вместе с 272 символами поверхности; в `FormRules` поле
осталось и вернётся, когда селектором можно будет управлять.

**Гейт строже, чем у правок раскладки, и это осознанно.** Неверная раскладка видна на канвасе
сразу; неверное правило выглядит правдоподобно. Проверяются три вещи, каждая уже всплывала:
пути модели существуют (правило на несуществующее поле не сработает никогда), нет циклов
(`a` из `b`, `b` из `a`), поле не пишется дважды (два `computeFrom` на один target — не
«последнее выигрывает», а гонка). Подсказки при опечатке берутся из `similarNames` — того же
механизма, что у реестра, а не второй самодельной похожести.

**Цепочка замкнута до файлов пользователя.** Правила идут: инструмент → `TabState` → история
(Ctrl+Z откатывает правило так же, как правку схемы) → черновик в IndexedDB → `buildExampleFiles`
→ экспорт в папку. Каждое звено закрыто тестом; сквозной проверяет, что в `validation.ts`
оказывается правило, а не мок. Разрыв был реальным: `deliver.ts` собирал файлы без правил, то
есть агент отчитывался о валидации, а пользователю уезжала заглушка.

Поле `rules` в записи черновика необязательное: записи, сделанные до его появления, читаются
как форма без правил, а не как повреждённый черновик — это отдельный тест.

#### Цель 3 — разведка проведена, блокер снят

**Мост `FormIntent` → `JsonFormSchema` в MCP есть** — `buildLayoutJson(intent)`
([builders.ts:321](packages/reformer-mcp/src/core/generate/builders.ts#L321)). Он отдаёт
`{ version: '1.0', root }` — ту же форму, что `JsonFormSchema`, и тот же операторный DSL. Ни
Node, ни stdio для стыка не нужны: билдер уже импортирует ядро MCP бандлом, а
`validateFormSchema` уже есть в браузере. Словарь правил тоже общий — `FormRules` билдера
собран из тех же типов `FormIntent`, так что правила из intent приземляются один в один.

**Но мост производил невалидную схему для любой формы с массивом — исправлено.** Узел массива
собирался с шаблоном прямо в `item` и со СПИСКОМ строк в `initialValue`, тогда как контракт
требует `item: { $template }` и литерал ОДНОГО пустого элемента
([json-schema.ts:69,81](packages/reformer-renderer-json/src/types/json-schema.ts#L69)). Прогон
через настоящий `validateFormSchema` давал `valid:false` и четыре ошибки, а `generate_form`
печатал «✅ Кросс-проверка пройдена»: `crossCheckBundle` структуру узлов renderer-json не знает,
а C8 прежней редакции ТРЕБОВАЛА массив — то есть закрепляла формат, который пакет отвергает.

Совпадение имён — `ArrayIntent.initialValue` (начальные строки) и `JsonArrayNode.initialValue`
(литерал пустого элемента) — и есть причина: одинаково называются, значат разное. Образец теперь
берётся из первой строки, а если строк нет — синтезируется из `itemFields` по типам (`''`,
`null`, `false`), потому что кнопке «Добавить» пустой элемент нужен всегда.

Дефект дожил потому, что **в MCP не было ни одного теста, прогоняющего собственный вывод через
валидатор renderer-json**, а локальный `interface JsonNode` в `builders.ts` с типами пакета не
связан — компилятор дрейф не поймает. Такой тест добавлен (3 кейса) и проверен на регрессию:
поломка `$template` роняет 5 тестов.

**Ещё одно расхождение, которое решается на мосту, а не правкой MCP.** MCP ставит массивам
`$component(FormArray)` — имя из ui-kit, и для генерации проекта это верно. Билдер же адресует
array-узлы ключом реестра `List` (`preview-runtime/known-names.ts`), и `FormArray` — единственное
из 14 имён MCP, которого нет среди 177 известных билдеру. Приводить имя должен импортёр intent'а
в билдере: навязывать одному потребителю словарь другого — значит сломать второго.

**Сквозной путь построен и проверен вживую.** «Файл → Форма по спеке…» → вставить текст или
выбрать `.md`/`.txt` → вкладка с формой и правилами. Проверено в браузере: из спеки на четыре
поля получается вкладка, которая рендерится настоящими контролами (Input, InputMask, Select),
ноль ошибок в консоли — снимки в `screenshots/spec-to-form/`.

- `model/from-intent.ts` — мост: `buildLayoutJson` из MCP, перевод словаря компонентов, правила
  один в один. Второго генератора layout здесь нет намеренно — это та же ошибка, от которой уже
  отказались в `codegen/emit-rules.ts`.
- `app/create-from-spec.ts` — оркестрация и гейт: схема проходит `validateSchema` в СТРОГОМ
  режиме без baseline (форма родилась из текста, доверять её именам не на что), пустой разбор
  вкладку не создаёт, предупреждения разбора доходят до пользователя.
- `openFormWithRules` — вкладка рождается со схемой и правилами разом. Отдельный вход, а не
  `openTab` + `replaceSchema`: второй ходит по АКТИВНОЙ вкладке, и между двумя вызовами правила
  могли уехать в чужую форму.
- Поверхность инструментов агента не тронута: приземление — прямое действие редактора.

### 3.1. `createKnowledge(sources)`

Фабрика вместо модульных синглтонов — решение принято сознательно, ценой правки тестов.
Что она даёт помимо чистоты: **два источника одновременно**. В Mode B билдер имеет папку проекта
через File System Access, а значит может прочитать `node_modules/@reformer/*/llms-index.json`
**пользователя** — то есть версии, реально у него установленные. Это ровно то свойство, ради
которого [loader.ts](packages/reformer-mcp/src/index/loader.ts) читает индекс у пакета, а не из
своего `dist`; глобальный синглтон его бы потерял.

Стоимость честно: сейчас `tools/*` зовут `getMergedIndex()` и `searchSections()` напрямую, а на
пакете 123 теста в 16 файлах. Правка механическая, но широкая — гейт на неё в §5, Э1.

### 3.2. Где живёт корпус в браузере

| Канал | Источник | Свежесть |
| --- | --- | --- |
| Pages / Mode A | артефакт, собранный при сборке билдера из `packages/*` | версия сборки билдера |
| Mode B (папка проекта открыта) | `node_modules/@reformer/*/{llms-index.json,llms.txt}` через FS Access | версии пользователя |

Объём: индекс 1 276 432 B + `llms.txt` 1 266 838 B = **2.54 MB raw**, порядка 600 KB gzip, лениво
отдельным чанком. Для сравнения в билдере уже есть `byok-*.js` 712 KB и App-чанк 1.81 MB.

**OPFS — только для второго случая.** Артефакт из бандла кэширует HTTP по immutable-хэшу бесплатно;
кэшировать между сессиями имеет смысл именно индекс, вычитанный из чужого проекта. Компоненты
готовы: [opfs.ts](packages/reformer-form-registry/src/storage/opfs.ts) + fallback на IndexedDB +
контракт, закреплённый `storage-contract.test.ts`.

## 4. Worker и MCP-протокол — почему не сейчас

Два независимых вопроса: worker про то, **где исполняется**, протокол — **как разговаривают**.

**Worker — по замеру.** Критерий RFC-0003: «оправдан бандлом, cold-джанком, отменяемостью — не
скоростью». Померить надо одно: `JSON.parse` 1.28 MB индекса. Порог наступит, когда в браузер поедет
`generate_form` (6 билдеров + кросс-проверка `C1..C9` — сотни мс). Worker — вторая обёртка над тем же
фасадом, не альтернативная архитектура. SharedArrayBuffer запрещён архитектурно (COOP/COEP не
настраиваются на Pages).

**MCP-протокол — нет, и это решение обратимо.** Асимметрия: фасад → протокол стоит ~50 строк поверх
тех же `xToolDefinition` + `xTool`; протокол → фасад стоит переделки всего, что на него оперлось.
Практическое: postMessage-транспорта в SDK нет (stdio / sse / streamableHTTP / websocket / inMemory) —
писать и тестировать самому, без продуктовой ценности. Единственный довод «протокол нужен, чтобы
eval мерил браузерную сборку» проверен и не работает: поверхность та же самая, стратегию `builder`
можно мерить на stdio-сервере с урезанным набором.

## 5. Ограничения, которые обязан соблюсти любой этап

1. **`TOOL_SURFACE_BUDGET = 7700`** ([types.ts](projects/reformer-builder/src/agent/core/types.ts)) —
   храповик, занятый на **7684 символа**: свободно шестнадцать (измерено Э0). Комментарий прямой:
   «его СНИЖАЮТ, поднимать нельзя». Единственное историческое повышение было оплачено измеренной
   экономией. Именно эта цифра, а не соображения вкуса, отсекает перенос набора инструментов MCP:
   самый дешёвый набор требует освободить 840 символов, самый качественный — 2858.
2. **`TOOL_DESCRIPTION_BUDGET = 500`.** `choose_api` имеет `description` = 824 — если он поедет,
   описание придётся сжать. Правка полезна и самому MCP: описание уходит в контекст при каждом
   подключении.
3. **`TOOL_TEXT_BUDGET = 1500`** и обрезка `clamp` в
   [registry.ts](projects/reformer-builder/src/agent/core/registry.ts). У `get_context` свой бюджет
   в токенах (`Math.ceil(chars/4)`) — два потолка надо согласовать, иначе `clamp` дорежет уже
   урезанное и собьёт пометку «обрезано».
4. **Юнит-тесты билдера в CI не запускаются** — `test.yml` гоняет только пакеты. Значит храповик
   поверхности сегодня охраняется лишь локально ([registry.test.ts:114](projects/reformer-builder/src/agent/core/registry.test.ts#L114)).
5. **Pages не ломать** — DoD F2 из RFC-0002 требует ещё и «размер начального чанка не вырос».
6. **P4 «No remote code»** (RFC-0001 §3.2): корпус — данные и часть сборки; загрузка кода по сети
   исключена.
7. **`sourcePath` в индексе** считается как `path.relative(process.cwd(), …)` — зависит от каталога
   запуска генератора. Для артефакта, который поедет в бандл, это надо сделать детерминированным.

### Э4 — цели 2 и 3 · ✅ выполнено 2026-08-23

**Главная находка: словарь и эмиттеры уже написаны.** Проектировать «декларативную модель
поведения» с нуля не нужно — она есть в MCP как `FormIntent`:

| нужно билдеру | есть в MCP |
| --- | --- |
| правила валидации | `ValidationRuleIntent { target, each?, when?, rules[], async? }` |
| реактивные связи | `BehaviorIntent { kind, target, sources[], expr? }` — 10 видов |
| условная видимость | `VisibilityIntent { selector, condition }` |
| генерация файлов | `buildValidationTs`, `buildBehaviorTs`, `buildRenderBehaviorTs`, `buildBundle` |
| проверка согласованности | `crossCheckBundle` (C1..C9), `findCycle` |

Формула хранится как `expr?: string` — «тело выражения на TS, вставляется как есть», а `sources`
перечислены отдельно. Это осознанный размен: произвольную формулу декларативно не выразить, но
граф зависимостей всё равно известен, и проверка циклов работает.

**Модель обязана быть сайдкаром — проверено.** В `JsonFormSchema` её положить некуда:
`additionalProperties: false` и на корне схемы, и внутри `meta` (там только `name` и
`description`). Расширять контракт `@reformer/renderer-json` план запрещает: набор операторов
закрыт в шести синхронизированных местах.

**Дублирование, которое придётся развести.** Эмиттеров два комплекта: `src/codegen/emit-*.ts` в
билдере и `core/generate/builders.ts` в MCP. Билдерские богаче по обвязке (prettier, импорты
кита, имена файлов), MCP-шные — по содержанию (у билдера `validation.ts` и `form.behavior.ts` —
заглушки с TODO, у MCP они собираются из правил).

**Упирается в тот же бюджет.** Свободно 14 символов. Любой новый write-инструмент над правилами
стоит 600–900 — то есть Э4 начинается не с модели, а с решения, откуда взять место. Замеченный
резерв: `get_form_outline` (263) и `get_form_node` (306) отвечают на близкие вопросы; слияние в
один с необязательным `ref` дало бы около 220 символов.

**Решения приняты (2026-08-23):** сайдкар в `TabState` с историей; гибрид эмиттеров — MCP для
правил, билдер для остального; бюджет поверхности поднимать только под замер.

**Сделано:**

- `model/rules.ts` — `FormRules { validation, behavior, visibility }`. Типы взяты из
  `FormIntent`, а не придуманы заново: второй словарь для того же самого разошёлся бы с первым
  на первой же правке, и разошёлся бы молча. Ни полей, ни раскладки там нет — это уже в схеме.
- Правила вошли в `TabState` и в `HistorySnapshot`: правка правил откатывается тем же Ctrl+Z,
  что и правка схемы. Вынести их за историю (как `mock`) означало бы, что испорченное агентом
  правило вернуть нечем.
- `codegen/emit-rules.ts` — `validation.ts` и `form.behavior.ts` собираются билдерами MCP, когда
  правила есть; пустые правила дают прежние заглушки с примерами. Одна несостыковка адаптируется
  явно: MCP кладёт тип в `model.ts`, билдер — в `types.ts`.
- `emit-rules.test.ts` прогоняет результат настоящим `tsc` с настоящими типами `@reformer/*`.
  Проверки на вхождение подстрок не отличают валидный код от мусора — этот тест отличает.

**Два дефекта, найденных этим тестом:**

1. **Баг MCP-билдера:** `ValidationRuleIntent.rules` документирован как «`required`, `email`,
   `minLength(2)`» — то есть допускает запись без скобок, — а рендер вставлял имя как есть, и
   `validate(…, [required])` не компилировался: `@reformer/core/validators` экспортирует ФАБРИКИ.
   Путь «спека → бандл» этого не показывал: анализатор спек всегда пишет со скобками. Показал
   агент, для которого `required` — самая естественная запись. Исправлено нормализацией в
   `builders.ts`.
2. **Пример в заглушке `form.behavior.ts`, которую билдер отдаёт пользователю, не
   компилировался.** Четыре ошибки сразу: аргумент у `compute` (его `read` — функция без
   параметров), `.value` на `model.country` (в модели `model.field` — уже значение, сигнал —
   `model.$.field`), стрелка вместо `{ when }` третьим аргументом `copyFrom`, и сам `model`,
   которого не было в области видимости: колбэк объявлен как `() => {}`, а операторы не
   импортированы вовсе.

   Дожил дефект потому, что закомментированный код не проверяется ничем, а тест на компиляцию
   подсовывал `tsc` СВОЮ строку-заглушку вместо настоящего выхода эмиттера. Исправлено: пример
   оформлен блоком-заменой (тело обязано остаться `() => {}` — деструктуризация `({ model })`
   при пустом теле даёт TS6133 под `noUnusedParameters`), а тест вырезает блок по границам,
   раскомментирует, подставляет вместо объявления — и компилирует настоящим `tsc`.

   **Отдельно: заявленного здесь ранее «расхождения JSDoc и сигнатуры `enableWhen`» не
   существует — это была моя ошибка чтения.** Наружу из `@reformer/core/behaviors` экспортируется
   версия из [operators.ts:155](packages/reformer/src/form/behaviors/operators.ts#L155) с
   `target: EnableTarget | EnableTarget[]`, то есть массив целей, группа и скаляр равно
   допустимы. Одноимённая функция в [node.ts:48](packages/reformer/src/form/behaviors/node.ts#L48)
   — низкоуровневая и в бочку `behaviors/index.ts` не входит; я прочитал её и принял за
   публичную. Примеры с массивом в JSDoc и в `docs/llms/*.md` верны, править их не нужно;
   проверено компиляцией против реальных типов.

**Инструмент `set_form_rules` (1259 символов) и повышение потолка 7686 → 8946.** Отчёт —
[builder-rules.md](../mcp-eval/builder-rules.md). Повышение оплачено не экономией шагов, а тем,
что происходит БЕЗ инструмента, и это главный результат замера:

| | с инструментом | без него |
| --- | --- | --- |
| «сделай email обязательным» | `set_form_rules` ✅ | `set_node_prop`, ход завершён успешно, **валидации нет** |
| «total = price × quantity» | `set_form_rules` ✅ | `ask_reformer`: справка прочитана, применить нечем |
| две задачи без правил | прежние инструменты, прежние шаги ✅ | — |

Первая строка и есть довод. Агент ставит проп на узел, отчитывается об успехе, форма выглядит
изменённой — а `required` в ReFormer живёт в `validation.ts`, а не в свойствах компонента.
Ложное «готово» обнаружится у пользователя при сабмите формы, которая обязана была не пройти.
Явный отказ обошёлся бы дешевле. Выбор инструмента верен 4/4, включая нецелевые задачи — плата
за поверхность не растеклась на соседние ходы.

**Условной видимости в инструменте нет — намеренно.** Правило видимости адресует узел по
`selector`, а селекторы проставляются только при экспорте и только секциям, массивам и кнопкам;
обычное поле его не получает, и задать селектор не умеет ни один инструмент агента. Принятое
правило видимости было бы no-op — ровно тот случай, который C6 в `crossCheckBundle` называет
худшим: ни ошибки, ни эффекта. Убрано вместе с 272 символами поверхности; в `FormRules` поле
осталось и вернётся, когда селектором можно будет управлять.

**Гейт строже, чем у правок раскладки, и это осознанно.** Неверная раскладка видна на канвасе
сразу; неверное правило выглядит правдоподобно. Проверяются три вещи, каждая уже всплывала:
пути модели существуют (правило на несуществующее поле не сработает никогда), нет циклов
(`a` из `b`, `b` из `a`), поле не пишется дважды (два `computeFrom` на один target — не
«последнее выигрывает», а гонка). Подсказки при опечатке берутся из `similarNames` — того же
механизма, что у реестра, а не второй самодельной похожести.

**Цепочка замкнута до файлов пользователя.** Правила идут: инструмент → `TabState` → история
(Ctrl+Z откатывает правило так же, как правку схемы) → черновик в IndexedDB → `buildExampleFiles`
→ экспорт в папку. Каждое звено закрыто тестом; сквозной проверяет, что в `validation.ts`
оказывается правило, а не мок. Разрыв был реальным: `deliver.ts` собирал файлы без правил, то
есть агент отчитывался о валидации, а пользователю уезжала заглушка.

Поле `rules` в записи черновика необязательное: записи, сделанные до его появления, читаются
как форма без правил, а не как повреждённый черновик — это отдельный тест.

#### Цель 3 — разведка проведена, блокер снят

**Мост `FormIntent` → `JsonFormSchema` в MCP есть** — `buildLayoutJson(intent)`
([builders.ts:321](packages/reformer-mcp/src/core/generate/builders.ts#L321)). Он отдаёт
`{ version: '1.0', root }` — ту же форму, что `JsonFormSchema`, и тот же операторный DSL. Ни
Node, ни stdio для стыка не нужны: билдер уже импортирует ядро MCP бандлом, а
`validateFormSchema` уже есть в браузере. Словарь правил тоже общий — `FormRules` билдера
собран из тех же типов `FormIntent`, так что правила из intent приземляются один в один.

**Но мост производил невалидную схему для любой формы с массивом — исправлено.** Узел массива
собирался с шаблоном прямо в `item` и со СПИСКОМ строк в `initialValue`, тогда как контракт
требует `item: { $template }` и литерал ОДНОГО пустого элемента
([json-schema.ts:69,81](packages/reformer-renderer-json/src/types/json-schema.ts#L69)). Прогон
через настоящий `validateFormSchema` давал `valid:false` и четыре ошибки, а `generate_form`
печатал «✅ Кросс-проверка пройдена»: `crossCheckBundle` структуру узлов renderer-json не знает,
а C8 прежней редакции ТРЕБОВАЛА массив — то есть закрепляла формат, который пакет отвергает.

Совпадение имён — `ArrayIntent.initialValue` (начальные строки) и `JsonArrayNode.initialValue`
(литерал пустого элемента) — и есть причина: одинаково называются, значат разное. Образец теперь
берётся из первой строки, а если строк нет — синтезируется из `itemFields` по типам (`''`,
`null`, `false`), потому что кнопке «Добавить» пустой элемент нужен всегда.

Дефект дожил потому, что **в MCP не было ни одного теста, прогоняющего собственный вывод через
валидатор renderer-json**, а локальный `interface JsonNode` в `builders.ts` с типами пакета не
связан — компилятор дрейф не поймает. Такой тест добавлен (3 кейса) и проверен на регрессию:
поломка `$template` роняет 5 тестов.

**Ещё одно расхождение, которое решается на мосту, а не правкой MCP.** MCP ставит массивам
`$component(FormArray)` — имя из ui-kit, и для генерации проекта это верно. Билдер же адресует
array-узлы ключом реестра `List` (`preview-runtime/known-names.ts`), и `FormArray` — единственное
из 14 имён MCP, которого нет среди 177 известных билдеру. Приводить имя должен импортёр intent'а
в билдере: навязывать одному потребителю словарь другого — значит сломать второго.

**Сквозной путь построен и проверен вживую.** «Файл → Форма по спеке…» → вставить текст или
выбрать `.md`/`.txt` → вкладка с формой и правилами. Проверено в браузере: из спеки на четыре
поля получается вкладка, которая рендерится настоящими контролами (Input, InputMask, Select),
ноль ошибок в консоли — снимки в `screenshots/spec-to-form/`.

- `model/from-intent.ts` — мост: `buildLayoutJson` из MCP, перевод словаря компонентов, правила
  один в один. Второго генератора layout здесь нет намеренно — это та же ошибка, от которой уже
  отказались в `codegen/emit-rules.ts`.
- `app/create-from-spec.ts` — оркестрация и гейт: схема проходит `validateSchema` в СТРОГОМ
  режиме без baseline (форма родилась из текста, доверять её именам не на что), пустой разбор
  вкладку не создаёт, предупреждения разбора доходят до пользователя.
- `openFormWithRules` — вкладка рождается со схемой и правилами разом. Отдельный вход, а не
  `openTab` + `replaceSchema`: второй ходит по АКТИВНОЙ вкладке, и между двумя вызовами правила
  могли уехать в чужую форму.
- Поверхность инструментов агента не тронута: приземление — прямое действие редактора.

 —
без точки. В спеках проекта составными путями записаны целые разделы формы
(`personalData.lastName`, `passportData.series`): такая строка не проходила разбор по шапке,
позиционная ветка camelCase-ячейки в ней тоже не находила, и строка исчезала без предупреждения.
На кредитной спеке так пропадало 17 полей — паспорт и персональные данные целиком. Показательно,
что `extractFieldKeyFromTrBlock`, питающий списки условных и вычисляемых полей, точки допускал
всегда: эти списки ссылались на поля, которых в `fields` не существовало.

**Запрет был согласован с ограничением генератора, а не случаен.** `buildModelTs` рендерил поля
плоско, и составной путь давал `personalData.lastName: string;` — не TypeScript вовсе. Поэтому
чинить пришлось с генератора: модель теперь строится деревом, вложенные группы разворачиваются
в объекты, `initialFormModel` повторяет ту же форму. Разметка составные пути принимала и раньше —
проверено валидатором `renderer-json`.

**Потолок разбора резал половину формы.** `slice(0, 60)` — при том, что страховая спека даёт
121 поле, кредитная 68. Обрезка была молчаливой, то есть форма выглядела разобранной целиком.
Потолок поднят до 200 (за ним начинается уже не форма, а ошибка разбора), а сам факт обрезки
теперь виден в предупреждениях.

**Результат на настоящих спеках проекта** — обе проходят строгий гейт билдера:

| спека | было | стало | правил валидации |
| --- | ---: | ---: | ---: |
| кредитная | 51 поле, составных 0 | **68**, составных 17 | 47 |
| страховая | 45 полей, составных 0 | **121**, составных 77 | 55 |

Закрыто тестами на реальных спеках с обеих сторон — в MCP (разбор) и в билдере (сквозной путь
до вкладки); проверено, что откат шаблона ключа их роняет.

**Шаги отложены сознательно, и вот почему.** Приёмник `LayoutNode kind:'step'` есть, и соблазн
был просто связать поля с шагами. Но разведка потребительского контракта показала: мастер читает
шаги из `componentProps.steps[]` wizard-ноды, а генератор кладёт их в `children` — то, что
документация `renderer-json` прямо называет анти-паттерном («top-level children wizard-компонент
не читает как шаги»). Схема при этом валидна и cross-check её пропускает, а мастера у
пользователя не появляется. То есть наивная реализация шагов дала бы **молчаливо неработающую
форму** — ровно тот класс дефекта, который мы весь день выкорчёвывали. Полная работа требует
узла-визарда в `LayoutNode`, рендера в `componentProps.steps[]` и генерации шима реестра
(в живых примерах это ~25 строк плюс инъекция `form`+`validation` через `onInit/patchProps`).

**Что осталось:**

1. **Многошаговость теряется.** `analysis.steps` и `fieldsPerStep` считают только КОЛИЧЕСТВО полей
   на шаг, а `SpecField` не несёт номера шага — связать поле с шагом сегодня нечем, поэтому
   любая спека даёт один плоский `Box`. Чтобы построить `layoutRoot` по шагам, `extractFields`
   должен разбирать текст посекционно и проставлять `step`.
2. **Массивы не извлекаются.** `extractArrays` — не разборщик, а список имён из ОДНОЙ конкретной
   постановки (`hasCoBorrower`, `coBorrowers`, …), причём без полей элемента. Построить
   `ArrayIntent` из этого нельзя: `itemFields` взять неоткуда.
3. **Надёжен только HTML-формат спек.** Проверено: markdown-таблица с полным набором колонок
   (`№ | Раздел | Ключ в форме | …`) даёт НОЛЬ полей, а укороченная (`Ключ | Название | Тип |
   Валидация`) — четыре поля, но ноль правил валидации. То есть `docs/specs/*.md` разбираются,
   а произвольная markdown-таблица — частично и молча.
4. **`.docx`/`.pdf`** — вне среза: ни `mammoth`, ни `pdfjs-dist` в репозитории нет, а pdfjs тянет
   воркер ~1.4 МБ при отсутствующей инфраструктуре воркеров.

Первые три — работа по анализатору спек в MCP, и она отдельная: цена в том, что `extractFields`
придётся переписать на посекционный разбор.

**Попутно найден и исправлен дефект в собственной вчерашней работе.** Ход агента начинался с
ПУСТОГО набора правил: `runAgentTurn` звал `createChangeSet(opts.base)` без `baseRules`, а
`run.ts` не передавал `tab.rules`. Поскольку `set_form_rules` по умолчанию работает в режиме
merge, второй запрос пользователя добавлял правило к пустоте — и применение стирало всё, что
поставил первый. Юнит-тесты инструмента этого не видели (подавали `ctx.rules` руками), живой
прогон — тоже (каждый кейс начинался с чистой формы). Исправлено, закрыто тремя тестами через
настоящий `runAgentTurn`; проверено, что откат починки их роняет.

**Найдено попутно:** тесты билдера, запускающие настоящий `tsc`, дают флаки при полном
параллельном прогоне — падает целиком произвольный сосед (2 раза из 6 прогонов, каждый раз
другой файл, изолированно все проходят). Тесты билдера с 2026-08-23 в CI, поэтому заведено
отдельной задачей bd.

Порядок обязателен.

1. **Спроектировать декларативную модель поведения.** Сегодня
   [collect.ts](projects/reformer-builder/src/codegen/collect.ts) собирает только структуру и
   `requiredPaths`, а `emit-validation` / `emit-form-behavior` эмитят заглушки с TODO. Модели
   поведения в состоянии редактора не существует. Правка текста файлов через FS Access
   отвергается: она вне undo/redo и не работает на Pages.
2. Перевести эмиттеры с «эмитим мок» на «эмитим из модели».
3. Write-инструменты над моделью + `validate_form` как гейт: коды `RF004`/`RF005`/`RF006` ловят ровно
   тот класс ошибок, который `tsc` пропускает, а `fix: { tool, arguments }` даёт агенту готовый
   следующий вызов.
4. **Цель 3** сверху: `plan_form` → `FormIntent` → `generate_form` → манифест файлов → существующий
   `src/codegen/`. Спека приходит через drag&drop (`spec-source`), `.docx`/`.pdf` — ленивыми
   парсерами, как спроектировано в RFC-0002 F4. Честная оговорка `plan_form` про неизвлекаемые
   формулы остаётся в силе.

## 8. Что не делать

1. **Не переносить все 10 инструментов.** Поверхность MCP — 8854 символа при бюджете билдера 7700,
   уже занятом. Набор выбирает Э0 замером.
2. **Не поднимать `TOOL_SURFACE_BUDGET` без замера.** Сначала освобождать сжатием. Повышение
   допустимо только с отчётом, показывающим, ЧТО именно покупается, — как в
   [builder-rules.md](../mcp-eval/builder-rules.md), где ценой 1259 символов убрана молчаливая
   неудача (агент отчитывается о валидации, которой нет).
3. **Не поднимать MCP-протокол внутри вкладки** (§4). Дверь оставить открытой, но не входить.
4. **Не заводить второй генератор индекса.** `index-builder.js` — единственный; браузерный артефакт
   собирается **из его выхода**, а не параллельным парсером.
5. **Не тащить `typescript`.** Фолбэк `symbols-parser` в браузере не резолвится и корректно даёт
   пустой массив — это уже обработано try/catch.
6. **Не использовать OPFS для артефакта из бандла.** Только для индекса, вычитанного из проекта.
7. **Не начинать с целей 2–3.** Пока нет модели поведения (Э4.1), знания об API применить нечем.
