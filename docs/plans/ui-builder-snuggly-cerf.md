# Редактирование схем валидации, поведения формы и поведения UI в ReFormer Builder

## Context

Билдер собирает раскладку формы (`JsonFormSchema`) визуально, а всю логику формы — валидацию,
реактивные связи и поведение render-слоя — отдаёт кодом в трёх файлах: `validation.ts`,
`form.behavior.ts`, `renderer.behavior.ts`. Сегодня эти три файла в билдере **не редактируются как
часть формы**: их можно открыть текстом, если форма пришла из проекта, но у формы, собранной в
билдере, их не существует вовсе, а сайдкар с правилами, из которого они генерируются, невидим ни в
одной панели.

Практическое следствие, которое и надо устранить: ассистент задаёт правила, отчитывается «готово»,
форма выглядит изменённой — а до кода изменение не доезжает. Причём тремя независимыми способами
сразу (Р2, Р4, Р6 ниже), каждый из которых молчалив.

Требуется: редактировать все три схемы в билдере и дать ассистенту возможность их править.

## 1. Что уже есть — задача не с нуля

Существенная часть контура построена. Это меняет смысл задачи: не «сделать редактирование», а
«соединить готовые куски и закрыть разрывы между ними».

**Сайдкар правил.** [`src/model/rules.ts`](../../projects/reformer-builder/src/model/rules.ts) —
`FormRules = { validation, behavior, visibility }`, словарь целиком заимствован у `@reformer/mcp`
(`ValidationRuleIntent`, `BehaviorIntent`, `VisibilityIntent`), чтобы не завести второй словарь того
же самого. Правила живут во вкладке, входят в историю Ctrl+Z (`HistorySnapshot.rules`), переживают
перезагрузку в черновике IndexedDB и уезжают в экспорт.

**Генерация.** [`codegen/emit-rules.ts`](../../projects/reformer-builder/src/codegen/emit-rules.ts)
собирает `validation.ts` и `form.behavior.ts` билдерами MCP (`buildValidationTs`, `buildBehaviorTs`) —
второго комплекта эмиттеров для них нет намеренно. А `renderer.behavior.ts` — наоборот, целиком
билдерский (`emit-behavior.ts`), и правил он сегодня не принимает вовсе (Р2).

**Живое превью уже исполняет эти файлы.** [`preview-runtime/live/`](../../projects/reformer-builder/src/preview-runtime/live/)
транспилирует (`typescript.transpileModule`) и линкует `model.ts`, `validation.ts`,
`form.behavior.ts`, `renderer.behavior.ts`, `registry.ts` на собственных инстансах `@reformer/*`,
причём [`sibling-sources.ts`](../../projects/reformer-builder/src/preview-runtime/live/sibling-sources.ts)
берёт текст из **несохранённой вкладки Monaco** раньше, чем с диска, а
[`useLiveForm.ts`](../../projects/reformer-builder/src/canvas/useLiveForm.ts) пересобирает форму
через 400 мс после нажатия клавиши. Цикл «правлю правило — вижу, как оно отрабатывает» построен —
но доступен только форме, открытой из проекта.

**Ассистент умеет задавать правила.**
[`set-form-rules.ts`](../../projects/reformer-builder/src/agent/core/tools/set-form-rules.ts) —
единственный write-инструмент, который правит не схему. Гейт строже схемного: пути модели,
отсутствие циклов (`findCycle`), запрет двух поведений на одно поле.

Проверено чтением кода.

## 3. Решения

Зафиксированы с пользователем:

| Развилка | Решение |
| --- | --- |
| Вид редактора | **Только код-вкладки `.ts`** в Monaco. Структурных редакторов правил не делаем |
| Место в UI | **Нижняя панель**, три вкладки сразу после «Модель»: `JSON · Модель · validation · form.behavior · renderer.behavior · Registry · Форма` |
| Охват поведения UI | **Видимость + события + пропсы** (`hideWhen`, `onComponentEvent`, `patchProps`) |
| Инструменты ИИ | **Оба, с приоритетом правил**: декларатив через инструмент, сырой TS — полями внутри правила; свободной записи файла целиком у ассистента нет |
| Бюджет поверхности | **Поднять осознанно, с замером** — третий раз за историю храповика, по обряду `docs/mcp-eval/builder-rules.md` |
| Режим формы | **Оба**, `FormRules` — источник истины |
| Рабочая копия | **Каталог в OPFS на каждую вкладку** с полным набором файлов модуля; правятся и показываются именно они. Диск — место сохранения, не рабочее место |
| Зависимости | **`@reformer/mcp` ничего не знает о билдере.** Направление одностороннее: билдер потребляет MCP, обратных правок нет |

### 3.1. Почему нижняя панель — правильное место

Решение с большими последствиями, и хорошими. Три схемы становятся **принадлежностью формы**, а не
самостоятельными файлами в общем таб-баре:

- не нужны виртуальные вкладки в `TabBar`. Расширение `TabSource.kind` обошлось бы дорого и опасно:
  шесть ветвлений по `source.kind` и пятнадцать по `tab.kind === 'code'` — все через `===`, а не
  через исчерпывающий `switch`, то есть **компилятор не подсказал бы ни одного** из них;
- у трёх схем общая с формой рабочая копия (§3.2), общий dirty и общее закрытие — машинерию
  вкладок-документов дублировать не приходится;
- рядом — «Модель» (засев и живые значения) и «Форма» (валидность полей, лог, сборка), то есть
  ровно тот контекст, в котором правило проверяют глазами;
- панель уже держит двусторонний редактор Monaco для raw-JSON
  ([`SchemaCodeEditor`](../../projects/reformer-builder/src/canvas/SchemaCodeEditor.tsx)), а
  [`MockDataEditor`](../../projects/reformer-builder/src/canvas/MockDataEditor.tsx) — готовый
  образец «секция с генерируемым значением по умолчанию, правкой поверх и кнопкой сброса».

**Два буфера на один файл недопустимы.** В Mode B `validation.ts` открывается и из дерева файлов, и
в нижней панели. Правило: три схемы **активной** формы редактируются только в нижней панели —
открытие такого файла из дерева переключает панель на нужную вкладку. Файл чужой формы открывается
code-вкладкой как раньше.

### 3.2. Рабочая копия формы — каталог в OPFS на вкладку

Каждая открытая вкладка получает **свой каталог в OPFS** с полным набором файлов модуля формы.
Именно эти файлы правятся и показываются в билдере. Диск — не рабочее место, а место сохранения.

```
  Mode B: диск проекта ──копия при открытии──▶ ┌──────────────────┐
                                               │  OPFS/tabs/<id>/ │ ◀── Monaco (нижняя панель)
  Mode A: кодоген ──материализация───────────▶ │  types.ts        │ ◀── regenerate() из правил
                                               │  model.ts        │
                                               │  validation.ts   │ ──▶ живое превью
                                               │  form.behavior.ts│     (compileForm читает отсюда)
                                               │  renderer.*      │
                                               │  api.ts …        │ ──▶ сохранение на диск (Mode B)
                                               └──────────────────┘     экспорт в папку (Mode A)
```

**Почему это лучше того, что было в плане.** Из плана исчезают четыре подпорки:

- `TabState.sources` с тремя текстами и персистенцией их в `DraftRecord` — не нужен: тексты и так
  лежат в файлах, а в сторе остаётся только имя каталога;
- развилка `SourcesRequest = dir | virtual` в живом превью — не нужна: путь чтения один;
- проблема неполного набора для линковки. `renderer.behavior.ts` импортирует **значения** из
  `./validation` и `./api`; дай компилятору три файла — `require('./api')` бросит. Рабочая копия —
  весь модуль, и вопрос снимается сам;
- правила предпочтения «несохранённый буфер Monaco важнее диска» в `sibling-sources.ts`. Буфер
  пишется в OPFS с дебаунсом, превью читает OPFS — один источник вместо двух с приоритетом.

**Слой IO уже готов.** `io/fs-ops.ts` написан против **структурного** типа
(`type Root = FileSystemDirectoryHandle`, доступ через локальный `FsDirHandle` — lib.dom неполон), а
`navigator.storage.getDirectory()` возвращает ровно такой хэндл. `createFile`, `createFileDeep`,
`listFilesDeep`, `readTextFile`, `deletePath`, `existsIn`, `uniqueName` работают над OPFS **без
единой правки**. Добавляется немного: `io/opfs.ts` (корень, каталог вкладки, сборка мусора) и
кросс-корневое копирование — `copyPath` сегодня односоставный, `copyPath(root, src, dest)`.

**Что хранит кто.** Черновик IndexedDB — состояние редактора: схему, правила, мок, выделение, имя
каталога OPFS. OPFS — тексты файлов модуля. Пересечение ровно одно и разрешается односторонне:
`renderer.schema.json` **проецируется** в рабочую копию из `tab.schema` (write-through) и обратно не
читается. Иначе у раскладки стало бы два владельца — canvas со своей историей undo и текстовый файл,
и разошлись бы они молча.

**Цена, которую надо заплатить явно.** Каталоги в OPFS живут вечно, пока их не удалить: нужен
манифест `tabId → каталог` и сборка мусора на старте, иначе за месяц работы там накопятся сотни
брошенных копий. Плюс OPFS в главном потоке полностью асинхронен (`createSyncAccessHandle` — только
в воркере), то есть чтение файла во вкладку становится async и требует состояния загрузки. И в Node
OPFS нет вовсе — доступ прячется за порт с поддельной реализацией для тестов, по образцу
`io/__fixtures__/fake-fs.ts`.

Побочная выгода: OPFS поддержан шире, чем File System Access (Chromium, Safari 15.2+, Firefox 111+),
так что Mode A перестаёт быть Chromium-only. Это не цель работы, но и терять это не надо.

### 3.3. Модель владения файлом

У каждого из трёх файлов два состояния.

```
                    инструмент правил (ИИ)
                            │
                            ▼
                   ┌─────────────────┐
                   │  FormRules      │  сайдкар: validation / behavior / render
                   └────────┬────────┘
                            │ regenerate() = эмиссия + prettier + маркер
                            ▼
         сгенерирован ─────────────────────── правлен руками
       правила доезжают     первая правка     текст — истина,
       автоматически        человеком         правила его не трогают
                              ─────────▶
                              ◀─────────
                         «вернуть к правилам» (через дифф)
```

**Состояние не хранится битом.** Бит на `TabState` — единственное место в билдере, где «расходится
ли X с Y» жило бы отдельно от Y: `isDirty` сравнивает с baseline, `prepareSave` — с `lastModified`,
гейт агента — с базовым мультимножеством ошибок. Хуже того, бит не пережил бы перезагрузку в Mode B:
`isDraft` (`reducers.ts:978-982`) возвращает `false` для `source.kind === 'file'`, такие вкладки в
IndexedDB не попадают вовсе.

**Признак выводится из самого файла — одним механизмом на оба режима.** Рабочая копия (§3.2) сделала
это возможным: раньше в Mode A файла не существовало и признак пришлось бы хранить отдельным полем,
теперь файл есть всегда. Шапка вида

```ts
// @reformer-generated 9f2c1ab74d0e
```

где хэш считается от тела без строки маркера. Маркера нет → файл написан руками (это же
автоматически покрывает «открыл существующий рукописный файл с диска»). Маркер есть и хэш сходится →
сгенерирован, перезаписывать безопасно. Маркер есть, хэш не сходится → человек правил
сгенерированный файл. Переживает перезагрузку, смену браузера и `git clone`, читается человеком и
`git diff`. Прецедент в коде есть: эмиттеры уже носят провенанс-шапки
(`emit-behavior.ts:21` — «Пишется один раз (не затирается при регенерации)»).

Тот же маркер решает **Р6**, и без диалога сохранения: `deliver.ts` переходит с предиката
«пропустить, если `user` и файл существует» на «перезаписать, если маркер сходится; иначе пропустить
и **сказать об этом** в `skipped`». Экспорт уже отчитывается `written`/`skipped` — достаточно, чтобы
`skipped` означало «ваши правки не тронуты», а не «молча устарело».

**Форма из проекта отцеплена по умолчанию, и это сообщается.** TS-парсера у билдера нет и не
появится: прочитать правила обратно из рукописного `validation.ts` невозможно. Если ассистент задал
правила, а целевой файл правлен руками, инструмент обязан **отказать с объяснением**, а вкладка —
показать «правила изменились, файл правлен руками» с кнопкой сравнения. Молчаливое «готово», за
которым ничего не уехало, — ровно тот отказ, который этот проект уже дважды чинил.

### 3.4. Регенерация обязана быть чистой — это предусловие, а не полировка

«Нет правок — нет диффа» работает, только если `regenerate` стабильна. Сейчас:

| Файл | Вход | Чистота |
| --- | --- | --- |
| `validation.ts` из правил | `rules.validation` + `names` | **чист** |
| `form.behavior.ts` из правил | `rules.behavior` + `names` | **чист** |
| `renderer.behavior.ts` | `names` + `SelectorInfo` от `assignSelectors(schema)` | **от правил не зависит вовсе** |

`assignSelectors` позиционен: `submitSelector` — «первый встреченный в обходе Button»; селектор
секции — `${kebab(title)}-section`, то есть **переименование заголовка секции обнуляет адресацию
правила, и обнуляет молча**. А если кнопки нет, узел **дописывается в схему-копию** — значит превью
показывает форму без кнопки, которая в экспорте есть. Это расхождение существует уже сегодня.

Отсюда порядок работ: селекторы обязаны материализоваться в **живую** схему (Э2) раньше, чем
появится регенерация в рабочую копию (Э4) и редактор поверх неё (Э5). Плюс три мелочи, каждая из
которых иначе даёт ложный дифф: prettier обязан быть частью `regenerate`, а не доставки; `now` для
синтеза мока фиксируется, как уже сделано в `codegen.test.ts:55`; правила канонически сортируются перед эмиссией
(в режиме `replace` порядок сегодня — это порядок аргументов модели).

## 4. Этапы

Каждый этап самостоятелен, оставляет приложение рабочим и откатывается отдельно. Ручная проверка
есть только у последнего — это и определило порядок.

### Э0. Три дефекта эмиттеров — без них дальше строить нельзя

- **Р4:** привести кодоген к каноническому контракту, на котором уже стоят
  `app/form-templates.ts:117`, `app/wizard-templates.ts:197`, `extract-exports.ts:82` и MCP:
  `emit-validation.ts` экспортирует `formValidation`, `emit-behavior.ts` зовёт

- **Р5:** добавить `createJsonRenderBehavior` в поиск фабрики в `extract-exports.ts`. **Именно

- **Р3:** расщепить `hasRules` на `hasValidationRules` / `hasBehaviorRules` / `hasRenderRules` и

### Э1. Словарь render-правил — в билдере

Словарь живёт в билдере, MCP не трогаем. Это не компромисс, а совпадение с тем, как уже устроено:
**`renderer.behavior.ts` целиком билдерский**. Его форму задаёт
[`emit-behavior.ts`](../../projects/reformer-builder/src/codegen/emit-behavior.ts) — фабрика
`createJsonRenderBehavior(form, model, options)` с submit-обвязкой; `emit-index.ts` импортирует
именно её; а MCP-шный `buildRenderBehaviorTs` (он эмитит `const formRenderBehavior` и умеет только
`hideWhen`) билдер **не зовёт ни из одного места**. Второго словаря здесь поэтому не возникает —
возникает первый.

Принцип «второй словарь для того же самого разойдётся с первым молча» продолжает действовать там,
где эмиттеры MCP **используются**: `validation.ts` и `form.behavior.ts` как собирались
`buildValidationTs`/`buildBehaviorTs` через `emit-rules.ts`, так и собираются.

```ts
/**
 * Правило render-слоя: поведение над УЗЛОМ разметки, адресуемым по `selector`.
 *
 * Надмножество `VisibilityIntent` из `@reformer/mcp`: та несёт ровно один вид (`hideWhen`) и
 * приезжает к нам из спеки через `from-intent`. Здесь она сворачивается в `hideWhen`-вариант, и
 * дальше живёт один список: разводить их по двум значило бы проверять селекторы в двух местах.
 */
export type RenderRuleIntent =
  | { kind: 'hideWhen'; selector: string; condition: string }
  | { kind: 'onEvent'; selector: string; event: string; body: string; async?: boolean }
  | { kind: 'patchProps'; selector: string; props: Record<string, unknown> };
```

`FormRules.render` добавляется; `visibility` остаётся полем чтения — из него сворачиваются правила,
пришедшие из спеки (`from-intent.ts`) и из старых `DraftRecord` (ту же любезность
`draft-store.ts:34-38` уже делает для `rules`). `emit-behavior.ts` перестаёт печатать
закомментированные TODO по секциям и печатает настоящие правила, сохраняя submit-обвязку. Снимает
**Р2**.

**Проверку селекторов билдер делает лучше, чем мог бы MCP.** C6 в `cross-check.ts` сверяет селектор
правила с сериализованной раскладкой; у билдера в руках **живая схема** и готовый
`collectSchemaSelectors` из `@reformer/renderer-json` — то самое множество, по которому
`schema.node()` ищет в рантайме. Проверка идёт в `model/rules-integrity.ts` (Э2) и покрывает и
опечатку, и осиротевшее правило — чего C6 не умеет, потому что видит только момент генерации.

Две тонкости, которые легко пропустить: **`patchProps` — метод `RenderNodeControl`**
(`schema.node(sel).patchProps({…})`), а не standalone-хелпер, в отличие от `hideWhen` и
`onComponentEvent`; и строка импорта обязана собираться из фактически использованных хелперов —
тем же приёмом, что в `buildValidationTs`, и по той же причине (`noUnusedLocals` у потребителя).

За скобками намеренно: `renderEffect` / `onInit` / `onMount` / `onUnmount`. Они принимают
произвольные замыкания над рефами — это территория сырого TS, которая по решению остаётся в
код-вкладке.

**Проверка.** `emit-rules.test.ts` (он уже гоняет настоящий `tsc`) расширяется правилами всех трёх
видов; `example-compiles.test.ts` — тоже. Тесты MCP не затрагиваются: пакет не меняется.

### Э2. Селекторы становятся управляемыми

- `set_render_rules` адресует узел по `ref` (JSON Pointer — то, чем инструменты уже пользуются) и
  **сам обеспечивает узлу `selector`**: выводит из `labelOf`/`componentOf` (`node-ref.ts:58-84`)
  через `kebab`, дедуплицирует против `collectSchemaSelectors(schema)` — ровно того множества, по
  которому `schema.node()` ищет в рантайме. Записывает существующим `setNodeKey`; новой мутации не
  нужно. Снимает **Р7**.
- Один вызов, меняющий и схему, и правила, **представим без единой правки машинерии**: `ToolOutcome`
  держит `schema?` и `rules?` независимо, `withOutcome` написан как
  `outcome.schema ?? set.draft, outcome.rules ?? set.draftRules` — он уже принимает оба, а
  `applyChangeSet` кладёт их в **один** `pushHistory`, то есть одна запись undo на всю правку.

- Схемная половина идёт через `gate.ts` `commitBatch`; `selector` легален на всех трёх видах узла,
  `structure-lint` его не смотрит — новых замечаний не появляется.
- Вставку submit-кнопки перенести из экспортной копии в живую схему — иначе превью и экспорт
  показывают разные формы (см. §3.4).
- **Осиротевшие правила** (узел удалили или селектор сменили руками) — новый
  `model/rules-integrity.ts`, результат идёт в существующий канал `warnings` (`io/validate.ts:40-47`

  работы без спроса; предупреждение с предложением удалить — можно.
- Инспектор: чип селектора в секции «Привязки» — чтобы человек, пишущий `schema.node('…')` руками,

## 7. Ограничения, которые нельзя обойти молча

**`TOOL_SURFACE_BUDGET = 8946`** ([`agent/core/types.ts:56`](../../projects/reformer-builder/src/agent/core/types.ts#L56)) —
храповик, равный фактически достигнутому размеру; `registry.test.ts` падает при любом добавлении.
Повышение делается **после** замера и отчёта, не до. Контекст, который стоит держать в голове:
эпик `ReFormer-nir` («ускорение хода агента») уже один раз сжимал поверхность с 9.1 до 7 КБ
(`ReFormer-nir.4`, закрыт), после чего её вернули к 8946 ради `set_form_rules`. Третье повышение
работает против той же цели — и потому должно быть проговорено, а не сделано молча.

**`docs/specs/` — read-only.** Спека MVP относит генерацию TS-заготовок к v2 (§12) и решает Q32
(«отдельный `*.builder.ts` + композиция»). Здесь принято другое: разделение проходит не по файлам, а
по состоянию файла, и оно видимо пользователю. Расхождение фиксируется здесь, в плане, а не правкой
спеки.

**Тесты — `vitest`, `environment: 'node'`, `include: ['src/**/*.test.ts']`.** Ни `.tsx`, ни jsdom.
Отсюда политика, которую проект уже сформулировал: решающая логика живёт в `.ts` и покрыта, а `.tsx`
её только зовёт. Для рабочей копии это значит, что **OPFS обязан быть за портом**: в Node его нет
вовсе, и без порта весь слой окажется непокрываемым.

**Рабочая копия в OPFS — три обязательства, которые нельзя отложить «на потом».**

1. **Сборка мусора.** Каталоги в OPFS живут, пока их не удалить. Без манифеста `tabId → каталог` и
   подметания на старте за месяц работы там накопятся сотни брошенных копий от закрытых вкладок и
   упавших сессий. Это не полировка: место занимает пользовательскую квоту молча.
2. **Асинхронность.** В главном потоке OPFS полностью async (`createSyncAccessHandle` — только в
   воркере), поэтому открытие вкладки с файлом обязано иметь состояние загрузки, а не пустой
   редактор, мигающий текстом.
3. **Один владелец у раскладки.** `renderer.schema.json` в рабочей копии — **проекция** `tab.schema`,
   пишется write-through и обратно не читается. Двусторонняя связка дала бы раскладке двух хозяев:
   canvas со своей историей undo и текстовый файл — и разошлись бы они молча.

Побочно: OPFS поддержан шире, чем File System Access (Chromium, Safari 15.2+, Firefox 111+), так что
Mode A перестаёт быть Chromium-only. Целью работы это не является — но и ронять это не надо.

**`@reformer/mcp` не меняется — направление зависимости одностороннее.** Билдер продолжает звать
`buildValidationTs` / `buildBehaviorTs` и импортировать `ValidationRuleIntent` / `BehaviorIntent` /
`VisibilityIntent`; всё, чего в MCP нет, реализуется у билдера. Практический эффект на этот план
ровно один: словарь render-правил и их эмиссия — билдерские (Э1), а проверка селекторов — своя,

**Существующий баг по соседству, который эта работа не чинит:** `renameEntry`
(`save-actions.ts:458-474`) не правит `source.path` открытых вкладок при переименовании каталога — а
id вкладки и есть путь. Стоит завести задачей в `bd`.

Отдельно отмечу, что дефект `buildValidationTs`/`buildBehaviorTs` (деструктуризация `({ model })`
при пустом теле → TS6133 у потребителя с `noUnusedParameters`) после Э0 до билдера не доходит:
пофайловая развилка `hasValidationRules` / `hasBehaviorRules` зовёт MCP-эмиттер только тогда, когда
правила соответствующего вида непусты, то есть тело никогда не пустое. Обходить его не нужно.
