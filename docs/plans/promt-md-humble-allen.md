# Замер ассистента ui-builder на спеке кредитной заявки

## Контекст

Нужно проверить, соберёт ли ИИ-ассистент внутри `projects/reformer-builder/` форму по
спецификации `docs/specs/credit-application-form.md`. **Ассистента билдера на полной спеке не
гоняли ни разу** — прошлые прогоны кредитной заявки (`new-mcp-test`, `new-mcp-test-v2`) шли
через MCP-only, то есть совсем другой контур. Этот замер будет первым.

Решения, принятые пользователем:

- **результат** — замер и сразу починка найденного;
- **база** — рабочее дерево, вместе с незакоммиченной починкой обрыва хода (`ReFormer-0hw`):
  без неё сложный ход обрывается и выглядит штатным завершением, то есть замер измерял бы стенд;
- **объём задания** — только структура формы: шаги, поля, типы, метки, значения по умолчанию,
  маски. Валидацию, условную видимость и формулы не просим.

## Граница спеки

`## 🔄 Сценарии формы` — **строка 1083**. В границе строки 1–1082. Не спутать с `## Сценарии
использования формы` (строка 49, чекбоксы режимов) и `### Сценарий использования` (строка 20).

В границе: 6 шагов, 76 строк-полей, 3 массива (`properties[]`, `existingLoans[]`,
`coBorrowers[]`), 5 вложенных групп, 10 типов компонентов, 7 масок (13 применений), 8
вычисляемых полей и 15 условных — последние два класса в задание **не входят** по решению выше.

Важно: обрезка по строке 1083 не убирает валидацию и поведение из спеки — они живут в колонке
«Валидация» каждой таблицы полей. Поэтому задание формулируется **по существу требуемого**, а не
«всё до строки 1083».

## Что заведомо не получится — не считать находками

| Что | Почему (проверено по коду) |
| --- | --- |
| Поля внутри массивов | `insertSlotOf` (`agent/core/slots.ts:37`) возвращает `null` для узла-массива → вставка отвечает `INVALID_PARENT`. Класть можно только по явному адресу `/…/item/$template`, и агенту про это нигде не сказано |
| Условная видимость | `set_form_rules` её не принимает намеренно (`set-form-rules.ts:18-23`): селекторы проставляются только при экспорте и только секциям/массивам/кнопкам |
| Значения справочников | `set_node_prop` принимает только `string\|number\|boolean\|null`, массивы отклоняются. Агент может выставить `$dataSource(NAME)`, но не сами значения |
| `data-sources.ts`, `api.ts` | инструмента нет вовсе |

Массив как узел агент создать может — под именем **`List`** (перевод `FormArray → List` в
`model/from-intent.ts`). Шаги визарда поддержаны: `insert-node.ts:139` отдельно отбивает попытку
положить поле прямо в визард.

## Как запускать

Штатно ассистент вызывается только из чата в браузере, но `runAgentTurn` — чистая функция и
работает в node. **Скрипта-обёртки в репозитории нет, его надо написать (~30 строк).** Образец —
хелпер `play` в `src/agent/core/loop.test.ts:18-45`.

```ts
// .tmp/builder-spec-run/run.mjs — вне репозитория, чтобы не засорять чужой проект
for await (const e of runAgentTurn({
  provider: createByokProvider({ kind: 'openai-compatible', baseUrl: 'http://localhost:11434/v1',
                                 model: 'qwen3.8:27b', maxInputTokens, maxSteps }),
  registry: createEditorToolRegistry(),   // все 15 инструментов
  base: emptySchema(),
  baseRules: emptyRules(),                // иначе merge-правки затрут накопленное
  messages: [{ role: 'user', content: <задание> }],
})) { /* копить text | reasoning | tool | done */ }
```

Ключевые файлы: `agent/core/loop.ts` (`runAgentTurn`), `agent/core/index.ts`
(`createEditorToolRegistry`), `agent/providers/byok.ts:148` (`createByokProvider` — принимает
конфиг объектом, стор и `localStorage` не нужны).

**Не использовать** `agent/run.ts` `sendMessage` — он привязан к `editorStore` и `localStorage`,
и прямо сейчас переписан больше чем наполовину.

### Предусловия

1. `npm run generate:knowledge` в билдере — иначе `ask_reformer` отвечает «корпус не собран»
   (артефакты `knowledge-docs.json` в git не коммитятся).
2. Ollama уже поднята, доступны две модели с поддержкой tools: **`qwen3.8:27b`** (окно 262144) и
   `gemma4:26b` (на ней шли прошлые битые прогоны). Основной прогон — на `qwen3.8`.
3. **Контекстное окно — главный технический риск.** Билдер `num_ctx` не задаёт, только советует
   его увеличить в тексте ошибок. Постоянная часть запроса ~3.5–4K токенов
   (`TOOL_SURFACE_BUDGET` 8946 симв. + `PROMPT_BUDGET` 4000 + карта формы 3000). При дефолтных
   `num_ctx=4096` ход оборвётся на первом же шаге. Первым делом — короткий пробный ход и проверка
   `peakStepInputTokens` из `TurnStats`; если окно мало, поднять `OLLAMA_CONTEXT_LENGTH` и
   перезапустить сервис.

## Что мерить

Основа формата — `docs/mcp-eval/builder-rules.md` (таблица «просьба → вызовы → ожидание» плюс
честная секция «что осталось неизмеренным»). Критерии качества формы — из таблицы браузерной
приёмки `.tmp/new-mcp-test-v2/dev-report.md`, там разобрана ровно эта спека.

| Метрика | Что показывает |
| --- | --- |
| Покрытие полей | сколько из 76 строк спеки стало узлами, с разбивкой по шагам |
| Раскладка | шаги визарда (`componentProps.steps`) против плоского `children` |
| Типы компонентов | совпали ли с колонкой «Тип поля»; маски как проп |
| Группы | легли ли `personalData`/`passportData`/`registrationAddress` в модель через точку |
| Батчинг | сколько узлов за вызов `insert_node` (промпт учит брать до дюжины) |
| Цена хода | вызовов и токенов против цели `ReFormer-nir`: 6–8 вызовов и 25–35K вместо исходных 23 и ~200K |
| **Молчаливые ложные «готово»** | ход завершился `complete`, а форма не изменилась — исторически главный класс дефекта |

Проверка результата: `validate_form` (инструмент самого агента), затем экспорт
`buildExampleFiles` и `tsc` по сгенерированному модулю. Правила смотреть только в файле сайдкара —
ни одна панель UI его не показывает.

## Порядок работ

1. Зафиксировать базу: `git stash list` пуст, рабочее дерево не трогать; записать `git rev-parse
   HEAD` и список незакоммиченных файлов билдера в отчёт — чтобы прогон был воспроизводим.
2. `npm run generate:knowledge`; проверить, что тесты билдера зелёные (чужая переделка в процессе).
3. Написать `.tmp/builder-spec-run/run.mjs`, прогнать **пробный короткий ход** («добавь одно поле
   email») — убедиться, что канал жив и `peakStepInputTokens` укладывается в окно.
4. Полный прогон на задании по спеке. Сохранить: поток событий, финальный `changeSet`, `stats`,
   `stop`, дословный текст ответа.
5. Разбор: посчитать метрики, экспортировать код, прогнать `tsc`.
6. Отчёт в `.tmp/builder-spec-run/report.md` + находки в bd. Отдельно пометить то, что попало в
   таблицу «заведомо не получится» — это не дефекты замера.
7. Починка найденного — в том же заходе, по решению пользователя. Файлы, которые сейчас правит
   другой человек (`run.ts`, `loop.ts`, `ai-sdk.ts`, `providers/types.ts`, `fake.ts`,
   `model/rules.ts`, `codegen/emit-validation.ts`), **не трогать** — находки по ним оформить
   задачами.

## Верификация

- пробный ход завершается `done` с непустым `changeSet` — канал и окно в порядке;
- полный прогон: `validate_form` по итоговой схеме не даёт структурных ошибок;
- экспорт `buildExampleFiles` → `npx tsc --noEmit` по сгенерированному модулю чист;
- метрики покрытия и цены хода посчитаны и записаны;
- отчёт содержит секцию «что осталось неизмеренным» — обязательный элемент формата.

## Риски

- **Контекстное окно** (см. предусловие 3) — самый вероятный срыв.
- **Движущийся фундамент**: семь файлов ядра агента правятся прямо сейчас; `TurnEvent.done`
  обрастает полем `stop`. Скрипт-обёртку писать по текущему состоянию и не полагаться на
  стабильность сигнатур.
- **Сравнимость**: прошлые прогоны шли на `gemma4:26b`. Замер на `qwen3.8:27b` покажет лучшее из
  возможного, но не будет прямо сопоставим с историей — при желании сравнить нужен второй прогон
  на `gemma4`.
