# Страница «Какие задачи решает ReFormer» + блок на лендинге

## Context

README, [intro.mdx](../../projects/reformer-doc/docs/intro.mdx) и лендинг перечисляют **возможности**
(«на сигналах», «декларативная валидация»). О **проблемах**, которые они снимают, там не сказано.
Пользователь хочет описать все проблемы, включая эффекты второго порядка. Главная мысль: ReFormer
задаёт единый стандарт кода формы. Из него вытекают читаемость, меньшая когнитивная нагрузка,
удобство, простое сопровождение и ревью без проблем. Код понятен, и его может править человек. MCP и
билдер пишут код по тому же стандарту, поэтому все эти следствия переходят на код, созданный ИИ.

Решения пользователя:
- страница на сайте и выжимка на лендинге;
- текст разбит **по ролям**;
- короткий честный раздел «где ReFormer уступает»;
- сразу RU и EN.

## Структура страницы `why-reformer.mdx`

Frontmatter: `title: Какие задачи решает ReFormer`, `sidebar_label: Какие задачи решает`,
`description` одной фразой.

**0. Вступление (2–3 предложения).** Форма — это не только поля. Это ещё значения, правила, реакции,
шаги, отправка и тексты ошибок. Без общего каркаса каждый собирает всё это по-своему. ReFormer задаёт
один стандарт, и большая часть пользы — следствия этого стандарта.

**1. «Один стандарт — много следствий».** `<StandardEffects />` плюс короткий список-цепочка.
- Корень: «Форма пишется одним способом — модель, схема, правила, поведение».
- Узел «Пишут человек, MCP и билдер».
- Следствия: читаемость → меньше когнитивной нагрузки → быстрое ревью → простое сопровождение →
  быстрый онбординг → код от ИИ правит человек, и наоборот.

**2–6. Разделы по ролям.** В каждом таблица «Проблема | Как снимает ReFormer | Подробнее» на 5–10
строк. Ссылка ведёт на страницу сайта, а не в код.

2. **Разработчику формы**
   - Перерисовка всей формы на каждую клавишу → сигналы, подписка только своего поля. Цифры:
     0 рендеров на клавишу с неуправляемым адаптером; 455 у Formik в строке массива.
   - Копии значений в `useState` и сторе расходятся → модель — единственный владелец значений.
   - Цепочки `useEffect`, зацикливания → операторы поведения: `compute`, `enableWhen`, `resetWhen`,
     `copyFrom`…
   - Правила размазаны по JSX → отдельная схема `defineValidation`, кросс-правила, стратегии показа.
   - Гонки async-проверок; сбой сервера выглядит как ошибка ввода → `AbortSignal`, статусы
     `pending`/`cancelled`/`error`.
   - Массивы: ключи, ошибки переезжают на чужую строку → `arrayOf`, `keyAt`, `applyEach`.
   - Мастер руками → `createForm({ flow })`, проверка по шагу, `firstInvalidStep`.
   - Отправка в обход проверки, try/catch → `submission.submit` и объединение `SubmitResult`.
     Предзагрузка и два вида сброса.
   - Строковые пути ломаются при рефакторинге → типизированные `form.address.city`, вывод типов.
   - Чтобы проверить правило, нужен рендер → ядро без React, юнит-тест.
   - Тексты ошибок зашиты в код → коды замечаний плюс словарь, смена языка без перепроверки.
3. **Тимлиду и ревьюеру** — главный раздел о стандарте и его следствиях.
   - Каждый файл формы находится по имени, а не поиском ([project-structure.md](../../projects/reformer-doc/docs/patterns/project-structure.md)).
   - Один способ собрать форму — `createForm`.
   - Слои разделены: правка правила — это дифф в файле правил, разметку при этом читать не нужно.
     Отсюда ревью без проблем.
   - Читаемость и меньше когнитивной нагрузки: один файл отвечает на один вопрос.
   - Сопровождение: разметка меняется без правил, и наоборот.
   - Единые контракты результатов: `SubmitResult`, коды замечаний.
   - Переиспользование через модули групп.
   - Онбординг: один словарь терминов, FAQ.
   - Объём кода кредитной заявки: в самой форме 399 строк против 890–992 у остальных.
   - Код читает и правит человек, даже если его написал ИИ или билдер.
4. **Команде с ИИ-ассистентом (MCP)**
   - Ассистент пишет по тому же стандарту, поэтому код не чёрный ящик и ревьюится как ручной.
   - Выдуманный API ловится проверкой типов и кодами `RF002`/`RF003`.
   - «Готово» ставит сервер после сборки и проверки типов, а не модель.
   - `llms.txt` поставляется вместе с пакетами.
   - Токены: статика подключения −85%.
   - Цифры замера 19.11.2026 (Claude Sonnet, 270 прогонов): 96% пройдено против 83% без MCP,
     в 3,5 раза быстрее, в 4,4 раза дешевле. Ссылка на `/docs/mcp/benchmark`.
5. **Продукту, аналитику, дизайнеру (билдер)**
   - Форма собирается визуально или просьбой обычным текстом.
   - Lock-in нет: форма — файлы в репозитории, экспорт даёт обычный модуль.
   - Правила читаются обратно из кода. Внешние правки приводят к трёхстороннему слиянию.
   - Свой UI-кит.
   - Встраивание в приложение.
   - Своя или локальная модель.
   - Ход ассистента отменяется целиком.
6. **Архитектору платформы**
   - Микрофронтенды — `form-registry`, общий `access`, проверки расхождения схемы и кода.
   - Формы с бэкенда — renderer-json:
     - +36,7 КБ gzip против +129,5 у RJSF;
     - `validateFormSchema` проверяет документ;
     - безопасный `$html`;
     - версия формата.
   - Дизайн-система: headless cdk, адаптеры, смена кита.
   - Ядро на React 16.8–19, работает без React, SSR.
   - Tree-shaking.
   - Тип из генератора OpenAPI.
   - Две копии рантайма → guard.

**7. «Где ReFormer уступает».** 6–8 пунктов, ссылка на `/benchmark`.
- Гидратация префиллом в ~2,8 раза медленнее Formik и RHF. Монтирование медленнее Formik.
- Бандл больше Formik: +28,9 против +24,5 КБ gzip. На маленькой форме кода больше, чем у RHF.
- Кривая обучения: у значения три объекта (`model.email`, `model.$.email`, `form.email`).
- Ноль рендеров на клавишу — только с неуправляемым адаптером.
- MCP:
  - на поверхности по умолчанию ручные правки в файлах сервера откатываются при следующем вызове
    MCP — продолжать либо руками, либо через MCP;
  - форму, написанную с нуля руками, MCP для правки пока не подхватывает;
  - раскладка файлов у MCP и билдера разная.
- Билдер работает только в Chromium.
- cdk и ui-kit — только React 18/19.

**8. «См. также».** Введение, быстрый старт, `/benchmark`, `/docs/mcp/benchmark`, `/docs/builder/overview`.
