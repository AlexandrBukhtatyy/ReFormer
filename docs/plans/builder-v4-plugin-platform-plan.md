### 1.2. Где RFC расходится с кодом или недооценивает объём

1. **`reformer.workspace` как capability не существует даже в зачатке.** В `@/sdk` нет ни одного имени, которым можно прочитать или записать текст документа (grep `documentOf|getText|writeText|Workspace` по `src/sdk` — ноль). Рабочую область плагины получают **только портами** (`MonacoHost.documentOf/writeText`, `FilesHost`, `CodegenHost`, …). RFC пишет `requires: reformer.workspace` у пяти плагинов как данность, но это самая большая новая служба во всём плане, и без неё внешний редактор кода невозможен в принципе (его `Body` получает только `documentId`).

2. **Порты — не «несколько plugin‑specific shared objects».** Их десять, суммарно больше шестидесяти методов, и они закрывают четыре разных потребности: доступ к рабочей области, доступ к чужому плагину (тело Monaco, живая поверхность превью), локализацию (`useTranslate`, перевод кодов диагностик словарём оболочки с приставкой `errors.`), сужение прав (превью не пишет, кодоген не выбирает каталог). Фаза 5 RFC «заменить поля `BuiltinPluginsOptions`» — самая тяжёлая фаза, а не рутинная.

3. **Локализация в RFC отсутствует.** Сегодня сервиса i18n в `PluginContext` нет, манифест внешнего плагина не умеет `messages`, и каждая команда внешнего плагина показывается маркером промаха `⟦…⟧`. Словари встроенных вносит либо композиция руками (`files`, `plugin-manager`), либо `activate` через `MessageSink`. Без i18n‑capability «независимо распространяемый плагин» не получит даже читаемого пункта в палитре.

4. **Идентификаторы плагинов — persisted‑ключи.** RFC переименовывает `editor-monaco` → `reformer.editor.monaco`. Но `id` — это пространство имён словаря, ключ хранилища плагина, ключ настроек `workspace.plugin.<id>`, владелец команд и вкладов, ключ `workspace.plugins.enabled`. Переименование = миграция сохранённых данных, RFC этого не упоминает.

5. **`PluginContext.subscriptions: DisposableStore`** противоречит зафиксированному решению «массив, а не реестр» (`types.ts:103-113`). Не ошибка, но смена решения должна быть названа.

6. **Capabilities и ServiceRegistry — два реестра одного и того же.** Служба уже ключуется строкой `id`; capability по RFC = `id + version + выбор провайдера`. Если завести параллельный `CapabilityRegistry`, получим ровно ту дублирующую пару, о которой предупреждает шапка `sdk/index.ts` (двойники токенов). Правильнее: capability = токен службы + версия + декларация в манифесте + правило выбора провайдера, поверх существующего `ServiceRegistry`.

7. **Декларации в манифесте против фактической регистрации.** RFC резолвит capabilities «только по манифестам», но провайдер регистрирует службу в `activate`. Нужна проверка «всё, что объявлено в `provides`, зарегистрировано к концу `activate`», иначе резолвер будет верить манифесту, а рантайм — молчать.

8. **Дерево каталогов §46 повторяет уже отвергнутый вариант.** В `docs/decisions-log.md:2331-2336` вариант kernel/platform/workbench отвергнут проверкой: платформа не автономна (`plugin/loader → source`, `modules/compile-cache → workspace`, `plugin/catalog → ui/keymap`), а `sdk` реэкспортирует `ui`. RFC кладёт в `shell/` только `Shell.tsx/layout/routing`, но не говорит, куда уходят `ui/{chrome,keyboard,menu,dialogs,contributions}`, `workspace/`, `source/` — то есть ровно те рёбра, из‑за которых прошлый раскол не прошёл. Переезд каталогов надо либо не делать в v4, либо делать последним и с теми же проверками.

9. **Хранилище установленных плагинов.** §21a/§22 смешивают две вещи: `.ui_builder/` лежит в **источнике проекта** (реальная папка через File System Access), а OPFS — рабочая копия и кэши. «Установить в `.ui_builder/plugins` через OPFS» означает либо запись в источник (он может быть read‑only: `source.capabilities.write`), либо OPFS‑слой поверх источника, которого нет. Нужно явное решение, где живёт артефакт при источнике без записи.

10. **Внешним плагинам сегодня недоступны:** `react-dom/client` (нет в линкере), кит (lazy‑модуль, прогрев только у порта превью), CSS плагина (атрибут `data-rb-plugin` никто не проставляет — `styles.ts:57` единственное вхождение), точка `preview.surface` и `defineExtensionPoint` (нет в SDK; работает только структурная копия по `id`). Это дыры **до** любой composability, и закрывать их дешевле, чем всё остальное.

11. **`sdk/index.ts:27-28, 99-100, 189-192` утверждают, что точки сравниваются по идентичности объекта.** Код говорит обратное (`extension-point.ts:33-35`), и билдер сам опирается на ключевание по `id` (`preview/contract.ts:4-10`). Для автора внешнего плагина SDK — контракт; расхождение нужно снять.

12. **Разделяемые объекты §15.** Реестр фокуса Monaco нужен **платформе** (`document-models.ts` откладывает перерисовку буфера по модели, пока человек печатает) раньше активации любого плагина. С capability это работает только при ленивом чтении из места использования; замена редактора, не пишущего в реестр, даёт тихую потерю набранного. Capability `EditorFocus` обязана быть частью контракта редактора, а не опцией.

13. **Статический/ленивый раскол встроенных.** Профиль перечисляет плагины строками, а сборщику нужен литерал `import()`. Карта `id → () => import('@/plugins/<id>')` обязана жить в `application/`, и храповик «оболочка не импортирует барель ленивого плагина значением» (`plugins.test.ts:434`) должен распространиться на `application/composer`. Причины пятерых статических (`plugins.ts:25-36`) при этом никуда не деваются.

14. **Тесты состава** (`plugins.test.ts:151-167`) сверяют владельцев вкладов поимённо. При профилях это становится тестом профиля `reformer.builder`, а для `minimal`/`ai-builder` нужны свои поимённые списки.

15. **Установка из npm в браузере.** Технически выполнимо (registry.npmjs.org отдаёт CORS, `DecompressionStream('gzip')`, tar разбирается вручную, `crypto.subtle.digest` для sha512), но это отдельный пакет работы: tar‑парсер, лимит 200 файлов у загрузчика (`loader.ts:69`), запрет `node_modules` (`loader.ts:84`) — то есть только «browser‑ready bundle», как RFC и говорит.

### 1.3. Чего в RFC не хватает

- Раздел про **локализацию** плагинов (манифест `contributes.messages` или i18n‑capability).
- Раздел про **рабочую область как capability** с явным составом (документы, запись, листинг, сохранение, права источника) — сегодня это распределено по портам.
- Раздел про **миграцию идентификаторов** и сохранённых данных.
- **Связь capabilities с ServiceRegistry** и с точками расширения (обе уже ключуются строкой).
- **Проверка деклараций** манифеста против фактической регистрации.
- **Судьба мостов композиции** (`live-surface`, `kit-namespace`, `printTemplate`, `attachPreviewLifecycle`): кто их провайдер после снятия портов.
- **Стили внешних плагинов** (нерабочий скоуп) и `react-dom` в линкере.

## Часть 2. План внедрения

### 2.0. Принципы, которые нельзя потерять

1. `activate` синхронный; набор вкладов полон к первой отрисовке.
2. Один экземпляр разделяемых реестров (фокус, снимки вида, состояния превью, загрузчик модулей) на приложение.
3. Ленивые встроенные плагины приезжают отдельным файлом; храповик на импорт барелей значением сохраняется и расширяется на `application/**`.
4. Необязательный член контракта = названная деградация, а не поломка.
5. Запись в источник только через рабочую область; права объявляет источник.
6. Каждая фаза заканчивается зелёными `tsc`, `eslint`, `vitest` (node + browser) и живым dev‑сервером; тесты состава переписываются, а не удаляются.

### 2.1. Обзор фаз и зависимости

```text
Ф0 Дыры SDK для внешних плагинов ──┐
                                   ├─► Ф3 Capabilities ─► Ф4 Разделяемое ─► Ф5 Порты → capabilities ─► Ф6 Public API
Ф1 Композиция в application/ ──► Ф2 Профили ─┘                                                          │
                                                                                                         ▼
                                                                          Ф7 Манифесты встроенных, id ─► Ф8 CLI ─► Ф9 npm ─► Ф10 Registry/Marketplace
```

Ф0 и Ф1 независимы и могут идти параллельно. Первый milestone (RFC §50) = Ф0 + Ф1 + Ф2 + Ф3 + часть Ф4.

### Фаза 0. Закрыть дыры, блокирующие любой внешний плагин

Цель: внешний плагин из `.ui_builder/plugins` может быть редактором кода или поверхностью превью. Не зависит от композиции, даёт быстрый проверяемый результат.

Шаги:

1. **Служба документов в SDK.** Токен `DocumentsServiceToken` и тип: `documentOf(id) → { ref, getText(), isDirty(), onDidChangeContent(cb) } | null`, `writeText(id, text, mark?)`, `activeResource()`, `onDidChangeActive(cb)`. Реализация переносится из `shell/boot/ports/monaco.ts:102-112` и `ports/ai.ts:50-67`; регистрируется в `boot.ts` рядом с остальными службами. Служба появляется до проекта и отвечает `null` без него — так же, как порты сегодня.
2. **Реестр фокуса текстового редактора → платформа.** `plugins/editor-monaco/sync/focus.ts` переезжает в `shell/platform/workspace/model/text-focus.ts`, токен `TextEditorFocusToken` в SDK. `boot.ts:438` читает из него; Monaco пишет в него через службу, а не через опцию фабрики. Обязанность редактора «сообщать фокус и звать `flush` на blur» фиксируется в доке SDK.
3. **`react-dom/client` в линкер** (`plugin-modules.ts:92-96`) — иначе внешней поверхности нечем рисовать.
4. **Скоуп стилей.** Проставлять `PLUGIN_SCOPE_ATTRIBUTE` на контейнер тела вклада в `EditorArea.tsx:146` и панелях (`:246, :325`) по `entry.pluginId`. Тест: CSS плагина применяется к его панели и не течёт наружу.
5. **Словари внешних плагинов.** Манифест: `contributes.messages: { "<locale>": "locales/<locale>.json" }`; каталог читает файлы при загрузке и вносит через `i18n.forPlugin(id).contribute`. Снимается вместе с плагином. Тест: команда внешнего плагина показывается заголовком, а не маркером.
6. **`PreviewSurfacePoint` и типы поверхности → SDK**; `plugins/preview/contract.ts` реэкспортирует (как и обещано в его шапке). Заодно `defineExtensionPoint` в SDK не отдавать — точки объявляет платформа.
7. **Поправить шапку `sdk/index.ts`** про ключевание точек по `id`; перенести `templates/stores/seeds-validate.test.ts` в `shell/boot/integration/` (единственное живое нарушение границы плагинов; сам паттерн линтера глубокие пути ловит).

Критерии приёмки: демонстрационный внешний плагин в `.ui_builder/plugins/` (а) открывает `.txt` своим редактором с чтением и записью, (б) вносит поверхность превью, которую видит и панель, и живой вид редактора схемы, (в) имеет переведённую команду и рабочий CSS. Существующие тесты зелёные.

Объём: ~2 недели. Риск: низкий, всё аддитивно.

### Фаза 1. Композиция уезжает из `shell/boot` в `application/`

Цель: `boot.ts` не импортирует фабрики плагинов; состав приложения описан в одном месте вне оболочки.

Шаги:

1. Создать `src/application/composer/`: `builtin-plugins.ts` (карта `id → { eager: () => Plugin } | { lazy: () => import(...) }`), `compose.ts` (собирает `readonly Plugin[]` по списку идентификаторов).
2. Перенести `BuiltinPluginsOptions`, `createEagerBuiltinPlugins`, `loadLazyBuiltinPlugins` из `shell/boot/plugins.ts` в `application/composer` **без изменения содержимого** — порты пока остаются.
3. `boot.ts` получает готовую функцию `compose(options)` параметром `BootOptions.application` (по умолчанию — `builderApplication`). `main.tsx` собирает приложение из `application/`.
4. Линтер: новая зона `src/application/**` — может импортировать `@/shell` и `@/plugins`; `src/shell/**` не может импортировать `@/application` и `@/plugins` (кроме типов через `contract.ts`). Храповик из `plugins.test.ts:434` обходит и `application/`.
5. Тесты состава переезжают в `application/composer/*.test.ts`.

Критерии: `boot.ts` не импортирует фабрики плагинов; `vite build` даёт тот же состав чанков, что до фазы.

Объём: ~1 неделя. Риск: низкий, чистый перенос.

**Сделано 2026‑09‑12.** Отступления от шагов названы: состав отдаёт значение `application/builder-application.ts`, а не `compose.ts`; поле `BootOptions.application` сделано ОБЯЗАТЕЛЬНЫМ, потому что умолчание внутри оболочки вернуло бы ей знание о составе. Исходный критерий «в `boot.ts` только `contract` и типы» НЕ достигнут и на этом шаге недостижим: там остаются пять значений из плагинов — словарь и идентификатор плагина файлов, сессии превью, реестр снимков вида с телом Monaco, токен китов. Это разделяемое состояние, а не фабрики, и уедет оно в capabilities фазами 4–5.

### Фаза 2. Профили и пресеты

Цель: состав приложения задаётся данными, переключается в тестах и конфиге.

Шаги:

1. `application/profiles/`: `defineProfile`, `definePreset` (с `extends`), профиль `reformer.builder` из текущего набора, тестовые `minimal` (files + monaco + validator) и `ai-builder`.
2. Конфиг: `runtime-config.ts` уже читает уровни launch и project; добавить `preset`, `plugins.enable/disable`, `providers` с приоритетом «встроенные умолчания → пресет → launch → project → пользовательские переопределения». Проектный уровень не может менять `defaults` (уже так).
3. Разрешение профиля в список идентификаторов: `application/resolver/profile-resolver.ts` (пока без capabilities, только имена и `extends`).
4. Тесты: профиль `minimal` поднимает оболочку без превью и редактора схемы, живой вид и режим «код» деградируют так, как обещают порты; `ai-builder` даёт панель ассистента.

Критерии: `boot({ application: fromProfile('minimal') })` в тесте композиции проходит поимённую проверку своего списка.

Объём: ~1 неделя.

**Сделано 2026‑09‑12.** Карта `BUILTIN_PLUGINS` вместо двух функций, `application/profiles/`
(`reformer.builder`, `minimal`, `ai-builder`), `application/resolver/profile-resolver.ts`,
`composer/compose.ts` с `fromProfile`. Отступления названы: `definePreset` отдельной функцией
НЕ заведён — пресет и профиль оказались одним понятием («данные со списком и `extends`»), и вторая
функция была бы синонимом; `providers` из шага 2 отложены до Ф3, потому что до capabilities
выбирать нечего; выбор профиля по конфигу живёт функцией `applicationFromRuntime` в
`application/builder-application.ts`, а не телом `main.tsx`, — у точки входа нет теста, а решать
там приходится ровно то, что проверяется только тестом (неизвестный пресет, опечатка в поправках,
и то, что ни один из случаев не оставляет человека без приложения). `preset`/`plugins` разбираются
на обоих уровнях конфига и применяются только на уровне запуска — как `defaults`, тем же приёмом.
Состав чанков сборки не изменился.

**Названо незакрытым.** Короткий профиль экономит активацию, но не стартовый граф: `boot` берёт
из плагинов пять значений и собирает порты для ВСЕХ встроенных, поэтому Monaco и превью
приезжают в entry даже при `minimal`. Уедет это вместе с портами в Ф4–Ф5.

### Фаза 3. Capabilities поверх ServiceRegistry

Цель: контракт с версией и выбором провайдера; предварительная проверка до активации.

Решения:

- `Capability<T> = ServiceToken<T> & { version }` — **не** второй реестр. `defineCapability({ id, version })` возвращает токен, совместимый с `services.get/register`.
- `ctx.capabilities` — вид на тот же реестр: `require(cap)` (бросает понятную ошибку), `get(cap)`, `observe(cap, cb)`.
- Манифест: `provides: [{ id, version }]`, `requires: { required, optional }` — семантика semver (`^`, `>=`), парсер manifest.ts переводится на настоящий semver.
- Резолвер (`application/resolver/capability-resolver.ts`): по манифестам строит граф, ищет отсутствующие и конфликтующие singleton‑провайдеры, применяет `providers` из профиля, отдаёт `CapabilityResolutionResult`. Работает до загрузки кода.
- Рантайм‑проверка: после `activate` провайдера сверяется, что каждая объявленная capability зарегистрирована; иначе плагин переводится в `failed` с кодом `provides-unregistered`.
- Провайдер не выбран профилем и их двое → конфликт до активации, в UI списка плагинов.

Шаги: тип и `defineCapability` в SDK; расширение манифеста и его валидации; `ctx.capabilities` в `context.ts`; резолвер и его тесты (graph fixtures); интеграция в `compose` (Ф1) и в каталог проектных плагинов (`catalog.ts` перед `enable`).

Критерии: плагин каталога с `requires: reformer.kit.catalog@^2` при провайдере 1.x не активируется, причина видна в разделе «Плагины».

Объём: ~2 недели.

### Фаза 4. Разделяемое состояние → capabilities

Порядок по возрастанию риска:

1. `reformer.kit.catalog` — уже служба (`KitsServiceToken`), нужна только версия и декларация в манифесте kits. Потребители в портах переключаются на `capabilities.get`.
2. `reformer.editor.focus` — из Ф0 п.2, объявить capability, провайдер — платформа (не Monaco): реестр общий, редакторы в него пишут.
3. `reformer.editor.view-state` — `monacoViewStates` создаётся в `boot.ts:428`; тип `MonacoViewState` обобщить до `unknown`‑снимка на пару «редактор + документ» (в платформе уже есть `ViewStateStore` с составным ключом — использовать его, а не второй реестр).
4. `reformer.preview.sessions` — `previewSessions` и `attachPreviewLifecycle` переезжают в плагин превью как провайдер; живой вид получает их через capability.
5. `reformer.workspace` (`DocumentsService` из Ф0) — объявить capability, версия 1.0.

Критерии: в `boot.ts` не остаётся ни `monacoFocus`, ни `monacoViewStates`, ни `previewSessions`.

Объём: ~1.5 недели.

**Сделано 2026‑09‑12.** Критерий достигнут буквально: разделяемых реестров в `boot.ts` нет ни одного, и `BuiltinPluginsOptions` потеряли все три поля. Правильность больше не держится на «это обязан быть тот же объект»: общим стало ХРАНИЛИЩЕ в реестре служб, а виды на него (`viewStatesOver`) состояния не держат и создаются сколько угодно раз.

Отступления и добавления названы:

- **`ViewStateStore` из `ui/contributions/editors` НЕ использовано как хранилище** — заведено платформенное `workspace/model/editor-view-states` с тем же составным ключом. Причина: это разные половины одной задачи. `ViewStateStore` снимает состояние у редактора в момент переключения вкладки (`capture`) и живёт в `EditorArea` через `useMemo`; новое хранилище принимает написанное редактором ЗАРАНЕЕ — потому что `capture` зовётся, когда тело уже размонтировано. Слить их значило бы спрашивать состояние у мёртвого экземпляра Monaco.
- **Реестр свёрнутых веток редактора схемы (`CollapseRegistry`) оставлен как есть.** Он не разделяемый: пишет и читает его один плагин. Фаза про РАЗДЕЛЯЕМОЕ состояние, и перевод частного хранилища был бы дифом без дефекта.
- **Идентификаторы прежние** (`shell.documents`, `shell.textEditorFocus`, `shell.editorViewStates`, `kits.active`), а не имена RFC: смена `id` службы — миграция сохранённых ключей и чужих манифестов, фаза 7.
- **Добавлено сверх плана: часть состава `builder.host`.** Возможности, у которых провайдер — сама оболочка, объявляет `platform/services/host-capabilities`, и состав подставляет их в резолвер наравне с плагинами. Без этого внешний плагин с `requires: shell.documents@^1` получал бы отказ «никто не предоставляет» у службы, заведённой ровно для него. Проверки `provides-unregistered` у оболочки нет (нет `activate`), поэтому совпадение объявленного с зарегистрированным стережёт приёмка на настоящем запуске.
- **Добавлено: `DocumentsService.openDocuments()` и `parentOf()`.** Правило жизни состояний превью переехало в плагин, и ему нужны «что открыто» и «чей это каталог». Разбирать адрес плагину по-прежнему нельзя — он спрашивает службу; `parentOf` в рабочей области предусмотрен планом фазы 5 (порт кодогена).
- **Долги фазы 3 закрыты оба.** `provides` встроенного плагина доезжает до рантайма (`register(plugin, provides)` парой, как у плагина каталога), поэтому проверка обещанного распространилась и на встроенных. Выбор провайдера стал полем профиля `providers` со склейкой по `extends`; бессмысленный выбор (назван тот, кто возможности не объявляет) отвергается сборкой состава. Оговорка: КОНФЛИКТА двух провайдеров во встроенном составе сегодня нет, поэтому применение выбора проверено на уровне резолвера, а не сквозным тестом.

Приёмка: внешний плагин каталога с требованием к возможности ОБОЛОЧКИ включается, с несовпавшей версией — нет и называет `builder.host` (`integration/capability-requires`); на настоящем запуске плагин находит каждую объявленную возможность оболочки, в том числе на коротком профиле (`integration/host-capabilities`). Состав чанков сборки не изменился.

**Сделано 2026‑09‑12, кроме двух шагов, отложенных по существу.** Фаза разбита по корзинам, а не по плагинам целиком: сначала общее (локализация, рабочая область), потом плагины по одному.

- **Предусловие, которого в плане не было: `ctx.i18n`.** Корзина «локализация → i18n‑служба» оказалась невыполнимой: службы локализации в SDK не было ВООБЩЕ, и каждый порт вёз свой `useTranslate` с одинаковым телом, а словари плагинам раздавала композиция видами `forPlugin(id)`. Теперь словарь — поле контекста (`PluginContext.i18n`), реактивный перевод — `useTranslate` из `@/sdk`, и то и другое доступно внешнему плагину каталога. Приёмка: внешний плагин отдаёт словарь СВОИМ КОДОМ, и строка находится в его пространстве имён (`integration/external-editor-plugin`).
- **Словари уехали из композиции у ВСЕХ десяти**: `BuiltinPluginsOptions.i18n` больше нет, как и полей `i18n`/`translate` в опциях плагинов. Заодно исчез `resolveMessageSink` — структурный поиск приёмника, заведённый ровно на время отсутствия поля.
- **Шаг 1 (kits)** был закрыт фазой 3: `provides` объявлен картой состава.
- **Шаг 2 (validator-schema)**: каталог кита приходит возможностью `kits.active` из реестра служб, а не параметром. Требование объявлено НЕобязательным — без кита валидатор проверяет структуру и молчит о компонентах, и это названная деградация, а не молчаливый `?? []`. Опций у плагина не осталось вовсе.
- **Добавлено: `requires` в карте состава.** Резолвер умел читать требования с самого начала (фаза 3), но объявлять их встроенным было негде.
- **Шаг 3 (codegen)**: порт из 27 членов сузился до ОДНОГО. Рабочую область плагин собирает сам (`plugins/codegen/workspace`) из четырёх служб контекста — документы, записи рабочей области, активный кит, словарь, — и композиции остаётся `save`.
- **Шаг 4 (templates)**: порт из 25 членов сузился до одного — сохранения. Печатник встроенных шаблонов стал возможностью `codegen.modules`, которую объявляет генерация кода: переходник из `boot` исчез вместе с динамическим импортом кодогена МИМО состава. Теперь «нет генерации — нет встроенных шаблонов» это названная деградация (`requires.optional`), а не тихое исключение из правил.
- **Шаг 5 (ai)**: порт закрыт ЦЕЛИКОМ — названных дыр не осталось ни одной. Пометка происхождения (`origin: 'agent'`) проходит до рабочей области, и её шов переехал из теста композиции в тест сборщика: компилятор потерю третьего аргумента не ловит.
- **Шаги 7–9 (редакторы)**: тело текстового редактора стало возможностью `editor.text`, которую объявляет плагин Monaco. Переходник из `boot` исчез, и вместе с ним — вторая копия вклада: композиция собирала свой вклад для соседей, плагин вносил свой в точку редакторов, и `Body` у них были РАЗНЫМИ функциями. Теперь тело одно на всех. Markdown и редактор схемы спрашивают провайдера в момент вопроса, поэтому выключение Monaco на ходу убирает режимы «рядом» и «исходник», а не оставляет пустую половину экрана.
- **НЕ СДЕЛАНЫ и почему: шаг 6 (files) и шаг 10 (plugin-manager).** Оба порта — привилегированные поверхности, и перевод их в возможности означал бы раздать КАЖДОМУ плагину каталога то, чего он получать не должен: у файлов это открытие каталога проекта, удаление, переименование и сохранение наружу; у управления плагинами — включение и выключение чужого исполняемого кода, то есть саму границу доверия. Шапка `plugins/plugin-manager/host` говорит это прямым текстом: «каталога плагинов в @/sdk нет и не будет». Это тот же довод, по которому `save` не отдан ни одной службе, и упирается он в одно и то же: политики прав плагинов не существует. Она появляется в фазе 9 (установка из npm), и до неё оба порта остаются портами. В фазе 5 это надо считать выполненным решением, а не невыполненной работой.

Итог по критериям фазы: `BuiltinPluginsOptions` пуст НЕ ПОЛНОСТЬЮ и каталог `shell/boot/ports/` не удалён — там остались привилегированные порты (files, plugin-manager), сохранение и три названные дыры. Остальные семь плагинов свои порты закрыли.

Открытый вопрос к шагу 3 решён, и не так, как написано в плане. План отправлял `save`/`list`/`exists` кодогена в `reformer.workspace`, но служба документов такой двери не имеет НАМЕРЕННО. Разделено по ПРАВАМ — на две возможности плюс одну названную дыру:

- `shell.documents` — что ОТКРЫТО: вкладки, текст, запись в рабочую копию, открытие вкладки. Единственная дверь записи, и пометка происхождения живёт у неё.
- `shell.workspaceFiles` (новая) — что ЛЕЖИТ и где: существование, один уровень каталога, чтение текста, путевая арифметика, право источника на запись. Ни записи, ни сохранения здесь нет.
- `save` не отдан НИКОМУ и остался у композиции: он один выносит написанное наружу, и без политики прав плагинов отдавать его службой нельзя. Когда права появятся (фаза 9), это место станет их первым потребителем.

Заодно путевая арифметика собралась в одну семью: `parentOf` уехал из службы документов к соседке вместе со своим тестом.

### Фаза 6. Публичный API `@reformer/builder-plugin-api`

1. Пакет в `packages/reformer-builder-plugin-api`: содержимое = сегодняшний `sdk/index.ts` + capabilities + типы манифеста. Билдер импортирует его как workspace‑пакет; линкер сажает тот же объект в слот `@builder/sdk` **и** `@reformer/builder-plugin-api` (переходный период).
2. Версия API независима от версии билдера; `apiVersion` манифеста и `compatibility.builder` проверяются semver.
3. Линтер: `src/plugins/**` импортируют только пакет, `@/lib` и свой каталог. Правило «плоский список, цена платформы видна в одном diff» переносится в шапку пакета.
4. Документация пакета: контракт редактора (фокус, `flush`, стабильное тело), контракт поверхности превью (токены хит‑теста `rbnode-*`, `keepValues`, `publishForm`, `report`), контракт словарей.

Объём: ~1.5 недели.

**Сделано 2026‑09‑13.** Пакет `packages/reformer-builder-plugin-api` опубликован в цепочке выпуска (сборка и тесты в CI до билдера, `.releaserc.json`, scope commitlint). Содержимое — ровно прежний `sdk/index.ts` (145 имён, набор сверен при переезде), плюс типы манифеста входом `./internal`. Переезд шёл слоями, и у каждого слоя граница одна: плагину — объявление, оболочке — решение. Модуль со смешанным содержимым разрезался по ИМЕНАМ (интерфейс и токен — в пакет, `create*` — в оболочку), и разрезано так больше тридцати модулей.

- **`src/sdk` удалён, а не оставлен реэкспортом.** Когда наборы имён сошлись один в один, файл-посредник перестал что-либо значить, кроме второго адреса одной вещи. Тело публичного входа пакета взято из него вместе с доводами; встроенные плагины импортируют пакет, линтер запрещает им `@/shell` и `./internal` (проверено пробником через stdin).
- **Два входа.** `.` — поверхность плагина, курированный плоский список; `./internal` — примитивы целиком, для оболочки. Без второго входа пришлось бы либо втащить в контракт путевую арифметику и помощники оболочки, либо разлучить `ResourceId` с его конструктором.
- **Билдер резолвит пакет в ИСХОДНИКИ** (`paths` и alias в трёх конфигах), а не в dist: пакет менялся вместе с билдером, и сборка между правкой и проверкой означала бы компиляцию против вчерашнего контракта. Публикуемый dist проверяется собственной сборкой пакета.
- **Слот линковщика** занят одним объектом под двумя именами — `@builder/sdk` и `@reformer/builder-plugin-api`; проверено тестом и мутацией.
- **Попутные находки.** Кэш разобранных условий команд делили разбор и реестр — вынесена функция, кладущая в кэш готовое, сам `WeakMap` остался тайной модуля. React объявлен обязательной peer-зависимостью: декларации ссылаются на тип компонента безусловно (сначала был объявлен необязательным — поймал knip).

**Не сделано и почему.**

- **Пункт 2, `compatibility.builder`** — поле не заведено. Проверять его нечем: версии приложения в рантайме у билдера нет, а поле, которое ничего не принуждает, это ровно тот случай, по которому в манифесте нет `permissions`. Совместимость контракта уже проверяет `apiVersion`. Вернуться, когда у оболочки появится своя версия (кандидат — CLI `validate` в фазе 8).
- **Пункт 4, контракт поверхности превью** описан в README пакета, но сами типы (`PreviewContext`, точка `preview.surface`) в пакет НЕ вынесены: их объявляет плагин превью, и пока поверхности вносит только он, вынос был бы «на будущее». Переедут вместе со вторым поставщиком поверхностей.
- **knip** показывает четыре дубликата экспорта вида `DocumentsCapability|DocumentsServiceToken` — намеренные псевдонимы одного объекта; раньше они жили в `projects/*`, который knip не анализирует. В CI knip не запускается.

### Фаза 7. Манифесты у встроенных, пространство имён идентификаторов

1. `manifest.json` у каждого встроенного плагина; `definePlugin` читает `id/version/provides/requires` из него (импорт JSON статический, это лист). Каталог встроенных = `PluginSource{kind:'builtin'}`.
2. Идентификаторы: перейти на `reformer.<id>` **с миграцией**: таблица `legacyId → id`, применяемая к ключам настроек (`workspace.plugin.*`, `workspace.plugins.enabled/dev`), хранилищу плагина, снимкам вида. Миграция однократная при `hydrate`, с тестом на старую запись.
3. Статический/ленивый раскол сохраняется полем манифеста `builtin.loading: 'eager' | 'lazy'`; причины пятерых eager переносятся в их манифесты.

Объём: ~1.5 недели. Риск: потеря пользовательских настроек при ошибке миграции — тест на фикстуре старой базы обязателен.

**Сделано 2026‑09‑12. Миграции нет — её предмет не нашёлся; подробности ниже.**

- **Манифест у каждого из одиннадцати** (`plugins/<каталог>/manifest.json`) — тем же форматом
  и через ТОТ ЖЕ разбор, что манифест плагина каталога проекта (`parsePluginManifestValue`).
  Своя, облегчённая проверка сделала бы из «одного контракта» два похожих, поэтому разбор
  получил не вторую ветку, а параметр «откуда плагин» (`PluginSource`), и различаются поставки
  ровно двумя вещами: у встроенного нет каталога (нечему совпадать с `id`) и нет точки входа
  (код уже в бандле), зато есть способ доставки. Лишнее поле ОТВЕРГАЕТСЯ: `main` у встроенного
  означал бы файл, которого никто не грузит.
- **Объявлений в карте состава не осталось ни одного**: `provides`, `requires`, имя и способ
  доставки читаются из манифеста, в записи остались фабрика и литерал `import()`. Манифест
  приезжает статическим импортом JSON — это лист, кода плагина за ним нет, поэтому объявление
  ленивого читается, не загружая его файла.
- **`builtin.loading` с причинами** (шаг 3): у `eager` разбор ТРЕБУЕТ `builtin.reason`, у `lazy`
  запрещает. Ленивость — умолчание, объяснять надо отступление от него. Синхронность фабрики
  и слово в манифесте сверяют конструкторы записей: компилятор их связать не может, `loading`
  приезжает строкой.
- **Довод Monaco оказался протухшим.** В карте было написано «`boot` синхронно вычисляет тело
  редактора и раздаёт одну ссылку троим» — это снято фазой 5, тело стало возможностью.
  Настоящая причина его статичности другой формы: порт композиции берёт у плагина
  идентификатор значением, и барель и так в стартовом графе. Так и записано в манифесте;
  ReFormer-29kx.14 — вынести идентификатор в `contract.ts` и замерить ленивость. У `files`
  и `preview` довод той же формы.
- **Объявлено то, что было зарегистрировано молча**: `reformer.editor` у Monaco (фаза 5 её
  ввела, но в карту не записала), необязательные требования редакторов markdown и схемы на неё,
  необязательный кит у ассистента и генерации.
- **Идентификаторы плагинов** переехали в `reformer.<id>` вместе со службами (коммит c8b9b1c8);
  `definePlugin` получает `id` из манифеста — каждый плагин импортирует свой `manifest.json`.

**Починен храповик, сломанный переименованием.** Проверка «стартовый граф не импортирует барель
ленивого плагина значением» строила шаблон `@/plugins/<id>` из идентификатора, а после
переименования идентификатор перестал быть именем каталога: шаблон не совпадал ни с чем,
и проверка молча проходила всегда. Теперь каталог выводится `builtinPluginDirectory`, а сама
проверка проверена мутацией — подложенный импорт бареля ассистента её роняет.

**Миграции сохранённых ключей нет, потому что мигрировать нечего.** План требовал таблицу
`legacyId → id` для ключей настроек, хранилища плагина и снимков вида; проверены все четыре
поверхности, и ни одна не хранит имя встроенного плагина: `ctx.storage` работает поверх
`createMemoryStorageBackend` (переживает вкладку, но не перезагрузку), `workspace.plugin.<id>.settings`
и списки `workspace.plugins.enabled`/`.dev` относятся к плагинам КАТАЛОГА (их имена не менялись),
поле `viewState` в записи открытой вкладки не пишется вовсе, а идентификаторы панелей, команд
и редакторов — собственные строки, а не производные от имени плагина. Единственная внешняя
поверхность, где имя пишет человек, — поправки состава в `.ui_builder/config.json`; для них
заведена таблица псевдонимов, выводимая из карты состава снятием префикса, и два теста:
прежнее имя работает, опечатка по-прежнему отвергается.

**Ключи настроек в пространство имён НЕ вошли** и остались `host.*`. Совпадение прежних строк
у темы и раскладки (`host.theme` было и токеном службы, и ключом настройки) было случайным:
токен адресует реализацию в реестре, ключ — запись в хранилище человека и стоит в ряду
с `host.locale` и `host.shell.*`. Переименуй мы второе заодно с первым — получили бы ровно ту
миграцию пользовательских настроек, которой фаза опасалась, ради симметрии.

**Не сделано из шага 1: «каталог встроенных = `PluginSource{kind:'builtin'}`» сделано наполовину.**
Тип есть, у каждого встроенного манифеста `source.kind === 'builtin'`, и список отдаётся
`BUILTIN_MANIFESTS`. Чего нет — показа встроенных в панели управления плагинами: строке нужен
признак управляемости, потому что `enable`/`disable`/`reload` у встроенного не работают (состав
собирается при запуске и на ходу не пересобирается), а предлагать неработающие действия хуже,
чем не показывать. Это ReFormer-29kx.15, и упирается оно в ту же политику прав, что ReFormer-29kx.13.

### Фаза 8. CLI `reformer-plugin`

`create` (шаблон: манифест, `main.ts`, `locales/`, тест), `dev` (сборка в `.ui_builder/plugins/development/<id>/` + пометка «в разработке» уже перезагружает плагин по сохранению), `build` (один `main.js` + `styles.css`, externals из списка линкера), `validate` (манифест, semver, `provides` против экспортов), `pack`.

Объём: ~2 недели. Может идти параллельно с Ф9.

**Сделано 2026‑09‑17: все пять команд.**

- **Общее — в контракт раньше CLI (8.1).** Разбор манифеста, список модулей рантайма
  (`PLUGIN_RUNTIME_MODULES`, билдер тестом сверяет с ним свой реестр) и нормализация пути модуля
  переехали из оболочки в `@reformer/builder-plugin-api`, вход `./tooling`. Туда же (8.2) —
  раскладка каталога (`PLUGIN_CATALOG_DIR`, `PLUGIN_FILE_LIMIT`, `isPluginCodeFile`) и разбор
  словаря: загрузчик оболочки и валидатор отказывают по одному коду.
- **Стадия «исходники» — отдельной функцией, а не третьей поставкой** (`parsePluginSourceManifest`).
  Оболочка манифест исходников не видит, и вариант `PluginSource`, который каждый её `switch`
  разбирал бы ради невозможного случая, был бы ложью в типе. Отличий от поставки `project` два:
  имя каталога с `id` не сверяется, `version` обязательна. Сверка с каталогом вернётся на выходе
  `build`: собранный каталог проверяется разбором `project` целиком.
- **Пакет `@reformer/builder-plugin-cli`, бинарь `reformer-plugin`** (Node, `tsc`, без зависимостей
  кроме контракта). `create` кладёт шаблон, который сразу проходит `validate` и разбор `project`
  (оба — тестами). `validate` своих правил почти не имеет: манифест, точка входа, стили и словари —
  правилами оболочки; своё одно — версия `package.json` против манифеста.
- **`build` (8.3)** — esbuild в один `main.js` формата CommonJS (линковщик исполняет CommonJS,
  готовый JS идёт без транспиляции). Модули рантайма внешние ровно по списку контракта; `@reformer/*`
  вне списка и CSS из кода — отказы. Выход проверяется разбором поставки `project`, потолком файлов
  и **«сухой» активацией**: `main.js` исполняется под Node с настоящим пакетом контракта (токены
  служб — объекты с `id`) и заглушками остального, реестр служб записывает регистрации. Так
  ловятся `not-a-plugin`, `id-mismatch` и `provides-unregistered`; падение на заглушке — заметка
  «не проверено», а не отказ. Узнавание плагина в экспортах (`pluginFromExports`) переехало
  в контракт. Сборка грузится настоящим загрузчиком оболочки — проверено разово на выходе CLI.
- **`dev` — не в `plugins/development/<id>/`, как было задумано, а в `plugins/<id>/`.** Загрузчик
  считает плагином каждый подкаталог каталога плагинов, и `development/` стал бы плагином
  `development`. Перезагрузку делает оболочка (пометка «в разработке», возврат фокуса) — канал
  между CLI и билдером не нужен.
- **`pack`** — сборка во временный каталог плюс `package.json` с ключевым словом
  `reformer-builder-plugin`, архив делает `npm pack`. Формат рассчитан на установку из npm (Ф9).
- **Найдено по пути:** `.d.ts` контракта импортируют соседей без расширения, и при `NodeNext` типы
  молча становятся `any` (ReFormer-29kx.18). CLI и шаблон плагина используют резолюцию `bundler`.

### Фаза 9. Установка из npm в браузере

Сначала решение по хранилищу (см. 1.2 п.9): предлагается **OPFS‑слой `installed/` рабочей области** (как кэш сборки) с записью в `.ui_builder/plugins/installed/` источника только когда `source.capabilities.write === true` и человек это подтвердил; в `state/installed.json` — id, package, exact version, integrity, source, trust, enabled.

Шаги: `NpmRegistryClient` (метаданные + tarball, CORS), gzip через `DecompressionStream`, tar‑парсер (свой, ~200 строк, с тестами на фикстурах), `crypto.subtle` sha512 против `integrity`, распаковка в `PluginArtifactStore`, валидация манифеста и резолвер (Ф3) до включения, side‑by‑side версии и откат. Новый `PluginSource{kind:'installed'}` в тот же каталог.

Объём: ~3 недели. Риск: браузерные ограничения на размер и CORS у зеркал npm.

1. Ф0 целиком: внешний плагин может быть редактором и поверхностью превью, с переводами и стилями.

### 2.3. Открытые вопросы, требующие решения владельца
