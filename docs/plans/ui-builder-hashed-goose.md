# Идея №12 — сменный источник файлов

> Черновик раздела для вклейки в `projects/reformer-builder-v2/docs/ui-builder-hashed-goose.md`.
> Плановый режим позволяет править только этот файл; после утверждения раздел переедет в брейншторм.

## Формулировка

Сегодня исходник формы попадает в билдер ровно одним способом — File System Access API.
Идея: сделать источник сменным. Помимо локального диска — FTP, либо отдельный сервер хранения
форм, у которого можно запросить список форм и конкретную форму.

## Что выяснилось по коду

### 1. Порт уже существует — и уже реализован трижды

`src/io/fs-ops.ts` написан не против `showDirectoryPicker`, а против **структурных типов**
`FsDirHandle`/`FsFileHandle` (:11-33). Благодаря этому:

- `src/io/opfs.ts:11-14` прямым текстом фиксирует, что весь path-слой (`createFile`,
  `listFilesDeep`, `readTextFile`, `deletePath`, `existsIn`) исполняется **над OPFS без единой
  правки**;
- в тестах живёт третья реализация того же контракта — `src/io/__fixtures__/fake-fs.ts:44-68`
  (`getFileHandle`/`getDirectoryHandle`/`removeEntry`/`values`/`createWritable`), используемая
  в `io/template-fs.test.ts`, `io/save-sources.test.ts`, `app/template-actions.test.ts`.

То есть абстракция уже есть, просто она не названа и не вынесена. Минимальный набор, который
обязан реализовать источник, — шесть методов: `values`, `getFileHandle(create?)`,
`getDirectoryHandle(create?)`, `removeEntry(recursive?)`, `getFile`, `createWritable`;
плюс опциональные `move` и `queryPermission`/`requestPermission`.

**Но резать порт надо не по handle.** Handle-форма требует пошагового обхода
(`resolveDir`, `fs-ops.ts:38-44` — `getDirectoryHandle` на каждый сегмент), то есть N round-trip'ов
на одну операцию по сети. При этом **публичная поверхность `fs-ops` уже path-образная**:
`createFileDeep(root, path)`, `readTextFile(root, path)`, `listFilesDeep(root, dir)`,
`deletePath(root, path)`, `existsIn(root, path)`. Обход по сегментам — деталь реализации.

Отсюда рекомендация: **портом становится сегодняшняя публичная сигнатура `io/fs-ops.ts`**,
где `root: Root` заменяется на `source: FileSource`. Локальный адаптер сохраняет нынешние
внутренности с обходом handle дословно; удалённый адаптер работает путями напрямую, один запрос
на операцию.

### 2. Поправка к прошлому разделу: рабочая копия изолирует НЕ всё

В разделе про OPFS сказано, что зеркало отвязывает всё нижележащее от источника. Проверка
показала, что это верно **только для живого превью, компиляции и редактора трёх схем** — они
адресуются по `tab.id` и о диске не знают (`preview-runtime/live/sibling-sources.ts:43-56`,
`canvas/FormSourceEditor.tsx`, `canvas/revert-to-rules.ts`).

Мимо рабочей копии к источнику ходят девять мест, и это не мелочи:

| # | Что | Где |
| --- | --- | --- |
| 1 | Сама схема формы — читается и пишется через `tab.source.handle` напрямую | `io/save.ts:37,49-52` |
| 2 | Code-вкладки Monaco: произвольный файл правится прямо на диске, без diff и без детекта конфликта | `app/save-actions.ts:253-270,359-371` |
| 3 | Write-back схем формы | `io/save-sources.ts:62,84` |
| 4 | Картинки markdown-предпросмотра | `canvas/markdown/assets.ts:43,47` |
| 5 | Переход по относительной ссылке из markdown | `app/save-actions.ts:344-352` |
| 6 | Все операции дерева: create/paste/mkdir/delete/rename/generate | `app/save-actions.ts:410-550` |
| 7 | Шаблоны | `io/template-repo.ts`, `app/template-actions.ts` |
| 8 | Экспорт примера — **свой собственный `showDirectoryPicker`**, корень вообще другой | `codegen/deliver.ts:54,86` |
| 9 | Корпус знаний агента: `node_modules` читается сырыми методами handle мимо `io/fs-ops` | `agent/knowledge/project-source.ts:43,53-54` |

Значит объём контракта задают панель файлов, code-вкладки и шаблоны, а не рабочая копия.
Четыре точки придётся переписывать явно, потому что они минуют `fs-ops`: `io/fs-access.ts`
(пикер, разрешения, `readPrettierConfigs`), `io/discovery.ts:155,182`,
`agent/knowledge/project-source.ts`, `codegen/deliver.ts`.

Хорошая новость: `agent/core/tools/*` — все 20 файлов — файловых операций не делают вовсе.
Агент правит схему в памяти, его это не касается.

### 3. Браузер не умеет FTP

`ftp://` удалён из Chrome в 2021 году; из вкладки к FTP-серверу подключиться нельзя в принципе.
Практически «источник FTP» означает **HTTP-шлюз к FTP** — либо отдельный сервер пользователя,
либо `@reformer/devhost` из RFC-0001. То есть проектировать надо **HTTP-контракт источника**,
а FTP/S3/WebDAV живут за шлюзом и билдера не касаются.

Это меняет формулировку задачи, но не её суть: сменный источник остаётся, просто его транспорт
всегда HTTP(S).

### 4. Острый край: удалённые данные — можно, удалённый код — нет, а `.ts` формы это код

RFC-0001, принцип **P4** (`:435`) дословно: *«Рантайм никогда не скачивает и не выполняет код
из сети»*. Формулировка про **выполнение кода**; удалённые **данные** он не запрещает — и сам RFC
перечисляет `http-client`, `figma-import`, `openapi-import` среди кандидатов в плагины (:983).

Но у формы ReFormer сайдкары — это `validation.ts`, `form.behavior.ts` и прочий **исполняемый
код**, который live-превью транспилирует и линкует через `new Function` в том же realm, где живут
FS-хендлы проекта и API-ключ AI-провайдера (`preview-runtime/live/link.ts:9-12,28-41`).

Сегодня этот код приходит с диска пользователя — уровень доверия «`npm run dev`». С удалённым
источником он приходит с сервера. **Это ровно исполнение удалённого кода, приехавшего под видом
данных**, и на это нужен явный ответ, а не умолчание.

Готовый образец решения есть в репозитории: `@reformer/form-registry` кодирует границу
**в типах** — `DataSource<T>` умеет `inline | module | http`, а `CodeSource<T>` варианта `http`
**не имеет по типу** (`packages/reformer-form-registry/src/types.ts:28-42`,
`src/loader.ts:139-151`). Не проверка в рантайме, а невыразимость.

### 5. Ловушки производительности, которые надо спроектировать заранее

Локально они незаметны, по сети — фатальны:

| Что | Сейчас | По сети |
| --- | --- | --- |
| `existsIn` (`fs-ops.ts:252-272`) | **два** запроса на одну проверку (сначала файл, потом каталог) | ×2 round-trip на каждую проверку |
| `uniqueName` (`fs-ops.ts:275-285`) | **до 1000 последовательных** `exists` | шторм запросов; лечится одним `list(dir)` и подсчётом в памяти — это улучшение и для локального случая |
| `discovery.scanLevel` (`:155,178-193`) | list уровня, затем `Promise.all` чтения **каждого** `.json`-кандидата | N+1 на каждый каталог |
| `readPrettierConfigs` (`fs-access.ts:75-104`) | 9 проверок в корне | 9 GET на открытие проекта |

Ответ на третью строку — не оптимизация обхода, а **capability**: если источник умеет отдать
список форм сам, обход не нужен вовсе. Классификация при этом остаётся чистой
(`classifyFormSchema`, `discovery.ts:40-47` — тестируется отдельно), её можно просто не вызывать,
заполняя `isForm`/`confidence` из ответа сервера.

### 6. Детект конфликта уже обобщается почти бесплатно

`io/save.ts:39` сравнивает `lastModified !== tab.source.lastModified` — **на неравенство,
а не «новее»**. Семантика уже сейчас «версия изменилась», поэтому любой непрозрачный токен
(ETag, rev, hash) подставляется без изменения логики; менять надо только тип
`number` → `string | number` (`store/types.ts:86`).

Источник без версий деградирует мягко: флаг `conflict` навсегда `false`, но diff всё равно
строится из свежепрочитанного текста, так что расхождение пользователь увидит. Плюс готовый
образец сравнения **по содержимому** вместо mtime уже есть — `io/save-sources.ts:67`.

Попутно: `TreeEntry.lastModified` (`discovery.ts:127,187`) пишется, но не читается никем —
мёртвое поле. `isSameEntry` не используется нигде. `clearDirHandle` и `sweepWorkdirsOnBoot`
экспортируются, но не вызываются.

### 7. Переоткрытие и учётные данные — один и тот же шов

`io/handle-store.ts` держится на том, что `FileSystemDirectoryHandle` structured-cloneable.
Для удалённого источника это заменяется **сериализуемым дескриптором** плюс реестром
«вид источника → фабрика адаптера»:

```ts
type SourceDescriptor =
  | { kind: 'fs' }                                   // handle по-прежнему в IndexedDB
  | { kind: 'http'; baseUrl: string; credentialsRef?: string };
```

`ensurePermission` (`fs-access.ts:49-57`) при отсутствии `queryPermission`/`requestPermission`
возвращает `false`, и переоткрытие отменяется (`save-actions.ts:176-178`). Значит источник без
модели разрешений с текущим кодом **не переоткроется** — правка на одну строку, но обязательная.
И место это не случайное: у HTTP-источника ровно там окажется аутентификация.

**Учётные данные не должны лечь в `localStorage` рядом с ключом AI-провайдера**
(`agent/keys.ts:92`) — эту ошибку в проекте уже один раз обсуждали как риск плагинной системы.
Варианты — в открытых вопросах.

### 8. Побочная выгода: лечится болезнь Mode A

Режим без проекта сегодня — это **не абстракция, а второй `if` в каждом месте**: около десяти
одинаковых `const root = projectRoot(); if (!root) { toast('Проект не открыт'); return; }`
(`save-actions.ts:411,438,463,478,498,537`, `template-actions.ts:81,136,206,227`), плюс ветки
в `workdir-actions.ts:41`, `templates-store.ts:40`, `markdown/assets.ts:45`,
`agent/knowledge/index.ts:53`, `FilesPanel.tsx:548`.

Ни один из них не выражен типом. Источник с объявленными возможностями схлопывает их в проверку
capability — то есть сменный источник платит не только за FTP, но и за уборку уже существующего
дублирования.

## Набросок контракта

Один порт с объявленными возможностями, а не два разных понятия — иначе «файловый источник»
и «источник форм» разведут код на две ветки в каждой точке, ровно как это уже случилось с Mode A.
Сервер форм, умеющий только список и получение, — это источник, у которого выключено почти всё.

```ts
interface FileSource {
  readonly descriptor: SourceDescriptor;      // сериализуемый, для переоткрытия
  readonly capabilities: SourceCapabilities;

  // обязательное
  read(path: string): Promise<{ text: string; revision?: string | number }>;
  list(dir: string): Promise<Entry[]>;        // один уровень, один запрос
  stat(path: string): Promise<Stat | null>;   // заменяет двойной existsIn

  // по capabilities
  write?(path: string, text: string, expected?: string | number): Promise<Written>;
  mkdir?(path: string): Promise<void>;
  remove?(path: string): Promise<void>;
  move?(from: string, to: string): Promise<void>;
  listForms?(): Promise<FormRef[]>;           // отменяет обход дерева целиком
  watch?(glob: string, cb: (path: string) => void): Disposable;
}

interface SourceCapabilities {
  write: boolean;
  tree: boolean;          // есть ли вообще каталоги, или это плоский список форм
  revisions: boolean;     // умеет ли детект конфликта
  executesCode: boolean;  // можно ли компилировать и исполнять сайдкары этого источника
  auth: 'none' | 'session' | 'persistent';
}
```

`executesCode` — не удобство, а граница из пункта 4: она решает, доступно ли для этого источника
live-превью, и должна быть выражена так же жёстко, как в `form-registry` (невыразимо по типу,
а не «проверим в рантайме»).

## Ограничения, которые остаются в силе

- **P1 «runtime-optional»** (RFC-0001 `:432`): статическая SPA на GH Pages обязана работать без
  какого-либо сервера. Значит FS-адаптер встроен и выбирается по умолчанию, удалённые —
  опциональны и настраиваются. Прецедент такой деградации в проекте уже двойной:
  `config/load.ts:95` (нет launcher'а → дефолты) и `storage/index.ts:66` (нет OPFS/IDB → память).
- **Плагинов не грузим** (решение по идее №10): адаптеры источников — встроенные контрибуции
  и/или конфигурация, а не сторонний код. Иначе «сменный источник» станет чёрным ходом для того,
  что уже решили не делать.

## Открытые вопросы

1. Форма контракта: один порт с capabilities или два понятия (файловый источник / источник форм).
2. Первая цель: сервер форм только на чтение (список + получение) или полноценный round-trip
   с записью.
3. Live-превью для удалённого источника: запрещать, требовать явного подтверждения доверия
   к источнику, или разрешать только схему без исполняемых сайдкаров.
4. Где живут учётные данные удалённого источника — только в памяти сессии (перезапрос каждый раз),
   в отдельном хранилище, или пользователь сам держит шлюз без аутентификации.
5. Общий ли это порт с `@reformer/form-registry` или отдельный — вопрос, уже поднятый
   и не решённый в `dynamic-form-branches.md:635-639`.
