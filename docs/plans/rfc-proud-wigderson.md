## Context

Пользователь просит добавить **ещё один RFC** в `projects/reformer-builder/docs/rfcs/` (там сейчас ровно один документ — [0001-local-development-runtime.md](../../projects/reformer-builder/docs/rfcs/0001-local-development-runtime.md)). Тема: чат с ИИ в билдере, поддержка стандарта **WebMCP**, «чат должен быть возможен с любым агентом», четыре сценария:

1. создание и редактирование схем через чат + голосовой ввод;
2. создание формы из постановки, переданной файлом;
3. создание формы из картинки / макета графического редактора;
4. справка по возможностям редактора и подсказкам.

**Зачем это нужно.** Билдер сегодня не имеет ни одного AI-канала: в `projects/reformer-builder/src/` ноль упоминаний `mcp`/`llm`/`ai`/`chat`. Существующий `@reformer/mcp` — stdio-сервер, браузер его вызвать не может; это ограничение **L7** уже зафиксировано в RFC-0001. Брейншторм билдера отложил AI на «v2+». RFC-0002 закрывает этот пробел документом того же жанра, что и RFC-0001: архитектурное исследование со статусом «предложение».

**Решения, согласованные с пользователем** (влияют на рекомендацию RFC):

| Развилка | Решение |
| --- | --- |
| Связь с RFC-0001 | **Независим**; `@reformer/devhost` — опциональный провайдер, а не предпосылка. Принцип **P1 runtime-optional** соблюдается. |
| Каналы модели в первой фазе | **Все три**: BYO-ключ пользователя, локальный агент через рантайм, встроенный ИИ браузера. |
| Хостед-сборка (GitHub Pages) | Чат **обязан** работать и там ⇒ нужен канал без локального процесса. |

## Ключевая мысль документа

Запрос смешивает **два ортогональных направления**, и это — центральный тезис RFC:

- **Inbound («чат»)** — билдеру нужна *модель*. Билдер выступает LLM-клиентом / MCP-хостом. Решается **слоем провайдеров**, а не WebMCP.
- **Outbound («поддержать WebMCP»)** — билдер *публикует свои возможности как инструменты*, чтобы им управлял внешний агент. Билдер выступает сервером. **Модели это не даёт вообще.**

Общее у них ровно одно — **единая поверхность инструментов редактора**. Её строим один раз и экспонируем через адаптеры. Отсюда рекомендуемый вариант и весь roadmap.

Следствие для формулировки «чат с любым агентом»: буквально недостижимо; достижимо «провайдер-агностичный чат + возможность вообще не иметь своего чата, когда билдером управляет внешний агент».

## Фактическая база (проверено)

### WebMCP на август 2026

| Факт | Значение для RFC |
| --- | --- |
| W3C Web Machine Learning CG, **Draft Community Group Report**, не standards-track, ~108 открытых issue | Нельзя класть в фундамент |
| API переехал `navigator.modelContext` → **`document.modelContext`** 21.07.2026; в Chrome 150 старое место deprecated. Ранее из черновика удалили `provideContext()`/`clearContext()` | Две ломающие правки за 12 месяцев ⇒ адаптер должен быть удаляемым |
| Chrome: dev trial 18.05.2026, **публичный origin trial Chrome 149–156**; **Edge 147 — нативная поддержка**. Firefox/Safari — нет реализации | Chromium-only, как и Mode B билдера (File System Access API) — новых ограничений по браузерам не вносит |
| Поверхность: `await document.modelContext.registerTool({name, description, inputSchema, execute, annotations:{readOnlyHint, untrustedContentHint}}, {signal, exposedTo})`; `execute` возвращает строку или `{content:[{type:'text',text}]}` | Реестр инструментов ложится 1:1 |
| Бюджеты: имя ≤30 симв., описание инструмента ≤500, описание параметра ≤150, вывод ≤1.5 КБ | Прямое ограничение на дизайн имён и на формат ответа инструментов |
| **Нормативного контракта ошибок нет**; `outputSchema` в спеке отсутствует (есть только в community-типах `@mcp-b/webmcp-types`); `requestUserInteraction` в спеке отсутствует | Подтверждение опасных действий делаем **своим** UI, а не спекой |
| **Локально токен origin trial не нужен**: WebMCP — `[SecureContext]`, `http://127.0.0.1` подходит; включается флагом `chrome://flags/#enable-webmcp-testing` (или `--enable-features=WebMCP`). Флаг **per-profile, не per-origin** — покрывает любой порт | Снимает опасение про port-fallback launcher'а. Цена — пользователь обязан включить флаг |
| Потребителей мало; **рабочий путь для CLI-агента существует**: `chrome-devtools-mcp` по CDP (`--browser-url=http://127.0.0.1:9222`, Chrome 150+ с `--enable-features=WebMCP`, категория `--categoryExperimentalWebmcp`). Исторический MCP-B (расширение + native messaging) — **deprecated** | Есть что конкретно написать в README вместо «когда-нибудь появится Gemini in Chrome» |

### Варианты (§3)

- **V0** — не делать чат; усилить внешний воркфлоу (watch + «перечитать с диска» + `devhost-plugin-mcp`). Честная база сравнения.
- **V1** — только outbound WebMCP, своего чата нет.
- **V2** — только чат на BYO-ключе.
- **V3** — только рантайм-канал (ждать F0–F4 из RFC-0001).
- **V4** — только встроенный ИИ браузера.
- **V5 ⭐** — **единая поверхность инструментов + слой провайдеров + N адаптеров**.
- **V6** — полноценный агентский рантайм внутри билдера (свой оркестратор, RAG, память) — отклонить как выход за скоуп.

### Разрешение противоречия «локальный агент в первой фазе, но devhost ещё нет»

Пользователь требует локальный канал в первой фазе, при этом RFC-0002 не должен блокироваться на RFC-0001. Предлагаемое разрешение, которое войдёт в RFC:

в существующий launcher (уже HTTP-сервер) добавляется **один эндпоинт** `POST /__reformer-builder/ai/stream` (SSE), спавнящий локально установленный CLI-агент. Это не devhost, а ≈150 строк в `bin/reformer-builder.mjs`, включаемые флагом `--enable-ai` (deny-by-default, принцип **P3** из RFC-0001). Когда devhost появится, эндпоинт **мигрирует в сервис `ai`** без изменения браузерного контракта — потому что браузер уже говорит с ним через `AiProvider`. Миграция описывается явно, чтобы решение не выглядело срезанным углом.

### Как внешний CLI-агент реально доберётся до билдера (§7)

Это конкретика, которой в RFC-0001 §6.3 не было (там сказано «плагин `devhost-plugin-mcp` наружу»). Рабочая цепочка на сегодня — **без своего расширения и без своего сервера**:

```
Claude Code / Codex ──stdio──▶ chrome-devtools-mcp ──CDP──▶ Chrome (--enable-features=WebMCP)
                                                              └─▶ вкладка http://127.0.0.1:4321
```

Требуется Chrome 150+, `--categoryExperimentalWebmcp=true`, подключение к уже запущенному браузеру через `--browser-url=http://127.0.0.1:9222`. Исторический путь MCP-B (расширение + native messaging + streamable-HTTP на `127.0.0.1:12306`) — **deprecated**, в RFC упоминается только как отклонённая альтернатива. Это же снимает нужду в `devhost-plugin-mcp` для сценария «агент из терминала правит открытую схему» — конкретное упрощение относительно RFC-0001.

### Roadmap (§12) — черновик

| Фаза | Содержание | Точка остановки |
| --- | --- | --- |
| **F0** | Поверхность инструментов + read-only инструменты + аудит-журнал. **Без всякого AI.** Покрывается юнит-тестами, как `model/`/`store/` сегодня | Поверхность есть, ничего не сломано |
| **F1** | WebMCP-адаптер за флагом, только read-only инструменты | Внешний агент может читать редактор |
| **F2** | Панель чата (RIGHT_PANELS), `AiProvider` + три адаптера, агентский цикл, write-инструменты, строгий режим валидации, транзакции истории | Сценарий 1 работает |
| **F3** | Голосовой ввод + справка (сценарий 4) на локальном индексе `llms.txt` | Сценарии 1 и 4 закрыты |
| **F4** | Файл постановки (сценарий 2) и картинка/макет (сценарий 3), lazy-парсеры | Все четыре сценария закрыты |
| **F5** | Провайдер `devhost` вместо мини-эндпоинта; `devhost-plugin-mcp` наружу; write-инструменты в WebMCP | — |

### Что RFC обязан сказать честно (не сглаживать)

1. WebMCP сегодня — **ставка на будущее**: потребителей практически нет, черновик за год ломали дважды. Адаптер обязан быть удаляемым за один коммит.
2. Три канала модели в первой фазе — **утроенная поверхность отладки**; контракт `AiProvider` фиксируется сразу, чтобы адаптеры были аддитивны, но порядок их появления внутри фазы стоит развести.
3. BYO-ключ в браузере **противоречит** духу RFC-0001 §3.3 («ключи в браузер не передаются никогда»). Это осознанное расхождение, вызванное требованием работать на GitHub Pages, и оно должно быть названо расхождением, а не замаскировано.
4. Существующий гейт валидации **не годится** как гейт для AI-выхода в текущем виде (L3).
5. Chrome Prompt API **не умеет tool-calling и не поддерживает русский** ⇒ как канал для агентских правок схемы в русскоязычном продукте он не работает. Пользователь выбрал его в число обязательных каналов первой фазы **до** того, как это выяснилось; RFC обязан вынести это на поверхность и предложить ему реальную роль (офлайновая подсказка на английском, классификация, извлечение полей) вместо роли канала чата.
6. Локально WebMCP требует включённого флага браузера, а origin trial истекает на Chrome 156 (L11) — сценарий «просто работает» не достигается ни в одном режиме.
7. Модель, генерирующая `JsonFormSchema` вслепую, галлюцинирует имена компонентов и `$model`-пути — отсюда дайджест каталога, строгая валидация и запрет автозаписи.
8. У части BYO-провайдеров прямой вызов из браузера упирается в CORS (Gemini — падает preflight официального SDK; OpenAI — противоречивые данные). RFC называет это непроверенным и предписывает проверку до реализации, а не обещает работоспособность.
9. Часть заявленного проверялась по третьим источникам (блоги, dev.to) — такие утверждения в RFC помечаются как непроверенные, а не выдаются за факт.
