# Анализ: можно ли объединить схемы поведения формы и UI

> Статус: **аналитическая записка**, не план имплементации. Пользователь явно попросил
> «сначала анализ, решение потом». Раздел «Рекомендация» содержит предложение, а не утверждённый курс.

## Context

В проекте сегодня две отдельные схемы поведения, которые в примерах формы лежат соседними файлами:

- `form.behavior.ts` — `defineFormBehavior` из `@reformer/core/behaviors`;
- `renderer.behavior.ts` — `RenderBehaviorFn` из `@reformer/renderer-react`.

Наблюдение пользователя: «мне кажется, это одна и та же схема — если со значением модели что-то
происходит, мы что-то где-то меняем». Задача — проверить это на коде, отделить реальное дублирование
от честного различия слоёв и оценить, можно ли схемы объединить.

Разбор проведён по трём направлениям: исходники обеих схем, реальные формы-примеры и зафиксированные
в `docs/plans/` архитектурные решения.

---

## 1. Что это за схемы на самом деле

| | `defineFormBehavior` | `RenderBehaviorFn` |
|---|---|---|
| Файл | [behaviors.ts](packages/reformer/src/form/behaviors.ts) (+ [behaviors-node.ts](packages/reformer/src/form/behaviors-node.ts)) | [render-behavior.ts](packages/reformer-renderer-react/src/core/render-behavior.ts) |
| Сигнатура | `({ model, form }) => void` | `(schema: RenderSchemaProxy<T>) => void` |
| Адресация цели | сигнал модели `model.$.path` / нода `form.path` | `schema.node('selector')` — id узла вёрстки |
| Механика сбора | ambient-сток cleanup'ов (module-level `current: RunContext`) | 6 `Map`/`Array`-реестров в `__overrideMaps` |
| Реактивность | `effect` из `@preact/signals-core` | `computed` + `useSyncExternalStore` (`useCondition`) |
| Lifecycle | владеет форма, отписка в `form.dispose()` | живёт вместе с render-схемой |
| Вход в систему | `createForm({ model, schema, behavior })` | проп `renderBehavior` / вызов на `createRenderSchema` |
| Сериализуемость | нет (TS-функции) | нет (TS-функции) |

Существенно: **обе схемы реактивны и работают на одном и том же субстрате** — `@preact/signals-core`.
Различаются они не семантикой времени, а только «стоком», куда складывают подписки, и способом
адресации цели.

Есть и третий условный слой — `defineValidationSchema` + `validateWhen`
([validation-schema.ts](packages/reformer/src/form/validation-schema.ts)). Вот он семантически
отличается по-настоящему: работает по **снапшоту**, запускается раннером `validateModel` по требованию,
а не живыми подписками.

## 2. Метрика дублирования на флагманском примере

Замер по [mcp-credit-application-renderer-react-v20](projects/react-playground/src/pages/examples/mcp-credit-application-renderer-react-v20/) —
самой полной форме репозитория (6 шагов, 3 массива, 8 вычисляемых полей).

**Уникальных бизнес-предикатов: 9** — `loanType==='mortgage'`, `loanType==='car'`,
`employmentStatus==='employed'`, `employmentStatus==='selfEmployed'`, `sameAsRegistration`,
`sameEmail`, `hasProperty`, `hasExistingLoans`, `hasCoBorrower`.

**Записей этих предикатов в коде: 28**

| Слой | Файл | Вхождений |
|---|---|---|
| Доступность | `form.behavior.ts` — `enableWhen` | 5 |
| Условная запись | `form.behavior.ts` — `compute`/`copyFrom` c `{ when }` | 3 |
| Условная очистка | `form.behavior.ts` — `onChange` + `clearArray` | 3 |
| Видимость | `renderer.behavior.ts` — `hideWhen` | 8 |
| Валидация | `validation.ts` — `validateWhen` | 9 |

Коэффициент дублирования ≈ **3.1×**. В core-варианте того же примера появляется четвёртый способ
записать тот же предикат — условный JSX (`{loanType === 'mortgage' && …}` в `index.tsx`, 8 вхождений).

### Показательный случай — правило «ипотека»

Один предикат, четыре записи, три разных синтаксиса и **две разные полярности**:

```ts
// form.behavior.ts — доступность (прямая полярность)
enableWhen([model.$.propertyValue], () => model.loanType === 'mortgage', { resetOnDisable: true });

// form.behavior.ts — условная запись производного поля
compute(model.$.initialPayment, () => Math.round((model.propertyValue ?? 0) * 0.2),
        { when: () => model.loanType === 'mortgage' });

// renderer.behavior.ts — видимость (ИНВЕРТИРОВАННАЯ полярность, адресация по selector)
hideWhen(schema.node('mortgage-section'), () => model.$.loanType.value !== 'mortgage');

// validation.ts — валидация (прямая полярность)
validateWhen(() => model.loanType === 'mortgage', () => { validate(model.$.propertyValue, [...]); });
```

Рассинхрон уже фактический, а не гипотетический: `enableWhen` покрывает **одно** поле
(`propertyValue`), а секция `mortgage-section` содержит **два** (`propertyValue` + `initialPayment`).
Второе поле держится отдельным `compute({ when })`. Числа по слоям не сходятся — 5 / 8 / 9.

Дублирование зафиксировано и в документации как **обязательное ручное правило**
([09-review-checklist.md](packages/reformer-renderer-json/docs/llms/09-review-checklist.md)):

> скрытие секции (`hideWhen`) идёт **в паре** с отключением/сбросом полей в `form.behavior` —
> иначе скрытое поле продолжает валидироваться и уезжает в payload

Правило, которое нельзя выразить в типах и которое проверяется только code review, — это ровно тот
класс проблем, который обычно решают объединением.

## 3. Что дублируется, а что различается честно

Пересечение — **только условная логика и мутация props**. Остальное принципиально односторонне.

| Операторы `form.behavior` | Операторы `renderer.behavior` | Вердикт |
|---|---|---|
| `enableWhen` / `disableWhen` | `hideWhen` | **дубль предиката**; эффекты разные (статус-машина vs ранний `return null`) |
| `updateComponentProps` | `patchProps` | **дубль механизма**: оба мержат props, но в разные хранилища |
| `onChange` + `updateComponentProps` (async options) | `renderEffect` | частичный дубль |
| `compute`, `computeFrom`, `copyFrom`, `transformValue`, `resetWhen`, `syncFields`, `aggregateInto`, `exclusiveFlag` | — | только данные, аналога нет |
| — | `onMount`, `onUnmount`, `onInit`, `onComponentEvent`, `getRef` | только рендер, аналога нет |

Важная деталь: **`form.behavior` уже сегодня меняет UI**. В том же флагмане три `onChange`-обработчика
вызывают `form.<field>.updateComponentProps({ options })` — это конфигурация компонента, живущая в
«схеме данных». Граница между схемами протекает в обе стороны уже сейчас.

## 4. Почему прошлый аргумент против слияния не бьёт по этой паре

В репозитории есть готовое адверсариальное исследование
[schema-contract-simplification.md](docs/plans/schema-contract-simplification.md), вывод которого —
«единый контракт не выживает — побеждает симметрия»:

> Все четыре варианта, пытающиеся описать валидацию и поведение **одним** механизмом (A, C, D, E),
> ломаются на одном и том же — на попытке прогнать через общий предикат две РАЗНЫЕ семантики:
> валидация работает по **снапшоту** (запускается на submit/шаг), поведение — **реактивно**
> (живые подписки). […] Ни один из этих багов не случаен — это цена слияния снапшот- и
> reactive-семантики за одним фасадом.

Это решение зафиксировано во фризе [contract-spec.md](docs/plans/contract-spec.md) («два **раздельных**
ambient-контракта… кормятся в форму по разным каналам»).

Ключевое: **исследование про пару «валидация ⟷ поведение», а не «поведение формы ⟷ поведение UI»**.
Оба убийственных аргумента к нашей паре не применяются:

1. *«снапшот vs реактив»* — обе behavior-схемы реактивны, обе на `@preact/signals-core`, у обеих живые
   подписки. Семантического барьера нет.
2. *«JSON-совместимость даром: layout в JSON, правила — TS»* — ни `defineFormBehavior`, ни
   `RenderBehaviorFn` в JSON не выражаются. Обе — TS-функции, инъектируемые в рантайме. Разделение их
   между собой сериализуемости не добавляет.

Более того, тот же документ сам называет `schema.node(selector)` **аналогом** швa `getNodeForSignal`:

> Для render/JSON-варианта резолв — стабильный `schema.node(selector).patchProps()`
> (рендер-аналог того же identity-шва).

Есть и прямой прецедент слияния в противоположную сторону:
[fieldconfig-witty-trinket.md](docs/plans/fieldconfig-witty-trinket.md) фиксирует **отказ** от
раздельных `FormSchema` и `RenderSchema` — по мотиву, дословно совпадающему с текущей жалобой:

> `loanType` объявлен и в `FormSchema` (с компонентом и значением), и в `RenderSchema` (по пути) —
> **дублирование**. […] **Размазанные ответственности.**

Схемы **описания** уже слиты в одно дерево (это и есть M1). Схемы **поведения** над этим деревом —
нет. Наблюдение пользователя фиксирует именно эту асимметрию.

## 5. Технические ограничения, которые обязан учесть любой вариант

Найдены при разборе исходников; каждое влияет на выбор дизайна.

1. **`when` в схеме уже объявлен, но мёртв.**
   [schema-node.ts:105](packages/reformer/src/form/types/schema-node.ts#L105) содержит
   `when?: (scope, root) => boolean` с комментарием «условие включения поддерева (branch-узел)» —
   но в `create-form.ts` слова `when` нет вообще. Это след удалённого branch-узла валидации; слот под
   единое условие в типе уже зарезервирован.

2. **В ядре нет понятия видимости.** Грепы `visible|hidden` по `packages/reformer/src` дают ноль.
   Видимость существует только в рендерере. Единое условие потребует либо ввести в ядро сигнал
   `hidden`, либо оставить видимость целиком в рендерере и передавать туда предикат.

3. **Секция не равна группе модели.** `hideWhen` адресует layout-узлы (`mortgage-section`), у которых
   нет соответствующей ноды формы: секция группирует поля из разных ветвей модели. Обратная адресация
   (от поля к секции) сегодня невозможна — `selector` до ноды не доезжает, `harvestFieldConfig`
   ([create-form.ts:154](packages/reformer/src/form/create-form.ts#L154)) доносит только
   `component/componentProps/updateOn/disabled/debounce`.

4. **Поля внутри массивов отсутствуют в реестре сигнал→нода.** `collectLeafPaths` пропускает массивы,
   поэтому `enableWhen` на поле строки — тихий no-op до построения per-item формы.

5. **`disabled` не исключает поле из payload.** `GroupNode.getValue()`
   ([group-node.ts:239](packages/reformer/src/form/nodes/group-node.ts#L239)) собирает все поля без
   фильтра, а в реальных примерах submit вообще читает `model.get()` напрямую, минуя форму — то есть
   выключенные и скрытые поля попадают в payload гарантированно. Это прямо задокументировано как
   источник утечки ([behaviors-node.ts:28-34](packages/reformer/src/form/behaviors-node.ts#L28-L34)).

6. **Два расходящихся понятия валидности на disabled-полях.** Агрегат `form.valid` игнорирует
   выключенных детей (`child.disabled.value || child.valid.value`,
   [aggregate-signals.ts:88-91](packages/reformer/src/form/aggregate-signals.ts#L88-L91)), а раннер
   `validateModel` про `disabled` не знает вообще — грепы по
   [validation-schema.ts](packages/reformer/src/form/validation-schema.ts) дают ноль совпадений, он
   возвращает `!hasBlocking(ctx.errors)` по собранным ошибкам. Поэтому `required` на выключенном поле
   заваливает `validateModel`, хотя `form.valid` показывает `true`. **Это и есть техническая причина,
   по которой `validateWhen` приходится писать в пару к `enableWhen`** — и главный кандидат на
   устранение при объединении.

7. **Инвариант `state ⇏ form`** ([snappy-bouncing-rossum.md](docs/plans/snappy-bouncing-rossum.md))
   держится ESLint-правилом. Ядро тем более не может зависеть от рендерера — значит объединённый DSL
   не может жить в `@reformer/core` целиком, если включает `onMount`/`getRef`.

8. **Масштаб миграции невелик:** 35 вхождений `hideWhen` (3 примера + кодоген билдера), 59 вхождений
   `enableWhen`/`disableWhen`. Обратной совместимости библиотека не обещает —
   `fieldconfig-witty-trinket.md`: «❌ **не требуется** (у библиотеки нет потребителей) → чистая
   breaking-миграция».

## 6. Варианты объединения

### Вариант A — «условие как сущность первого класса» (минимальный)

Предикат объявляется один раз обычным `computed` и передаётся во все три слоя. Полярность
фиксируется одна.

```ts
// conditions.ts — общий артефакт формы
export const makeConditions = (model: FormModel<CreditForm>) => ({
  isMortgage: computed(() => model.loanType === 'mortgage'),
  isEmployed: computed(() => model.employmentStatus === 'employed'),
});

// form.behavior.ts
enableWhen([model.$.propertyValue, model.$.initialPayment], () => c.isMortgage.value, { resetOnDisable: true });
// renderer.behavior.ts
hideWhen(schema.node('mortgage-section'), () => !c.isMortgage.value);
// validation.ts
validateWhen(() => c.isMortgage.value, () => { … });
```

**Что даёт:** убирает дублирование самого предиката (9 записей вместо 28 в замере) и разнобой
полярностей. Рассинхрон «какие поля покрыты» остаётся.

**Стоимость:** ноль изменений в библиотеке — это прикладная дисциплина, доступная уже сегодня.
Схемы не объединяются, объединяется только источник условия.

### Вариант B — «одна ось availability» (единый оператор)

Один оператор описывает всё правило целиком и разворачивается в эффекты трёх слоёв.

```ts
branch(() => model.loanType === 'mortgage', {
  fields:  [model.$.propertyValue, model.$.initialPayment],
  section: 'mortgage-section',
  reset:   true,
});
```

**Проблема размещения:** оператору нужны одновременно модель, ноды формы и render-схема. В
`@reformer/core` он жить не может (инвариант `state ⇏ form` и запрет зависимости ядра от рендерера),
значит его дом — `@reformer/cdk` или отдельный слой композиции, а core-вариант формы (без рендерера)
получает деградированную версию без `section`.

**Проблема связности:** `fields` и `section` перечисляются вручную и по-прежнему могут разъехаться —
оператор не выводит одно из другого. Это делает вариант B синтаксическим сахаром над A, а не
устранением класса ошибок.

### Вариант C — «условие как данные узла схемы» (структурный)

Условие переезжает на узел дерева схемы — в уже существующий, но мёртвый слот `when`.

```ts
{
  selector: 'mortgage-section',
  when: () => model.loanType === 'mortgage',   // ← оживить
  component: Section,
  children: [
    { value: model.$.propertyValue,  component: InputField },
    { value: model.$.initialPayment, component: InputField },
  ],
}
```

Три потребителя читают **одно и то же** объявление:

- `createForm` — выключает все листья поддерева (реактивно), опционально сбрасывает;
- рендерер — заполняет `conditionRegistry` из `when` вместо ручного `hideWhen`;
- `validateModel` — пропускает выключенные поля, и `validateWhen` для условных веток становится не нужен.

**Почему это технически ложится:** дерево схемы **уже единое** — в
[index.tsx](projects/react-playground/src/pages/examples/mcp-credit-application-renderer-react-v20/index.tsx#L22-L31)
одна и та же `buildCreditApplicationSchema(model)` идёт и в `createForm`, и в `createRenderSchema`; в
JSON-варианте одна `JsonFormSchema` идёт в `convertJsonToM1Tree` и в рендерер. Узел
`mortgage-section` виден обоим слоям, поэтому проблема «секция без ноды формы» решается сама:
адресатом становится узел дерева, а не нода.

**Что придётся сделать в ядре:** `harvestFieldConfig`
([create-form.ts:119-122](packages/reformer/src/form/create-form.ts#L119-L122)) сегодня обходит дерево
рекурсивно, но структуру теряет — форма строится по форме **модели** (`buildModelConfig` идёт по
`model.get()`), а не по layout. Значит нужно вести при обходе стек условий (ровно как `whenStack` в
[validation-schema.ts:71](packages/reformer/src/form/validation-schema.ts#L71)) и запоминать для
каждого листа цепочку `when`-предков. Дальше — один `effect` на цепочку, вызывающий
`enable()/disable()`.

**Что придётся решить отдельно:** payload. Сегодня submit читает `model.get()` напрямую, поэтому
«выключено» никак не влияет на отправляемые данные (см. ограничение 5). Единая ось availability
осмысленна только вместе с ответом на вопрос «попадает ли скрытое поле в payload».

**Бонус:** это единственный вариант, который в перспективе сериализуется — `when` выразим в JSON через
`$fn(name)` или condition-DSL. Для текущего этапа пользователь пометил это как неважное, но дорога не
закрывается.

### Где вообще может жить объединённый код — ограничение по зависимостям

Проверено по `package.json`: `@reformer/cdk` и `@reformer/renderer-react` **не зависят друг от друга**,
оба зависят только от `@reformer/core`. Ядро не может зависеть от рендерера (и не должно —
инвариант `state ⇏ form` и общий принцип направления слоёв).

Отсюда важный вывод, который сам по себе почти выбирает вариант:

- Оператору из **варианта B** нужны одновременно ноды формы и render-схема. Такого места в текущей
  топологии пакетов нет — его пришлось бы создавать (новый пакет либо зависимость
  `renderer-react → cdk`), и core-вариант формы остался бы без него.
- **Вариант C** этой проблемы не имеет: условие лежит в **схеме** — артефакте, который оба слоя уже
  читают. Направление зависимостей не меняется, `renderer-react` продолжает читать из `core`.

Прецедент такой адресации в проекте уже принят: `defineSteps`
([define-steps.ts](packages/reformer-cdk/src/components/form-wizard/define-steps.ts)) связывает
**правила валидации** с **layout-узлами по `selector`** — и по ровно тому же мотиву, что обсуждается
здесь:

> Раньше правила шагов держались МАССИВОМ (`STEP_SCHEMAS[step - 1]`): добавление или перестановка
> шага молча рассинхронизировали правила с позицией, а шаг без правил получался «валидным» по
> умолчанию (тихая дыра).

То есть «адресовать по узлу схемы, чтобы слои не разъезжались» — уже работающий в репозитории
паттерн, а не новая идея.

## 7. Риски

1. **Payload — главный нерешённый вопрос.** «Скрыто ⇔ выключено» звучит стройно ровно до момента
   отправки: `GroupNode.getValue()` не фильтрует disabled, а примеры и вовсе шлют `model.get()`.
   Объединение осей без явного решения по payload не устранит проблему, а замаскирует её.

2. **Потеря выразительности.** Сегодня возможны и используются комбинации «видно, но disabled»
   (computed-поля: `RO = { disabled: true }` в
   [renderer.schema.ts:32](projects/react-playground/src/pages/examples/mcp-credit-application-renderer-react-v20/renderer.schema.ts#L32))
   и «скрыто, но участвует» (вычисляемые поля вне вёрстки). Жёсткая одна ось их запрещает. Отдельно
   отмечу ловушку, уже описанную в доке: `componentProps.disabled` — это UI-проп, он **не** влияет на
   состояние ноды; в репозитории существуют два разных `disabled`.

3. **Поля внутри массивов.** `collectLeafPaths`
   ([create-form.ts:175](packages/reformer/src/form/create-form.ts#L175)) пропускает массивы, поэтому
   их листья отсутствуют в реестре сигнал→нода. Любое единое условие на поле строки массива будет
   тихим no-op вне `applyEach`. Это уже сегодня источник неочевидного поведения и при объединении
   станет заметнее.

4. **Состояние скрытой секции переживает скрытие.** `hideWhen` делает ранний `return null` в
   [render-node.tsx](packages/reformer-renderer-react/src/core/render-node.tsx#L719) — размонтируется
   только вёрстка. Ноды формы, их `errors`, `touched` и значения остаются. Без `resetOnDisable`
   повторный показ секции вернёт старые ошибки.

5. **Частичная миграция даёт два источника истины.** Пока часть условий живёт в схеме, а часть — в
   `renderer.behavior.ts`, приоритет должен быть определён явно. В рендерере уже есть трёхуровневый
   приоритет `setHidden` > `hideWhen` > видимо-по-умолчанию — единое условие станет четвёртым
   уровнем, и порядок надо зафиксировать до, а не после.

6. **Порядок инициализации.** Форма и behavior строятся синхронно в `createForm`, render-behavior
   применяется позже, при создании render-схемы. Если условие переезжает в схему, оба потребителя
   читают его из одного места — риск снимается; но при варианте с оператором-фасадом (B) остаётся
   вопрос, что делать, если оператор вызван до существования render-схемы.

7. **Расхождение с зафиксированным фризом.** [contract-spec.md](docs/plans/contract-spec.md) — это
   намеренно замороженный контракт. Даже если аргументы фриза не покрывают нашу пару (раздел 4),
   изменение потребует явного обновления фриза, иначе документация и код разъедутся.

## 8. Рекомендация

### Короткий ответ на вопрос

**Объединять — да, но не схемы целиком, а их пересечение.** Наблюдение верное ровно наполовину:
дублируется **условная логика** (и она дублируется втройне, а местами вчетверне), но остальные
операторы двух схем описывают честно разные вещи — `compute`/`aggregateInto` не имеют смысла в
рендере, `onMount`/`getRef`/`onComponentEvent` не имеют смысла в модели. Слияние всего DSL в один
файл дало бы одну функцию с двумя непересекающимися половинами и потребовало бы новой зависимости
между пакетами — то есть цена выше выгоды.

### Что предлагаю

**Шаг 1 (сейчас, без изменений в библиотеке) — вариант A.** Вынести предикаты формы в общий
`conditions.ts` и подписать на них все три слоя. Это устраняет 2/3 записей и разнобой полярностей
уже сегодня, ничего не ломая, и служит дешёвой проверкой гипотезы на флагманском примере.

**Шаг 2 (целевой) — вариант C: оживить `when` в узле схемы.** Он единственный:

- убирает не только дублирование предиката, но и **рассинхрон покрытия** (какие поля попали под
  условие) — потому что покрытие выводится из структуры дерева, а не перечисляется руками;
- решает проблему «секция без ноды формы» естественно — адресатом становится узел общего дерева;
- не меняет направление зависимостей между пакетами (см. раздел 6);
- опирается на уже зарезервированный слот в типе и на уже принятый в проекте паттерн `defineSteps`;
- в перспективе сериализуется, если билдер вернётся к теме (сейчас это не приоритет).

Порядок работ для шага 2: `whenStack` в `harvestFieldConfig` → `effect` на цепочку условий листа
(`enable`/`disable`) → рендерер заполняет `conditionRegistry` из `when` → раннер `validateModel`
пропускает выключенные поля → миграция примеров → удаление ставших избыточными `hideWhen`/`validateWhen`.

### Чего мы при этом лишаемся — честно

1. **Независимости осей.** Комбинации «видно, но disabled» и «скрыто, но участвует» перестают
   выражаться самим условием и потребуют явного opt-out (например `when: { enable: …, hide: … }`
   вместо одного предиката). Если такие кейсы окажутся частыми, вариант C деградирует в вариант A.
2. **Простоты `create-form`.** Появляется обход дерева со стеком условий и реактивные подписки на
   этапе построения формы — сегодня там чистая структурная сборка.
3. **Соответствия фризу.** [contract-spec.md](docs/plans/contract-spec.md) придётся обновить явно.

### Что решить до начала работ

Единственный по-настоящему блокирующий вопрос — **payload**: попадает ли скрытое/выключенное поле в
`model.get()` при submit. Сегодня попадает всегда (раздел 5, п. 5). Пока на него нет ответа, любое
объединение осей будет косметическим — оно уберёт дублирование записи, но не устранит тот баг-класс,
ради которого правило «hideWhen в паре с enableWhen» вообще появилось.
