# Guard: двойной рантайм

## Что ломается

Две копии одного пакета в одном realm — авария, у которой нет ни одного видимого симптома.

- **Две копии `@preact/signals-core`** → восемь точек `instanceof Signal` начинают давать `false`.
- **Две копии `@reformer/core`** → раздваиваются модульные `WeakMap`:
  - `derived-registry` — bulk-set **затирает вычисляемые поля** (тихая порча данных);
  - `signal-node-registry` — `enableWhen`/`disableWhen` превращаются в **тихий no-op**.

Юнит-тесты этого не ловят: vitest резолвит один инстанс. Ломается только собранный артефакт, и
только в сборке из нескольких бандлов.

Репозиторий про проблему знает — комментарии в `renderer-json/vite.config.ts` и `cdk/vite.config.ts`
это постмортемы. Но те защиты работают на уровне «одна сборка»: они не дают вшить зависимость внутрь
бандла. В микрофронтах отказ приходит с другой стороны — два независимо собранных бандла грузят по
своей копии, и ни один из них при этом не «неправильный».

## Как пользоваться

Каждый бандл при инициализации ставит свои штампы, хост потом спрашивает результат:

```ts
// в каждом микрофронте, при загрузке:
import { Signal } from '@reformer/core/signals';
import { CORE_RUNTIME_TOKEN } from '@reformer/core';
import { stampRuntime } from '@reformer/form-registry/guard';

stampRuntime('@preact/signals-core', Signal);
stampRuntime('@reformer/core', CORE_RUNTIME_TOKEN);
```

```ts
// в хосте, после загрузки всех ремоутов:
import { reportRuntime } from '@reformer/form-registry/guard';

const { ok, duplicates, observed } = reportRuntime((d) => telemetry.error(d.message));
```

## Сравниваются объекты, а не версии

Штамп обязан быть объектом или функцией — примитив отвергается с ошибкой. Строка с версией совпала
бы у разных копий по значению, и дубль остался бы невидимым: **две копии одной и той же версии
ломают всё ровно так же**, как две копии разных.

Подходящие штампы: конструктор `Signal`, `CORE_RUNTIME_TOKEN`, `React.createContext`.

`CORE_RUNTIME_TOKEN` существует в ядре ровно для этого — быть объектом, уникальным в пределах одной
копии модуля.

## Строгость — рантайм-флагом

```ts
setRuntimeStrict(true); // бросить на второй копии
```

Дефолт — `report`: рушить хост из-за диагностики хуже, чем работать с известной проблемой. `throw`
осмыслен в CI и на стенде.

Флаг именно рантайм-ный, и это не вкусовщина:

- `import.meta.env.DEV` **вырезается** при сборке пакета — в `packages/*/dist` ноль вхождений;
- `process.env.NODE_ENV` в голом ESM и web-components даёт `ReferenceError: process is not defined`
  (в `packages/reformer/dist` таких вхождений шесть).

Ни на то, ни на другое опираться нельзя. Отсутствие node-глобалей в собранном пакете проверяется
`scripts/check-no-node-globals.mjs` в CI.

## Ограничение, которое важно понимать

Guard видит **только те копии, которые сами себя штампанули**. Бандл, не вызвавший `stampRuntime`,
останется невидимым — из JS нет способа пересчитать все загруженные модули.

Поэтому `checkRuntime()` возвращает не только `duplicates`, но и `observed`: пустой `observed`
означает «guard просто не подключили», и это НЕ то же самое, что подтверждённое отсутствие дублей.

## Хранилище состояния

Состояние лежит в `globalThis` под `Symbol.for('reformer.runtime.v1')`. `Symbol.for` живёт в
cross-realm registry — это единственный ключ, совпадающий у двух независимо собранных копий модуля.
Модульный синглтон здесь бесполезен: у каждой копии он был бы свой, и дубль остался бы незамеченным.

Тот же приём использует и сам реестр форм (`Symbol.for('reformer.form-registry.v1')`) — иначе при
Module Federation без общего chunk'а хост не увидел бы форм, зарегистрированных ремоутом.
