# Сеть, кэш и хранилище

Схемы объёмные: шестишаговая кредитная заявка — **68 КБ**, каталог компонентов — 128 КБ. Тянуть их
заново на каждый F5 расточительно, поэтому кэш персистентный.

## Быстрый старт

```tsx
import { createSchemaCache, getFormRegistry } from '@reformer/form-registry';
import { pickStorage } from '@reformer/form-registry/storage';
import { FormRegistryProvider } from '@reformer/form-registry/react';

const cache = createSchemaCache({ storage: await pickStorage() });

<FormRegistryProvider
  registry={getFormRegistry()}
  context={resolveContext}
  baseRegistry={coreComponents}
  cache={cache}
>
  <App />
</FormRegistryProvider>;
```

Кэш нужен только сетевым источникам. У `kind: 'inline'` загрузчик отдаёт значение до кэша, поэтому
на inline-записях счётчики останутся нулевыми — это норма, а не признак неработающего кэша.

## Загрузка по сети

```ts
schema: { kind: 'http', url: '/schemas/checkout.json' }
```

Что делает `fetchJson` и почему:

- **Ретраит 5xx, 408, 425, 429** с экспоненциальной задержкой и джиттером. Джиттер обязателен: без
  него все клиенты, получившие 503 одновременно, повторят запрос тоже одновременно и добьют сервер,
  который только начал подниматься. `Retry-After` уважается — сервер знает лучше.
- **Не ретраит 4xx.** Повторять запрос, на который сервер ответил «так нельзя», значит множить
  нагрузку без шанса на успех.
- **Проверяет `content-type`.** SPA-fallback отдаёт `index.html` со статусом 200 вместо JSON; без
  этой проверки отказ всплывает как «Unexpected token <» далеко от причины. Приём взят с работающего
  кода в `projects/reformer-builder/src/config/load.ts`.
- **Проверяет форму объекта** (`assertFormSchemaShape`) до кэша: класть чужой JSON в кэш значит
  закрепить ошибку до истечения срока годности.

Причина отказа машиночитаема: `http-error`, `not-json`, `not-a-form-schema`, `aborted`, `network`.

## Два уровня кэша

L1 — в памяти: разобранные объекты и промисы «в полёте». L2 — сериализованные тела через
`StorageStrategy`. Чтение L1 → L2 → сеть; запись сеть → L2 → L1. Устаревшее в L2 ревалидируется
условным запросом по `ETag`; ответ 304 продлевает жизнь записи.

### Правило отмены

Отмена **не пробрасывается** в общий запрос. Если два `FormOutlet` ждут одну схему и один
размонтировался, отменять нельзя — второй остался бы ни с чем. Учёт идёт по числу ожидающих, и
запрос прерывается только когда ушёл последний.

### Дедупликация регистрируется синхронно

Внутренняя функция `load` намеренно **не** `async`. Всё, что решает, заводить ли новый запрос,
обязано выполниться синхронно относительно вызывающего: поставь `await` (хотя бы чтение L2) перед
регистрацией запроса «в полёте» — и два одновременных вызова проскочат мимо проверки и заведут два
запроса, а отмена, пришедшая сразу после вызова, не найдёт подписки. Оба случая закрыты тестами.

### Отказ кэша не ломает загрузку

Падение `storage.get`/`storage.set`, битое тело, очистка данных сайта посреди сессии — всё это даёт
диагностику и уход в сеть, но не исключение. **Кэш выбрасываемый**: `clear()` в любой момент
безопасен.

## Метрики

```ts
const cache = createSchemaCache({ storage, onEvent: (e) => log.push(e) });
cache.stats(); // { l1Hit, l2Hit, dedup, stale, miss, fetched, ... }
cache.resetStats(); // обнулить счётчики; содержимое кэша НЕ трогает
```

События образуют **две независимые оси**, и это не оформление, а условие того, что счётчики сходятся:

| ось | события | сколько на что |
| --- | --- | --- |
| исход поиска | `l1-hit`, `l2-hit`, `dedup`, `stale`, `miss` | ровно одно на каждый `get()` |
| исход сети | `fetched`, `refetched`, `revalidated`, `error`, `aborted` | не больше одного на заведённый запрос |

Свести их в один список нельзя: один вызов `get()` даёт событие либо из обеих осей (`stale` →
`revalidated`), либо только из первой (`l1-hit`). Отсюда проверяемые инварианты:

```text
l1Hit + l2Hit + dedup + stale + miss                === числу вызовов get()
fetched + refetched + revalidated + error + aborted === stale + miss
```

Правая часть второго — именно `stale + miss`, а не число заведённых запросов: попадание в L2
закрывает запрос ДО сети и события сетевой оси не даёт вовсе. В сеть уходят ровно те чтения, которые
не нашли свежего значения.

Что стоит знать, глядя на цифры:

- **`stale` — не разновидность промаха.** «Тело было, но протухло» ведёт к условному запросу и,
  скорее всего, к `revalidated`; «тела не было» (`miss`) — к полной загрузке.
- **Исход поиска фиксируется до сети.** Иначе на каждом сетевом отказе событие терялось бы, и первый
  инвариант перестал бы сходиться.
- **`aborted` отделён от `error`.** Запрос без ожидающих гасим мы сами — в счётчике ошибок это
  выглядело бы сбоем сервера.
- **`l2ReadFailed` / `l2WriteFailed` / `l2Corrupt` считаются отдельно от `error`.** Сорванный кэш не
  срывает загрузку; свести их в одну цифру — потерять смысл обеих.
- **`bytes` — размер после сериализации**, а не байты по проводу: сжатие и заголовки не учтены.
- **`stats()` возвращает копию.** Живой объект потребитель, сравнивающий снимки по ссылке (`useMemo`,
  `useSyncExternalStore`), не увидел бы меняющимся ни разу. Для потока — `onEvent`.

## Стратегии хранения

```ts
import {
  createOpfsStorage,
  createIndexedDbStorage,
  createMemoryStorage,
  pickStorage,
  DEFAULT_STORAGE_ORDER, // ['opfs', 'indexeddb', 'memory']
} from '@reformer/form-registry/storage';
```

Интерфейс один, реализации взаимозаменяемы — это проверяется **одним** контрактным набором против
всех трёх. Порядок в `pickStorage` — настройка, а не архитектурное решение: меняется одной строкой.

`pickStorage` проверяет не только наличие API, но и работоспособность пробной операцией: в приватном
режиме части движков `indexedDB` объявлен, а открытие падает. Иначе отказ всплыл бы при первой
записи схемы, далеко от места выбора.

### OPFS

Четыре свойства, определившие реализацию:

1. **Синхронные хэндлы только в Worker.** `createSyncAccessHandle()` на главном потоке бросает,
   поэтому путь записи выбирается **попыткой**, а не проверкой окружения — так детект переживает и
   Worker, и главный поток, и движки, где поддержка появилась позже самого OPFS.
2. **`createWritable()` атомарна по спецификации** — пишет в swap-файл и коммитит на `close()`.
   Синхронный путь атомарности не даёт и сериализуется через `navigator.locks`.
3. **Хранилище общее на origin** — отсюда `owner` в ключе.
4. **В имени файла не может быть `/`**, а ключ его содержит — имена кодируются `encodeURIComponent`.

`navigator.storage.persist()` не запрашивается: просить постоянное хранилище ради кэша, который в
любой момент можно перекачать, несоразмерно. Флаг оставлен под будущий офлайн и выключен.

### IndexedDB

Существующий в репозитории `handle-store` за образец **не** взят: он открывает соединение на каждую
операцию и не закрывает, резолвит промис по `request.onsuccess` (для `readwrite` это резолв ДО
коммита — читатель следом может не увидеть запись) и не обрабатывает ни `onabort`, ни квоту.

Здесь наоборот: одно кэшированное соединение, резолв записи по `transaction.oncomplete`, отдельная
ветка на `QuotaExceededError` — вытеснение и один повтор. Оба отличия закреплены тестами.

### Вытеснение

LRU по `lastUsedAt`, потолок 32 МБ. Чтение обновляет возраст — иначе LRU выродился бы в FIFO.
Политика вынесена чистой функцией `selectEvictions` и тестируется отдельно от ввода-вывода.
