# @reformer/builder-plugin-cli

`reformer-plugin` — командная строка автора плагина ReFormer Builder: создать плагин из шаблона,
проверить и собрать его **теми же правилами, которыми его проверит оболочка**, разрабатывать
прямо в открытом проекте и упаковать для npm, а киту — собрать каталог компонентов из его
TypeScript-типов.

```bash
npx @reformer/builder-plugin-cli create acme-forms --name "Acme Forms"
cd acme-forms && npm install
npx reformer-plugin validate
npx reformer-plugin dev --project ../my-builder-project
npx reformer-plugin pack
```

Нужен Node 20 или новее (`dev` наблюдает за каталогом рекурсивно).

## Команды

### `create <каталог> [--id <id>] [--name <имя>]`

Кладёт в пустой (или несуществующий) каталог готовый плагин:

| Файл                            | Что это                                                                       |
| ------------------------------- | ----------------------------------------------------------------------------- |
| `manifest.json`                 | манифест исходников: `main` → `src/main.ts`, словари объявлены                |
| `src/main.ts`                   | плагин с одной командой, подпись которой берётся из словаря                   |
| `src/main.test.ts`              | `id` кода совпадает с `id` манифеста — иначе оболочка откажет (`id-mismatch`) |
| `locales/ru.json`, `en.json`    | плоские словари «ключ → строка»                                               |
| `package.json`, `tsconfig.json` | `@reformer/builder-plugin-api` в `devDependencies`                            |

Идентификатор по умолчанию — имя каталога. Годится ли он, решает разбор манифеста оболочки,
а не собственное правило CLI. В непустой каталог команда не пишет.

Созданный плагин можно положить в `.ui_builder/plugins/<id>/` проекта как есть: оболочка сама
транспилирует `src/main.ts`.

### `validate [каталог]`

Код выхода `0` — оболочка плагин примет, `1` — нет, и почему именно, напечатано построчно.

- **манифест** — разбором из `@reformer/builder-plugin-api/tooling`, тем же, что у оболочки.
  Отличий у исходников два: имя каталога с `id` не сверяется (репозиторий зовётся как угодно),
  а `version` обязательна и должна быть версией — по ней публикуется пакет;
- **файлы, на которые ссылается манифест**: точка входа существует и это код, таблица стилей
  существует, словари существуют и плоские. Эти отказы собираются все сразу;
- **версия `package.json`** совпадает с версией манифеста. Этого оболочка не проверяет —
  `package.json` она не читает, — а расхождение означает пакет одной версии с плагином другой.

Коды отказов — коды оболочки (`manifest-invalid`, `api-version`, `entry-missing`,
`messages-invalid`, `provides-unregistered`…). Свои коды у CLI — для того, чего оболочка не видит:
`package-version`, `build-failed`, `module-unavailable`, `css-from-code`, `output-not-ours`,
`output-is-source`, `pack-failed`, три кода кита (`kit-no-id`, `kit-invalid-catalog`,
`kit-mismatch`, см. `build`) и коды генератора каталога (`catalog-config-invalid`, `catalog-symbol-missing`, `catalog-drift`,
`typescript-missing`, см. `catalog`).

Соответствие `provides` регистрации и потолок числа файлов `validate` не проверяет: первое
требует исполнить код, второе относится к собранному каталогу. Обе проверки делает `build`.

### `build [каталог] [--out <каталог>] [--minify] [--bundle-css]`

Собирает каталог, который оболочка грузит как есть (по умолчанию `dist/`): `manifest.json`
с `main: "main.js"` и секцией `build`, `main.js`, `styles.css`, если стили объявлены, словари
по тем же путям и отложенные модули в `chunks/` — если код импортирует что-то через `import()`.

- код — CommonJS: линковщик оболочки исполняет CommonJS, и готовый JS идёт у него без
  транспиляции;
- `await import('./engine')` — отложенный импорт СВОЕГО модуля уезжает файлом в `chunks/`,
  вместе со всем, что нужно только ему; оболочка исполнит его при первом обращении, а не при
  загрузке плагина. Так везут тяжёлый движок, который нужен не каждому запуску. Модуль, нужный
  и `main.js`, и отложенному файлу, попадает в общий чанк и существует в одном экземпляре —
  его состояние не раздваивается. Делит код esbuild (сборка ESM с делением), после чего каждый
  файл переводится в CommonJS: нативного `import()` в собранном не остаётся;
- `import()` в собранном коде — вызов функции оболочки `__reformerImport("./chunks/…")`:
  оболочка ЧИТАЕТ отложенный файл только в этот момент, а не при загрузке плагина. Писать
  так руками не нужно — обычный `import()` в исходниках сборка переводит сама. Импорт пакета
  оболочки (`await import('@reformer/ui-kit/chart')`) переводится так же, и пакет перестаёт
  готовиться при запуске. Вычисляемый спецификатор (`import(name)`) остаётся отложенным
  `require`: прочитать заранее по нему нечего;
- секция `build` собранного манифеста — граф файлов: каждый файл кода и то, что ему нужно
  сразу (`imports` — свои файлы, `runtime` — пакеты оболочки). По ней оболочка читает при
  включении плагина точку входа с её статическим замыканием, а не каталог. Пишет секцию только
  сборка; в манифесте исходников она не читается. После сборки печатается, сколько кода
  читается сразу и сколько — по требованию;
- оболочке, которая секцию `build` не знает, собранный каталог по-прежнему годится: в начале
  файла с отложенным импортом лежит запасная реализация `__reformerImport` через `require`,
  и каталог остаётся самодостаточным графом CommonJS;
- модули, которые подставляет оболочка (`PLUGIN_RUNTIME_MODULES` контракта: React, `@reformer/*`,
  сам контракт), остаются внешними. Импорт `@reformer/*` или `@builder/*` вне этого списка —
  отказ `module-unavailable`: вложенная копия была бы вторым экземпляром пакета;
- импорт CSS из кода — отказ `css-from-code`: стили объявляются полем `styles` манифеста,
  и только такую таблицу оболочка изолирует. Параметр `--bundle-css` снимает отказ: CSS,
  который импортирует код — свой и зависимостей, в том числе из отложенных модулей, —
  собирается и дописывается в объявленную таблицу (перед правилами автора). Так плагин везёт
  стороннюю библиотеку, чьи модули сами импортируют свои стили. Таблица при этом обязана быть
  объявлена — иначе тот же отказ;
- файл, на который ссылается CSS (`url(./icons.ttf)`, картинка), вкладывается в таблицу
  data-URL: сборка состоит из текстовых файлов, и лежащий отдельно шрифт оболочка не прочла бы;
- `import EchoWorker from './echo.worker?worker'` — конструктор воркера, как у Vite. Воркер
  собирается отдельным самостоятельным файлом (в его потоке нет линковщика оболочки, поэтому
  в него вложено всё), кладётся в сборку текстом — в тот модуль, который его импортировал, —
  и запускается из Blob-URL. Адрес заводится один на вид воркера, при первом `new`;
- `import text from './form.eta?raw'` — текст файла строкой, как у Vite: так плагин держит
  шаблоны файлами. Путь — относительный, текст вкладывается в `main.js`;
- `await import('./corpus.json')` — отложенный импорт JSON уезжает отдельным модулем
  в `chunks/<имя>.js`, а в `main.js` остаётся вызов оболочки: она прочтёт и исполнит модуль
  при первом обращении, а не при загрузке плагина. Так держат большие данные, которые нужны
  не сразу, —
  вложенные в `main.js`, они разбирались бы движком при каждом включении плагина. Статический
  `import data from './a.json'` вкладывается, как и раньше. Имя такого файла — по имени
  исходника, без хэша. Свои файлы в `chunks/` сборка узнаёт по первой строке и чужих там
  не трогает;
- `--minify` сжимает код, воркеры и стили. Для сборки в поставку это вдвое меньше байт; для
  сборки на месте — нечитаемый стек, поэтому не умолчание;
- текст в `main.js` — UTF-8, без экранирования символов вне ASCII: оболочка читает файлы
  плагина как UTF-8, а кириллица в строках занимала бы втрое больше места.

На выходе сборка проходит то, что пройдёт у оболочки: разбор манифеста поставки `project`, потолок
числа файлов кода и **«сухую» активацию** — `main.js` исполняется под Node с настоящим пакетом
контракта и заглушками остального. Общие чанки, которые `main.js` требует сразу, исполняются
вместе с ним; отложенные — нет: движок, которому нужен DOM, пробный запуск не трогает. Так ловятся `not-a-plugin`, `id-mismatch` и
`provides-unregistered`. Кит, внесённый в точку `reformer.kit.source`, проверяется теми же правилами,
что у реестра китов билдера: кит назвал себя (`kit-no-id`), каталог проходит контракт
`component-catalog.schema.json` (`kit-invalid-catalog`) и называет себя так же, как шапка
(`kit-mismatch`). Каталог-загрузчик вызывается, пространство имён кита — нет: это сами компоненты. Если код падает на заглушке (например, `activate` трогает DOM), это
не отказ, а заметка `! … не проверено`: вне оболочки так ведут себя и рабочие плагины.

В каталоге вывода сборка удаляет только своё — файлы, которые называет манифест прошлой сборки
этого же плагина; каталог целиком она не стирает. Непустой каталог без такой сборки — отказ
`output-not-ours`, сам каталог исходников — отказ `output-is-source`. Не прошедшая проверки
сборка прошлую не затирает.

#### Сборка на месте

Пакет плагина может лежать прямо там, где оболочка ищет плагины, — в
`<проект>/.ui_builder/plugins/<id>/`, — и собираться в собственный корень:

```text
.ui_builder/plugins/<id>/
├── package.json
├── src/                 исходники: manifest.json, код, стили, словари
├── manifest.json        ┐
├── main.js              ├ сборка `reformer-plugin build src --out .` — её грузит оболочка
└── locales/…            ┘
```

Каталог вывода, внутри которого лежат исходники, чужим не считается, даже когда не пуст: сборка
пишет рядом и не трогает остального. Файл, которого прошлая сборка не писала, она не
перезаписывает — это тоже `output-not-ours`, с именем файла. Собранное держат вне git.

### `dev [каталог] --project <каталог проекта>` · `dev [каталог] --out <каталог>`

Собирает в `<проект>/.ui_builder/plugins/<id>/` и пересобирает на каждое изменение исходников
(`node_modules`, `dist` и скрытые каталоги не наблюдаются). Перезагружает плагин оболочка:
отметьте его в списке плагинов «в разработке», и он перечитывается при возврате в окно билдера.

`--out <каталог>` вместо `--project` называет каталог вывода прямо. Для пакета, собираемого
на месте, — `reformer-plugin dev src --out .`: тот же каталог, что у `build src --out .`.
Параметры сборки `--minify` и `--bundle-css` принимают и `dev`, и `pack` — плагин обязан
собираться одинаково, чем бы его ни собирали.

### `pack [каталог] [--out <каталог>]`

Собирает во временный каталог и упаковывает `npm pack` в `<имя>-<версия>.tgz`. В архиве только
сборка и `package.json` (имя, описание, лицензия и ключевые слова из исходного, версия — из
манифеста, ключевое слово `reformer-builder-plugin` добавляется); исходников и зависимостей нет.

### `catalog [каталог] [--config <файл>] [--check]`

Собирает каталог кита (`catalog.json` — контракт `component-catalog.schema.json` из
`@reformer/builder-plugin-api`) из TypeScript-типов **входа пакета кита**: каждая запись описывает
тот символ, который импортирует кодоген и рисует превью. Набор пропсов выводится из типов,
поэтому разойтись с кодом каталог не может; конфиг решает только то, чего типы не знают.

Конфиг — `catalog.config.mjs` (или `.js`, `.json`) в каталоге кита либо файл из `--config`:

```js
// @ts-check
import { defineKitCatalog, optionsProp } from '@reformer/builder-plugin-cli/catalog-config';

export default defineKitCatalog({
  entry: './src/index.ts',
  kit: { id: 'acme', label: 'Acme DS', package: '@acme/ds', infra: { fieldWrapper: 'FormField' } },
  ownership: { packages: ['@acme/ds'] }, // чьи пропсы — «свои»
  fields: {
    Input: { value: 'string | null' },
    DatePicker: { exportName: 'DateField', value: 'Date | null' },
  },
  statics: { 'Textbox.Password': 'InputPassword', 'Tabs.TabPane': 'TabPane' },
  parts: { TabPane: 'Tabs' },
  categories: { 'Поля ввода': ['Input', 'DatePicker'], Контейнеры: ['Tabs'] },
  limited: { Modal: 'оверлей — нужен триггер' },
  service: ['FormField', 'KitProvider'],
  exclude: ['Wizard'],
  leaves: ['Divider'],
  props: {
    omit: { '@field': ['validationStatus'] },
    override: { Select: { options: optionsProp() } },
  },
});
```

`typescript` — необязательная peer-зависимость: грузится из каталога кита, затем рядом с CLI;
нет нигде — отказ `typescript-missing`. Если из каталога кита разрешается `prettier`, файл
форматируется им (иначе `JSON.stringify`).

- **Тип пропсов** — первый параметр сигнатуры (функция, `FC`, `forwardRef`, `memo`, класс).
  Когда тип символа в чужом `.d.ts` не разрешился (`VFC` нет в `@types/react` 19, у
  `styled-components` 5 нет типов), разбирается аннотация: `FC`/`VFC`/`FunctionComponent`/
  `ComponentType`/`ForwardRefExoticComponent`/`NamedExoticComponent` — первый аргумент,
  `MemoExoticComponent<T>` — компонент `T`, `StyledComponent<C, T, O, A>` — пропсы `C` (тег,
  функция, компонент) и `O`, пересечение — компонентная часть. Тип не вывелся — пропсов у записи
  нет (палитровой записи это отказ; запасной путь — `propsFrom`).
- **Владение пропсами**: исходники кита и `ownership.packages` → `properties`; `@types/react` →
  `x-inherits.react`; прочие пакеты (`antd`, `rc-*`) → `x-inherits.packages`, нужные возвращает
  `props.pick`. `className` остаётся всегда; `children`/`key`/`ref`/`style`, aria/data-атрибуты,
  DOM-события (`onClick`, но не `onOpenChange`) и `@deprecated` — нет. `props.omit` убирает,
  `props.override` уточняет схему (только выведенного пропа). Селектор — имя записи, `'*'`,
  `'@field'` или `'@container'`.
- **Поля** — экспорты со статикой `reformerAdapter`; каждое описывает `fields` (биекция
  обязательна). `properties` поля — пропсы обёртки без шва (`value`/`onChange`/`onBlur`/
  `disabled` и `seam` поля) плюс пропсы обёртки поля (`fieldWrapper`, по умолчанию `'reformer'`:
  `label`, `required`, `description`, `labelTooltip`, `testId`, `tooltip`); `x-runtimeProps` —
  шов, где `value.type` — тип значения из конфига (только встроенные типы: `Date | null`,
  `[Date, Date] | null`, `File[] | null`).
- **Статики** (`Textbox.Masked`) находятся сами; каждая требует решения в `statics`: `'ignore'`
  или плоский экспорт кита. **Части** составных компонентов — только явно, через `parts`.
- **Роли**: поля, `categories`, `palette`, `limited` (заглушка в превью), `parts` — палитра;
  `service` — `palette: false`; `exclude` — вне каталога; функции, хуки, контексты и константы в
  каталог не попадают сами. Компонент без роли записывается служебным с заметкой
  (`unclassified: 'refuse'` — отказ). Разделы палитры (`kit.palette.categoryByName`, `order`)
  выводятся из `categories`.
- **Детерминизм**: записи и пропсы — по кодовым точкам имени, порядок ключей фиксирован, enum — в
  порядке объявления, `x-doc.type` без `import("…").` и не длиннее 160 знаков; описания — только
  из JSDoc типов и конфига, из прошлой версии файла ничего не переносится.

Каталог проходит ту же проверку контракта, что у реестра китов билдера (`loadCatalogValidator`), —
до записи; не прошедший не пишется. Отказы (код выхода `1`):

- `catalog-config-invalid` — форма конфига; имя без записи; синтетика билдера (`Wizard`, `Step`,
  `$html…`, `FieldArray` в палитре); противоречие ролей; статика без решения; биекция полей;
  непереносимый тип значения; палитровая запись без пропсов;
- `catalog-symbol-missing` — символ записи, `propsFrom`, `statics`, `kit.infra` или `kit.adapters`
  не экспортирован входом;
- `kit-invalid-catalog` — результат не проходит контракт каталога;
- `typescript-missing` — TypeScript не установлен;
- `catalog-drift` — `--check`: файл разошёлся с типами.

`--check` ничего не пишет: сравнивает разобранный JSON файла с тем, что дают типы (форматирование
и порядок ключей не влияют), и при расхождении печатает дифф (`+` есть по типам, нет в файле; `-`
наоборот; `~` изменилось). Так кит держит каталог в репозитории и узнаёт в CI, что обновлённая
дизайн-система требует перегенерации.

## Программный вход

```ts
import { buildPlugin } from '@reformer/builder-plugin-cli';

const result = await buildPlugin({ dir: './acme-forms', outDir: './out' });
if (!result.ok) console.log(result.findings);
```

Генератор каталога — отдельным подпутём (`typescript` нужен только ему):

```ts
import { checkKitCatalog, generateKitCatalog } from '@reformer/builder-plugin-cli/catalog';

const result = await generateKitCatalog({ dir: './my-kit' }); // файл не пишет
if (result.ok) await writeFile(result.outFile, result.text);

const check = await checkKitCatalog({ dir: './my-kit' }); // check.diff — расхождения
```
