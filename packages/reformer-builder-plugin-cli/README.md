# @reformer/builder-plugin-cli

`reformer-plugin` — командная строка автора плагина ReFormer Builder: создать плагин из шаблона,
проверить и собрать его **теми же правилами, которыми его проверит оболочка**, разрабатывать
прямо в открытом проекте и упаковать для npm.

```bash
npx @reformer/builder-plugin-cli create acme-forms --name "Acme Forms"
cd acme-forms && npm install
npx reformer-plugin validate
npx reformer-plugin dev --project ../my-builder-project
npx reformer-plugin pack
```

Нужен Node 20 или новее (`dev` наблюдает за каталогом рекурсивно).

## Команды

### `create <каталог> [--id <id>] [--name <имя>]`

Кладёт в пустой (или несуществующий) каталог готовый плагин:

| Файл                            | Что это                                                                       |
| ------------------------------- | ----------------------------------------------------------------------------- |
| `manifest.json`                 | манифест исходников: `main` → `src/main.ts`, словари объявлены                |
| `src/main.ts`                   | плагин с одной командой, подпись которой берётся из словаря                   |
| `src/main.test.ts`              | `id` кода совпадает с `id` манифеста — иначе оболочка откажет (`id-mismatch`) |
| `locales/ru.json`, `en.json`    | плоские словари «ключ → строка»                                               |
| `package.json`, `tsconfig.json` | `@reformer/builder-plugin-api` в `devDependencies`                            |

Идентификатор по умолчанию — имя каталога. Годится ли он, решает разбор манифеста оболочки,
а не собственное правило CLI. В непустой каталог команда не пишет.

Созданный плагин можно положить в `.ui_builder/plugins/<id>/` проекта как есть: оболочка сама
транспилирует `src/main.ts`.

### `validate [каталог]`

Код выхода `0` — оболочка плагин примет, `1` — нет, и почему именно, напечатано построчно.

- **манифест** — разбором из `@reformer/builder-plugin-api/tooling`, тем же, что у оболочки.
  Отличий у исходников два: имя каталога с `id` не сверяется (репозиторий зовётся как угодно),
  а `version` обязательна и должна быть версией — по ней публикуется пакет;
- **файлы, на которые ссылается манифест**: точка входа существует и это код, таблица стилей
  существует, словари существуют и плоские. Эти отказы собираются все сразу;
- **версия `package.json`** совпадает с версией манифеста. Этого оболочка не проверяет —
  `package.json` она не читает, — а расхождение означает пакет одной версии с плагином другой.

Коды отказов — коды оболочки (`manifest-invalid`, `api-version`, `entry-missing`,
`messages-invalid`, `provides-unregistered`…). Свои коды у CLI — для того, чего оболочка не видит:
`package-version`, `build-failed`, `module-unavailable`, `css-from-code`, `output-not-ours`,
`pack-failed`.

Соответствие `provides` регистрации и потолок числа файлов `validate` не проверяет: первое
требует исполнить код, второе относится к собранному каталогу. Обе проверки делает `build`.

### `build [каталог] [--out <каталог>]`

Собирает каталог, который оболочка грузит как есть (по умолчанию `dist/`): `manifest.json`
с `main: "main.js"`, один `main.js`, `styles.css`, если стили объявлены, и словари по тем же путям.

- `main.js` — CommonJS: линковщик оболочки исполняет CommonJS, и готовый JS идёт у него без
  транспиляции;
- модули, которые подставляет оболочка (`PLUGIN_RUNTIME_MODULES` контракта: React, `@reformer/*`,
  сам контракт), остаются внешними. Импорт `@reformer/*` или `@builder/*` вне этого списка —
  отказ `module-unavailable`: вложенная копия была бы вторым экземпляром пакета;
- импорт CSS из кода — отказ `css-from-code`: стили объявляются полем `styles` манифеста,
  и только такую таблицу оболочка изолирует.

На выходе сборка проходит то, что пройдёт у оболочки: разбор манифеста поставки `project`, потолок
числа файлов кода и **«сухую» активацию** — `main.js` исполняется под Node с настоящим пакетом
контракта и заглушками остального. Так ловятся `not-a-plugin`, `id-mismatch` и
`provides-unregistered`. Если код падает на заглушке (например, `activate` трогает DOM), это
не отказ, а заметка `! … не проверено`: вне оболочки так ведут себя и рабочие плагины.

Каталог вывода очищается, только если он пуст или содержит сборку этого же плагина; иначе —
отказ `output-not-ours`. Не прошедшая проверки сборка прошлую не затирает.

### `dev [каталог] --project <каталог проекта>`

Собирает в `<проект>/.ui_builder/plugins/<id>/` и пересобирает на каждое изменение исходников
(`node_modules`, `dist` и скрытые каталоги не наблюдаются). Перезагружает плагин оболочка:
отметьте его в списке плагинов «в разработке», и он перечитывается при возврате в окно билдера.

### `pack [каталог] [--out <каталог>]`

Собирает во временный каталог и упаковывает `npm pack` в `<имя>-<версия>.tgz`. В архиве только
сборка и `package.json` (имя, описание, лицензия и ключевые слова из исходного, версия — из
манифеста, ключевое слово `reformer-builder-plugin` добавляется); исходников и зависимостей нет.

## Программный вход

```ts
import { buildPlugin } from '@reformer/builder-plugin-cli';

const result = await buildPlugin({ dir: './acme-forms', outDir: './out' });
if (!result.ok) console.log(result.findings);
```
