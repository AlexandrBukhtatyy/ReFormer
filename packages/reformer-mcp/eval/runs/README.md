# Опубликованные прогоны `@reformer/mcp`

Записи всех стендов качества в одном формате: `reformer-mcp-run/1`
([схема](../records/schema.json)). Один файл `.jsonl` — один батч,
одна строка — один прогон.

Файл появляется здесь только по `--publish`. Без флага запись остаётся в
`.tmp/mcp-runs/<батч>/records.jsonl` вместе с сырьём: транскриптами, журналами вызовов и файлами форм.
Отладочные прогоны в истории не нужны, а сырьё в репозиторий не кладётся.

| Стенд                  | Как опубликовать                                                  |
| ---------------------- | ----------------------------------------------------------------- |
| извлечение знания      | `npm run mcp:evaluate -- --publish`                               |
| калибровка             | `npm run mcp:calibrate -- --publish`                              |
| сценарии               | `npm run mcp:scenarios -- --matrix <имя> --publish`               |
| ассистент конструктора | `npm run mcp:import-builder -- <form-scenarios-*.json> --publish` |

## Как читать

```bash
npm run mcp:compare -- <A> <B>            # файл, идентификатор батча или baseline:<ключ>
npm run mcp:compare -- <A> <B> --gate     # код 1 при регрессии
npm run mcp:report                        # .tmp/mcp-eval/report/index.html: тренды и матрица
```

`baselines.json` даёт эталонным батчам имена: `{ "scenarios-qwen": "20261102T164814Z-188b" }`.

Сырьё неопубликованного прогона читается одним диалогом: `npm run mcp:log -- <батч>` пишет в каждый
прогон `dialog.md` — задание, шаги модели, вызовы с ответами сервера и итог
([как устроено](../../../../docs/mcp-eval/scenarios.md)).

## Снимки отчётов `approaches/`

Отчёт сравнения подходов (`npm run mcp:approaches`) считается по сырью, а сырьё в git не едет. Его
снимок — `.json` в формате `reformer-mcp-approaches/1`: строки отчёта и цепочки вызовов, по строке на
прогон. Снимок сохраняет `--save`, а отчёт по нему пересобирается и после клона:

```bash
npm run mcp:approaches -- packages/reformer-mcp/eval/runs/approaches/<имя>.json [--sequence]
```

Это не записи: `mcp:compare` и `mcp:report` читают только `.jsonl` и снимков не видят.

| Снимок                                                | Отчёт                                               |
| ----------------------------------------------------- | --------------------------------------------------- |
| [code-mode-weak.json](approaches/code-mode-weak.json) | [Code Mode](../../../../docs/mcp-eval/code-mode.md) |

## Что важно помнить

- **Один прогон с моделью ничего не доказывает.** При трёх повторах значим только переход 0/3 ↔ 3/3
  (точный тест Фишера, p=0.1). Для решений нужно N=5 и больше.
- **`invalid` — сломался прибор, а не форма:** нарушена изоляция, агент не запустился, исчерпан бюджет.
  В статистику такие прогоны не входят.
- **`costUsd` у Claude Code — оценка:** запуск идёт по подписке (`agent.auth: "oauth"`), это не списание.
- **Токены у стендов без модели — оценка `chars / 4`**, у агентов — данные провайдера. Между собой не
  сравниваются.
- **`source.provenance: "imported"`** — коммит в записи текущий на момент импорта, а не коммит прогона.
- **`source.provenance: "reverified"`** — формы оценены заново после правки контракта или верификатора,
  без запуска модели; браузерные проверки остаются из прогона. Сравнивать можно только записи, оценённые
  одним прибором: при его правке `npm run mcp:verify -- --reverify <батч>` прогоняется по обоим плечам.
- **Holdout** в сравнении и в сводке виден только агрегатом. Провалы holdout не становятся задачами на
  правку сервера.
- **Запись ужимается до потолка** (`RECORD_SIZE_LIMITS`, у сценариев 4000 байт). У длинного
  сценария проверок с причинами набирается больше потолка, поэтому по шагам укорачиваются причины
  проверок, затем хвост `toolSequence`, а в крайнем случае от проверки остаётся только статус.
  Срезанное помечено «…», полные причины лежат в `verify.json` прогона.
- **Негодная запись не теряет батч.** Если запись не прошла схему или не влезла в потолок и после
  ужатия, `records.jsonl` всё равно пишется целиком, а проблема печатается в stderr. С `--publish`
  батч в таком случае не публикуется, и раннер завершается с ошибкой.
