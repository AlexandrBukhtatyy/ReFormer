# Прогоны `@reformer/mcp` в git

Сырьё и записи прогонов остаются в `.tmp/mcp-runs/<батч>/`: `records.jsonl` (формат
`reformer-mcp-run/1`, [схема](../records/schema.json), строка на прогон), транскрипты, журналы
вызовов и файлы форм. В git они не едут. Здесь лежит то, что нужно после клона:

| Файл                             | Что в нём                                                                 |
| -------------------------------- | ------------------------------------------------------------------------- |
| [history.json](history.json)     | история метрик: точка на батч × серию и события — по ней строится дашборд |
| [baselines.json](baselines.json) | имена эталонных батчей для `mcp:compare -- baseline:<ключ>`               |
| [approaches/](approaches/)       | снимки отчётов сравнения подходов (`mcp:approaches --save`)               |

До 2026-11-13 записи публиковались сюда же флагом `--publish` (`<год>/*.jsonl`). Флаг убран: восемь
опубликованных батчей sonnet от 02.11 перенесены в историю, их записи остались в истории git.

## История метрик

Батч попадает в историю явно, когда замер осмысленный:

```bash
npm run mcp:history -- add <батч>… [--tag <тег>]…   # точки батча; повторный add заменяет их
npm run mcp:history -- add --all                     # все батчи .tmp/mcp-runs
npm run mcp:history -- tag <батч> <тег>…             # свои теги; untag — снять
npm run mcp:history -- event --kind server --title "…" [--date Г-М-Д] [--refs ReFormer-x]
npm run mcp:history -- events-from-git [--since Г-М-Д]   # события из коммитов с Refs
npm run mcp:history -- list | check
npm run mcp:report                                   # дашборд → .tmp/mcp-eval/report/index.html
```

Стенды в конце батча печатают готовую команду `add`. Флаг `--publish` стенды отвергают сразу.

**Точка** — один батч одной серии. Серия — стенд · агент · подход: сравнивать значения можно только
внутри неё. В точке лежат:

- агрегаты: доля pass и средний счёт по настроечным ячейкам, медианы шагов, токенов, времени и
  метрик `process.*`, стоимость батча; у калибровки и извлечения знания — их метрики как есть;
- ячейки `сценарий.таргет → [pass, всего, счёт, контракт]`; holdout — только агрегатом;
- отпечатки: коммит и грязное ли дерево, поверхность, сборка и знание сервера, прибор;
- теги.

**Теги** отбирают точки на графики. Автоматические: `smoke` (агент `replay`, путь без модели),
`dirty` (незакоммиченное дерево), `reconstructed` (у батча нет `records.jsonl`, записи восстановлены
по `verify.json` и журналу), `reverified`, `imported`. Свои — `--tag` и `tag`, повторный `add` их
сохраняет.

**События** — вертикальные отметки на графиках, по видам:

| Вид          | Что изменилось                                                            |
| ------------ | ------------------------------------------------------------------------- |
| `server`     | сервер: инструменты, ответы, сборка                                       |
| `knowledge`  | корпус знаний (`docs/llms`, `llms.txt`)                                   |
| `instrument` | верификатор, контракты, стенд — скачок метрики здесь не улучшение сервера |
| `agent`      | модель или промпт агента                                                  |

`events-from-git` относит коммит по путям: `packages/reformer-mcp/src` → `server`, документация
`llms` пакетов → `knowledge`, `packages/reformer-mcp/eval` → `instrument`. Берутся только коммиты с
`Refs:`, без `docs`, `chore`, `style`, `ci` и `build`. При `add` скрипт сравнивает новую точку с
предыдущей точкой серии и печатает, что сменилось (контракт ячейки, поверхность, сборка, знание,
набор ячеек), и коммиты с `Refs` между ними — из этого собирается ручное событие.

Файл пишется по строке на точку и на событие и исключён из Prettier: переформатированный, он
оставался бы изменённым после каждого `add`.

## Дашборд

`npm run mcp:report` собирает самодостаточный HTML без сети. В нём:

- фильтры одной строкой: ось (по батчам или по времени), период, теги (у каждого условие «только с
  ним» или «скрыть»; `smoke` скрыт по умолчанию), виды событий (`knowledge` выключен, их много);
- серии сценариев и конструктора по выбранной метрике. Линия рвётся там, где точки несравнимы
  (другой набор ячеек или сменился контракт ячейки), подсказка называет причину. У одной видимой
  серии доля pass идёт с 90% интервалом Уилсона;
- тепловая карта ячеек серии по батчам;
- малые графики калибровки и извлечения знания;
- список событий, у каждого графика — таблица.

## Записи и сравнение

```bash
npm run mcp:compare -- <A> <B>            # батч .tmp/mcp-runs, путь к records.jsonl или baseline:<ключ>
npm run mcp:compare -- <A> <B> --gate     # код 1 при регрессии
npm run mcp:log -- <батч>                 # прогоны батча одним диалогом
npm run mcp:approaches -- <батч>…         # было/стало по подходам
```

`baselines.json` даёт эталонным батчам имена: `{ "scenarios-qwen": "20261102T164814Z-188b" }`.
Батч в нём — локальный, из `.tmp/mcp-runs`.

`mcp:log` пишет в каждый прогон `dialog.md`: задание, шаги модели, вызовы с ответами сервера и итог
([как устроено](../../../../docs/mcp-eval/scenarios.md)).

## Снимки отчётов `approaches/`

Отчёт сравнения подходов (`npm run mcp:approaches`) считается по сырью. Его снимок — `.json` в
формате `reformer-mcp-approaches/1`: строки отчёта и цепочки вызовов, по строке на прогон. Снимок
сохраняет `--save`, а отчёт по нему пересобирается и после клона:

```bash
npm run mcp:approaches -- packages/reformer-mcp/eval/runs/approaches/<имя>.json [--sequence]
```

| Снимок                                                | Отчёт                                               |
| ----------------------------------------------------- | --------------------------------------------------- |
| [code-mode-weak.json](approaches/code-mode-weak.json) | [Code Mode](../../../../docs/mcp-eval/code-mode.md) |

## Что важно помнить

- **Один прогон с моделью ничего не доказывает.** При трёх повторах значим только переход 0/3 ↔ 3/3
  (точный тест Фишера, p=0.1). Для решений нужно N=5 и больше. На графике это видно по ширине
  интервала Уилсона.
- **`invalid` — сломался прибор, а не форма:** нарушена изоляция, агент не запустился, исчерпан бюджет.
  В статистику такие прогоны не входят.
- **`costUsd` у Claude Code — оценка:** запуск идёт по подписке (`agent.auth: "oauth"`), это не списание.
- **Токены у стендов без модели — оценка `chars / 4`**, у агентов — данные провайдера. Между собой не
  сравниваются.
- **`source.provenance: "imported"`** — коммит в записи текущий на момент импорта, а не коммит прогона.
- **`source.provenance: "reverified"`** — формы оценены заново после правки контракта или верификатора,
  без запуска модели; браузерные проверки остаются из прогона. Сравнивать можно только записи, оценённые
  одним прибором: при его правке `npm run mcp:verify -- --reverify <батч>` прогоняется по обоим плечам,
  а затем батчи заново добавляются в историю.
- **Holdout** в сравнении, истории и дашборде виден только агрегатом. Провалы holdout не становятся
  задачами на правку сервера.
- **Почти все замеры шли на грязном дереве** (62 из 66 батчей к 13.11): коммит в точке тогда только
  ориентир, а состояние сервера фиксируют отпечатки поверхности, сборки и знания.
- **Запись ужимается до потолка** (`RECORD_SIZE_LIMITS`, у сценариев 4000 байт). У длинного
  сценария проверок с причинами набирается больше потолка, поэтому по шагам укорачиваются причины
  проверок, затем хвост `toolSequence`, а в крайнем случае от проверки остаётся только статус.
  Срезанное помечено «…», полные причины лежат в `verify.json` прогона.
- **Негодная запись не теряет батч.** Если запись не прошла схему или не влезла в потолок и после
  ужатия, `records.jsonl` всё равно пишется целиком, а проблема печатается в stderr.
