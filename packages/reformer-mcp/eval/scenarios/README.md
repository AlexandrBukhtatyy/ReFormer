# Сценарии MCP

Три формы и операции над ними: создать с нуля, изменить готовую, удалить часть. Агент выполняет
задание через MCP-сервер, верификатор судит результат по контракту. Метод и итоги —
[docs/mcp-eval/scenarios.md](../../../../docs/mcp-eval/scenarios.md).

| Форма                                    | create                | split          | edit                | delete                |
| ---------------------------------------- | --------------------- | -------------- | ------------------- | --------------------- |
| Регистрация: логин, email, пароль, капча | `registration-create` | —              | `registration-edit` | `registration-delete` |
| Оформление заказа, одна страница         | `order-create`        | —              | `order-edit`        | `order-delete`        |
| Тот же заказ — мастер по шагам           | `wizard-create`       | `wizard-split` | `wizard-edit`       | `wizard-delete`       |

Каждый сценарий идёт на трёх стеках: `core`, `renderer-react`, `renderer-json`.

- **Регистрация** — задание одной фразой. Покрывает правила полей, межполевое правило, асинхронную
  проверку (капча — заглушка без сети) и кнопку отправки.
- **Заказ** — по спецификации [order/spec.md](order/spec.md), около 30 полей. В ней каждая
  возможность ReFormer встречается хотя бы раз, и на каждую есть проба. Список возможностей — ниже.
- **Мастер** — та же спецификация, разделы становятся шагами. `wizard-create` строит мастер с нуля, а
  `wizard-split` переделывает в мастер готовую одностраничную форму. Контракт у них один.

## Раскладка

```
<форма>/<операция>/
  scenario.json          уровень, операция, таргеты, бюджет, спека, затравка, эталон
  prompt.md              задание словами разработчика
  contract.json          что проверить; у правки — наследник контракта создания
  reference.intent.json  эталон: FormIntent, из которого сервер обязан собрать форму, проходящую контракт
order/spec.md            спецификация заказа (общая для order-* и wizard-*)
```

Каталог без `scenario.json` — группа и обходится вглубь. Каталоги `_*` и скрытые — служебные.

## `scenario.json`

- `level` — 1 регистрация, 2 заказ, 3 мастер. `operation` — `create`, `split`, `edit` или `delete`.
  Сценарии идут по уровню, внутри уровня — по операции.
- `reference` — путь к intent относительно каталога сценария либо `plan_form`: сервер строит intent
  из спеки сам. Эталон доказывает, что контракт выполним: `npm run mcp:verify -- --golden`.
- `referenceFiles` — файлы, которые агент пишет руками, например тело своего оператора:
  `{ "operators.ts": "reference.operators.ts" }`. Они ложатся рядом с intent до сборки, сборка их
  не трогает и только проверяет типы.
- `seed` — id сценария, с формы которого начинается правка. До старта агента стенд собирает эталон
  затравки в `form/` под таргет прогона. Сборка идёт без трассы и в метрики агента не входит. Intent
  затравки остаётся в `<прогон>/seed.intent.json`, а в задании вместо «положи модуль в `form/`»
  стоит «форма уже лежит в `form/`, меняй её там». Затравка — всегда сценарий с нуля: цепочек нет.
  Эталон правки собирается поверх затравки: так он проверяет и пересборку готовой формы.
- `contract` — свой путь к контракту, если он не `contract.json`. Например, `wizard-split` судится
  контрактом `wizard-create`.
- `builder` — идёт ли сценарий в лестницу ассистента конструктора: `enabled`, а также
  `replay: false` с `reason`, если эталон одним `build_form` не собрать. Правки в ассистенте пока
  не идут: лестница не кладёт затравку (ReFormer-mhsh.4).

## Контракт

- `fields[]` — `id`, `bind` (`path`, `paths` — кандидаты, `label` — регулярка по подписи), `type`,
  `aria` (`role` — через `|`, `name` — регулярка, `step` — номер шага мастера, если поле не на первом
  экране). Роль, подпись и порядок сверяются со снимком доступности.
- `steps[]` — шаги мастера: `title` (регулярка) и `fields` (id полей контракта или пути массивов).
  Проверяются число шагов, заголовок и состав каждого шага. Это гейт.
- `arrays[]` — массивы и поля их строк.
- `absent[]` — чего в форме быть не должно (удалённое, переименованное): `id` и `bind`. Поле не
  должно найтись ни по пути, ни по подписи. Это гейт `runtime.structure.absent`, в браузере —
  `browser.absent`.
- `buttons[]` — кнопки первого экрана: `name` — регулярка подписи (`browser.buttons`).
- `sample` — валидное заполнение, от которого отклоняется каждая проба. Поле образца, которого нет в
  форме, пропускается: его отсутствие называет проверка полей.
- `probes[]` — `id`, `gate` (провал роняет вердикт), `sample: false` (без образца), `step` (номер
  шага с 1: проверяются только правила этого шага, как при переходе «Далее»).
  - `set` — значения. `{ push: {…} }` добавляет строку массива, `{ removeAt: n }` удаляет. Список
    объектов означает шаги по порядку: между ними отрабатывает поведение. Дата задаётся как
    `{ "$date": "+3d" }` (объект `Date`) или `{ "$dateString": "-18y" }` (`YYYY-MM-DD`): сдвиг от
    сегодняшнего дня в днях, месяцах или годах, либо ISO-дата.
  - `expect` — `valid`, `invalid[]` (ошибка поля; предупреждение ошибкой не считается), `anyInvalid[]`,
    `noIssues[]`, `warnings[]` (предупреждение `severity: 'warning'`), `errorCode{}`, `disabled[]`,
    `enabled[]`, `values{}`, `positive[]`, `expressions[]`, `arrayLength{}`.
  - `where: "browser"` — `hidden[]`, `visible[]`, `readonly[]`: видимость и доступность ввода
    исполняет только рендерер. Эталон на core нарисован схемой без слоя рендера, поэтому пробы с
    `hidden` у него пропускаются, а у агента на core проверяются.

### Контракт правки: `extends`

Контракт правки — контракт формы-затравки плюс дельта. Так «остальное не сломано» проверяют пробы
базы, а не их копия.

- `extends` — путь к базовому контракту относительно файла.
- `drop: { fields, probes, arrays }` — что снять из базы. Поле уходит вместе со значением в
  `sample`. Проба базы, которая упоминает снятое поле, должна быть снята или заменена явно, иначе
  чтение контракта упадёт с ошибкой.
- `fields` — поле с тем же `id` заменяет базовое на его месте (так переименование оставляет пробы
  базы в силе). Новое поле встаёт после `after` или в конец.
- `probes`, `arrays` — замена по `id` (`path`). `sample` накладывается поверх базового, `absent`
  дописывается, остальные ключи заменяют базовые.

Проба не должна требовать того, чего нет в задании. Пример: образец сообщения длиннее, чем обычно
просят, а агент вправе добавить минимальную длину. Иначе честная работа окажется красной.

## Что покрывает заказ

| Возможность                                                                                        | Где в `order/spec.md`                               |
| -------------------------------------------------------------------------------------------------- | --------------------------------------------------- |
| string, number, boolean, `type: date` (строка и `Date`), массив значений                           | все разделы, `birthDate`, `deliveryDate`, `sources` |
| Input, InputMask, RadioGroup, Select, DatePicker, Checkbox, Switch, Slider, Textarea, SelectMulti  | по разделам                                         |
| группы (`a.b`), части (`parts`) на две группы                                                      | `contact.*`, адреса доставки и счёта                |
| required, minLength, maxLength, email, pattern, integer, min, max, nonNegative, minAge, futureDate | по таблице полей                                    |
| условное правило (`when`), межполевое (`cross`), предупреждение (`severity: warning`)              | компания, доставка, `paymentMethod`, `total`        |
| асинхронное правило, своё правило-оператор                                                         | `promoCode`, `innChecksum`                          |
| правила строк (`each`), правило на сам массив                                                      | `items`, `recipients`                               |
| compute (сумма по массиву, в строке), computeFrom                                                  | `lineTotal`, `subtotal`, `total`                    |
| copyFrom, syncFields, enableWhen и disableWhen (группа, с `resetOnDisable`), resetWhen             | адреса, `receiptEmail`, `discount`, `deliveryDate`  |
| onChange, revalidateWhen, transformValue, exclusiveFlag, aggregateInto                             | тип покупателя, промокод, получатели                |
| видимость (`visibility`), скрытый шаг мастера, `dataSources`, начальные значения                   | раздел «Компания», `deliveryDate`                   |
| кнопка отправки — событие узла (`onComponentEvent`), `submitLabel` мастера                         | «Оформить заказ»                                    |

Не покрыто, с причиной: FileUpload (файл в пробу без браузера не задать), InputSuggest,
`onInit`/`onMount`/`renderEffect` (без браузера их не наблюдать), Tabs, вложенные массивы (грамматика
их не выражает).
